01 · OVERVIEW & ROLE

무엇을 만들었고, 내가 맡은 범위는 어디까지였는가

사내 Jenkins 기반 배포 환경을 GitHub Actions 중심의 표준화된 CI/CD 및 개발 하네스로 전환한 v2 프로젝트입니다. v1이 하네스 구조와 인프라 선택지를 검증한 PoC였다면, v2는 실제 사내 프로젝트에 적용하고 팀 피드백을 받는 운영 도구로 설계했습니다.

저는 문제 정의, GitHub Actions 파이프라인 설계, Infisical wiring, 배포 스크립트, harness 전용 CLI, shared/project-owned 업데이트 정책, GSD·GStack·Superpowers 기반 에이전트 작업 규칙까지 전반을 주도했습니다.

02 · PROBLEM

Jenkins를 없애는 것만으로는 문제가 해결되지 않았다

운영 비용과 장애 원인 추적

Jenkins 서버 2대가 운영되었고 월 20만 원의 고정 비용이 발생했습니다. 실제 사용 범위는 단순 배포 자동화에 가까웠지만, 별도 관리 담당자가 없어 플러그인과 버전 관리가 충분히 이뤄지지 않았습니다. 배포 실패가 workflow 문제인지 Jenkins 서버 장애인지 분리하는 데도 비용이 들었습니다.

프로젝트마다 반복되는 설정

프로젝트가 추가될 때마다 CI/CD, PM2·Docker·Vercel 배포 방식, 시크릿 연결, 브랜치와 환경 매핑을 다시 결정해야 했습니다. 단순한 도구 교체만으로는 이 반복이 다른 형태로 남을 뿐이었습니다.

05 · IMPLEMENTATION DETAIL

구현 과정에서 실제로 부딪힌 지점

초기에는 Jenkins workflow를 GitHub Actions로 옮기는 데 집중했지만, v1의 구조를 실제 프로젝트에 적용하면서 공통 도구가 복사되어 버전 드리프트가 생기는 문제가 드러났습니다. 그래서 v2에서는 shared와 project-owned 경계를 나누고, 공통 변경은 upstream에서 전파하되 앱 소유 파일은 업데이트가 덮어쓰지 않도록 했습니다.

또한 GitHub Secrets에는 Infisical 접근용 bootstrap secret만 남기고, backend runtime·frontend runtime·배포 workflow용 변수를 각각 경로로 분리했습니다. 이 선택은 단순히 저장 위치를 바꾼 것이 아니라, 누가 어떤 목적으로 값을 쓰는지 책임 경계를 재정의한 것이었습니다.

pipeline.yml
├─ changed files 계산
├─ backend_changed / frontend_changed 판단
├─ Node 검증 + dependency security gate
├─ Infisical에서 목적별 secret 주입
└─ PM2 / Docker / Vercel reusable workflow 실행

07 · RETROSPECTIVE

다시 설계한다면

이 프로젝트를 통해 재사용성은 같은 파일을 여러 곳에 복사하는 것이 아니라, 공통 변경이 생겼을 때 프로젝트별 소유권을 침범하지 않고 안전하게 전파되는 구조라는 관점을 얻었습니다. 현재는 실제 사용 과정의 피드백을 바탕으로 doctor 검증과 업데이트 정책을 보완하고 있습니다.
