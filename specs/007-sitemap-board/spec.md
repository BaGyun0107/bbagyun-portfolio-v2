# Feature Specification: 기능정의서 사이트맵 보드 + 사이트맵 선행 플로우

**Feature Branch**: `007-sitemap-board`

**Created**: 2026-07-16

**Status**: Draft

**Input**: User description: "기능정의서 사이트맵 보드 + 사이트맵 선행 플로우.
설계 확정본 설계 초안(2026-07-18 정리 — git history)
기반. 사이트맵 독립 산출물 선행 + 허브 기능정의서 탭 사이트맵 보드 재구성 +
기존 표는 토글 보조 뷰. include test tasks (TDD)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 사이트맵 보드로 기능정의서를 한눈에 파악 (Priority: P1)

팀원(PM/디자이너/개발자)이 `docs/index.html`의 기능정의서 탭을 열면,
화면 구조 트리 + 요약 숫자 + 화면별 기능 카드가 기본으로 보여
전체 기능 규모와 구조를 스크롤/클릭 최소로 파악한다.

**Why this priority**: 사용자가 지목한 핵심 불만(8컬럼 표의 가독성)을
직접 해결하는 가치. 사이트맵 파일이 없어도(파생 모드) 동작하므로
단독 배포 가능한 MVP다.

**Independent Test**: 기존 기능정의 데이터만 있는 상태에서 `docs:build`
실행 후 허브를 열어 보드(요약 바/트리/카드)가 기본 화면으로 렌더되고
"표로 보기" 토글로 기존 표가 그대로 나오는지 확인.

**Acceptance Scenarios**:

1. **Given** 기능정의 행이 존재, **When** 기능정의서 탭 진입,
   **Then** 요약 바(기능 수·화면 수·Phase 분포·보류·미배치)와
   좌측 트리, 화면별 기능 카드가 기본으로 보인다.
2. **Given** 보드 화면, **When** 트리 노드 클릭,
   **Then** 우측 본문이 해당 화면 범위의 기능 카드로 좁혀진다.
3. **Given** 보드 화면, **When** "표로 보기" 토글,
   **Then** 기존 8컬럼 표가 동일한 필터 상태로 표시된다.
4. **Given** 보드 화면, **When** 기능 카드 클릭,
   **Then** 기존 행 상세 화면이 열린다.

---

### User Story 2 - 최초 기능정의 전 사이트맵 선행 확인 (Priority: P2)

외부 문서로 기능정의를 시작하는 사용자가 정규화 전에 사이트맵 초안을
확인·확정하고, 확정본이 `data/sitemap.json`으로 저장되며 이후 기능
행이 그 노드에 매핑된다.

**Why this priority**: 구조-먼저 플로우의 근원. P1 보드가 있어야
확정 사이트맵의 가치(빈 노드 표시 등)가 화면에 드러난다.

**Independent Test**: normalizer 절차를 따라 사이트맵 초안 제시→확정
저장 후, 정규화된 행의 Area가 노드 id와 일치하고 허브 보드가 확정
사이트맵 기준으로 렌더되는지 확인.

**Acceptance Scenarios**:

1. **Given** 외부 기능정의 소스, **When** 정규화 시작,
   **Then** 화면/영역 후보로 만든 사이트맵 초안이 먼저 제시된다.
2. **Given** 사용자 확정, **When** 저장,
   **Then** `data/sitemap.json`이 스키마에 맞게 기록된다.
3. **Given** 확정 사이트맵, **When** 행 정규화,
   **Then** 각 행의 Area가 노드 id(또는 aliases)로 정규화된다.
4. **Given** 기능 0건인 노드, **When** 보드 렌더,
   **Then** 해당 노드가 회색으로 표시되어 "정의 안 된 화면"이 보인다.

---

### User Story 3 - 사이트맵 없는 프로젝트의 무중단 동작 (Priority: P3)

`data/sitemap.json`이 없는 기존 프로젝트에서도 빌드와 허브가 기존과
동일하게 성공하고, 보드는 기능 행에서 파생한 트리로 렌더된다.

**Why this priority**: 하위 호환 보증. 기존 프로젝트를 깨지 않아야
업스트림 배포가 가능하다.

**Independent Test**: sitemap.json 부재/손상 상태에서 `docs:build`가
성공하고 파생 트리(사용자/관리자 2그룹)로 보드가 렌더되는지 확인.

**Acceptance Scenarios**:

1. **Given** sitemap.json 부재, **When** `docs:build`,
   **Then** 빌드 성공 + "사이트맵 미정의 — 행에서 파생 중" 힌트 출력.
2. **Given** sitemap.json이 스키마 위반, **When** `docs:build`,
   **Then** 빌드 성공 + 경고 출력 + 파생 모드로 렌더 (fail-open).

### Edge Cases

- Area가 어떤 노드 id/aliases와도 일치하지 않는 행 → "미배치" 버킷에
  표시되고 빌드 힌트로 개수가 보고된다.
- 서로 다른 노드가 같은 alias를 가진 경우 → 스키마 검증에서 경고,
  먼저 선언된 노드가 우선한다.
- 검색/Phase/처리·검토 필터와 트리 선택이 동시에 적용된 경우 →
  교집합으로 좁혀지고 요약 바 숫자도 함께 갱신된다.
- 표 토글 후 다시 보드로 복귀 → 필터/선택 상태가 유지된다.
- 사이트맵에 노드가 있으나 기능정의 행이 전혀 없는 경우 → 트리는
  구조 전체를 보여주고 모든 노드가 0건(회색)으로 표시된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 사이트맵은 독립 산출물 `data/sitemap.json`으로 저장되며
  사람이 소유한다(생성물이 아님). 진실의 원천 스키마는
  `.harness/config/sitemap-schema.json`이다.
- **FR-002**: 사이트맵 surface는 `user`(사용자 앱), `admin`(관리자/운영),
  `common`(공통/시스템) 3종을 표준으로 한다.
- **FR-003**: 기능정의 행은 기존 `Area` 값이 노드 `id` 또는 `aliases`와
  일치할 때 해당 노드에 배치된다. 기능정의 행 스키마에 새 필드를
  추가하지 않는다.
- **FR-004**: 어떤 노드와도 일치하지 않는 행은 "미배치" 버킷으로
  표시하고, 빌드 시 비차단 힌트로 개수를 보고한다.
- **FR-005**: 기능 0건인 노드도 트리에 회색으로 표시한다.
- **FR-006**: `data/sitemap.json`이 없거나 유효하지 않으면 빌드는
  성공하고(fail-open) 기능 행에서 파생한 트리(사용자/관리자 2그룹)로
  동일한 보드 UI를 렌더한다.
- **FR-007**: 기능정의서 탭의 기본 화면은 사이트맵 보드다 — 상단
  요약 바(기능 수·화면 수·Phase 분포·보류/미결정·미배치, 숫자 클릭 시
  필터 적용) + 좌측 트리(건수 뱃지) + 우측 화면별 기능 카드(기능명·
  Phase 뱃지·처리/검토 뱃지·한 줄 요약).
- **FR-008**: 기능 카드 클릭 시 기존 행 상세 화면을 재사용한다.
- **FR-009**: 기존 8컬럼 표는 "표로 보기" 토글의 보조 뷰로 유지하고,
  기존 사이트맵 모달은 제거한다.
- **FR-010**: 검색/Phase/처리·검토 필터는 보드(트리·카드·요약 바)와
  표 양쪽에 동시 적용되며, 뷰 전환 시 상태가 유지된다.
- **FR-011**: `docs:build` 종료 시 비차단 힌트를 출력한다 —
  사이트맵 미정의, 미배치 N건, 빈 화면 노드 N개.
- **FR-012**: normalizer 절차 맨 앞에 0단계를 추가한다 — 소스에서
  화면/영역 후보 추출 → 사이트맵 초안 제시 → 사용자 확인 → 저장 →
  행 Area를 노드 id로 정규화. 새 mise 태스크는 추가하지 않는다.
- **FR-013**: 기능정의 중 새 화면이 발견되면 사이트맵 갱신을 정상
  플로우로 허용한다. 불일치는 차단 없이 힌트로만 알린다.

### Key Entities

- **사이트맵(Sitemap)**: surface 3종의 목록. 각 surface는 노드 트리를
  가진다. 사람이 소유하는 확정 산출물.
- **사이트맵 노드(Node)**: `id`, `title`, 선택적 `description`,
  `aliases`, `children`. 화면 또는 화면 그룹을 표현한다.
- **기능정의 행(Feature Row)**: 기존 canonical row
  (feature-definition-schema 기준). `Area`로 노드에 매핑된다.
- **미배치 버킷(Unassigned)**: 어떤 노드에도 매핑되지 않은 행의 집합.
  트리 최하단에 표시된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 기능정의서 탭 진입 직후 추가 클릭 없이 전체
  기능 수, 화면 수, Phase 분포, 미배치 수를 확인할 수 있다.
- **SC-002**: 특정 화면의 기능 목록까지 2회 이하 클릭으로 도달한다.
- **SC-003**: 사이트맵 파일이 없는 기존 프로젝트에서 `docs:build`
  성공률 100% — 기존 표·검색·필터·상세 기능이 모두 그대로 동작한다.
- **SC-004**: 기능정의가 없는 화면(0건 노드)이 기본 화면에서 즉시
  식별된다(별도 탐색 불필요).
- **SC-005**: 외부 문서 정규화 시 사이트맵 확인 단계가 항상 정규화보다
  먼저 수행되고, 확정 후 정규화된 행의 100%가 노드 또는 미배치 버킷
  중 한 곳에 배치된다.

## Assumptions

- 기능 행 매핑 키는 기존 `Area` 필드를 재사용한다 — 행 스키마 변경
  없음(설계 확정 사항).
- 이 저장소는 하네스 업스트림이므로 스킬 갱신은 `.harness/skills/`
  (공유 소유) 대상이다.
- 사이트맵 편집 UI는 범위 밖 — 파일 직접 편집 + 에이전트 플로우로
  충분하다(YAGNI).
- `registry.json`, `status.yaml`, Spec Kit 플로우는 변경하지 않는다.
- 허브는 단일 파일 `docs/index.html` 생성물이라는 기존 제약(외부
  의존성 0, 파일 하나로 열림)을 유지한다.
- 테스트는 TDD로 진행한다 — 스키마 검증, 매핑(미배치/aliases/0건
  노드), fail-open 빌드, 렌더 스모크를 구현 전에 테스트로 고정한다.
- `data/` 경로의 project-owned 분류(Node 분류기·셸 fallback·정책
  3경로) 등재 여부를 구현 중 확인하고 누락 시 함께 갱신한다.
