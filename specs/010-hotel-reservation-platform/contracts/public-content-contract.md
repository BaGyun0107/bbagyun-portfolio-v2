# Contract: 호텔 예약 플랫폼 공개 콘텐츠와 연결

**Date**: 2026-09-09

## 작업물 계약

- 플랫폼화 전은 별도 프로젝트 복제가 아니라 하나의 코드베이스에 호텔별 조건 분기가 누적된 구조다.
- 1차 구축 `2024.11 – 2025.10`과 `core/platform` 리빌딩 `2026.06 – 2026.08`을 구분한다.
- 1차 구축은 FE 2명(사용자 포함), BE 1명 협업이며 사용자는 Config 구조·예약 상태·NICEPAY 복귀 흐름의 설계와 주요 구현을 주도했다.
- 2026년에는 사용자가 `core/platform` 경계와 통합 방식을 설계하고 주요 마이그레이션을 수행했다.
- 서버 설정·코드 설정·환경변수와 호텔별 배포 구성을 함께 사용했으며 관리자 설정만으로 무수정·무배포 온보딩한 구조가 아니다.
- 2026년 기준은 공통 동작 `core`, 값 차이 `rsConfig`, 화면·로직 차이 `platform`이다.
- 기준 소스는 하나지만 5개 플랫폼은 각각 build해 운영 서버의 호텔별 프로젝트 폴더에 배포한다.
- 이전 기준점으로 시작해 빠진 최신 운영 변경은 운영 배포 전 발견하고 운영 브랜치 감사와 수동 이식으로 보완했다.
- 예약 Context 결과는 중간 props 전달 감소와 route 생명주기 경계이며 접근 통제·성능·순차성을 보장하지 않는다.
- NICEPAY 복귀는 `sessionStorage` 1시간 만료와 예약번호 기반 최종 조회까지다.
- 결과는 5개 운영 적용, 공통 변경의 기준 코드 1회 수정, 호텔별 변경 격리, 최신 브랜치 비교 제거로 제한한다.

## 코드 경계 인사이트 계약

- 제목: `Config 이후의 경계: 멀티플랫폼 React를 core·rsConfig·platform으로 나눈 이유`
- Config만으로 호텔별 브랜치 편차가 사라지지 않았다는 배경을 설명한다.
- 모든 플랫폼이 같으면 `core`, 값만 다르면 `rsConfig`, 화면·로직이 다르면 `platform`으로 배치한다.
- 공통 사용자 흐름을 공유하면서 플랫폼별 build·deploy를 유지해야 할 때 적용한다.
- runtime tenant 전환이 필요하거나 공통 도메인 흐름이 거의 없으면 그대로 적용하지 않는다.
- 전체 구현 위임 영역에는 contract와 행동 패리티 검증 비용이 남는다.
- 작업물의 역할·연혁·Context·NICEPAY를 반복하지 않는다.

## 예약 Context 인사이트 계약

- 제목: `Props Drilling을 줄이기 위해 예약 Context의 생명주기를 라우터에 둔 이유`
- 직접 문제는 중간 컴포넌트가 사용하지 않는 예약 상태와 setter를 전달하던 Props Drilling이다.
- 실제 비교 대안은 Redux이며 예약 라우터 범위와 팀의 전환 비용 때문에 선택하지 않았다.
- 예약 라우터에 `ReservationProvider`를 두고 하위 단계가 `useReservation`으로 직접 소비한다.
- 결과는 중간 props 전달 감소와 예약 흐름 이탈 시 상태 정리 경계다.
- Provider 밖 Hook 오류는 접근 권한 통제가 아니며 Context가 성능을 자동 보장하지 않는다.
- 관계없는 여러 route의 전역 상태나 최신 서버 응답이 기준인 데이터에는 Context만 사용하지 않는다.
- 작업물의 플랫폼 연혁과 NICEPAY를 반복하지 않는다.

## 금지 주장

다음은 세 기록에서 사용자의 실제 문제·대안·구현·성과로 나타나면 안 된다.

- 호텔마다 프로젝트를 복제한 구조
- 관리자 설정만으로 코드 수정·build·deploy 없이 신규 호텔을 추가한 성과
- 신규 호텔 코드 변경 `N건 → 0건`, 단일 배포로 전체 호텔 반영
- 모노레포·npm package·runtime 단일 앱·branch 자동 동기화를 당시 정식 대안으로 비교했다는 주장
- Provider Hell과 확인하지 않은 rerender 문제를 직접 장애로 규정한 주장
- Zustand를 검토했다는 주장
- Custom Hook이 상태 접근 권한을 통제하거나 route 밖 변경을 불가능하게 했다는 주장
- Context가 예약 순차성·성능 향상을 보장했다는 주장
- `localStorage` TTL 사용
- 결제 복귀 때 가격·재고를 재검증하거나 불일치 시 PG 승인을 자동 취소했다는 주장
- 프로젝트가 중단돼 운영 검증이 없었다는 주장
- React Query·Next.js SSR을 확정 개선안으로 검토했다는 주장
- 개발·배포 시간, 오류 감소율, 생산성, 결제 성공률, 신규 호텔 온보딩 속도

## 연결 계약

- 작업물의 관련 인사이트 영역에 두 인사이트 링크가 모두 존재한다.
- 각 인사이트의 연관 기록 영역에 호텔 예약 시스템 작업물 링크가 존재한다.
- 링크의 보이는 이름은 정정된 제목을 사용하고 keyboard Enter로 활성화된다.
- 목록→상세와 상세→연결 기록 탐색 중 slug redirect나 404가 발생하지 않는다.
