# Feature Specification: 호텔 예약 플랫폼 구조화 상세와 연결 인사이트 정정

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-09-09

**Status**: Complete

**Input**: 2026-09-09 사용자 인터뷰에서 승인된 호텔 예약 시스템 작업물과 연결 인사이트 두 건을 구조화 상세로 이전하고, 기존 과장·사실 오류를 정정한다. 작업 목록에는 테스트 우선 개발(TDD) 항목을 포함한다.

## Context

`hotel-reservation-platform`은 2024~2025년 설정 중심 플랫폼화와 2026년 `core/platform` 리빌딩을 거친 작업물이다. 현재 공개 내용은 프로젝트별 복제, 무배포 호텔 추가, 상태 접근 통제와 결제 복구 범위 등에서 실제 경험보다 넓은 주장을 포함한다. 이 기능은 작업물 하나와 기존 연결 인사이트 두 건을 하나의 사실 계약으로 다룬다.

승인된 인터뷰:
`docs/portfolio-interviews/2026-09-09-hotel-reservation-platform.md`

핵심 공개 경계는 다음과 같다.

- 플랫폼화 전 구조는 프로젝트 복제가 아니라 하나의 코드베이스에 호텔별 조건 분기가 누적된 형태였다.
- 1차 설정 중심 구조는 조건 분기를 줄였지만 5개 호텔 배포 브랜치의 반복 수정과 편차를 해소하지 못했다.
- 2026년에는 공통 동작, 값 차이, 화면·로직 차이를 각각 `core`, `rsConfig`, `platform`으로 분리했다.
- 소스 기준은 하나로 통합했지만 플랫폼별 빌드와 운영 서버의 호텔별 배포 단위는 유지했다.
- 구조 리빌딩 중 최신 운영 변경 일부가 빠진 사실은 운영 배포 전 검증에서 발견하고 이식했으며, 운영 장애로 표현하지 않는다.
- 예약 상태 구조는 Props Drilling을 줄이기 위한 라우터 범위 Context였고 접근 통제나 성능 향상을 보장하지 않는다.
- NICEPAY 복귀 흐름은 `sessionStorage`의 1시간 만료와 예약번호 기반 최종 조회까지이며 가격·재고 재검증이나 자동 취소를 포함하지 않는다.
- 신규 호텔 추가, 개발시간, 배포시간, 오류 감소율, 생산성, 결제 성공률에 관한 측정 성과를 만들지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채용 담당자가 플랫폼화의 진화와 실제 책임을 읽는다 (Priority: P1)

채용 담당자가 호텔 예약 시스템 상세를 열었을 때 조건 분기 중심의 단일 코드가 설정 중심 구조를 거쳐 하나의 기준 코드와 명시적 확장 경계로 발전한 이유, 사용자의 책임, 운영 적용 결과를 공통 읽기 순서로 이해한다.

**Why this priority**: 현재 서술의 과장된 신규 호텔 성과와 잘못된 프로젝트 복제 전제는 사용자가 실제로 해결한 브랜치 편차와 코드 경계 설계를 흐린다.

**Independent Test**: 작업물 상세에서 역할, 두 시기의 문제와 선택, 마이그레이션 검증, 예약 상태, NICEPAY 복귀, 근거가 붙은 결과와 회고를 읽고 승인 인터뷰와 대조한다.

**Acceptance Scenarios**:

1. **Given** 작업물 상세, **When** 기간과 역할을 읽는다, **Then** 1차 구축의 3인 협업과 사용자의 주도 영역, 2026년 경계 설계·주요 마이그레이션 책임이 구분된다
2. **Given** 1차 구조 설명, **When** 개선 전후를 읽는다, **Then** 단일 코드의 호텔별 조건 분기를 설정과 배포 구성으로 옮긴 효과와 호텔별 브랜치 편차라는 잔여 문제가 함께 드러난다
3. **Given** 2차 구조 설명, **When** 배치 기준과 운영 방식을 읽는다, **Then** `core`, `rsConfig`, `platform`의 역할과 플랫폼별 빌드·배포 유지가 구분된다
4. **Given** 결과와 근거 범위, **When** 성과를 읽는다, **Then** 5개 플랫폼 운영 적용과 실제 관찰만 확인되고 신규 호텔 온보딩이나 측정하지 않은 개선율은 나타나지 않는다

---

### User Story 2 - 독자가 설정과 코드 경계의 구분 기준을 이해한다 (Priority: P1)

독자가 첫 번째 연결 인사이트를 열었을 때 설정을 추가하는 것만으로 해결되지 않은 브랜치 편차와, 공통 동작·값·화면 및 로직 차이를 서로 다른 소유 경계에 배치한 판단을 이해한다.

**Why this priority**: 이 인사이트는 작업물 전체 연혁을 반복하지 않고 멀티플랫폼 프론트엔드에서 차이의 성격을 분류하는 재사용 가능한 판단을 제공한다.

**Independent Test**: 기존 인사이트 경로에서 승인된 제목, 한 질문에 집중한 본문, 적용·회피 조건, 한계와 코드 배치 시각 자료가 일관되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `config-driven-architecture-react` 인사이트, **When** 핵심 판단을 읽는다, **Then** 모든 플랫폼의 공통 동작은 `core`, 값 차이는 `rsConfig`, 화면·로직 차이는 `platform`이라는 기준을 이해한다
2. **Given** 적용 조건, **When** 선택 기준을 읽는다, **Then** 공통 사용자 흐름과 서비스별 빌드·배포가 필요한 경우임을 이해한다
3. **Given** 회피 조건과 한계, **When** 경계를 읽는다, **Then** 런타임 테넌트 전환이나 공통 도메인이 거의 없는 경우는 같은 구조를 그대로 적용하지 않으며 전체 구현 위임에는 패리티 검증 비용이 남음을 이해한다
4. **Given** 인사이트 본문, **When** 작업물과 비교한다, **Then** 프로젝트 전체 역할·연혁·예약 Context·결제 복귀 흐름을 반복하지 않는다

---

### User Story 3 - 독자가 예약 Context의 소유 범위 판단을 이해한다 (Priority: P1)

독자가 두 번째 연결 인사이트를 열었을 때 깊은 예약 단계의 Props Drilling을 줄이기 위해 전역 상태가 아니라 예약 라우터에 상태의 소유 범위와 생명주기를 둔 판단을 이해한다.

**Why this priority**: 현재 인사이트는 직접 확인하지 않은 Provider Hell과 성능 문제를 전제로 삼고 Context를 접근 통제 수단처럼 과장한다.

**Independent Test**: 기존 인사이트 경로에서 직접 문제, 실제 검토 대안, 선택 기준, 결과와 한계가 승인된 범위로 정정됐는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `context-api-encapsulation-and-router-level-isolation` 인사이트, **When** 문제를 읽는다, **Then** 중간 컴포넌트가 사용하지 않는 상태와 변경 함수를 전달하던 Props Drilling이 직접 문제로 제시된다
2. **Given** 대안 설명, **When** 선택 과정을 읽는다, **Then** 실제 검토한 Redux와 예약 라우터 범위·팀 전환 비용만 비교되고 Zustand는 나타나지 않는다
3. **Given** 결과 설명, **When** Context의 효과를 읽는다, **Then** 중간 전달 감소와 예약 흐름 생명주기 경계만 확인되고 성능·접근 통제·순차성 보장은 주장되지 않는다
4. **Given** 적용·회피 조건, **When** 판단 범위를 읽는다, **Then** 라우터에 묶인 다단계 클라이언트 상태와 전역·서버 기준 상태를 구분한다

---

### User Story 4 - 독자가 서로 다른 세 판단을 시각적으로 이해한다 (Priority: P2)

독자가 작업물과 두 인사이트를 이동하며 개발·검증·배포 흐름, 코드 배치 기준, 예약 상태 전달 전후를 서로 다른 시각 자료로 이해한다.

**Why this priority**: 세 주제는 모두 구조를 다루지만 같은 그림을 반복하면 작업물과 인사이트의 화면 역할이 흐려진다.

**Independent Test**: 각 시각 자료가 승인된 관계만 표시하고 동등한 텍스트 설명을 제공하며, 서로 다른 질문에 답하고 지원 화면 크기에서 겹침이나 문서 전체 가로 넘침이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 작업물 시각 자료, **When** 변경 흐름을 따라간다, **Then** 요구사항 분류, 세 소유 경계, 플랫폼별 빌드·계약 및 동작 검증, 배포와 패리티 누락 복구 경로를 이해한다
2. **Given** 첫 번째 인사이트 시각 자료, **When** 세 갈래 흐름을 따라간다, **Then** 공통 동작·값·화면 및 로직 차이가 각 소유 위치로 배치되는 기준을 이해한다
3. **Given** 두 번째 인사이트 시각 자료, **When** 전후를 비교한다, **Then** 중간 컴포넌트를 거친 props 전달과 예약 라우터 Provider를 통한 직접 소비의 차이를 이해한다
4. **Given** 시각 자료를 볼 수 없는 독자, **When** 텍스트 대안을 읽는다, **Then** 각 시각 자료의 핵심 관계와 한계를 이해한다

---

### User Story 5 - 공개 경로와 출처 연결이 유지된다 (Priority: P1)

독자가 기존 작업물·인사이트 주소를 계속 사용할 수 있고, 작업물에서 두 인사이트로 이동한 뒤 각 인사이트에서 원본 작업물로 돌아올 수 있다.

**Why this priority**: 사실 정정이 기존 탐색 경로를 깨뜨리거나 출처 없는 독립 인사이트를 만들면 콘텐츠 신뢰성이 낮아진다.

**Independent Test**: 세 기존 공개 경로, 공개 목록 진입, 양방향 링크, 키보드 활성화, 지원 화면 크기의 읽기 상태를 실제 화면에서 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 작업물과 두 인사이트 주소, **When** 각각 연다, **Then** 모두 승인된 콘텐츠로 응답한다
2. **Given** 호텔 예약 시스템 작업물, **When** 두 인사이트 링크를 각각 활성화한다, **Then** 올바른 인사이트로 이동한다
3. **Given** 각 인사이트, **When** 연결 작업물 링크를 활성화한다, **Then** 호텔 예약 시스템 작업물로 돌아간다
4. **Given** 키보드 사용자와 지원 화면 크기, **When** 목록과 상세를 탐색한다, **Then** 초점·라벨·본문·시각 자료가 읽히고 문서 전체 가로 넘침이 없다

### Edge Cases

- `플랫폼화 전`이 호텔마다 별도 프로젝트를 복제했다는 뜻으로 읽히는가? → 하나의 코드베이스에 호텔별 조건 분기가 누적된 구조로 고정한다.
- 설정 중심 개선이 코드 수정과 재배포 없는 신규 호텔 추가로 읽히는가? → 설정·환경변수·배포 구성을 추가했고 공통 기능 코드 수정이 줄었다는 범위로 제한한다.
- 공통 코드 1회 수정이 단일 산출물의 일괄 배포로 읽히는가? → 플랫폼별 빌드와 호텔별 운영 폴더 배포가 유지됨을 함께 표시한다.
- 2026년 마이그레이션 누락이 운영 장애로 읽히는가? → 운영 배포 전 개발·통합 검증에서 발견하고 보완한 사실을 명시한다.
- `ReservationContext`가 상태 변경 권한을 통제하거나 성능을 자동 개선한 것으로 읽히는가? → Props 전달 감소와 생명주기 경계만 결과로 제시한다.
- 결제 복귀가 가격·재고 재검증과 불일치 자동 취소까지 수행한 것으로 읽히는가? → 1시간 만료 임시 저장과 예약번호 기반 최종 조회까지만 표시한다.
- 운영 적용이 신규 호텔 추가 속도나 오류 감소율을 증명한 것으로 읽히는가? → 측정하지 않은 수치와 신규 온보딩 성과를 제외한다.
- 세 시각 자료가 같은 플랫폼 구조를 반복하거나 성능·접근 통제를 암시하는가? → 각 화면의 질문과 텍스트 대안을 독립적으로 검토한다.
- 좁은 화면에서 시각 자료의 노드·화살표·라벨이 본문을 가리거나 문서 전체가 넘치는가? → 기존 반응형 시각 계약에 따라 실제 화면에서 확인한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 작업물 구조화 상세

- **FR-001**: 호텔 예약 시스템 작업물은 기존 구조화 상세와 같은 공통 읽기 순서로 제공되어야 한다
- **FR-002**: 기간은 1차 구축 `2024.11 – 2025.10`, 구조 리빌딩 `2026.06 – 2026.08`, 현재 5개 플랫폼 운영 유지 상태를 구분해야 한다
- **FR-003**: 역할은 1차 구축의 FE 2명·BE 1명 협업, 사용자의 설정 중심 구조·예약 상태·모바일 결제 복귀 설계와 주요 구현, 2026년 경계 설계와 주요 마이그레이션을 구분해야 한다
- **FR-004**: 플랫폼화 전 구조를 단일 코드베이스의 호텔별 조건 분기로 설명하고 프로젝트별 복제라고 쓰지 않아야 한다
- **FR-005**: 1차 구조에서 서버 설정, 코드 설정, 환경변수와 호텔별 배포 구성이 담당한 차이를 설명해야 한다
- **FR-006**: 관리자 설정만으로 코드 수정·빌드·배포 없이 호텔을 추가했다거나 신규 호텔 코드 수정이 0건이 됐다고 주장하지 않아야 한다
- **FR-007**: 1차 구조의 결과와 한계로 공통 기능 코드 수정 범위 감소, 5개 호텔 배포 브랜치의 반복 수정과 편차를 함께 설명해야 한다
- **FR-008**: 2026년 구조의 배치 원칙을 모든 플랫폼의 공통 동작은 `core`, 값 차이는 `rsConfig`, 화면·로직 차이는 `platform`으로 명시해야 한다
- **FR-009**: 하나의 기준 소스와 플랫폼별 빌드·호텔별 운영 폴더 배포를 구분하고 단일 산출물 일괄 배포라고 쓰지 않아야 한다
- **FR-010**: 정식으로 비교하지 않은 모노레포, 별도 패키지, 런타임 단일 앱, 브랜치 자동 동기화를 당시 대안으로 제시하지 않아야 한다
- **FR-011**: 2026년 마이그레이션에서 최신 운영 변경 일부가 빠진 사건, 운영 배포 전 발견, 차이 목록화와 수동 이식을 공개하되 내부 감사 수치를 노출하지 않아야 한다
- **FR-012**: 5개 플랫폼 빌드, 확장 경로·공통 계약, 운영 브랜치 패리티, 플랫폼별 주요 흐름이라는 서로 다른 검증 범위를 설명해야 한다
- **FR-013**: 예약 상태는 Props Drilling, 실제 검토한 Redux, 라우터 범위 Provider, 중간 전달 감소와 생명주기 경계로 설명해야 한다
- **FR-014**: Provider Hell, 확인하지 않은 리렌더링 문제, Zustand 검토, 접근 통제, 순차성 보장, 성능 향상을 실제 문제·대안·성과로 쓰지 않아야 한다
- **FR-015**: NICEPAY 복귀는 외부 이동·재로딩, `sessionStorage` 1시간 만료, 예약번호 기반 최종 예약 조회, 개발·QA와 정상 운영 관찰 범위로 설명해야 한다
- **FR-016**: `localStorage`, 가격·재고 재검증, 불일치 시 자동 취소, 전체 결제 건수·성공률·개선율을 구현 또는 성과로 쓰지 않아야 한다
- **FR-017**: 결과는 5개 플랫폼 운영 적용, 공통 변경의 기준 코드 1회 수정, 호텔별 변경 격리, 최신 브랜치 비교 제거로 제한해야 한다
- **FR-018**: 회고는 최신 운영 기준선 선고정, 전체 플랫폼 구현 위임의 세분화, 계약 검사를 넘어선 예약·결제 동작 검증 확대를 포함해야 한다

#### 코드 경계 인사이트

- **FR-019**: `config-driven-architecture-react`의 기존 공개 경로를 유지하면서 제목을 `Config 이후의 경계: 멀티플랫폼 React를 core·rsConfig·platform으로 나눈 이유`로 정정해야 한다
- **FR-020**: 코드 경계 인사이트는 설정만으로 브랜치 편차가 해소되지 않은 배경과 `core`, `rsConfig`, `platform` 배치 판단에 집중해야 한다
- **FR-021**: 코드 경계 인사이트는 공통 사용자 흐름과 서비스별 빌드·배포 유지라는 적용 조건, 런타임 테넌트 전환 또는 공통 도메인 흐름이 거의 없는 회피 조건을 설명해야 한다
- **FR-022**: 코드 경계 인사이트는 플랫폼 위임 영역의 계약·동작 패리티 검증 비용을 한계로 밝히고 프로젝트 전체 역할·연혁·Context·결제 사례를 반복하지 않아야 한다

#### 예약 Context 인사이트

- **FR-023**: `context-api-encapsulation-and-router-level-isolation`의 기존 공개 경로를 유지하면서 제목을 `Props Drilling을 줄이기 위해 예약 Context의 생명주기를 라우터에 둔 이유`로 정정해야 한다
- **FR-024**: 예약 Context 인사이트는 Props Drilling, Redux 비교, 예약 라우터 범위 Provider와 직접 소비라는 한 질문에 집중해야 한다
- **FR-025**: 예약 Context 인사이트는 중간 props 전달 감소와 예약 흐름 이탈 시 상태를 정리할 생명주기 경계를 결과로 설명해야 한다
- **FR-026**: 예약 Context 인사이트는 Provider 밖 사용 오류가 접근 권한 통제가 아니며 Context가 성능을 자동 보장하지 않는다는 한계를 설명해야 한다
- **FR-027**: 예약 Context 인사이트는 프로젝트 플랫폼화 연혁과 NICEPAY 복귀 흐름을 반복하지 않아야 한다

#### 시각 자료와 연결·회귀

- **FR-028**: 작업물은 요구사항 분류부터 소유 경계, 플랫폼별 빌드·검증·배포로 이어지고 패리티 누락 시 감사·재이식으로 돌아가는 스윔레인 하나를 제공해야 한다
- **FR-029**: 코드 경계 인사이트는 공통 동작, 값 차이, 화면·로직 차이가 각 소유 위치로 이동하는 세 갈래 데이터 흐름을 제공해야 한다
- **FR-030**: 예약 Context 인사이트는 중간 컴포넌트를 거친 props 전달과 예약 라우터 Provider의 직접 소비를 비교하는 Before/After 시각 자료를 제공해야 한다
- **FR-031**: 세 시각 자료는 각각 질문, 승인된 관계, 정상·예외 또는 전후 구분, 동등한 텍스트 대안, 다른 두 자료와 중복되지 않는 이유를 가져야 한다
- **FR-032**: 시각 자료는 성능 향상, 접근 통제, 런타임 테넌트 전환이나 단일 배포를 사실처럼 암시하지 않아야 한다
- **FR-033**: 작업물은 두 인사이트로, 각 인사이트는 작업물로 돌아가는 의미 있는 양방향 링크를 제공해야 한다
- **FR-034**: 작업물과 두 인사이트의 기존 공개 경로를 유지하고 경로 이름을 변경하지 않아야 한다
- **FR-035**: 공개 목록, 양방향 링크, 키보드 초점·활성화, 320·768·1024·1440px 읽기 상태를 실제 화면에서 검증해야 한다
- **FR-036**: 시각 자료의 노드·화살표·라벨은 서로의 핵심 텍스트를 가리지 않아야 하고 문서 전체 가로 넘침을 만들지 않아야 한다
- **FR-037**: 공개 콘텐츠와 검증 산출물은 고객 정보, 시크릿, 비공개 소스·내부 감사 수치를 노출하지 않아야 한다
- **FR-038**: 다른 작업물·인사이트의 공개 내용과 기존 구조화 상세 계약을 변경하거나 관련 없는 파일을 다시 포맷하지 않아야 한다

### Key Entities

- **호텔 예약 시스템 작업물 상세**: 두 차례의 플랫폼화, 역할, 제약, 코드 경계, 마이그레이션 검증, 예약 상태, 결제 복귀, 결과와 회고를 공통 순서로 제공하는 원본 기록
- **코드 경계 인사이트**: 설정 이후 공통 동작·값·화면 및 로직 차이를 어디에 배치할지 다루는 프로젝트 사례
- **예약 Context 인사이트**: 예약 라우터 내부 Props Drilling과 상태 생명주기 경계를 다루는 프로젝트 사례
- **플랫폼 차이 분류**: 모든 플랫폼의 공통 동작, 값만 다른 항목, 화면·로직이 다른 항목을 구분하는 판단 기준
- **검증 근거**: 5개 플랫폼 빌드, 확장 경로·공통 계약, 운영 브랜치 패리티, 플랫폼별 주요 흐름을 서로 다른 범위로 확인한 기록
- **시각 자료**: 작업물 개발·검증·배포 스윔레인, 코드 경계 데이터 흐름, 예약 상태 Before/After 및 동등한 텍스트 설명
- **출처 연결**: 작업물과 각 프로젝트 사례 인사이트 사이의 양방향 공개 관계

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 호텔 예약 시스템 작업물 1개와 연결 인사이트 2개가 승인된 문안과 사실 경계로 공개된다
- **SC-002**: 철회 대상으로 승인된 프로젝트 복제, 무수정·무배포 신규 호텔 추가, 단일 산출물 일괄 배포, 미검토 대안, Context의 접근 통제·성능 보장, 결제 가격·재고 재검증·자동 취소 주장이 세 공개 기록에서 0건이다
- **SC-003**: 2026년 구조로 운영 적용된 플랫폼 5개와 플랫폼별 빌드·배포 유지가 같은 공개 설명에서 모순 없이 확인된다
- **SC-004**: 작업물에서 두 인사이트로 가는 링크 2개와 각 인사이트에서 작업물로 돌아오는 링크 2개가 모두 실제 화면에서 동작한다
- **SC-005**: 작업물 1개와 인사이트 2개가 각자 다른 질문을 답하는 시각 자료를 하나씩 제공하며 모든 시각 자료에 동등한 텍스트 설명이 있다
- **SC-006**: 320·768·1024·1440px에서 세 공개 기록의 본문과 시각 자료가 읽히고 문서 전체 가로 넘침 및 핵심 노드·라벨 겹침이 0건이다
- **SC-007**: 키보드만으로 공개 목록에서 세 기록에 진입하고 모든 양방향 링크를 식별·활성화할 수 있다
- **SC-008**: 승인된 인터뷰의 공개 사실, 철회 항목, 화면별 비중복 기준을 다루는 자동 검사가 모두 통과한다
- **SC-009**: 기존 공개 작업물·인사이트 경로와 관련 없는 콘텐츠에 대한 회귀 검사가 모두 통과한다

## Assumptions

- 2026-09-09 승인 인터뷰와 승인 공개 문안이 호텔 예약 시스템 작업물 및 두 연결 인사이트의 최우선 사실 근거다.
- 세 기존 공개 경로는 유지하며 사용자가 별도로 승인하지 않은 이름 변경·통합·비공개 처리는 범위 밖이다.
- 코드 확인 저장소는 구현 사실을 확인하는 읽기 전용 근거이며 비공개 코드나 내부 운영 자료를 포트폴리오로 복사하지 않는다.
- 승인된 시각 자료 세 건 외에 ERD나 NICEPAY 전용 시각 자료를 추가하지 않는다.
- NICEPAY 복귀와 마이그레이션 패리티는 별도 인사이트를 만들지 않고 작업물의 핵심 구현·검증 및 회고에 둔다.
- 현재 공개 데모 주소는 검증되지 않았으므로 데모 요소를 새로 만들지 않는다.
- 콘텐츠와 시각 자료 변경은 기존 구조화 상세 및 인사이트 편집 계약을 재사용하며 새로운 일반 목적 콘텐츠 모델은 범위에 포함하지 않는다.
