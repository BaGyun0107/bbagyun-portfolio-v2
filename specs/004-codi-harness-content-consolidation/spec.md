**Created**: 2026-08-21

**Status**: Draft

**Input**: User description: "하네스 작업물 상세에 대표 설계 결정 네 개를 복원하고, harness.lock과 소유권 경계, CLI와 doctor 제품화, Claude/Codex 정책 패리티, 멀티 세션과 컨텍스트 수명 인사이트를 발전 과정 중심의 대표 글 하나로 통합한다. 기존 네 글은 제거하고 redirect하지 않는다. 작업물 상세와 대표 인사이트의 중복 정본을 제거하며 기존 스윔레인, 지표와 다른 작업물은 보존한다. include test tasks (TDD)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 작업물 상세에서 구현 실체 파악 (Priority: P1)

면접관은 별도의 인사이트를 열지 않아도 하네스가 어떤 문제를 해결했고 작성자가 어떤
구조를 직접 설계·구현했으며 결과가 어떻게 검증됐는지 작업물 상세에서 파악하고 싶다.
도구 이름만 나열된 설명보다 문제, 선택과 결과가 연결된 대표 설계 결정이 필요하다.

**Why this priority**: 작업물 상세는 포트폴리오의 첫 판단 지점이다. 여기서 구현 실체가
보이지 않으면 좋은 스윔레인과 결과 지표가 있어도 도구 조합 사례로 오해할 수 있다.

**Independent Test**: 하네스 작업물 상세만 읽고 프로젝트 문제, 작성자의 세 책임 범위,
대표 설계 결정 네 개, 각 결정과 연결된 결과를 설명할 수 있다.

**Acceptance Scenarios**:

1. **Given** 방문자가 하네스 상세를 처음 열었을 때, **When** 제목 아래 설명과 개요를 읽으면, **Then** 같은 문장의 반복 없이 사내 개발 운영 플랫폼의 목적과 Jenkins 교체에서 문제 범위가 확장된 과정을 이해한다.
2. **Given** 방문자가 역할과 핵심 설계를 읽을 때, **When** 네 대표 설계 결정을 확인하면, **Then** CLI·진단, 버전·소유권 경계, 런타임별 정책 집행, 변경 범위·시크릿 배포 경계를 작성자가 직접 담당한 구현으로 식별한다.
3. **Given** 방문자가 결과와 회고를 읽을 때, **When** 각 설계 결정의 검증 근거를 확인하면, **Then** 배포 시간, 환경 혼입 관찰, 적용 범위와 비용 추정이 어떤 결정에서 나온 결과인지 설명한다.

### User Story 2 - 하나의 발전 서사로 하네스 변화 이해 (Priority: P1)

기술 면접관은 여러 짧은 글을 오가지 않고 복사형 v1의 한계가 소유권 경계, 초기화 제품화,
AI 정책 집행과 멀티 세션 실험으로 어떻게 이어졌는지 하나의 글에서 이해하고 싶다.

**Why this priority**: 네 짧은 글과 별도의 얇은 종합 글은 같은 프로젝트의 인과관계를
분산시키고 클릭 비용에 비해 충분한 깊이를 제공하지 못한다.

**Independent Test**: 대표 인사이트 하나만 읽고 Jenkins 제거에서 시작해 v1 복사 구조,
버전·소유권 경계, CLI·진단, AI 정책 패리티, 멀티 세션 실험과 회고까지의 발전 순서를
설명할 수 있다.

**Acceptance Scenarios**:

1. **Given** 방문자가 대표 인사이트를 열었을 때, **When** 위에서 아래로 읽으면, **Then** 승인된 여덟 구간을 원인과 다음 결정이 이어지는 순서로 확인한다.
2. **Given** 운영 중인 핵심 구조와 최신 확장 내용을 함께 읽을 때, **When** 성숙도 설명을 확인하면, **Then** 실제 운영 구조·적용 결과와 약 2주의 멀티 세션 실험을 혼동하지 않는다.
3. **Given** 방문자가 더 깊은 인프라 내용을 원할 때, **When** 관련 기록을 탐색하면, **Then** Jenkins·Infisical·Cloudflare의 독립 글은 기존 경로에서 계속 읽을 수 있다.

### User Story 3 - 중복·삭제 경로 없이 일관된 콘텐츠 운영 (Priority: P1)

포트폴리오 운영자는 화면에 사용되지 않는 긴 본문이나 오래된 글이 현재 콘텐츠와 다른
사실을 주장하지 않도록 작업물 상세와 대표 인사이트의 정본을 각각 하나로 유지하고 싶다.

**Why this priority**: 숨은 중복 본문은 지금 화면이 올바르더라도 다음 수정에서 오래된
비용·도구·운영 범위가 다시 공개되는 원인이 된다.

**Independent Test**: 작업물과 인사이트 데이터를 확인해 표시되지 않는 하네스 장문과
대표 글의 이전 장문이 없고, 제거된 네 글을 참조하는 내부 링크가 0개인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 하네스에 구조화 상세가 존재할 때, **When** 콘텐츠 정본을 검사하면, **Then** 기본 작업물 데이터에는 별도의 긴 본문이 없고 구조화 상세만 작업물 본문을 소유한다.
2. **Given** 대표 인사이트가 통합됐을 때, **When** 해당 글의 본문을 검사하면, **Then** 오래된 대체 장문 없이 하나의 현재 본문만 존재한다.
3. **Given** 짧은 인사이트 네 개가 제거됐을 때, **When** 포트폴리오 내부 링크를 검사하면, **Then** 제거된 경로를 가리키는 링크는 0개이고 해당 경로에 직접 접근하면 찾을 수 없는 페이지로 응답한다.

---

### User Story 4 - 기존 증거와 다른 작업물 보존 (Priority: P2)

기존 방문자는 콘텐츠 통합 이후에도 마음에 든 연결형 스윔레인, 근거 지표, 접근성,
다른 작업물과 유지 대상 인사이트를 같은 방식으로 이용하고 싶다.

**Why this priority**: 이번 변경은 콘텐츠 깊이와 정본을 정리하는 작업이며 이미 검증된
흐름·지표·다른 프로젝트까지 다시 작성하는 범위가 아니다.

**Independent Test**: 하네스의 두 흐름과 여섯 지표, 전체 8개 작업물, 하네스 외 7개
본문, 유지 대상 인프라 인사이트와 지원 화면 너비의 탐색 계약이 이전과 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방문자가 하네스 상세를 다시 열었을 때, **When** 시스템 흐름과 결과를 확인하면, **Then** 두 연결형 스윔레인과 여섯 지표의 값·근거 범위를 이전과 동일하게 확인한다.
2. **Given** 방문자가 키보드 또는 작은 화면을 사용할 때, **When** 다이어그램을 탐색하면, **Then** 페이지 전체 가로 넘침 없이 기존 이름·설명·내부 가로 탐색을 이용한다.
3. **Given** 방문자가 다른 작업물 또는 유지 대상 인프라 글을 열 때, **When** 공개 경로를 방문하면, **Then** 기존 본문과 접근 경로를 그대로 확인한다.

### Edge Cases

- 기본 작업물 데이터의 긴 본문만 제거하고 구조화 상세까지 누락되면 하네스 상세가 비게 되므로 공개를 차단한다.
- 대표 인사이트를 통합한 뒤 작업물이나 다른 글에 제거된 네 경로가 하나라도 남으면 끊어진 내부 링크로 취급한다.
- 제거된 네 경로가 목록에서는 사라졌지만 직접 접근에서 이전 글을 계속 반환하면 통합이 완료되지 않은 것으로 취급한다.
- 대표 인사이트가 운영 구조와 멀티 세션 실험을 같은 성숙도로 표현하면 공개 범위가 과장되므로 수정한다.
- 대표 인사이트의 분량이 늘어도 제목, 요약, 읽기 시간과 본문 순서가 서로 다르면 게시하지 않는다.
- 작업물 개요, 문제와 역할이 같은 문장을 반복해 각 섹션의 목적을 구분할 수 없으면 콘텐츠 압축이 완료되지 않은 것으로 본다.
- 삭제 과정에서 Jenkins·Infisical·Cloudflare 독립 인사이트 중 하나가 함께 사라지면 회귀로 취급한다.
- 콘텐츠 변경이 연결형 흐름, 지표 값, 데모 없음 정책 또는 다른 작업물 본문을 바꾸면 범위 이탈로 취급한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 하네스 제목 아래 설명은 도구 나열보다 팀원과 AI 에이전트의 설계·검증·배포 기준을 집행하는 사내 개발 운영 플랫폼의 가치를 한 문장으로 전달해야 한다.
- **FR-002**: 프로젝트 개요는 Jenkins 교체에서 개발 운영 기준 통합으로 문제 범위가 확장된 과정을 설명하고 결과 지표의 숫자를 반복하지 않아야 한다.
- **FR-003**: 역할 설명은 하네스 아키텍처·소유권, 초기화·진단·AI 규칙, CI/CD·시크릿·운영 검증의 세 책임 범위를 제공해야 한다.
- **FR-004**: 문제 상황은 반복 초기화·배포 설정, 사람·AI별 작업 규칙 편차, 다중 호텔의 환경·배포 대상 혼입 위험을 구분해 제공해야 한다.
- **FR-005**: 제약 조건은 비공개 자료, 두 AI 런타임의 서로 다른 집행 방식, 업데이트 시 프로젝트 소유 파일 보존을 포함해야 한다.
- **FR-006**: 대안 검토는 Jenkins 유지, 프로젝트별 배포 절차 복사, 공통 정책·초기화·검증 하네스를 비교하고 반복 가능성과 안전한 변경 전파를 선택 기준으로 제공해야 한다.
- **FR-007**: 핵심 설계는 CLI·진단, 버전·소유권 경계, 공통 정책·런타임 어댑터, 변경 범위·시크릿 경계의 대표 결정 네 개를 승인된 순서로 제공해야 한다.
- **FR-008**: 각 대표 설계 결정은 발생한 문제, 선택한 구조, 검증 근거 또는 트레이드오프를 함께 설명해야 한다.
- **FR-009**: 현재와 과거 도구를 혼동하지 않도록 GSD에서 Spec Kit, GStack에서 Playwright MCP로의 전환 이유를 정책 집행 설계 안에서 제공해야 한다.
- **FR-010**: 결과 설명은 변경 범위 기반 병렬 배포, 환경별 시크릿 경계, 초기화·진단·공통 정책, Jenkins 제거를 각각 기존 검증 결과와 연결해야 한다.
- **FR-011**: 회고는 안전한 변경 전파로서의 재사용성과 반드시 지켜야 하는 경계로서의 guardrail 판단을 제공해야 한다.
- **FR-012**: 작업물 본문은 발전 과정을 다루는 대표 인사이트 하나를 직접 연결하고 제거되는 네 짧은 글을 연결하지 않아야 한다.
- **FR-013**: 대표 인사이트는 기존 종합 글의 공개 경로를 유지하고 `DX 하네스 v2: 복사형 도구에서 사내 개발 운영 플랫폼까지` 제목과 9분 읽기 안내를 제공해야 한다.
- **FR-014**: 대표 인사이트는 Jenkins 출발점, v1 복사 한계, 버전·소유권 경계, CLI·진단, AI 정책 집행, 멀티 세션 실험, 결과, 회고의 여덟 구간을 승인된 순서로 제공해야 한다.
- **FR-015**: 대표 인사이트는 운영 중인 핵심 구조, 실제 적용 결과, 운영 확장 실험을 서로 다른 성숙도 범위로 구분해야 한다.
- **FR-016**: 하네스 기본 작업물 데이터는 구조화 상세와 중복되는 별도 긴 본문을 보유하지 않아야 한다.
- **FR-017**: 대표 인사이트는 현재 본문과 중복·충돌할 수 있는 오래된 대체 장문을 보유하지 않아야 한다.
- **FR-018**: `harness.lock과 소유권 경계`, `CLI와 doctor 제품화`, `Claude/Codex 정책 패리티`, `멀티 세션과 컨텍스트 수명`의 네 짧은 인사이트는 목록과 공개 콘텐츠에서 제거해야 한다.
- **FR-019**: 제거된 네 인사이트 경로는 redirect 없이 찾을 수 없는 페이지로 응답하고, 이를 가리키는 내부 링크는 0개여야 한다.
- **FR-020**: Jenkins·Infisical·Cloudflare 독립 인사이트의 기존 본문과 공개 경로는 유지해야 한다.
- **FR-021**: 하네스의 연결형 스윔레인 두 개, 여섯 근거 지표, 데모 없음 정책과 공통 읽기 순서는 변경하지 않아야 한다.
- **FR-022**: 하네스 외 7개 작업물의 기존 본문과 전체 8개 작업물 공개 경로는 유지해야 한다.
- **FR-023**: 320px, 768px, 1024px와 1440px 화면에서 페이지 전체 가로 넘침과 다이어그램 키보드 탐색 계약을 유지해야 한다.
- **FR-024**: 모든 행동·공개 경로 변경은 실패하는 콘텐츠 계약, 렌더링 또는 사용자 흐름 테스트를 먼저 확인한 뒤 구현해야 한다.

### Key Entities

- **작업물 기본 정보**: 제목, 한 문장 설명, 개요, 기간, 팀과 기술 맥락을 가진 작업물의 상단 정보다.
- **구조화 작업물 상세**: 역할, 근거 지표, 문제·제약, 대안, 시스템 흐름, 대표 설계, 결과와 회고를 공통 순서로 제공하는 하네스 본문의 단일 정본이다.
- **대표 설계 결정**: 발생한 문제, 선택한 구조, 검증 또는 트레이드오프를 묶어 작성자의 구현 판단을 설명하는 네 콘텐츠 단위다.
- **대표 인사이트**: 하네스가 복사형 v1에서 내부 개발 운영 플랫폼으로 발전한 과정을 여덟 구간으로 설명하는 단일 심화 글이다.
- **제거 인사이트 경로**: 통합 후 목록과 내부 링크에서 사라지고 직접 접근 시 찾을 수 없는 페이지로 응답하는 네 과거 글 경로다.
- **독립 인프라 인사이트**: Jenkins 전환, Infisical 시크릿 경계와 Cloudflare 연결을 각각 독립적인 문제 해결로 설명하며 유지되는 글이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 작업물 상세에서 대표 설계 결정이 정확히 4개 제공되고 각 결정의 문제·선택·검증 또는 트레이드오프가 모두 확인된다.
- **SC-002**: 방문자는 작업물 상세만 읽고 프로젝트 문제 3개, 작성자의 책임 범위 3개, 대표 설계 결정 4개와 기존 결과 4개 범주를 설명할 수 있다.
- **SC-003**: 작업물 본문에서 직접 제공하는 발전 과정 대표 인사이트 링크는 1개이며 제거된 네 경로 링크는 0개다.
- **SC-004**: 대표 인사이트는 승인된 8개 구간을 순서대로 제공하고 읽기 시간은 9분으로 표시된다.
- **SC-005**: 대표 인사이트에서 운영 중 핵심 구조, 실제 적용 결과와 운영 확장 실험이 각각 명시돼 방문자가 멀티 세션 실험을 기본 운영 기능으로 오해할 수 있는 표현이 0개다.
- **SC-006**: 하네스 작업물과 대표 인사이트에는 공개 화면이 사용하지 않는 중복 장문 정본이 각각 0개다.
- **SC-007**: 제거 대상 네 글은 목록에서 0개, 내부 참조에서 0개이며 네 기존 경로 모두 찾을 수 없는 페이지로 응답한다.
- **SC-008**: Jenkins·Infisical·Cloudflare 유지 대상 인사이트 3개는 기존 공개 경로에서 모두 접근 가능하다.
- **SC-009**: 하네스의 두 스윔레인, 여섯 지표와 데모 CTA 0개 계약이 콘텐츠 통합 전과 동일하게 유지된다.
- **SC-010**: 전체 8개 작업물 공개 경로에 접근할 수 있고 하네스 외 7개 작업물의 기존 본문 손실은 0건이다.
- **SC-011**: 320px, 768px, 1024px와 1440px에서 페이지 전체 가로 넘침은 1px 이하이고 두 다이어그램은 각각 한 번의 키보드 정지로 가로 탐색된다.
- **SC-012**: 콘텐츠 계약, 서버 렌더링, 공개 경로, 접근성, 전체 페이지 생성과 기존 작업물 회귀 검증이 모두 통과한 상태에서만 완료로 판정된다.

## Assumptions

- 현재 연결형 스윔레인은 사용자 승인을 받은 최종 구조이며 이번 콘텐츠 통합에서 수정하지 않는다.
- 기존 여섯 지표의 값, 기준 시점과 근거 범위는 다시 산정하거나 변경하지 않는다.
- 대표 인사이트의 기존 공개 경로를 유지하므로 작업물에서 연결되는 심화 글 주소는 하나로 안정화된다.
- 사용자는 제거된 네 글의 과거 외부 링크 호환성보다 콘텐츠 통합을 우선하며 redirect를 원하지 않는다.
- 멀티 세션 테스트베드는 약 2주의 제한된 운영 확장 실험으로 표현하고 모든 하네스 프로젝트의 기본 기능으로 일반화하지 않는다.
- 하네스의 긴 기본 본문과 대표 글의 오래된 대체 본문은 현재 공개 화면의 정본이 아니며 제거해도 다른 작업물의 fallback에 영향을 주지 않는다.
- 작업물 상세 목표 분량은 약 5~7분, 대표 인사이트 공개 읽기 시간은 9분이다.
- 새 구현은 기존 공통 상세 형식을 재사용하며 별도 페이지 유형을 추가하지 않는다.
