## 작업물 계약

- 백엔드 단독 책임과 프론트엔드 2인 협업을 구분한다.
- 2024.08~2025.08 코드 작업 기간, 2026-06 거래 운영 종료, 이후 관리자 조회·데이터 보존 상태를 구분한다.
- 월 주문 약 100건, 월 결제액 약 400~500만 원, 월 정산 포함 완료 주문 약 70건, 등록 대상 약 50곳 중 월 실지급 약 10~20곳의 단위와 범위를 혼동하지 않는다.
- 월 2회 내부 정산과 지급대행 실제 지급 내역을 운영팀이 2026-06까지 대사했고, 그 관찰 범위에서 불일치·중복을 확인하지 못했다고 표현한다.
- 개발 환경에서 결제 보상 취소 성공과 취소 API 실패를 모두 확인했으며, 이중 실패 자동 복구는 없었다고 표현한다.
- 스윔레인은 결제·보상 취소 흐름 정확히 1개다.

## 정산 인사이트 계약

- 제목: `정산 상태는 DB에, 재처리 입력은 JSON에 둔 이유`
- DB 상태가 지급 판단 기준이고 JSON은 계산된 지급 입력·실패 항목 보존 수단이다.
- 성공 항목 제거, 실패 항목 보존, 매일 10시·14시 재실행 전 DB 재확인을 설명한다.
- 별도 단일 PM2 scheduler가 중복 스케줄 실행 방지와 웹 요청 처리 분리를 위해 사용됐다.
- 단일 서버·단일 scheduler·현재 규모에서 사용한 선택이며 scale-out 환경에 그대로 권장하지 않는다.
- Redis, DB-only, scheduler 개선 중 확정한 답은 없다.

## Socket.io 인사이트 계약

- 제목: `공용 Room에서 화원별 User Room으로: 전달 범위와 전달 보장은 다르다`
- 신규 구축 때 Polling과 Socket.io를 비교했다.
- 개발 중 코드 재검토로 공용 Room의 과도한 수신 범위를 발견하고 `user_<gardenId>`로 변경했다.
- 개발 다계정 테스트에서 관련 화원만 받은 사실과 성능·유실 보장 미검증을 구분한다.
- 공용 Room 시절 미수신 관찰의 원인은 규명하지 못했고, User Room 이후 같은 현상을 재현하지 못했을 뿐 해결을 증명하지 않았다.
- PM2 3개 worker와 Socket.io cluster adapter는 운영 적용·브라우저 관찰 범위만 말한다.
- 특정 사용자/조직 상태는 user room, 진짜 공지는 public room을 적용 기준으로 제시한다.

## 금지 주장

다음은 세 기록에서 사용자의 당시 비교·구현·검증·성과로 나타나면 안 된다.

- 간이/정규 Outbox로 설계했다는 주장
- RabbitMQ, Kafka, Redis Stream, Redis Adapter, ACK, DLQ, cursor 복구를 당시 검토·구현했거나 확정 로드맵으로 삼았다는 주장
- k6 처리량·성공률·성능 개선 결과
- 기존 Polling을 제거했다는 주장
- 외부 결제와 내부 DB가 하나의 원자적 transaction이라는 주장
- User Room이 메시지 유실 또는 다중 worker 전달 신뢰성을 해결했다는 주장
- DB 재조회 0회, 다음 영업일만 재시도, JSON이 DB 장애에서도 금융 원본을 보장한다는 주장
- 측정하지 않은 생산성·트래픽·장애 감소율

## 연결 계약

- 작업물의 관련 인사이트 영역에 두 인사이트 링크가 모두 존재한다.
- 각 인사이트의 연관 기록 영역에 하이패스 작업물 링크가 존재한다.
- 링크의 보이는 이름은 정정된 제목을 사용하고 keyboard Enter로 활성화된다.
- 목록→상세와 상세→연결 기록 탐색 중 slug redirect나 404가 발생하지 않는다.
