# Feature Specification: 하이패스 B2B 플랫폼 구조화 상세와 연결 인사이트 정정

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-09-04

**Status**: Complete

**Input**: 2026-09-04 사용자 인터뷰에서 승인된 하이패스 B2B 플랫폼 작업물과 연결 인사이트 두 건을 구조화 상세로 이전하고, 사실과 다른 기존 서술을 함께 정정한다. 이후 작업 목록에는 테스트 우선 개발(TDD) 항목을 포함한다.

## Context

`hipass-b2b-platform`은 현재 장문 본문만 제공되며 연결된 두 인사이트도 승인된 인터뷰와 다른 내용을 포함한다. 이 기능은 작업물 하나와 연결 인사이트 두 건을 하나의 사실 계약으로 다룬다.

승인된 인터뷰:
`docs/portfolio-interviews/2026-09-04-hipass-b2b-platform.md`

핵심 공개 경계는 다음과 같다.

- 백엔드는 사용자가 혼자 담당했고 프론트엔드는 사용자를 포함한 두 명이 개발했다.
- 하이패스는 전화·팩스·카카오톡 주문과 계좌이체에 의존하던 업무를 온라인 주문·승인·배송·결제·정산 흐름으로 새로 구축한 프로젝트다.
- 정산 상태는 DB가 기준이며 JSON은 계산 결과와 실패 후 재처리 입력을 보존하는 보조 저장소다. 이를 Outbox로 분류하지 않는다.
- Socket.io는 공용 Room에서 화원별 User Room으로 전달 대상을 좁혔지만 이벤트 도달을 보장했다고 주장하지 않는다.
- 공개 근거가 없는 k6 결과, MQ·Outbox·ACK·DLQ·Redis 계열 개선 로드맵은 제거한다.
- 작업물 1개와 인사이트 2개에 서로 다른 질문을 답하는 시각 자료를 제공한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채용 담당자가 하이패스의 실제 책임과 결과를 읽는다 (Priority: P1)

채용 담당자가 하이패스 상세를 열었을 때 사용자의 백엔드 단독 책임, 프론트엔드 협업 범위, 실제 결제·정산 운영 결과와 검증 한계를 같은 구조로 빠르게 이해한다.

**Why this priority**: 현재 장문은 실제로 검토하지 않은 기술과 과장된 결과를 포함해 사용자의 핵심 책임과 운영 근거를 흐린다.

**Independent Test**: 작업물 상세에서 역할, 문제, 제약, 실제 선택, 핵심 구현, 근거가 붙은 결과, 회고가 공통 읽기 순서로 표시되고 승인되지 않은 주장이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 하이패스 작업물 상세, **When** 역할과 팀 구성을 읽는다, **Then** 백엔드 단독 담당과 프론트엔드 2인 협업·초기 구조 기여가 구분된다
2. **Given** 운영 지표, **When** 값과 설명을 읽는다, **Then** 월 주문, 결제액, 정산 포함 완료 주문, 등록·실지급 화원의 단위와 근거 범위를 혼동하지 않는다
3. **Given** 현재 서비스 상태, **When** 상태와 기간을 읽는다, **Then** 사용자 코드 작업 기간과 2026년 6월까지의 거래 운영 기간, 이후 조회·보존 상태가 구분된다
4. **Given** 결과와 회고, **When** 검증 범위를 읽는다, **Then** 월말 대사에서 확인한 결과와 개발 환경에서만 검증한 결제 보상 흐름이 분리된다

---

### User Story 2 - 독자가 정산 상태와 재처리 입력의 역할 분리를 이해한다 (Priority: P1)

독자가 정산 인사이트를 열었을 때 DB가 지급 상태의 기준이고 JSON은 계산 결과와 실패 건을 보존하는 재처리 입력 저장소였음을 이해한다.

**Why this priority**: 현재 인사이트의 Outbox·MQ 비교는 실제 경험이 아니며 정산 구조의 핵심을 잘못 설명한다.

**Independent Test**: 정산 인사이트의 제목, 소개, 본문, 적용·회피 조건, 시각 자료가 승인된 역할 분리와 단일 서버 한계를 일관되게 전달하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정산 인사이트, **When** 정상 흐름을 읽는다, **Then** DB 상태 확인, JSON 입력 사용, 지급 성공 후 완료 처리와 파일 제거 순서를 이해한다
2. **Given** 지급 실패, **When** 재처리 흐름을 읽는다, **Then** 실패 항목만 JSON에 남고 매일 10시·14시에 DB 상태를 재확인해 다시 처리됨을 이해한다
3. **Given** 적용 기준, **When** 한계를 읽는다, **Then** 단일 서버·단일 스케줄러·작은 규모의 조건과 로드밸런싱·스케일 아웃 회피 조건을 구분한다
4. **Given** 현재 회고, **When** 다음 선택을 읽는다, **Then** Redis·DB 단독·스케줄러 개선 중 어느 것도 검증된 정답으로 제시되지 않는다

---

### User Story 3 - 독자가 Socket.io 전달 범위와 전달 보장의 차이를 이해한다 (Priority: P1)

독자가 Socket.io 인사이트를 열었을 때 공용 Room에서 화원별 User Room으로 바꾼 이유와 그 변경이 메시지 유실 해결을 의미하지 않는다는 한계를 함께 이해한다.

**Why this priority**: 현재 인사이트는 이미 변경된 공용 Room을 현재 구조로 쓰고, 검토하지 않은 복구 기술과 신뢰성 성과를 사용자의 판단처럼 제시한다.

**Independent Test**: Socket.io 인사이트에서 발견 경위, User Room 구현, 개발·운영 확인 범위, 미검증 범위, 적용·회피 조건이 승인 문안과 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 초기 설계, **When** 선택 배경을 읽는다, **Then** 신규 구축 시 Polling과 Socket.io를 비교했으며 기존 Polling을 제거한 작업이 아님을 이해한다
2. **Given** 공용 Room 문제, **When** 발견 경위를 읽는다, **Then** 개발 중 코드 재검토에서 관계없는 사용자도 받을 수 있는 구조를 발견했음을 이해한다
3. **Given** User Room 결과, **When** 검증 설명을 읽는다, **Then** 관련 화원만 수신한 개발 테스트와 성능·유실 미검증 범위가 구분된다
4. **Given** 운영 다중 워커 설명, **When** 근거를 읽는다, **Then** 운영 적용과 브라우저 관찰만 확인됐고 내부 워커 전달을 분리 검증하지 않았음을 이해한다

---

### User Story 4 - 독자가 세 흐름을 서로 혼동하지 않고 시각적으로 이해한다 (Priority: P2)

독자가 작업물과 두 인사이트를 이동하며 결제 보상, 정산 재처리, Socket.io 수신 대상 변경을 각각 독립된 시각 자료로 이해한다.

**Why this priority**: 세 주제는 실패·재처리·전후 관계가 있어 시각 자료의 가치가 높지만 같은 전체 흐름을 반복하면 작업물과 인사이트의 역할이 흐려진다.

**Independent Test**: 각 시각 자료가 승인된 관계만 표시하고 텍스트 대안을 제공하며, 서로 다른 질문을 답하고 지원 화면 크기에서 겹침이나 문서 전체 가로 넘침이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 작업물 스윔레인, **When** 결제 흐름을 따라간다, **Then** 주문 생성, 결제 승인, DB 실패, 자동 취소, 취소 API 실패가 정상·예외 경로로 구분된다
2. **Given** 정산 인사이트 시각 자료, **When** 상태와 데이터를 따라간다, **Then** DB 상태, JSON 입력, 지급 성공·실패, 다음 재시도의 관계를 이해한다
3. **Given** Socket.io Before/After 시각 자료, **When** 두 구조를 비교한다, **Then** 공용 Room의 넓은 전달 범위와 화원별 User Room의 제한된 전달 범위를 구분한다
4. **Given** 시각 자료를 볼 수 없는 독자, **When** 텍스트 대안을 읽는다, **Then** 각 시각 자료의 핵심 정상·예외·한계 관계를 이해한다

---

### User Story 5 - 공개 경로와 연결 관계가 유지된다 (Priority: P1)

독자가 기존 작업물·인사이트 주소를 계속 사용할 수 있고, 작업물에서 두 인사이트로 이동한 뒤 각 인사이트에서 원본 작업물로 돌아올 수 있다.

**Why this priority**: 내용 정정이 기존 북마크를 깨뜨리거나 출처 없는 인사이트를 만들면 공개 콘텐츠 신뢰성과 탐색성이 손상된다.

**Independent Test**: 작업물과 두 인사이트의 기존 경로, 공개 목록 진입, 양방향 링크, 키보드 활성화, 지원 화면 크기의 읽기 상태를 실제 화면에서 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 세 공개 주소, **When** 각각 연다, **Then** 모두 정정된 콘텐츠로 응답한다
2. **Given** 하이패스 작업물, **When** 두 인사이트 링크를 각각 활성화한다, **Then** 올바른 인사이트로 이동한다
3. **Given** 각 인사이트, **When** 연결 작업물 링크를 활성화한다, **Then** 하이패스 작업물로 이동한다
4. **Given** 키보드 사용자와 지원 화면 크기, **When** 목록과 상세를 탐색한다, **Then** 초점·라벨·본문·시각 자료가 읽히고 문서 전체 가로 넘침이 없다

### Edge Cases

- `월 70건`이 지급 화원 수나 정산 실행 수로 읽히는가? → 정산에 포함된 완료 주문 수로 단위를 고정하고 실제 지급 화원 월 10~20곳과 분리한다.
- 등록 화원 약 50곳이 매월 지급된 화원으로 읽히는가? → 등록된 정산 대상 풀과 해당 월 실지급 대상을 별도 문장으로 표시한다.
- `Production`이 현재 신규 주문·정산도 운영 중이라는 의미로 읽히는가? → 2026년 6월 거래 운영 종료와 현재 조회·데이터 보존 상태를 구분한다.
- 내부 DB 트랜잭션이 외부 결제까지 원자적으로 보장한 것으로 읽히는가? → 외부 승인 뒤 내부 실패 시 보상 취소를 호출하는 구조와 취소 API 이중 실패 한계를 함께 표시한다.
- JSON이 정산 상태의 원본 또는 Outbox로 읽히는가? → DB 상태를 지급 판단 기준으로 반복 표시하고 JSON의 보조 입력 역할을 구분한다.
- 실패 재처리가 다음 영업일에만 실행된 것으로 읽히는가? → 매일 10시·14시 실행으로 정정한다.
- User Room이 이벤트 유실을 해결하거나 다중 워커 신뢰성을 보장한 것으로 읽히는가? → 전달 대상 검증과 유실·워커 전달 미검증을 분리한다.
- 시각 자료의 곡선·라벨이 노드 텍스트를 가리거나 좁은 화면에서 문서 전체가 넘치는가? → 기존 반응형 시각 계약을 적용하고 각 시각 자료의 라벨과 노드가 겹치지 않는지 실제 화면에서 확인한다.
- 사실과 다른 문장만 지우고 빈 제목이나 출처 카드가 남는가? → 승인된 대체 문안을 제공하고 양방향 연결을 실제 화면에서 확인한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 작업물 구조화 상세

- **FR-001**: 하이패스 작업물은 기존 구조화 상세와 같은 공통 읽기 순서로 제공되어야 한다
- **FR-002**: 역할은 백엔드 단독 책임과 프론트엔드 2인 협업·초기 구조 기여를 구분해야 한다
- **FR-003**: 작업 기간 `2024.08 – 2025.08`, 거래 운영 종료 `2026.06`, 이후 관리자 조회·데이터 보존 상태를 서로 다른 의미로 표시해야 한다
- **FR-004**: 월 주문 약 100건, 월 결제액 약 400~500만 원, 월 정산 포함 완료 주문 약 70건, 등록 정산 대상 화원 약 50곳, 월 실지급 화원 약 10~20곳은 단위·근거·관찰 범위를 함께 제공해야 한다
- **FR-005**: 월말 내부 정산과 지급대행 내역 대사에서 2026년 6월까지 불일치·중복 지급을 확인하지 못한 결과를 운영 관찰 범위로 제한해야 한다
- **FR-006**: 결제 흐름은 내부 DB 처리와 외부 결제가 하나의 원자적 트랜잭션이라는 주장을 제거하고, 내부 실패 시 보상 취소와 취소 API 이중 실패 한계를 구분해야 한다
- **FR-007**: 프론트엔드 기여는 기능·페이지 단위 구조, 기능 내부 상태, 공통 전역 상태 최소화와 협업 관찰로 설명하고 측정하지 않은 생산성 수치를 만들지 않아야 한다
- **FR-008**: 검증 근거가 없는 k6 본문과 결과·회고를 공개 작업물에서 제거해야 한다

#### 실제 선택과 정산 인사이트

- **FR-009**: 실시간 대안은 신규 구축 시 실제 비교한 Polling과 Socket.io만 포함하고 기존 Polling을 제거했다고 쓰지 않아야 한다
- **FR-010**: `json-outbox-pattern-for-settlement`의 기존 공개 경로를 유지하면서 제목과 내용을 승인된 `정산 상태는 DB에, 재처리 입력은 JSON에 둔 이유`로 정정해야 한다
- **FR-011**: 정산 인사이트는 DB 상태가 지급 판단의 기준이고 JSON은 계산 결과·실패 건을 보존하는 재처리 입력 저장소임을 설명해야 한다
- **FR-012**: 정산 인사이트는 성공 항목 제거, 실패 항목 보존, 매일 10시·14시 재처리, 단일 PM2 스케줄러의 중복 실행 방지·웹 요청 분리 목적을 설명해야 한다
- **FR-013**: 정산 인사이트에서 Outbox, RabbitMQ, Kafka를 당시 비교·선택 또는 확정된 미래 로드맵으로 제시하지 않아야 한다
- **FR-014**: 정산 인사이트는 단일 서버·단일 스케줄러·작은 규모의 적용 조건과 로드밸런싱·스케일 아웃 회피 조건을 명시해야 한다
- **FR-015**: Redis 보존, DB 단독 관리, 스케줄러 개선은 미검증 고민으로만 구분하고 어느 하나를 정답으로 단정하지 않아야 한다

#### Socket.io 인사이트

- **FR-016**: `socketio-realtime-architecture-and-reliability`의 기존 공개 경로를 유지하면서 제목과 내용을 승인된 `공용 Room에서 화원별 User Room으로: 전달 범위와 전달 보장은 다르다`로 정정해야 한다
- **FR-017**: Socket.io 인사이트는 공용 Room 문제를 개발 중 코드 재검토에서 발견했고 화원별 User Room으로 변경했음을 설명해야 한다
- **FR-018**: 관련 화원만 수신한 개발 테스트, 공용 Room 시절 서버 송신·브라우저 미수신 관찰, User Room 이후 유실 미재현을 서로 다른 근거 범위로 표시해야 한다
- **FR-019**: 운영 PM2 3개 워커와 cluster adapter 적용 및 브라우저 정상 관찰은 유지하되 내부 워커 전달 구조 이해·분리 검증 성과로 확대하지 않아야 한다
- **FR-020**: ACK, 재시도 큐·DLQ, Redis Stream cursor 복구, Redis Adapter를 실제 검토하거나 구현할 계획으로 제시하지 않아야 한다
- **FR-021**: 특정 사용자·조직 이벤트는 사용자별 Room, 진짜 공지성 이벤트는 공용 Room이라는 적용 기준과 전달 범위·전달 보장의 분리를 명시해야 한다

#### 시각 자료와 연결·회귀

- **FR-022**: 작업물은 주문·결제·보상 취소 스윔레인 정확히 하나를 제공하고 결제 취소 API 실패를 복구된 경로로 표시하지 않아야 한다
- **FR-023**: 정산 인사이트는 DB 상태, JSON 입력, 지급 성공·실패와 재시도의 상태·데이터 흐름을 제공해야 한다
- **FR-024**: Socket.io 인사이트는 공용 Room과 화원별 User Room의 전달 대상 차이를 보여주는 Before/After 구조도를 제공해야 한다
- **FR-025**: 세 시각 자료는 각각 질문, 승인된 관계, 정상·예외 또는 전후 구분, 동등한 텍스트 대안, 다른 두 시각 자료와 중복되지 않는 이유를 가져야 한다
- **FR-026**: 작업물은 두 인사이트로, 각 인사이트는 작업물로 돌아가는 의미 있는 양방향 링크를 제공해야 한다
- **FR-027**: 작업물과 두 인사이트의 기존 공개 경로를 유지하고 경로 이름을 변경하지 않아야 한다
- **FR-028**: 공개 목록, 양방향 링크, 키보드 초점·활성화, 320·768·1024·1440px 읽기 상태를 실제 화면에서 검증해야 한다
- **FR-029**: 시각 자료의 노드·화살표·라벨은 서로의 핵심 텍스트를 가리지 않아야 하고 문서 전체 가로 넘침을 만들지 않아야 한다
- **FR-030**: 다른 작업물·인사이트의 공개 내용과 기존 구조화 상세 계약을 변경하거나 관련 없는 파일을 다시 포맷하지 않아야 한다
- **FR-031**: 고객 거래 데이터, 계좌 정보, 시크릿, 비공개 로그·소스 내용을 공개 콘텐츠나 검증 산출물에 포함하지 않아야 한다

### Key Entities

- **하이패스 작업물 상세**: 역할, 근거 지표, 문제, 제약, 실제 선택, 결제·정산·실시간·프론트엔드 구현, 결과와 회고를 공통 순서로 제공하는 원본 기록
- **정산 인사이트**: DB 상태와 JSON 재처리 입력의 역할 분리라는 한 질문을 다루는 프로젝트 사례
- **Socket.io 인사이트**: 공용 Room과 화원별 User Room의 전달 범위 및 전달 보장 한계를 다루는 프로젝트 사례
- **근거 지표**: 값, 단위, 근거 종류, 기준 시점, 설명, 필요한 유의 범위를 함께 제공하는 운영 관찰
- **시각 자료**: 작업물 결제 보상 스윔레인, 정산 상태·데이터 흐름, Socket.io Before/After 구조도 및 동등한 텍스트 설명
- **출처 연결**: 작업물과 각 프로젝트 사례 인사이트 사이의 양방향 공개 관계

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 하이패스 작업물 1개와 연결 인사이트 2개가 승인된 문안과 사실 경계로 공개된다
- **SC-002**: 철회 대상으로 기록된 Outbox·MQ 비교, k6 결과, 기존 Polling 제거, 원자적 외부 결제 트랜잭션, User Room의 유실 해결, 미검토 소켓 복구 기술 주장이 세 공개 기록에서 0건이다
- **SC-003**: 공개하는 운영 수치의 100%가 단위, 근거 종류, 기준 시점과 관찰 한계를 함께 제공한다
- **SC-004**: 작업물에서 두 인사이트로 가는 링크 2개와 각 인사이트에서 작업물로 돌아오는 링크 2개가 모두 실제 화면에서 동작한다
- **SC-005**: 작업물 1개와 인사이트 2개가 각자 다른 질문을 답하는 시각 자료를 하나씩 제공하며 모든 시각 자료에 동등한 텍스트 설명이 있다
- **SC-006**: 320·768·1024·1440px에서 세 공개 기록의 본문과 시각 자료가 읽히고 문서 전체 가로 넘침 및 핵심 노드·라벨 겹침이 0건이다
- **SC-007**: 키보드만으로 공개 목록에서 세 기록에 진입하고 모든 양방향 링크를 식별·활성화할 수 있다
- **SC-008**: 기존 공개 작업물·인사이트 경로와 관련 없는 콘텐츠에 대한 회귀 검사가 모두 통과한다

## Assumptions

- 2026-09-04 승인 인터뷰와 승인 공개 문안이 하이패스 작업물 및 두 연결 인사이트의 최우선 사실 근거다.
- 세 기존 공개 경로는 유지하며 사용자가 별도로 승인하지 않은 이름 변경·통합·비공개 처리는 범위 밖이다.
- 코드 확인 저장소는 구현 사실을 확인하는 읽기 전용 근거이며 비공개 코드나 실제 거래 데이터를 포트폴리오로 복사하지 않는다.
- 승인된 시각 자료 세 건 외에 ERD나 추가 흐름을 의무적으로 만들지 않는다.
- 현재 공개 데모 주소는 검증되지 않았으므로 데모 요소를 새로 만들지 않는다.
- 콘텐츠와 시각 자료 변경은 기존 구조화 상세 및 인사이트 편집 계약을 재사용하며 새로운 일반 목적 콘텐츠 모델은 범위에 포함하지 않는다.
