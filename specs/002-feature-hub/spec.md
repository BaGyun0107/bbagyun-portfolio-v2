# Feature Specification: 기능 허브 + 기능정의 상태 flow

**Feature Branch**: `feat/feature-hub-and-status-flow`

**Created**: 2026-07-08

**Status**: Draft

**Input**: STICKY-v1의 두 기능(역할별 md→html 허브, 기능정의 상태 flow)을 하네스(Spec Kit 기반)에 이식. 전체 설계: `설계 초안(2026-07-18 정리 — git history)`

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 팀 협업 진입 허브 (Priority: P1)

새로 합류한 팀원(PM/PL, 웹 디자이너, 프론트, 백)이 저장소를 열었을 때, 한 장의 HTML을
브라우저로 열어 자기 역할이 무엇을 먼저 봐야 하는지, 어떤 문서가 있는지, 지금 어떤 기능이
어느 단계인지를 한눈에 파악한다.

**Why this priority**: 사용자가 가장 먼저 꼽은 기능이며, 나머지 상태 데이터가 없어도 문서
색인과 역할 안내만으로 독립적 가치를 준다. 협업의 진입점.

**Independent Test**: 상태 데이터(specs/registry)가 하나도 없어도 `mise run docs:build`를
실행하면 역할별 카드와 MD 문서 색인이 담긴 `docs/index.html`이 생성되고, Chrome에서 파일
하나로 열려 검색이 동작하는 것으로 검증 가능.

**Acceptance Scenarios**:

1. **Given** 저장소에 여러 MD 문서가 있고 기능 상태 데이터는 없는 상태, **When** 팀원이
   허브 생성을 실행하면, **Then** 역할별 진입 카드와 검색 가능한 MD 문서 색인이 담긴 단일
   HTML이 생성되고 외부 네트워크 없이 열린다.
2. **Given** 생성된 허브 HTML, **When** 팀원이 문서 제목·경로·카테고리로 검색하면,
   **Then** 일치하는 문서만 실시간으로 필터링되어 보인다.
3. **Given** 기능 상태 데이터가 존재하는 상태, **When** 허브를 다시 생성하면, **Then**
   같은 HTML에 기능별 phase/status/담당역할 대시보드 섹션이 함께 나타난다.

### User Story 2 - 기능정의 상태 추적 flow (Priority: P1)

팀이 각 기능을 계획→구현→검증→완료 단계로 진행하면서, 그 상태를 한 곳(진실의 원천)에서
추적하고, 명시적 커맨드로 단계를 전이하며, 전이 이력을 남긴다.

**Why this priority**: 사용자가 꼽은 두 번째 핵심 기능. 협업에서 "지금 뭐가 어디까지
됐는지"를 공유하는 뼈대. 허브 대시보드가 이 데이터를 소비한다.

**Independent Test**: 한 기능의 상태 파일을 두고 전이 커맨드로 planned→in-progress→
in-review→done을 순서대로 실행하면 상태 파일과 이력이 갱신되고, 잘못된 전이는 거부되는
것으로 검증 가능.

**Acceptance Scenarios**:

1. **Given** 상태가 `planned`인 기능, **When** 담당자가 `in-progress`로 전이하는 커맨드를
   실행하면, **Then** 상태 파일이 갱신되고 전이 이력(언제, 어느 상태로)이 기록된다.
2. **Given** 기능의 모든 작업 항목이 완료 표시된 상태에서 상태가 아직 `in-progress`,
   **When** 허브 생성이나 상태 조회를 실행하면, **Then** "in-review로 전이할까요?"라는
   제안이 출력되지만 자동으로 바꾸지는 않는다(차단·자동변경 없음).
3. **Given** 검증(e2e) 증거가 해당 기능 변경보다 신선하고 상태가 `in-review`, **When**
   상태 점검을 실행하면, **Then** "done으로 전이할까요?" 제안이 출력된다.
4. **Given** 어떤 상태, **When** 정의되지 않은 순서로 전이를 시도하면(예: planned→done),
   **Then** 커맨드가 경고하거나 거부한다.

### User Story 3 - 기능정의 유무에 무관한 유연성 (Priority: P2)

기능정의가 먼저 주어진 프로젝트든, 정의 없이 바로 만드는 프로젝트든 같은 flow로 수렴한다.

**Why this priority**: 사용자가 "가장 중요"하다고 강조한 유연성. P1 두 기능의 동작 방식을
규정하는 제약이라 P2로 두되 반드시 충족해야 한다.

**Independent Test**: (a) 기능 목록을 registry에 먼저 넣고 spec을 만드는 경로와 (b) spec을
먼저 만들고 나중에 registry에 역등록하는 경로 둘 다 최종적으로 같은 대시보드 결과를 내는지
확인.

**Acceptance Scenarios**:

1. **Given** registry에 아직 spec 없는 기능 항목들이 있는 상태, **When** 허브를 생성하면,
   **Then** 그 기능들이 `planned` 상태로 대시보드에 나타난다.
2. **Given** registry 없이 spec만 만든 기능, **When** 허브를 생성하면, **Then** 그 기능이
   spec 상태 그대로 대시보드에 나타난다(registry가 필수가 아니다).
3. **Given** registry 항목과 같은 id의 spec이 나중에 생긴 상태, **When** 허브를 생성하면,
   **Then** spec 상태가 우선하고 registry 항목에 spec 링크가 자동 연결된다.

### Edge Cases

- 작업 항목 파일(tasks)이 없는 기능의 진행률은 어떻게 표시하나? (예: "작업 미정"으로 표기)
- 상태 파일의 값이 허용되지 않은 값일 때 생성기는 어떻게 처리하나? (건너뛰고 경고)
- registry와 spec에 같은 id가 있지만 제목이 다를 때 어느 쪽 제목을 쓰나? (spec 우선)
- 생성된 HTML을 사람이 손으로 고쳤을 때 다음 생성이 덮어쓰는 것을 어떻게 알리나?
  (손수정 금지 배너)
- 색인 대상 폴더가 비어 있거나 존재하지 않을 때 생성이 실패하지 않아야 한다.

## Requirements *(mandatory)*

### Functional Requirements

**허브 생성 (US1)**

- **FR-001**: 시스템은 단일 커맨드로 하나의 자체 완결 HTML 파일을 생성해야 한다. 이 파일은
  외부 네트워크·CDN·폰트·스크립트에 의존하지 않고 브라우저에서 파일 하나로 열려야 한다.
- **FR-002**: 생성된 HTML은 역할별(PM/PL, 웹 디자이너, 프론트, 백) 진입 카드 섹션을
  포함해야 한다.
- **FR-003**: 생성된 HTML은 저장소의 MD 문서를 색인해 제목·경로·카테고리·발췌로 검색·필터
  가능한 섹션을 포함해야 한다.
- **FR-004**: 생성된 HTML은 기능별 phase·status·담당역할·진행률을 필터 가능한 대시보드
  섹션으로 포함해야 한다. 상태 데이터가 없으면 이 섹션은 비어 있거나 생략될 수 있으나 생성은
  실패하지 않아야 한다.
- **FR-005**: 생성된 HTML은 손으로 수정하지 말라는 안내(배너)를 포함해야 하며, 재생성 시
  전부 덮어써진다.

**상태 flow (US2)**

- **FR-006**: 각 기능은 진실의 원천이 되는 상태 정보(phase, status, decision_level,
  담당역할, surface, 의존성, 전이 이력)를 기능별 위치에 보관해야 한다.
- **FR-007**: 기능 진행률은 별도로 저장하지 않고 해당 기능의 작업 항목 완료 여부에서 실시간
  계산해야 한다.
- **FR-008**: 시스템은 명시적 커맨드로 기능 상태를 전이하고, 전이 시각과 대상 상태를 이력에
  기록해야 한다.
- **FR-009**: 유효 전이 순서는 planned → in-progress → in-review → done이며, 어느
  상태에서든 on-hold로 갈 수 있어야 한다. 정의되지 않은 전이는 경고하거나 거부해야 한다.
- **FR-010**: 시스템은 상태 전이를 자동으로 강제하지 않는다. 대신 작업 항목이 모두 완료되면
  in-review를, 검증 증거가 신선하면 done을 **제안(출력)만** 하고 사용자의 명시적 커맨드를
  기다려야 한다.
- **FR-011**: QA 활동은 별도 담당역할이 아니라 in-review 상태로 표현하며, 시스템은 기존
  하네스 e2e 검증 게이트(사용자 플로우 마커, e2e 실행, 실행 증거 스탬프)와 연결되어야 한다.

**유연성 (US3)**

- **FR-012**: 선택적 기능 목록(registry)이 존재하면 시스템은 이를 대시보드에 병합하되,
  기능별 상태(spec)가 있으면 그것을 우선해야 한다.
- **FR-013**: registry가 없어도 시스템은 기능별 상태(spec)만 스캔해 정상 동작해야 한다
  (registry는 필수가 아니다).
- **FR-014**: registry 항목과 같은 id의 기능 상태(spec)가 존재하면 시스템은 둘을 연결(링크
  자동 부여)하고 상태는 spec 값을 사용해야 한다.
- **FR-015**: 기능정의가 먼저 있는 경로(목록 → 기능 명세 씨앗)와 정의 없이 시작하는
  경로(명세 → 완료 후 목록 역등록은 선택)가 모두 지원되고 동일한 대시보드 결과로 수렴해야
  한다.

**품질/경계**

- **FR-016**: 색인 대상 폴더가 비어 있거나 없거나, 상태 값이 허용 범위를 벗어나도 생성은
  실패하지 않고 해당 항목을 건너뛰며 경고를 남겨야 한다.
- **FR-017**: 이 기능의 재사용 가능한 구성 단위(색인, 병합, 전이 판정)는 독립적으로 단위
  테스트 가능해야 한다.

### Key Entities *(include if feature involves data)*

- **기능 상태(Feature Status)**: 기능 하나의 진실의 원천. id, 제목, phase, 진행 상태,
  결정 수준, 담당역할(복수), surface, 의존성, 전이 이력을 가진다.
- **기능 레지스트리 항목(Registry Entry)**: 아직 명세가 없는 기능이나 담당 배정을 담는
  선택적 시드. id, 제목, phase, 상태, 담당역할, surface, 명세 링크(있으면)를 가진다.
- **MD 문서 색인 항목(Doc Index Entry)**: 색인된 문서 하나. 경로, 제목, 카테고리, 발췌,
  링크를 가진다.
- **역할(Role)**: pm, designer, frontend, backend 네 가지 고정 값.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 상태 데이터가 전혀 없는 저장소에서도 허브 생성 커맨드가 성공하고, 결과 HTML이
  브라우저에서 오프라인으로 열려 역할 카드와 문서 색인이 표시된다.
- **SC-002**: 팀원이 문서 색인에서 검색어를 입력하면 일치하는 문서만 즉시 필터링되어 보인다.
- **SC-003**: 한 기능을 planned에서 done까지 전이 커맨드만으로 진행할 수 있고, 각 전이가
  이력에 남아 나중에 "언제 어느 단계로 갔는지" 확인할 수 있다.
- **SC-004**: 정의되지 않은 전이(예: planned에서 done으로 건너뜀)는 100% 차단되거나
  경고된다.
- **SC-005**: registry를 삭제한 뒤에도 허브 생성이 실패 없이 동작하며, 기능 상태(spec)만으로
  대시보드가 채워진다.
- **SC-006**: 같은 기능을 registry-먼저 경로와 spec-먼저 경로로 각각 만들었을 때 최종
  대시보드 표시가 동일하다.
- **SC-007**: 색인/병합/전이 판정 구성 단위 각각에 대해 자동 테스트가 존재하고 통과한다.

## Assumptions

- 이 저장소는 harness upstream이므로 새 공유 도구는 모든 downstream이 상속하는 공유 위치에
  둔다(별도 결정으로 확정됨).
- 팀원은 로컬에서 브라우저(Chrome 권장)로 생성된 HTML을 연다. 웹 호스팅은 범위 밖.
- 기능 명세와 그 상태는 커밋되는 `specs/<NNN>/` 디렉터리 관례를 따른다(하네스 기존 관례).
- 상태 전이 커맨드에 필요한 실행 시각 등은 실행 환경(태스크 러너)이 주입한다. 생성 스크립트는
  시각을 직접 읽지 않는다.
- 검증(e2e) 증거는 하네스의 기존 e2e 게이트 산출물(실행 증거 스탬프)을 재사용한다. 새 e2e
  하네스를 만들지 않는다.
- 역할 집합은 pm/designer/frontend/backend 4개로 고정한다. QA는 역할이 아니라 상태 단계다.

## Out of Scope

- 상태 전이를 자동으로 강제하는 차단형 훅.
- 커밋 시 허브를 자동 재생성하는 훅(1차는 수동 생성만).
- registry를 필수로 요구하는 동작.
- STICKY의 기획 이력 상태값(원본기록/개정반영 등) 전체 이식.
- Google Workspace / FigJam 등 외부 문서 연동.
