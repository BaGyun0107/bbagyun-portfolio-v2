# Feature Specification: 프로젝트별 디자인 시스템 지원 구조 (codi-design-system)

**Feature Branch**: `feat/codi-design-system`

**Created**: 2026-07-08

**Status**: Draft

**Input**: User description: "프로젝트별 디자인 시스템 지원 구조 — 하네스가 계약(위치/형식/프로세스)을 소유하고 값은 다운스트림 프로젝트가 소유. 대화형 생성 스킬 + 스캐폴드 템플릿 + 기존 자산 연결. deep-research로 검증된 업계 관행(CSS 변수 토큰, 스킬 기반 JIT 로딩, 문서를 에이전트 입력으로) 반영."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 대화형 디자인 시스템 생성 (Priority: P1)

다운스트림 프로젝트의 개발자가 스킬을 호출해 브랜드 질문(무드, 주 색상,
타이포그래피·CJK 여부, 라운드/밀도)에 하나씩 답하면, 검증된 토큰 파일과
디자인 원칙 문서가 표준 위치에 생성된다.

**Why this priority**: 이 기능의 존재 이유. 이것 하나만 있어도 프로젝트가
일관된 디자인 시스템을 갖고 시작할 수 있다.

**Independent Test**: front 앱이 있는 임시 프로젝트에서 스킬을 호출해
질문에 답하고, 표준 위치에 토큰 파일과 문서가 생성되며 검증 게이트를
통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 디자인 시스템이 없는 프로젝트, **When** 스킬을 호출해 브랜드
   질문에 모두 답하면, **Then** 표준 위치에 토큰 파일과 원칙 문서가
   생성되고 모든 전경/배경 토큰 쌍이 접근성 대비 기준을 통과한다.
2. **Given** 생성된 토큰 파일, **When** 앱 전역 스타일이 토큰을 불러오는지
   확인하면, **Then** 연결이 확인되거나 연결 방법이 안내된다.
3. **Given** 브랜드 질문 중 사용자가 접근성 기준을 통과하지 못하는 색을
   선택, **When** 검증 게이트가 실행되면, **Then** 실패 사유와 조정안이
   제시되고 통과할 때까지 값을 재조정한다.

---

### User Story 2 - 에이전트가 디자인 시스템을 자동으로 따름 (Priority: P2)

프로젝트에 디자인 시스템이 생성된 뒤, 에이전트가 UI 작업을 할 때 표준
위치의 토큰과 원칙 문서를 읽고 그 제약 안에서 작업한다. 문서가 실사용
경로에 있으므로 방치·부패하지 않는다.

**Why this priority**: 생성만 되고 에이전트가 따르지 않으면 무용지물.
업계 리서치에서 확인된 "문서는 만들지만 유지되지 않는" 실패 패턴의 해법.

**Independent Test**: 디자인 시스템이 있는 프로젝트에서 프론트엔드
작업을 요청하고, 에이전트가 토큰/문서를 먼저 읽으며 하드코딩 색상 없이
시맨틱 토큰만 사용하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 디자인 시스템이 있는 프로젝트, **When** 에이전트에게 UI
   작업을 요청하면, **Then** 에이전트는 작업 전 토큰 파일과 원칙 문서를
   읽고 시맨틱 토큰만 사용한다.
2. **Given** 디자인 시스템이 없는 프로젝트, **When** 에이전트에게 UI
   작업을 요청하면, **Then** 공용 디자인 표준 문서를 기본값으로 따른다.

---

### User Story 3 - 기존 디자인 시스템 수정 (Priority: P3)

이미 디자인 시스템이 있는 프로젝트에서 스킬을 다시 호출하면 수정 모드로
동작한다. 토큰 값을 바꾸면 원칙 문서도 함께 갱신되어 둘이 어긋나지 않는다.

**Why this priority**: 생성은 한 번이지만 수정은 반복된다. 토큰-문서
동기화가 깨지면 문서 부패가 시작된다.

**Independent Test**: 디자인 시스템이 있는 상태에서 스킬을 호출해 주
색상을 바꾸고, 토큰 파일과 문서가 함께 갱신되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 디자인 시스템이 있는 프로젝트, **When** 스킬을 호출하면,
   **Then** 수정 모드로 진입해 현재 값을 보여주고 바꿀 항목을 묻는다.
2. **Given** 수정 모드에서 토큰 값 변경, **When** 변경이 적용되면,
   **Then** 검증 게이트를 다시 통과하고 원칙 문서의 해당 절이 함께
   갱신된다.

---

### User Story 4 - 신규 프로젝트 초기화 시 안내 (Priority: P4)

새 프로젝트를 초기화할 때 프론트 앱 구성이 끝나면 디자인 시스템 생성을
안내받는다(강제 아님).

**Why this priority**: 발견 가능성(discoverability) 개선. 없어도 스킬을
직접 호출하면 되므로 우선순위 낮음.

**Independent Test**: 프로젝트 초기화 흐름을 실행하고 프론트 구성 후
디자인 시스템 생성 안내가 출력되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 프론트 앱이 포함된 신규 프로젝트 초기화, **When** 초기화
   흐름이 프론트 구성을 마치면, **Then** 디자인 시스템 생성 안내가 한 줄
   표시된다.

### Edge Cases

- 토큰 파일은 있는데 원칙 문서가 없는 부분 상태에서 스킬 호출 시: 수정
  모드로 진입하되 누락된 문서를 먼저 생성해 완전한 상태로 복구한다.
- backend-only 프로파일(front 앱 없음)에서 스킬 호출 시: 프로파일을
  확인하고 front 앱이 없음을 안내하며 중단한다(파일을 만들지 않음).
- 사용자가 검증 게이트 실패를 무시하고 강행을 요청할 때: 실패 사실과
  영향을 문서의 결정 기록에 명시한 뒤에만 진행한다(암묵적 통과 금지).
- CJK 지원이 필요한 서비스: 타이포 질문에서 CJK 대응 폰트 스택을
  우선한다(기존 공용 디자인 표준과 동일 규칙).
- 다크모드 쌍이 한쪽만 정의된 토큰: 검증 게이트가 잡아내고 쌍 완성을
  요구한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 하네스는 프로젝트 디자인 시스템의 표준 위치와 형식 계약을
  문서로 소유해야 한다 — 토큰은 `apps/front/src/styles/tokens.css`
  (Tailwind v4 `@theme`, shadcn 시맨틱 토큰명, 라이트/다크 쌍), 원칙
  문서는 `docs/design-system.md`, 커스텀 컴포넌트는
  `apps/front/components/ui/`(기존 프리미티브 조합 + cva variant 규약).
- **FR-002**: 신규 shared 스킬 `codi-design-system`은 브랜드 질문(무드,
  주 색상, 타이포·CJK, 라운드/밀도)을 한 번에 하나씩 물어 답을 수집해야
  한다.
- **FR-003**: 스킬은 표준 위치의 기존 파일 존재 여부로 생성/수정 모드를
  자동 판별해야 한다.
- **FR-004**: 검증 게이트 — 생성/수정된 모든 전경/배경 토큰 쌍은 WCAG AA
  대비 기준을 통과해야 하고, 공용 디자인 표준의 안티패턴 검사와 다크모드
  쌍 완결성 검사를 통과해야 한다. 실패 시 조정안을 제시하고 재검증한다.
- **FR-005**: 스킬은 중립 기본값이 채워진 토큰 템플릿과 원칙 문서 골격
  템플릿을 resources로 보유하고, 실행 시 프로젝트 값으로 치환해
  인스턴스화해야 한다. 템플릿의 중립 기본값은 추후 공통 베이스의
  출발점(v0) 역할을 겸한다.
- **FR-006**: 수정 모드에서 토큰 값이 바뀌면 원칙 문서의 해당 절을 같은
  실행 안에서 동기화해야 한다(토큰-문서 불일치 상태로 종료 금지).
- **FR-007**: `codi-frontend` 스킬은 UI 작업 전 표준 위치의 토큰 파일과
  원칙 문서를 읽는 계약을 명시해야 하며, 기존 `packages/design-tokens`
  참조는 표준 경로 참조로 교체되어야 한다.
- **FR-008**: 공용 디자인 표준 문서(`imported-rules/design.md`)에
  "프로젝트 디자인 시스템이 있으면 그것이 우선, 없으면 이 문서가
  기본값"이라는 우선순위 규칙이 추가되어야 한다.
- **FR-009**: 스킬 키워드 트리거(디자인 시스템, 토큰, 브랜드 컬러 등)가
  등록되어 관련 요청 시 스킬이 제안되어야 한다.
- **FR-010**: `init-project` 스킬은 프론트 구성 완료 후 디자인 시스템
  생성을 안내(강제 아님)해야 한다.
- **FR-011**: 디자인 시스템 내용은 상시 컨텍스트(CLAUDE.md, 항상 로드되는
  규칙)에 사전 로드되어서는 안 된다 — 필요 시점에 파일을 읽는 온디맨드
  로딩만 허용한다(context rot 방지). 값의 정본은 토큰 파일이고 문서는
  원칙/근거만 얇게 유지한다.
- **FR-012**: 스킬은 생성 후 앱 전역 스타일이 토큰 파일을 불러오는지
  확인하고, 아니면 연결 방법을 안내해야 한다.
- **FR-013**: 계약 문서에 확장 경로가 명시되어야 한다 — front 앱이 여러
  개가 되면 shadcn 공식 모노레포 규약(`packages/ui` 중앙화)으로 승격,
  공통 베이스 도입 시 템플릿 기본값 교체(기존 프로젝트 무영향).

### Key Entities

- **토큰 파일**: 프로젝트의 색상/타이포/라운드 값의 정본. 라이트/다크
  쌍을 가진 시맨틱 토큰 집합. project-owned.
- **원칙 문서**: 디자인 결정과 근거의 기록(무드/타이포/색상/모션/컴포넌트
  규약). 에이전트의 UI 작업 입력. project-owned.
- **템플릿**: 중립 기본값이 채워진 토큰/문서의 출발점. shared
  (하네스 소유, 업데이트로 전파).
- **계약**: 표준 위치·형식·프로세스의 정의. shared. 값이 아닌 구조만
  규정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 디자인 시스템이 없는 프로젝트에서 브랜드 질문 답변만으로
  (질문 6개 이하, 별도 사전 지식 불필요) 완전한 디자인 시스템(토큰 +
  문서)이 생성된다.
- **SC-002**: 생성된 전경/배경 토큰 쌍의 100%가 접근성 대비 기준(WCAG
  AA)을 통과한다 — 라이트/다크 모두.
- **SC-003**: 디자인 시스템이 있는 프로젝트에서 에이전트 UI 작업 산출물에
  하드코딩 색상이 0건이고 시맨틱 토큰만 사용된다.
- **SC-004**: 수정 모드 실행 후 토큰 파일과 원칙 문서가 불일치하는 경우가
  0건이다(동기화 100%).
- **SC-005**: 기존 하네스 검증(doctor, 테스트 스위트, 스킬 머지 트리)에
  회귀가 0건이다.

## Assumptions

- 프론트 스택은 하네스 표준(Tailwind v4 + shadcn/ui + React/Next.js)을
  전제한다. 다른 스택은 범위 외.
- 프로젝트별 디자인 시스템은 상호 독립이며, 공통 베이스는 추후 템플릿
  기본값 교체로 도입한다(이번 범위 외).
- Figma 연동, Storybook 문서화, 디자인 시스템 전용 MCP 서버는 범위 외
  (업계 리서치 결과 AI 통합은 초기 단계로, 온디맨드 파일 읽기 계약으로
  충분).
- 검증 게이트의 대비 계산은 스킬 실행 중 도구(스크립트)로 수행 가능하다.
- 구현 tasks 생성 시 테스트 태스크(TDD)를 명시적으로 포함한다.
