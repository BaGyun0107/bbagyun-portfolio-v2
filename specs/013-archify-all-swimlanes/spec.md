# Feature Specification: 전체 스윔레인 Archify 임베드 전환

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-09-10

**Status**: Draft

**Input**: 사용자 승인에 따라 호텔 예약 시스템에서 검증한 Archify 기반 작은 보기·크게 보기 구조를 포트폴리오의 모든 기존 스윔레인으로 확장한다. 총 8개 스윔레인의 실제 흐름을 보존하면서 공통 범례, 좁은 화면 transcript, 접근성, 반응형, 실패 fallback을 제공하고 테스트 작업을 포함한다.

## Context

현재 포트폴리오의 스윔레인은 작업물마다 표현 밀도와 읽기 방식이 달랐다. Feature 012에서 호텔 예약 시스템 한 건을 실제 Archify 결과로 전환하면서, 작은 보기에서는 전체 topology를 무스크롤 구조 미리보기로 유지하고 `크게 보기`에서는 같은 결과의 세부 문구와 관계 설명을 복원하는 구성을 검증했다. 사용자는 이 구조와 시각적 결과를 승인했으며, 이제 동일한 읽기 경험을 전체 작업물의 기존 스윔레인에 적용한다.

이번 전환의 대상은 현재 데이터에 존재하는 다음 8개 스윔레인이다.

| 작업물 | 스윔레인 ID | 공개 흐름 |
| --- | --- | --- |
| Codi Harness DX Platform | `design-development-verification` | 설계·개발·검증 |
| Codi Harness DX Platform | `cicd-secrets-deployment` | CI/CD·시크릿·배포 |
| 한마음과학원 | `ingestion-and-recovery` | 원문 적재와 실패 복구 |
| 한마음과학원 | `search-request-flow` | 검색 요청 처리 |
| 블랙스톤 벨포레 리조트 | `payment-and-compensation` | 결제·보상취소 흐름 |
| 하이패스 B2B 플랫폼 | `order-payment-compensation` | 주문·결제·보상 취소 흐름 |
| 호텔 예약 플랫폼 | `platform-change-verification-deployment` | 플랫폼 변경·검증·배포 흐름 |
| 통합 SSO 서버 | `central-account-auth-flow` | 중앙 회원 인증과 서비스 로컬 검증 |

각 대상은 인터뷰와 기존 구조화 상세의 승인된 사실을 기반으로 새 Archify 의미 원본과 생성 결과를 만든다. 원본 문구, 단계·관계의 방향, 예외 의미를 시각적으로 보기 좋게 만든다는 이유로 삭제하거나 재해석하지 않는다. 생성 자료를 사용할 수 없는 경우 기존 React 스윔레인을 fallback으로 유지해 작업물 본문이 빈 영역이 되지 않게 한다.

### Visual Evidence Decision

- **Visual decision: provided** — 여러 역할 경계, 정상 경로, 분기와 복구를 한 번에 비교해야 하므로 8개 스윔레인 모두 시각 자료를 유지한다.
- **Existing visual disposition: replace renderer for all existing swimlanes** — 각 스윔레인의 작은 보기와 `크게 보기`를 해당 흐름에서 생성한 실제 Archify 결과로 전환한다.
- 작은 보기와 크게 보기는 한 스윔레인의 같은 artifact를 공유하며 정보 밀도만 다르게 한다.
- 기존 카드 구조, 전체 흐름 설명, 예외 상황과 대응, 연결 인사이트의 공개 문구는 유지한다.
- 범례는 실제로 사용되는 공통 선 의미만 설명한다. 현재 portfolio theme에서 구분되는 기본색 실선과 예외색 점선을 각각 일반 진행·검증 통과, 예외 발견·복구 및 재검증으로 설명하고 사용하지 않는 조합의 의미를 만들지 않는다.
- 좁은 화면에서 node 내부 글자가 작아지는 문제는 topology를 변형하지 않고 `크게 보기`의 구조화 transcript로 보완한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 독자가 어떤 작업물에서도 같은 방식으로 흐름을 파악한다 (Priority: P1)

독자는 8개 대상 작업물의 스윔레인을 열었을 때 현재 호텔 예약 시스템에서 승인한 것과 같은 작은 보기 구조로 전체 단계와 정상·예외·복구 topology를 빠르게 비교할 수 있다.

**Why this priority**: 작업물마다 다른 다이어그램 동작을 학습하지 않아도 되고, 포트폴리오의 시각 자료가 실제 흐름을 설명하는 공통 읽기 경험을 제공해야 한다.

**Independent Test**: 8개 스윔레인을 순회해 작은 보기마다 해당 흐름의 모든 단계·관계가 보존되고, 카드 폭 안에 가로 넘침 없이 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 8개 대상 스윔레인 중 하나가 카드에 표시된 상태, **When** 독자가 작은 보기를 읽는다, **Then** 기존 데이터의 모든 단계와 관계 방향 및 정상·예외 구조를 한눈에 확인할 수 있다.
2. **Given** 여러 작업물의 스윔레인이 연속으로 표시된 상태, **When** 독자가 카드를 비교한다, **Then** 작은 보기의 비율·범례 위치·확대 동작이 같은 공통 구조를 따른다.
3. **Given** 320px, 768px, 1024px 또는 1440px 화면, **When** 독자가 작은 보기를 확인한다, **Then** 페이지 전체와 카드에 가로 넘침이나 제목·동작·다이어그램 겹침이 없다.
4. **Given** 밝은 화면 또는 어두운 화면, **When** 독자가 스윔레인을 표시한다, **Then** 다이어그램의 배경·경계·문구·정상·예외 표현이 포트폴리오 색상 체계와 일치한다.

### User Story 2 - 독자가 작은 보기에서 같은 흐름을 상세하게 읽는다 (Priority: P1)

독자는 각 카드의 기존 `크게 보기`를 사용해 작은 보기와 같은 배치의 상세 표현, 단계 설명, 관계 문구와 공통 선 범례를 읽을 수 있다. 좁은 화면에서는 다이어그램을 억지로 확대하지 않고 transcript에서 문구를 판독한다.

**Why this priority**: 작은 보기의 구조적 장점과 상세 보기의 사실 전달을 동시에 유지해야 하며, 모바일에서도 단계와 관계의 의미를 잃지 않아야 한다.

**Independent Test**: 각 대상 카드에서 mouse·touch·keyboard로 `크게 보기`를 열고, 같은 단계·관계 배치와 상세 문구, 범례, 좁은 화면 transcript를 확인한 뒤 Escape 또는 닫기로 초점이 돌아오는지 검사한다.

**Acceptance Scenarios**:

1. **Given** 대상 스윔레인의 카드, **When** 독자가 `크게 보기`를 활성화한다, **Then** 현재 포트폴리오 Dialog 안에 같은 스윔레인의 실제 Archify 상세 표현이 열린다.
2. **Given** 열린 상세 표현, **When** 독자가 단계와 관계를 읽는다, **Then** 원본 데이터의 단계 설명과 의미 있는 관계 문구 및 두 종류의 선 범례를 확인할 수 있다.
3. **Given** 1024px 미만의 Dialog, **When** 독자가 문구를 읽는다, **Then** 대상 스윔레인의 모든 단계명·설명과 라벨이 있는 관계의 출발·도착·문구를 14px 이상의 구조화 텍스트로 확인할 수 있다.
4. **Given** 열린 Dialog, **When** 독자가 닫기 또는 Escape를 사용한다, **Then** Dialog가 닫히고 원래 `크게 보기` trigger로 초점이 돌아온다.

### User Story 3 - 시각 자료가 실패해도 작업물의 설명이 유지된다 (Priority: P1)

독자는 artifact가 늦거나 없거나 예상한 구조가 아니어도 작업물의 전체 흐름 설명과 예외 상황을 읽고 기존 스윔레인으로 흐름을 확인할 수 있다.

**Why this priority**: 8개 자료를 새로 생성하는 과정에서 하나의 결과가 실패하더라도 공개 콘텐츠 전체가 빈 공간이나 깨진 임베드로 남아서는 안 된다.

**Independent Test**: 유효한 자료, 네트워크 실패, 잘못된 DOM, 준비 제한 시간 초과를 각각 재현해 정상 자료는 Archify 표현으로, 실패 자료는 기존 React 스윔레인으로 수렴하는지 검사한다.

**Acceptance Scenarios**:

1. **Given** 유효한 대상 artifact, **When** 작은 보기와 크게 보기를 연다, **Then** 두 표현은 같은 검증된 원본에서 만들어진 실제 Archify 결과를 사용한다.
2. **Given** artifact가 없거나 허용되지 않은 경로인 상태, **When** 카드가 표시된다, **Then** 빈 영역 없이 기존 스윔레인이 표시된다.
3. **Given** artifact가 응답했지만 다이어그램 구조가 예상과 다른 상태, **When** 준비를 완료하려 한다, **Then** 성공으로 처리하지 않고 기존 스윔레인으로 대체한다.
4. **Given** 로드 또는 준비가 제한 시간을 넘긴 상태, **When** 독자가 카드를 확인한다, **Then** 제한된 로딩 영역이 남지 않고 fallback과 전체 설명·예외 대응이 표시된다.

### User Story 4 - 포트폴리오 소유자가 8개 전환의 사실성과 범위를 검증한다 (Priority: P1)

소유자는 각 Archify artifact가 기존 승인 데이터에서 생성됐고, 공개 문구·관계 방향·예외 의미·다른 작업물의 동작이 승인 없이 바뀌지 않았는지 하나의 검증 기록에서 확인할 수 있다.

**Why this priority**: 여러 흐름을 일괄 전환할수록 편의를 위해 의미를 추정하거나 원본을 다시 그릴 위험이 커지므로 사실성 검증이 기능 자체만큼 중요하다.

**Independent Test**: 8개 원본 데이터와 생성 artifact를 대조해 단계·관계 parity, stable ID, 방향, 공개 콘텐츠, 범위를 자동·수동으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 8개 기존 스윔레인 데이터와 새 Archify artifact, **When** 소유자가 대조한다, **Then** 각 스윔레인의 단계 수·ID·관계 수·ID·방향·정상/예외 의미에 누락·추가·변경이 없다.
2. **Given** 각 artifact의 생성 근거, **When** 소유자가 검증 기록을 확인한다, **Then** 원본 입력, 생성 결과, validation receipt와 브라우저 검사 결과가 스윔레인별로 추적된다.
3. **Given** 전환 전후의 작업물과 연결 인사이트, **When** 공개 문구를 대조한다, **Then** 제목·목적·전체 흐름·예외 대응·근거 수치·인사이트의 사실 변경이 0건이다.
4. **Given** 이번 전체 전환이 완료된 상태, **When** 후속 작업 범위를 판단한다, **Then** 새 작업물·새 다이어그램 생성·기존 artifact 재생성은 별도 사용자 승인 없이는 수행하지 않는다.

### Edge Cases

- 기존 스윔레인의 단계나 관계에 설명 문구가 없으면 어떻게 되는가? → 실제 데이터에 있는 의미만 유지하고, 양 끝점으로 완전히 함의되는 문구를 임의로 만들지 않는다.
- 작업물마다 lane 수·단계 수·관계 수가 다르면 어떻게 되는가? → 단계·관계 topology와 책임 의미는 그대로 생성한다. 독립 viewer의 무스크롤 판독을 위해 인접 책임을 presentation band로 합칠 때는 canonical lane→band 매핑을 검증 기록에 남기고, 공통 wrapper가 모든 스윔레인에 같은 개수나 비율을 강제하지 않는다.
- 여러 스윔레인의 artifact가 동시에 준비되면 어떻게 되는가? → 작은 보기는 viewport 근접 시 개별적으로 준비하고 Dialog는 열린 대상만 준비한다.
- 한 스윔레인의 preview가 실패하고 Dialog가 성공하면 어떻게 되는가? → 각 표시 인스턴스가 독립적으로 fallback 또는 Archify 결과를 선택하며 카드 본문은 항상 유지된다.
- 한 스윔레인의 Dialog가 실패하고 preview가 이미 표시 중이면 어떻게 되는가? → Dialog만 기존 상세 fallback으로 전환하고 preview 상태를 변경하지 않는다.
- Archify variant가 실제 포트폴리오 theme에서 같은 색으로 수렴하면 어떻게 되는가? → 사용자가 구분할 수 있는 선 종류만 범례로 설명하고 기술 종류별 색상 의미를 추가하지 않는다.
- 좁은 화면에서 Archify node 문구가 작아지면 어떻게 되는가? → 전체 topology를 가로 스크롤 없이 유지하고 1024px 미만 Dialog transcript에서 문구를 제공한다.
- iframe 내부의 toolbar·검색·확대·단축키가 남아 있으면 어떻게 되는가? → 표시 전에 제거·비활성화하고 pointer·keyboard·focus가 내부 도구로 이동하지 않는지 검사한다.
- 기존 React fallback의 데이터와 생성 artifact가 서로 다르면 어떻게 되는가? → 성공 처리하지 않고 source parity를 수정·확인한 뒤 승인된 fallback을 유지한다.
- 하나의 artifact 경로가 외부 URL·query·hash를 포함하면 어떻게 되는가? → 허용된 same-origin 정적 경로가 아니므로 표시하지 않고 fallback으로 수렴한다.
- 동결 artifact를 수정해야만 색상이나 레이아웃을 맞출 수 있으면 어떻게 되는가? → artifact를 수정하지 않고 표시 계층의 theme bridge·CSS·fallback으로 해결하거나 범위를 중단한다.
- 기존 artifact가 사용자에게 직접 열리는 새 탭 경로를 남기면 어떻게 되는가? → 별도 새 탭 action은 제공하지 않고 카드 Dialog 안에서만 표시한다.
- 생성 도구가 없어도 공개 화면이 동작해야 하는가? → 배포된 정적 artifact와 기존 fallback만으로 동작하며 런타임 제작 도구 설치에 의존하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

#### 전체 전환 범위와 사실 보존

- **FR-001**: 전환 대상은 명세에 열거한 8개 기존 스윔레인으로 한정되어야 한다.
- **FR-002**: 각 대상의 작은 보기와 크게 보기는 해당 스윔레인의 승인된 사실에서 생성된 실제 Archify 결과를 사용해야 한다.
- **FR-003**: 각 원본의 단계·관계 ID, 의미, 출발·도착 방향, 정상·분기·복구 구조를 변경하거나 임의로 보완하지 않아야 한다.
- **FR-004**: 작업물 제목·목적·요약·예외 상황과 대응, 연결 인사이트의 공개 문구를 전환 때문에 변경하지 않아야 한다.
- **FR-005**: 각 artifact의 입력 원본, 생성 결과, validation receipt, 공개 URL과 브라우저 검증 결과를 스윔레인 ID로 추적할 수 있어야 한다.
- **FR-006**: 기존 승인 artifact를 수정하거나 재생성해 의미를 바꾸지 않아야 하며, 생성 결과는 각 대상의 새로운 정적 근거로 동결해야 한다.
- **FR-007**: 명세에 없는 작업물·스윔레인·새 다이어그램의 전환 및 생성은 별도 사용자 승인 없이 수행하지 않아야 한다.

#### 작은 보기와 크게 보기

- **FR-008**: 모든 대상의 작은 보기는 전체 단계와 관계 topology를 유지하는 동일한 공통 embed 구조를 사용해야 한다.
- **FR-009**: 작은 보기에서는 단계명 요소와 관계 구조를 보존하되 단계 세부 설명과 관계 문구는 숨겨야 한다.
- **FR-010**: 작은 보기 아래에는 실제 사용되는 기본색 실선과 예외색 점선의 의미를 설명하는 공통 범례를 제공해야 한다.
- **FR-011**: 모든 대상의 크게 보기는 작은 보기와 같은 artifact와 단계·관계 배치를 사용해야 한다.
- **FR-012**: 크게 보기에서는 단계 세부 설명, 의미 있는 관계 문구와 같은 공통 범례를 복원해야 한다.
- **FR-013**: 1024px 미만 크게 보기에서는 원본 스윔레인 데이터에서 파생한 단계·관계 transcript를 제공해 문구를 판독할 수 있어야 한다.
- **FR-014**: 기존 `크게 보기` trigger, Dialog 열기·닫기, Escape, mouse·touch·keyboard 활성화와 trigger 초점 복귀를 유지해야 한다.
- **FR-015**: 작은 보기와 크게 보기에서 별도 Archify 새 탭 action을 제공하지 않아야 한다.

#### 시각 통합과 접근성

- **FR-016**: 배경·lane·node·문구·경계·관계선과 범례는 현재 포트폴리오의 semantic token 체계를 사용해야 한다.
- **FR-017**: 일반 진행은 기본색 실선, 예외·복구는 예외색과 점선을 함께 사용해야 하며 색상만으로 차이를 전달하지 않아야 한다.
- **FR-018**: 기술 종류별 node 색상을 설명하는 별도 범례를 추가하지 않아야 한다.
- **FR-019**: 밝은 화면과 어두운 화면 전환은 다이어그램 문서를 재로딩하지 않고 반영해야 한다.
- **FR-020**: 준비 전 원래 Viewer toolbar·검색·내보내기·테마·프레젠테이션·확대·축소·관계 추적·단축키가 사용자에게 노출되거나 활성화되지 않아야 한다.
- **FR-021**: 각 다이어그램은 의미 있는 accessible name과 기존 전체 흐름 설명에 연결되어야 한다.
- **FR-022**: iframe과 다이어그램 내부 탐색 요소는 pointer, keyboard, Tab 순서에서 비활성화되어야 한다.
- **FR-023**: 작은 보기와 Dialog는 320px, 768px, 1024px, 1440px에서 페이지 전체 가로 넘침을 만들지 않아야 한다.
- **FR-024**: 범례·transcript·예외 차이는 색상, 선 종류, 방향, 구조화 텍스트를 함께 사용해야 한다.

#### 실패·성능·경계

- **FR-025**: 허용되지 않은 경로·외부 URL·query/hash·누락 artifact는 표시하지 않고 기존 fallback으로 수렴해야 한다.
- **FR-026**: artifact가 예상한 다이어그램 DOM을 포함하지 않거나 same-origin 준비에 실패하면 fallback으로 수렴해야 한다.
- **FR-027**: 단일 준비 제한 시간을 넘긴 preview/Dialog는 빈 로딩 상태를 남기지 않고 fallback으로 전환해야 한다.
- **FR-028**: 작은 보기 artifact는 viewport에 가까워질 때 준비하고, Dialog artifact는 Dialog를 열 때 준비해야 한다.
- **FR-029**: 페이지 진입 시 8개 preview와 8개 Dialog artifact를 모두 동시에 불필요하게 준비하지 않아야 한다.
- **FR-030**: 한 인스턴스의 실패·테마 observer·timer·iframe lifecycle이 다른 스윔레인의 표시 상태를 오염시키지 않아야 한다.
- **FR-031**: fallback 상태에서도 카드의 전체 흐름 설명과 예외 상황과 대응을 유지해야 한다.

#### 검증과 회귀

- **FR-032**: 각 생성 artifact는 Archify 구조 검사를 통과하고 오류·경고 결과를 검증 기록에 남겨야 한다.
- **FR-033**: 각 대상의 원본과 artifact의 단계·관계 parity 및 공개 URL 일치를 자동 검사해야 한다.
- **FR-034**: 모든 대상의 preview/Dialog, 범례, transcript, 테마, 내부 상호작용 차단, fallback, 초점 복귀를 단위 또는 통합 테스트로 검사해야 한다.
- **FR-035**: 8개 대상의 4개 지원 화면 폭에서 가로 넘침·겹침·문구 판독을 실제 브라우저에서 검사해야 한다.
- **FR-036**: Archify 전환이 없는 legacy 또는 예외 데이터 작업물의 공개 문구·동작·renderer 회귀를 실제 브라우저에서 검사해야 한다.
- **FR-037**: 검증 기록은 자동 테스트, 실제 브라우저 검사, artifact 생성 근거와 사람의 이미지 검토를 구분해 기록해야 한다.

### Key Entities

- **대상 스윔레인**: 명세에 열거한 8개 기존 흐름이다. 단계·관계·공개 문구와 fallback의 사실 기준이다.
- **Archify 의미 원본**: 각 대상 스윔레인의 승인된 단계와 관계 의미를 보존하는 편집 가능한 입력이다.
- **Archify 생성 결과**: 의미 원본에서 생성되고 구조 검증을 통과한 정적 다이어그램 문서다.
- **작은 표현**: 전체 topology와 단계명 중심의 무스크롤 MAP 표현이다.
- **상세 표현**: 같은 topology에 문맥·관계 문구를 복원한 READ 표현이다.
- **좁은 화면 transcript**: 1024px 미만 Dialog에서 단계와 라벨 관계의 문구를 판독하게 하는 구조화 텍스트다.
- **fallback 표현**: artifact가 실패하거나 허용되지 않을 때 기존 React 스윔레인 데이터를 사용한 흐름이다.
- **검증 기록**: artifact provenance, parity, UI·브라우저·이미지 검토와 잔여 위험을 연결하는 feature 문서다.

## Assumptions

- Feature 012의 호텔 Archify 임베드 구조와 사용자 승인 A 정책은 전체 전환의 시각·상호작용 기준이다.
- 현재 데이터에 존재하는 8개 스윔레인의 단계·관계·공개 문구는 각 작업물의 승인된 사실 기준이며, 별도 인터뷰 없이 의미를 재작성하지 않는다.
- 기존 React 스윔레인은 모든 대상에서 fallback과 사실 비교 기준으로 보존한다.
- 각 스윔레인의 단계 수·canonical lane 수·관계 수는 서로 다를 수 있다. 공통 wrapper는 topology를 같은 개수로 맞추지 않으며, artifact의 presentation band 통합은 책임 의미와 단계·관계 parity를 유지하고 매핑을 기록한 경우에만 허용한다.
- 실제 Archify 생성 결과는 정적 artifact로 배포하며 공개 화면이 생성 도구 설치에 의존하지 않는다.
- 작은 보기의 무스크롤 topology 원칙은 유지하고, 좁은 화면 문구 판독은 `크게 보기` transcript로 제공한다.
- 공통 범례는 실제 포트폴리오 theme에서 구분되는 두 선 의미만 표시하며, variant 이름이나 기술 종류를 공개하지 않는다.
- 동결된 Feature 012 JSON·HTML은 이번 전체 전환의 입력 기준으로 수정하지 않는다.
- 사용자는 현재 1104 dev server를 직접 관리하며 임의 종료·재시작을 승인하지 않았다. 최종 브라우저 검증은 별도 production server와 임시 설정으로 수행한다.
- 저장소 전역 lint baseline이 있으므로 변경한 파일만 검사하고 관련 없는 파일은 포맷하지 않는다.
- 기존 연결 인사이트의 출처·작업물 연결·공개 문구는 전환과 독립적으로 유지한다.
