# Phase 0 Research: 골프 예약 시스템 구조화 상세

**Date**: 2026-09-11

승인 인터뷰, 현재 포트폴리오 콘텐츠·DTO·렌더러·Archify 계약을 기준으로 아래 결정을 확정했다. Technical Context의 미확정 항목은 없다.

## D-001. 공통 구조화 상세로 이전하고 legacy 본문은 제거한다

**Decision**: `the-siena-golf-reservation.ts`를 추가해 기존 `FeatureDetailDto`의 역할, 근거 지표, 문제, 제약, 대안, 스윔레인, 구현, 결과, 회고 순서를 사용한다. `features.ts`의 legacy `content`는 제거하고 기존 slug와 목록 위치는 유지한다.

**Rationale**: 이미 이전된 작업물과 같은 순서로 읽혀야 실제 책임과 판단을 비교할 수 있고, 승인 문구를 타입과 품질 테스트로 검증할 수 있다.

**Alternatives considered**: legacy Markdown만 정정하는 안은 구조적 비교와 근거 카드 검증이 어렵다. 전용 페이지는 공통 정보 구조 원칙에 맞지 않아 제외했다.

## D-002. 첫 프로젝트의 구현 책임과 운영 개선 판단을 분리한다

**Decision**: 최초 구축에서는 정해진 구조 안에서 예약 화면, PHP 요청 처리, 외부 PMS 연동, 중복 방어, 통신 로그 기록을 FE/BE 범위 모두 단독으로 구현했다고 쓴다. 운영 유지보수 중 로그 저장 경계를 업무 DB에서 `syslog`로 분리한 판단과 구현은 별도 성장 사례로 설명한다.

**Rationale**: 사용자는 전체 아키텍처를 설계하지 않았지만 구현 범위는 넓었고, 로그 분리는 이후 직접 문제를 파악하고 선택한 개선이다. 두 책임을 합치면 최초 설계 주도처럼 과장된다.

**Alternatives considered**: 역할을 단순 기능 구현으로 낮추는 안은 실제 담당 범위를 숨긴다. 전체 설계 주도 서술은 사실과 달라 제외했다.

## D-003. 기간은 최초 구축과 현재 유지보수를 함께 표시한다

**Decision**: 카드에는 `2023.05 – 현재`를 표시한다. 본문과 근거 카드에서는 최초 구축 `2023.05 – 2023.06`과 2023년 오픈 이후 현재까지의 유지보수를 구분한다. 로그 분리 사건은 정확한 날짜를 만들지 않고 `운영 유지보수 과정`으로만 표현한다.

**Rationale**: 유지보수 계약과 사용자의 유지보수는 현재도 진행 중이지만 최초 구축이 계속된 것은 아니다. 로그 개선 일시는 기억나지 않으므로 거짓 정밀도를 피해야 한다.

**Alternatives considered**: 카드 기간을 최초 구축만으로 닫으면 현재 유지보수 사실이 사라지고, 로그 분리 날짜를 추정하면 근거 우선 원칙에 어긋난다.

## D-004. 공개 근거 카드는 세 범위만 사용한다

**Decision**: 최초 구축 기간, 오픈 이후 현재까지 유지보수, 장애 조사 당시 직접 확인한 `수백만 건` 로그 규모를 근거 카드로 제공한다. 로그 규모는 정확한 전수 집계가 아니라 당시 직접 확인한 규모임을 밝힌다.

**Rationale**: 승인된 서사를 설명하는 데 필요한 최소 근거이며 각각 보고값·직접 확인값의 경계를 명시할 수 있다.

**Alternatives considered**: 전체 예약 건수, 중복률, 처리 시간 감소와 장애율은 확인할 수 없어 사용하지 않는다.

## D-005. 예약 방어는 세 계층과 세 예외로 제한한다

**Decision**: 사용자 화면의 버튼 비활성화·스피너, PHP 세션의 2초 동일 요청 필터, 외부 PMS 요청의 30초 timeout을 실제 구현으로 설명한다. 예외는 외부 호출 전 중복 차단, PMS 5xx 재시도 안내, timeout 혼잡 안내의 세 종류로 구분한다.

**Rationale**: 서로 다른 경계에서 반복 입력과 외부 장애를 완화한 실제 구현을 보여 준다. 이 조합은 외부 PMS의 예약 무결성을 보장하는 체계가 아니다.

**Alternatives considered**: Redis lock, queue, idempotency key 등은 당시 검토·구현 근거가 없어 비교 대안으로 추가하지 않는다.

## D-006. 결과는 유지보수 관찰 범위로만 공개한다

**Decision**: 2023년 오픈 이후 현재까지 직접 유지보수한 범위에서 통신 로그상 동일 예약의 중복 호출 이력과 관련 CS를 확인하지 못했다고 쓴다. 외부 5xx·timeout에는 구현한 재시도 안내가 동작했다고 설명한다.

**Rationale**: 실제 운영 관찰을 숨길 필요는 없지만 전체 예약 건수 분모나 전수 집계가 없으므로 비율·영구 보장으로 확대할 수 없다.

**Alternatives considered**: `중복률 0%`, `장애 0건`, 전체 예약에 대한 무결성 보장은 근거가 없어 금지한다.

## D-007. 로그 개선 성과는 조회 가능성 회복으로 제한한다

**Decision**: 업무 DB의 로그 테이블에 수백만 건이 누적돼 장애 조사 중 DB GUI가 다운되고 당사 기록을 조회하지 못해 PMS 업체에 확인을 요청했던 문제를 설명한다. 저장 위치를 `syslog`로 분리한 후 실제 예약 문제에서 당사 시스템 로그의 요청·응답을 확인할 수 있었던 결과만 공개한다.

**Rationale**: 예약 기능 자체의 영향은 거의 없었고, 직접 해결한 문제는 업무 데이터와 통신 로그의 저장 경계 및 장애 조사 가능성이었다.

**Alternatives considered**: 처리 시간·장애 감소율·파일 쓰기 감소율과 요청 간 버퍼링 성과는 측정되지 않았거나 PHP-FPM 실행 구조상 근거가 없어 제외한다.

## D-008. 작업물과 인사이트는 서로 다른 질문을 답한다

**Decision**: 작업물은 전체 구현과 예약 정상·예외 흐름을 보여 주고 로그 분리 판단은 짧게 요약한 뒤 인사이트로 연결한다. 기존 인사이트는 왜 로그 저장 경계를 업무 DB에서 `syslog`로 바꿨는지를 깊게 설명하고 작업물의 역할·전체 연혁·예약 방어를 반복하지 않는다.

**Rationale**: 같은 프로젝트에서 나온 기록이라도 채용 담당자가 작업 범위와 하나의 기술 판단을 서로 다른 깊이로 읽을 수 있어야 한다.

**Alternatives considered**: 두 기록에 같은 로그 전후 시각 자료를 반복하는 안과 인사이트를 작업물 본문으로 흡수하는 안은 독립적인 질문과 연결 구조를 잃어 제외했다.

## D-009. 작업물 시각 자료는 예약 흐름 하나만 제공한다

**Decision**: 사용자, React, PHP 서버, 외부 PMS의 네 레인으로 `예약 요청·중복 방어·외부 장애 안내 흐름` 하나를 만든다. 정상 경로와 승인된 예외 세 종류를 포함하고 로그 저장 전후 비교는 넣지 않는다.

**Rationale**: 예약 요청이 어디에서 차단되고 외부 장애가 어떤 안내로 돌아오는지는 여러 경계에 걸쳐 있어 시각화 가치가 있다. 로그 경계는 기존 인사이트 시각 자료가 이미 담당한다.

**Alternatives considered**: ERD는 당사 서비스가 외부 PMS의 예약 원본을 소유하지 않아 핵심 질문과 맞지 않는다. 로그 전후 그림 추가는 인사이트와 중복된다.

## D-010. Archify source와 기존 임베드 계약을 재사용한다

**Decision**: 새 workflow source JSON을 Archify showcase 품질로 validate·deliver하고 생성된 HTML을 typed allowlist와 preview ratio에 등록한다. React fallback용 `FeatureSwimlane` 데이터는 같은 lane/node/edge/exception 의미를 유지한다. 기존 작은 보기·크게보기·공통 선 범례·theme·fallback 컴포넌트는 수정 없이 우선 재사용한다.

**Rationale**: 현재 모든 구조화 작업물 스윔레인이 같은 표현 계약을 사용한다. 골프만 전용 renderer를 만들면 포맷과 검증이 다시 갈라진다.

**Alternatives considered**: 수동 SVG나 iframe 전용 페이지는 공통 동작과 fallback을 잃는다. 기존 로그 인사이트 visual을 재사용하면 질문이 달라 의미가 맞지 않는다.

## D-011. 테스트를 사실·구조·artifact·브라우저 계층으로 나눈다

**Decision**: Vitest에서 구조화 상세 등록, 승인 문구, 금지 주장, 스윔레인 의미, allowlist와 embed rendering을 먼저 RED로 만든다. Archify CLI로 source/artifact를 검증하고 Playwright로 두 공개 route, 목록, 양방향 keyboard 탐색, preview/dialog, 4개 viewport의 overflow와 겹침을 검증한다.

**Rationale**: 문자열 테스트만으로 생성 artifact와 실제 배치를 증명할 수 없고, 브라우저 테스트만으로 모든 금지 주장을 안정적으로 검사하기 어렵다.

**Alternatives considered**: 수동 화면 확인만으로 끝내는 안과 1104 dev server만 최종 증거로 쓰는 안은 반복 가능성과 격리가 부족하다.

## D-012. 1104는 보존하고 별도 production 포트를 사용한다

**Decision**: 사용자가 실행한 1104 dev server는 기준선과 구현 중 확인에만 재사용하며 종료·재시작하지 않는다. 최종 E2E는 build 뒤 별도 빈 포트의 production server에서 수행하고 임시 Playwright 설정은 `apply_patch`로 만들었다가 삭제한다.

**Rationale**: 1104의 `.next/dev` lock 때문에 두 번째 dev server가 실행되지 않고, dev HMR 상태는 재현 가능한 최종 증거로 적합하지 않다.

**Alternatives considered**: 1104를 중단하거나 lock을 제거하는 안은 사용자 소유 실행 상태를 침범하므로 제외했다.
