# Feature Specification: 골프 예약 시스템 구조화 상세

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-09-11

**Status**: Draft

**Input**: 2026-08-21, 2026-08-26, 2026-09-11 사용자 인터뷰에서 승인된 골프 예약 시스템 작업물을 공통 구조화 상세로 이전하고, 예약 요청·중복 방어·외부 장애 안내 스윔레인 하나를 제공한다. 연결된 로그 분리 인사이트는 승인된 본문과 전후 비교 시각 자료를 유지하며 사실·중복·양방향 연결을 함께 검증한다. 작업 목록에는 테스트 우선 개발(TDD) 항목을 포함한다.

## Context

`the-siena-golf-reservation`은 현재 공개 목록과 상세 경로가 존재하지만 장문 본문만 제공한다. 작업물 인터뷰와 연결 인사이트 후속 인터뷰는 완료됐으며, 이전 검토에서 과장된 설계 역할과 사실이 아닌 로그 버퍼링 성과를 제거했다. 이 기능은 승인된 현재 본문을 공통 구조화 상세로 이전하고 작업물의 예약 처리 흐름을 별도 시각 자료로 제공한다.

승인된 인터뷰:
`docs/portfolio-interviews/2026-08-21-the-siena-golf-reservation.md`

핵심 공개 경계는 다음과 같다.

- 사용자는 입사 후 첫 프로젝트에서 새 아키텍처를 설계한 것이 아니라 정해진 구조 안의 예약 화면, PHP 요청 처리, 외부 PMS 연동, 중복 요청 방어와 통신 로그 기록을 FE/BE 범위 모두 단독으로 구현했다.
- 운영 유지보수 과정의 로그 조회 문제에서는 저장 경계를 업무 DB에서 `syslog`로 분리하는 방향을 정하고 직접 구현했다.
- 최초 구축은 `2023.05 – 2023.06`이고, 오픈 이후 유지보수 계약과 사용자의 유지보수는 현재도 진행 중이다. 로그 분리의 정확한 적용 시점은 기억나지 않으므로 특정 날짜를 만들지 않는다.
- 예약 버튼 잠금·스피너, PHP 세션 2초 필터, 외부 API 30초 timeout, 5xx와 timeout 안내 분기는 사용자가 실제 구현했다고 확인했다.
- 2023년 오픈 이후 현재까지의 유지보수 범위에서 통신 로그상 동일 예약의 중복 호출 이력과 관련 CS가 확인되지 않았다. 이를 전체 예약 건수 기반 중복률이나 영구적인 무결성 보장으로 확대하지 않는다.
- 로그 분리 이후 실제 예약 문제를 당사 시스템 로그의 요청·응답으로 조사할 수 있었다. 처리 시간 단축과 장애 감소율은 측정하지 않았다.
- 작업물 스윔레인은 예약 처리와 예외 분기를, 연결 인사이트 시각 자료는 로그 저장 경계의 전후 비교를 맡아 같은 그림을 반복하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채용 담당자가 첫 프로젝트의 실제 책임과 성장을 읽는다 (Priority: P1)

채용 담당자가 골프 예약 시스템 상세를 열었을 때 정해진 구조 안에서 담당한 구현 범위와 운영 과정에서 직접 판단한 로그 저장 경계 개선을 과장 없이 구분해 이해한다.

**Why this priority**: 신입 시기의 구현 책임과 이후 운영 개선을 정확히 구분해야 다른 작업물의 주도 역할과 함께 읽어도 경력 서술의 신뢰성이 유지된다.

**Independent Test**: 작업물 상세에서 역할, 기간, 문제, 제약, 실제 선택, 핵심 구현, 관찰 근거, 결과 한계와 회고를 읽고 승인 인터뷰와 항목별로 대조한다.

**Acceptance Scenarios**:

1. **Given** 작업물 상세, **When** 역할을 읽는다, **Then** 정해진 구조 안의 FE/BE 단독 구현과 로그 저장 경계 개선에서의 직접 판단이 구분된다
2. **Given** 기간 정보를 읽는다, **When** 최초 구축과 현재 상태를 비교한다, **Then** `2023.05 – 2023.06` 최초 구축과 오픈 이후 현재까지의 유지보수가 분리된다
3. **Given** 예약 방어 구현을 읽는다, **When** 요청 흐름을 따라간다, **Then** 사용자 화면, 내부 요청 처리, 외부 PMS 경계와 세 예외 분기를 이해한다
4. **Given** 결과를 읽는다, **When** 운영 관찰의 의미를 판단한다, **Then** 확인되지 않은 중복 호출·CS와 전수 통계·중복률 보장이 구분된다

---

### User Story 2 - 독자가 예약 정상·예외 흐름을 시각적으로 이해한다 (Priority: P1)

독자가 작업물 스윔레인을 통해 예약 요청이 사용자 화면과 내부 서버를 거쳐 외부 PMS로 전달되는 정상 흐름과, 동일 세션 재요청·5xx·30초 timeout이 어디에서 분기되는지 이해한다.

**Why this priority**: 외부 시스템 의존과 중복 방어의 책임 경계는 문장만으로 읽을 때 구현 위치와 실패 대응을 혼동하기 쉽다.

**Independent Test**: 스윔레인의 레인, 단계, 방향, 정상·예외 관계, 예외 설명과 동등한 텍스트 설명을 승인된 흐름과 대조한다.

**Acceptance Scenarios**:

1. **Given** 작업물 스윔레인, **When** 정상 경로를 따라간다, **Then** 예약 요청, 화면 잠금, 내부 중복 검사, 외부 PMS 호출과 예약 결과 표시 순서를 이해한다
2. **Given** 2초 이내 동일 세션 요청, **When** 예외 경로를 따라간다, **Then** 외부 PMS 호출 전에 차단됨을 이해한다
3. **Given** 외부 PMS의 5xx 또는 30초 timeout, **When** 각 예외 경로를 따라간다, **Then** 잠시 후 재시도 안내와 일시적 혼잡 안내를 구분한다
4. **Given** 시각 자료를 볼 수 없는 독자, **When** 텍스트 설명을 읽는다, **Then** 같은 정상·예외 흐름과 책임 경계를 이해한다

---

### User Story 3 - 작업물과 로그 분리 인사이트가 서로 다른 질문을 답한다 (Priority: P1)

독자가 작업물과 연결 인사이트를 오가며 작업물에서는 예약 시스템 전체 구현과 운영 맥락을, 인사이트에서는 업무 DB와 `syslog` 사이의 로그 저장 경계 판단을 깊게 읽는다.

**Why this priority**: 같은 프로젝트에서 나온 두 기록이 역할·연혁·결과와 시각 자료를 반복하면 인사이트의 독립적인 가치가 사라진다.

**Independent Test**: 두 공개 본문과 시각 자료를 비교해 사실 일치, 장문 비중복, 시각 비중복, 출처 관계와 양방향 링크를 확인한다.

**Acceptance Scenarios**:

1. **Given** 작업물 본문, **When** 로그 개선 부분을 읽는다, **Then** 문제·선택·확인된 결과를 요약하고 상세 판단은 인사이트 링크로 분리한다
2. **Given** 로그 분리 인사이트, **When** 작업물과 비교한다, **Then** 프로젝트 전체 역할·예약 방어·전체 연혁을 반복하지 않는다
3. **Given** 두 시각 자료, **When** 질문을 비교한다, **Then** 작업물은 예약 정상·예외 처리, 인사이트는 로그 저장 경계 전후를 각각 보여 준다
4. **Given** 어느 한 상세 경로, **When** 연결 링크를 활성화한다, **Then** 의미 있는 링크 이름으로 다른 기록에 이동하고 다시 돌아올 수 있다

---

### User Story 4 - 기존 공개 경로와 주변 작업물이 회귀 없이 유지된다 (Priority: P2)

독자가 기존 골프 예약 작업물과 로그 분리 인사이트 주소를 계속 사용하고, 지원 화면 크기와 키보드 환경에서 내용을 읽고 이동할 수 있다.

**Why this priority**: 구조화 이전이 기존 북마크, 공개 목록, 연결 관계 또는 이미 완료된 다른 작업물의 표현을 깨뜨리면 안 된다.

**Independent Test**: 기존 두 경로, 공개 목록 진입, 키보드 이동, 지원 화면 크기, 다른 작업물의 구조화 상세와 공통 시각 계약을 실제 화면에서 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 작업물과 인사이트 주소, **When** 각각 연다, **Then** 승인된 콘텐츠로 정상 응답한다
2. **Given** 공개 작업물 목록, **When** 골프 예약 항목을 활성화한다, **Then** 구조화 상세로 이동한다
3. **Given** 키보드 사용자, **When** 작업물과 인사이트의 양방향 링크를 탐색한다, **Then** 초점을 확인하고 각 링크를 활성화할 수 있다
4. **Given** 320·768·1024·1440px 화면, **When** 본문과 시각 자료를 읽는다, **Then** 문서 전체 가로 넘침과 핵심 노드·라벨 겹침 없이 내용을 확인할 수 있다

### Edge Cases

- `FE/BE 단독`이 전체 아키텍처를 단독 설계했다는 의미로 읽히는가? → 정해진 구조 안의 구현 범위와 운영 로그 개선의 직접 판단을 분리한다.
- 카드의 `2023.05 – 현재`가 현재까지 신규 구축을 계속했다는 뜻으로 읽히는가? → 최초 구축 기간과 오픈 이후 유지보수를 별도 근거로 표시한다.
- 로그 분리 시점이 특정 연도·월로 추정되는가? → 정확한 시점은 기억나지 않으므로 `운영 유지보수 과정`으로만 표시한다.
- 중복 호출·CS 미확인이 중복률 `0%`나 전체 예약 전수 검증으로 읽히는가? → 유지보수 기간의 로그·접수 CS 관찰 범위와 비율 미산출을 함께 표시한다.
- 수백만 건 로그가 정확한 집계값으로 읽히는가? → 장애 조사 당시 직접 확인한 규모이며 정확한 전수 건수는 복원하지 않았음을 밝힌다.
- 예약 기능 자체가 로그 테이블 문제로 중단된 것으로 읽히는가? → 예약 영향은 거의 없었고 장애 조사 시 로그 조회가 불가능했던 운영 문제로 제한한다.
- `syslog` 분리가 처리 속도나 장애율을 개선한 것으로 읽히는가? → 당사 기록으로 요청·응답을 확인할 수 있게 된 결과만 제시한다.
- 실제로 검토하지 않은 로그·잠금 대안이 당시 선택지로 제시되는가? → 확인되지 않은 대안 비교를 공개 본문에서 제외한다.
- 작업물 스윔레인이 인사이트의 로그 저장 전후 그림을 반복하는가? → 예약 흐름과 로그 경계라는 질문을 분리한다.
- 좁은 화면이나 크게보기에서 스윔레인이 잘리거나 기술 종류 범례가 중복되는가? → 기존 공통 시각 계약으로 실제 화면을 검증한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 작업물 구조화 상세

- **FR-001**: 골프 예약 작업물은 기존 구조화 상세와 같은 공통 읽기 순서로 제공되어야 한다
- **FR-002**: 작업물의 기존 공개 경로와 공개 목록 항목을 유지해야 한다
- **FR-003**: 카드 기간은 `2023.05 – 현재`로 표시하되 `2023.05 – 2023.06` 최초 구축과 오픈 이후 현재까지의 유지보수를 구분해야 한다
- **FR-004**: 역할은 정해진 구조 안에서 예약 화면, 내부 요청 처리, 외부 PMS 연동, 중복 방어, 통신 로그 기록을 FE/BE 범위 모두 단독으로 구현한 것으로 설명해야 한다
- **FR-005**: 사용자가 프로젝트 전체 아키텍처나 최초 구조를 단독 설계했다고 주장하지 않아야 한다
- **FR-006**: 운영 로그 개선에서는 사용자가 업무 DB에서 `syslog`로 저장 경계를 분리하는 방향을 정하고 직접 구현했음을 구분해야 한다
- **FR-007**: 근거 카드에는 최초 구축 기간, 오픈 이후 유지보수 기간, 장애 조사 당시 직접 확인한 수백만 건 로그 규모의 근거 종류·기준 시점·관찰 한계를 제공해야 한다
- **FR-008**: 로그 개선의 정확한 적용 시점을 특정 날짜로 만들지 않아야 한다
- **FR-009**: 예약 원본과 결과가 외부 PMS에 있고 당사 서비스는 요청 전달과 사용자 안내를 담당한 경계를 설명해야 한다
- **FR-010**: 초기 업무 DB에 예약·회원 데이터와 외부 API 통신 로그가 함께 저장됐고, 수백만 건 누적 뒤 장애 조사 시 DB GUI 접근이 불가능했던 문제를 설명해야 한다
- **FR-011**: 로그 테이블 문제는 예약 기능 자체의 중단이 아니라 필요한 시점에 당사 기록을 조회하지 못한 운영 문제로 제한해야 한다
- **FR-012**: 확인되지 않은 Redis, 별도 로그 DB, 큐, 내부 DB 잠금 등의 비교를 당시 실제 대안으로 제시하지 않아야 한다

#### 예약 방어와 로그 구현

- **FR-013**: 예약 요청 직후 버튼 비활성화와 스피너 표시로 반복 클릭을 막은 구현을 설명해야 한다
- **FR-014**: 동일 PHP 세션에서 2초 이내 들어온 같은 요청을 외부 PMS 호출 전에 필터링한 구현을 설명해야 한다
- **FR-015**: 외부 PMS 요청에 30초 timeout을 적용하고 5xx와 timeout에 서로 다른 사용자 안내를 제공한 구현을 설명해야 한다
- **FR-016**: 로그 개선은 React에서 내부 서버를 거쳐 외부 PMS로 전달되는 예약 경로를 유지하고 저장 위치만 업무 DB에서 `syslog`로 분리한 것으로 설명해야 한다
- **FR-017**: 로그 분리 이후 실제 예약 문제를 당사 시스템 로그의 요청·응답으로 조사한 결과를 설명해야 한다
- **FR-018**: 처리 시간 단축, 장애 감소율, 파일 쓰기 감소율, 여러 요청의 버퍼링 성과를 주장하지 않아야 한다
- **FR-019**: 회고는 인증값·개인정보 마스킹, 장애 추적에 필요한 정보만 기록, 로그 보존 기간 관리라는 승인된 현재 판단으로 제한해야 한다

#### 운영 결과와 근거 경계

- **FR-020**: 2023년 오픈 이후 현재까지 직접 유지보수한 범위에서 통신 로그상 동일 예약의 중복 호출 이력과 관련 CS가 확인되지 않았음을 설명해야 한다
- **FR-021**: 중복 결과를 전체 예약 건수 기반 비율, 중복률 `0%`, 전수 집계 또는 영구적인 무결성 보장으로 표현하지 않아야 한다
- **FR-022**: 외부 PMS의 5xx와 timeout에 사용자 재시도 안내가 동작한 범위를 설명하되 사용자 이탈률이나 전환율을 만들지 않아야 한다
- **FR-023**: 공개 근거에 고객 예약 내역, 실제 요청·응답 값, 인증 정보, 개인정보, 시크릿 또는 비공개 소스 내용을 포함하지 않아야 한다

#### 시각 자료와 연결·회귀

- **FR-024**: 작업물은 예약 요청·중복 방어·외부 장애 안내 스윔레인 정확히 하나를 제공해야 한다
- **FR-025**: 스윔레인은 사용자, React, PHP 서버, 외부 PMS 경계를 구분하고 정상 예약 완료 경로를 제공해야 한다
- **FR-026**: 스윔레인은 2초 이내 동일 세션 요청 차단, 외부 PMS 5xx, 30초 timeout을 서로 구분되는 예외 경로로 제공해야 한다
- **FR-027**: 스윔레인은 승인된 단계·관계·예외와 동등한 텍스트 설명을 제공하고 로그 저장 경계의 전후 비교를 반복하지 않아야 한다
- **FR-028**: 연결 인사이트는 기존 공개 경로, 승인된 본문과 로그 저장 전후 시각 자료를 유지해야 한다
- **FR-029**: 작업물은 로그 분리 인사이트로, 인사이트는 원본 작업물로 돌아가는 의미 있는 양방향 링크를 제공해야 한다
- **FR-030**: 작업물과 인사이트의 장문 및 시각 자료 비중복 판정을 별도로 기록해야 한다
- **FR-031**: 작업물·인사이트의 공개 목록, 양방향 링크, 키보드 초점·활성화와 320·768·1024·1440px 읽기 상태를 실제 화면에서 검증해야 한다
- **FR-032**: 스윔레인의 노드·화살표·라벨은 서로의 핵심 텍스트를 가리지 않고 문서 전체 가로 넘침을 만들지 않아야 한다
- **FR-033**: 스윔레인의 작은 보기와 크게보기는 전체 흐름을 자르지 않고 포트폴리오의 공통 선 범례만 제공해야 한다
- **FR-034**: 다른 작업물·인사이트의 공개 내용과 완료된 구조화 상세 계약을 변경하거나 관련 없는 파일을 다시 포맷하지 않아야 한다

### Key Entities

- **골프 예약 시스템 작업물 상세**: 역할, 근거 카드, 문제, 제약, 선택, 예약·로그 구현, 결과와 회고를 공통 순서로 제공하는 원본 기록
- **예약 처리 스윔레인**: 사용자, React, PHP 서버, 외부 PMS 사이의 정상 예약과 동일 세션 재요청·5xx·timeout 예외를 표시하는 시각 자료
- **로그 분리 인사이트**: 장애 시 조회 가능한 로그 경계를 업무 DB에서 `syslog`로 옮긴 한 질문을 다루는 프로젝트 사례
- **운영 관찰 근거**: 최초 구축·유지보수 기간, 로그 누적 규모, 중복 호출 이력·관련 CS 미확인의 근거 종류와 관찰 한계
- **출처 연결**: 작업물과 프로젝트 사례 인사이트 사이의 양방향 공개 관계

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 골프 예약 작업물 1개가 승인된 문구와 공통 읽기 순서의 구조화 상세로 공개된다
- **SC-002**: 공개하는 근거 카드의 100%가 값, 근거 종류, 기준 시점, 설명과 필요한 관찰 한계를 함께 제공한다
- **SC-003**: 설계 역할 과장, 확인되지 않은 대안, 로그 버퍼링·파일 쓰기 감소 성과, 중복률 `0%`, 처리 시간·장애율 개선 주장이 작업물과 인사이트에서 0건이다
- **SC-004**: 작업물 스윔레인 1개가 정상 경로 1개와 승인된 예외 종류 3개를 서로 구분해 제공하며 동등한 텍스트 설명을 포함한다
- **SC-005**: 작업물에서 인사이트로 가는 링크 1개와 인사이트에서 작업물로 돌아오는 링크 1개가 실제 화면과 키보드 환경에서 모두 동작한다
- **SC-006**: 작업물과 인사이트의 장문 중복 및 시각 중복 검토에서 각각 0개의 미해결 중복이 남는다
- **SC-007**: 320·768·1024·1440px에서 작업물과 인사이트 본문·시각 자료를 읽을 수 있고 문서 전체 가로 넘침과 핵심 노드·라벨 겹침이 0건이다
- **SC-008**: 기존 두 공개 경로, 공개 목록 진입, 다른 구조화 작업물과 공통 시각 계약에 대한 관련 회귀 검사가 모두 통과한다

## Assumptions

- 승인된 인터뷰 기록이 작업물과 연결 인사이트의 최우선 사실·문구 근거다.
- 연결 인사이트의 현재 승인 본문과 시각 자료는 유지하며, 구조화 이전 때문에 새로운 기술 판단이나 프로젝트 연혁을 추가하지 않는다.
- 골프 예약 시스템의 별도 공개 데모 주소는 검증되지 않았으므로 데모 요소를 새로 만들지 않는다.
- 정확한 로그 분리 시점은 복원하지 않으며 유지보수 타임라인 안의 날짜 없는 사건으로만 표시한다.
- 작업물에는 승인된 스윔레인 한 건만 제공하고 ERD나 로그 저장 전후 비교를 추가하지 않는다.
- 기존 구조화 상세 컴포넌트와 공통 시각 계약을 재사용하며 새로운 일반 목적 콘텐츠 모델은 범위에 포함하지 않는다.
- Feature 013의 독립 Archify HTML 세로 containment 잔여 작업은 별도 미완료 상태로 보존하며 Feature 014의 콘텐츠 사실 범위에 포함하지 않는다.
