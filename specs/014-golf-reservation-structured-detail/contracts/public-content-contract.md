# Contract: 골프 예약 시스템 공개 콘텐츠와 연결

## 작업물 계약

- 입사 후 첫 프로젝트였음을 공개한다.
- 최초 구축에서 새 아키텍처를 설계했다고 쓰지 않고, 정해진 구조 안에서 예약 화면, PHP 요청 처리, 외부 PMS 연동, 중복 방어와 통신 로그 기록을 FE/BE 범위 모두 단독으로 구현했다고 쓴다.
- 운영 유지보수 중 업무 DB에서 `syslog`로 로그 저장 경계를 분리하는 방향을 정하고 직접 구현한 판단은 최초 구축 역할과 구분한다.
- 카드 기간은 `2023.05 – 현재`이며, 최초 구축 `2023.05 – 2023.06`과 2023년 오픈 이후 현재까지의 유지보수를 본문에서 분리한다.
- 로그 분리의 정확한 적용 날짜를 만들지 않고 `운영 유지보수 과정`으로만 표현한다.
- 예약 원본과 최종 결과는 외부 PMS가 소유하고, 당사 서비스는 요청 전달·중복 완화·사용자 안내를 담당한다.
- 예약 요청 직후 React에서 버튼을 비활성화하고 스피너를 표시했다.
- PHP 서버에서 동일 세션의 같은 요청이 2초 이내 반복되면 외부 PMS 호출 전에 차단했다.
- 외부 PMS 요청에는 30초 timeout을 적용했고, 5xx에는 잠시 후 재시도, timeout에는 일시적 혼잡 안내를 제공했다.
- 초기에는 예약·회원 업무 데이터와 외부 API 통신 로그가 같은 업무 DB에 있었고, 수백만 건 누적 뒤 예약 문제 조사 중 로그 테이블 접근으로 DB GUI가 다운됐다.
- 로그 테이블 문제는 예약 기능 자체의 중단이 아니라 필요한 시점에 당사 기록을 조회하지 못한 운영 문제였다.
- 당사 로그를 확인하지 못한 당시에는 PMS 업체에 예약 건 확인을 요청했다.
- `syslog` 분리 뒤 실제 예약 문제에서 당사 시스템 로그의 요청·응답을 직접 확인할 수 있었다.
- 회고는 `syslog` 분리를 유지하면서 인증값·개인정보를 마스킹하고, 추적에 필요한 정보만 기록하며, 보존 기간을 관리하는 현재 판단으로 제한한다.

## 운영 결과 계약

- 2023년 오픈 이후 현재까지 직접 유지보수한 범위에서 통신 로그상 동일 예약의 중복 호출 이력과 관련 CS를 확인하지 못했다고 쓴다.
- 외부 PMS 5xx·timeout에는 구현한 사용자 안내가 동작했다고 쓴다.
- 결과는 유지보수 로그와 접수 CS에서 관찰한 범위이며 전체 예약 전수 집계나 영구 보장이 아니다.

## 연결 인사이트 계약

- 현재 승인된 제목, excerpt, 본문과 업무 DB→`syslog` 전후 시각 자료를 유지한다.
- 로그를 남기는 것과 장애 시점에 조회할 수 있는 것은 다른 문제라는 질문에 집중한다.
- 작업물의 전체 역할·기간·예약 방어 구현과 예약 스윔레인을 반복하지 않는다.
- 인증값·개인정보 마스킹, 필요한 추적 정보, 보존 기간 관리의 회고 범위를 유지한다.

## 금지 주장

다음은 작업물·연결 인사이트에서 사용자의 실제 역할·대안·성과로 나타나면 안 된다.

- 전체 아키텍처 또는 최초 구조를 단독 설계·주도했다는 주장
- 정확한 로그 분리 연월
- 전체 예약 건수, 중복률 `0%`, 중복 제거율 또는 영구적인 예약 무결성 보장
- 처리 시간 단축, 장애 감소율, 사용자 이탈률, 전환율
- `20건`, `2초마다 flush`, `파일 I/O 약 95% 감소`, 여러 PHP-FPM 요청을 모은 인메모리 버퍼링 성과
- ELK, Loki, Datadog, Redis TTL lock, queue, 별도 로그 DB를 당시 검토·기각했다는 주장
- 로그 테이블 문제로 예약 서비스가 중단됐다는 주장
- 고객 예약 내역, 실제 요청·응답 값, 인증 정보, 개인정보, 시크릿, 비공개 소스
