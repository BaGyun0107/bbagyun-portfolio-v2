# Feature Specification: 패키징 단일화

**Feature Branch**: `feature/014-packaging-unification`

**Created**: 2026-07-30

**Status**: Draft

**Input**: User description: "패키징 단일화 — bootstrap 을 단일 사용자 표면으로 만들고 copy 모드를 단계적으로 은퇴시킨다."

## Clarifications

### Session 2026-07-30

- Q: 미전환 레포 판정 수단을 어떻게 만드나 → A: 만들지 않는다. 대상 레포를 아는 사람이 전환 완료를 직접 판단해 알린다. 개별 레포의 모드 확인은 기존 상태 점검 명령으로 충분하다.
- Q: 준비 명령 재실행 시 무거운 단계(도구 설치·인증)를 어떻게 처리하나 → A: 단계 구성을 그대로 두고 각 단계의 스킵 판정만 확실히 한다. 실행 빈도가 하루 1회 수준이라 속도보다 완결성이 중요하고, 빠른 경로를 두면 "언제 뭘 쓰나" 판단이 되살아난다.
- Q: 실행 결과를 어떻게 알리나 → A: 끝에 요약을 출력한다 — 하네스 버전 변화(이전→현재 또는 "변경 없음"), 회수된 잔재 건수, 사용자 조치가 필요한 항목.
- Q: 고급/디버깅 명령을 도움말에서 어떻게 구분하나 → A: 기본 도움말에는 일상 명령 소수만 싣고, 나머지는 확장 표시 옵션으로 본다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 팀원이 명령 하나만 알면 된다 (Priority: P1)

새로 합류한 팀원이든 매일 쓰는 팀원이든 `./harness bootstrap` 하나만 기억하면
된다. 레포를 처음 clone 했을 때도, 다른 사람이 하네스를 갱신한 뒤 `git pull`
했을 때도, 하네스 상태가 어긋난 것 같을 때도 같은 명령을 친다. 결과는 항상
"지금 이 레포에 맞는 하네스가 준비된 상태" 다.

**Why this priority**: 팀 확장의 병목이 여기다. 지금은 상황에 따라
`install` / `pkg-sync` / `update` / `migrate` 중 무엇을 쳐야 하는지 사람이
판단해야 하고, 틀리면 하네스가 반쯤 빠진 상태로 남는다. 명령 선택을 없애면
온보딩 문서도 한 줄로 줄고 오작동 문의도 사라진다.

**Independent Test**: 전환 완료된 레포를 새로 clone 한 상태, `git pull` 로
하네스가 빠진 상태, 링크가 어긋난 상태 각각에서 `./harness bootstrap` 만
실행해 세 경우 모두 동일한 정상 상태에 도달하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 전환 완료된 레포를 처음 clone 한 상태, **When** `./harness bootstrap` 을 실행하면, **Then** 하네스가 완전히 준비되고 추가 명령이 필요 없다.
2. **Given** 이미 정상인 레포, **When** `./harness bootstrap` 을 다시 실행하면, **Then** 결과 상태가 같고 워킹트리에 불필요한 변경이 생기지 않는다.
3. **Given** 다른 팀원이 배포 모드를 전환한 커밋을 받아 하네스가 비어 보이는 상태, **When** `./harness bootstrap` 을 실행하면, **Then** 정책·훅·스킬이 모두 복구된다.
4. **Given** 하네스 상태가 어긋났다고 느끼는 팀원, **When** 도움말을 확인하면, **Then** 기본 목록에는 일상 명령 소수만 보이고 나머지는 확장 표시로 볼 수 있다.
5. **Given** 하네스가 갱신됐다는 공지를 본 팀원, **When** `./harness bootstrap` 을 실행하면, **Then** 끝에 버전이 무엇에서 무엇으로 바뀌었는지와 조치가 필요한 항목이 요약된다.
6. **Given** 이미 최신인 상태, **When** 준비 명령을 실행하면, **Then** 요약에 "변경 없음" 이 명시되어 재실행할 이유가 없음을 알 수 있다.

### User Story 2 - copy 모드가 안전하게 은퇴한다 (Priority: P2)

하네스 관리자가 남은 구버전 레포를 모두 전환한 뒤, copy 모드 코드 경로를
제거한다. 전환이 끝나지 않은 레포가 하나라도 남아 있는 동안에는 제거하지
않으며, 그런 레포의 사용자는 제거 전에 경고와 전환 방법을 먼저 본다.

**Why this priority**: copy 경로는 lock 모드와 다른 가정 위에서 동작해
유지보수 비용과 버그 표면을 두 배로 만든다. 다만 미전환 레포가 남은 상태에서
지우면 그 레포는 하네스를 갱신할 방법을 잃는다. 그래서 예고 → 확인 → 제거
순서가 본질이다.

**Independent Test**: copy 모드 레포에서 갱신을 시도하면 은퇴 예고와 전환
안내가 나오고 갱신 자체는 계속 동작하는지 확인한다. 별도로, 임의의 레포에서
상태 점검이 현재 배포 모드를 정확히 보고하는지 확인한다.

**이번 범위**: 은퇴 예고와 개별 레포 모드 보고까지 구현한다. 제거 실행은
Out of Scope 참조. 전체 전환 완료 판정은 관리자가 직접 한다.

**Acceptance Scenarios**:

1. **Given** copy 모드 레포, **When** 하네스 갱신을 실행하면, **Then** 은퇴 예고 경고와 전환 방법이 표시되고 갱신은 정상 완료된다.
2. **Given** 미전환 레포가 남아 있는 상황, **When** copy 경로 제거를 시도하면, **Then** 제거가 진행되지 않고 남은 레포가 무엇인지 알 수 있다.
3. **Given** 모든 대상 레포가 전환 완료된 상황, **When** copy 경로를 제거하면, **Then** lock 모드 동작에 회귀가 없다.

---

### User Story 3 - 새 프로젝트는 처음부터 패키징 구조다 (Priority: P3)

새 프로젝트를 만들 때 하네스는 처음부터 lock 구조로만 배선된다. 복사본을
만들었다가 지우는 중간 단계가 없어, 생성 과정이 짧아지고 실패 지점이 준다.

**Why this priority**: 사용자 영향이 가장 작다(새 프로젝트 생성은 드물다).
다만 copy 경로 제거의 전제 조건이라 함께 다뤄야 하고, 지금 구조에는 "복사본을
만들 이유가 없는데도 지우는 단계" 가 남아 있다.

**Independent Test**: 새 프로젝트를 생성해 lock 구조가 갖춰지고, 생성
과정에서 복사본 제거 단계를 거치지 않으며, 결과가 전환 완료 레포와 같은
형태인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 새 프로젝트 생성 요청, **When** 생성이 끝나면, **Then** lock 구조가 갖춰지고 별도 전환 작업이 필요 없다.
2. **Given** 새로 생성된 프로젝트, **When** 구조를 확인하면, **Then** 전환 완료된 기존 레포와 같은 형태다.

---

### Edge Cases

- 네트워크가 끊긴 상태에서 `bootstrap` 을 실행하면? — 캐시된 버전이 있으면 그것으로 진행하고, 없으면 원인(네트워크/인증)을 구분해 알린다.
- 하네스 상태가 copy 와 lock 이 섞인 중간 상태라면? — `bootstrap` 이 lock 기준으로 수렴시키고, 수렴 불가한 부분은 사용자에게 보고한다.
- 은퇴 예고 경고가 매번 떠서 소음이 되면? — 경고는 copy 모드 레포에서만 뜨고, 전환하면 즉시 사라진다.
- 미전환 레포 판정을 사람이 잊고 제거를 강행하면? — 제거 단계가 판정 없이는 진행되지 않는다.
- 자동화가 사람용 준비 명령을 쓰지 않고 최소 경로만 쓰는 경우? — 그 경로는 그대로 유지되며 이 변경의 영향을 받지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

#### 단일 진입점 (US1)

     이어 붙이되 위치는 이 그룹에 둔다. -->


- **FR-001**: 팀원용 일상 명령은 하나여야 하며, 최초 준비와 이후 갱신 모두 그 명령으로 수행된다.
- **FR-002**: 그 명령은 멱등해야 한다 — 정상 상태에서 다시 실행해도 결과 상태가 같고 워킹트리에 불필요한 변경을 남기지 않는다.
- **FR-003**: 그 명령은 어긋난 상태(하네스 일부 소실, 링크 드리프트, 버전 불일치)를 정상 상태로 수렴시킨다.
- **FR-004**: 기존 하위 명령들은 제거하지 않고 유지하되, 기본 도움말에는 일상 명령 소수만 싣는다. 나머지는 확장 표시 옵션으로 볼 수 있어야 한다.
- **FR-005**: 하위 명령이 수행하던 준비 작업(스킬 트리 구성, 도구 자산 배치, 외부 도구 설치)은 어느 것도 누락되지 않는다.
- **FR-017**: 준비 명령은 끝에 실행 결과를 요약한다 — 하네스 버전 변화(이전→현재, 또는 "변경 없음"), 정리된 잔재 건수, 사용자 조치가 필요한 항목.
- **FR-018**: 준비 명령은 이미 갖춰진 준비 단계를 다시 수행하지 않는다. 각 단계는 자신이 필요한지 판정하고 불필요하면 건너뛴다.

#### copy 모드 은퇴 (US2)

- **FR-006**: copy 모드 레포에서 하네스 갱신을 실행하면 은퇴 예고와 전환 방법이 표시된다. 갱신 자체는 계속 정상 동작한다.
- **FR-007**: 은퇴 예고는 copy 모드 레포에서만 표시되고, 전환 완료 후에는 표시되지 않는다.
- **FR-008**: 개별 레포에서 현재 배포 모드(copy / lock)를 확인할 수 있어야 한다. 전체 레포의 전환 완료 판정은 자동화하지 않는다 — 대상 레포를 아는 사람이 직접 판단한다.
- **FR-009**: copy 경로 제거는 전환 완료가 확인된 뒤에만 수행된다.
- **FR-010**: copy 경로 제거 후에도 lock 모드 동작에 회귀가 없어야 한다.
- **FR-011**: copy 모드에서만 의미가 있던 보조 기능들은 copy 경로와 함께 정리된다.

#### 신규 프로젝트 (US3)

- **FR-012**: 새 프로젝트 생성 결과는 전환 완료된 기존 레포와 같은 구조여야 한다.
- **FR-013**: 새 프로젝트 생성 과정에 복사본을 만들었다가 제거하는 중간 단계가 없어야 한다. **(후속 작업 — Out of Scope 참조)**

#### 안전장치 (전 범위)

- **FR-014**: 기존 자동화(CI)가 의존하는 최소 준비 경로는 이 변경의 영향을 받지 않아야 한다.
- **FR-015**: 각 사용자 스토리는 독립적으로 되돌릴 수 있어야 한다 — 한 스토리의 변경을 되돌려도 다른 스토리가 깨지지 않는다. (구현 시에는 스토리별로 원자 커밋을 만들어 충족한다.)
- **FR-016**: 사용자에게 보이는 진행 표시는 단계 변경 후에도 일관되어야 한다(번호 누락·중복 없음).

### Key Entities

- **하네스 준비 상태**: 레포가 하네스를 쓸 수 있는 상태인지를 나타낸다. 정상 / 일부 소실 / 버전 불일치 / 미전환 으로 구분된다.
- **배포 모드**: 레포가 하네스를 받는 방식. 현재는 copy 와 lock 두 가지이며, 이 작업의 종착점은 lock 하나다.
- **전환 대상 목록**: copy 경로 제거 가능 여부를 판정하기 위해 추적해야 하는 레포 집합.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 팀원이 하네스를 준비·갱신하기 위해 알아야 하는 명령이 1개다(현재는 상황에 따라 4개 중 선택).
- **SC-002**: 새 팀원이 온보딩 문서를 보고 하네스 준비를 마치기까지 사람이 내리는 판단이 0회다 — 명령 선택도, 상태 진단도 필요 없다.
- **SC-003**: 준비 명령을 연속 2회 실행했을 때 두 번째 실행이 워킹트리에 남기는 변경이 0건이다.
- **SC-004**: 하네스가 일부 소실된 상태에서 준비 명령 1회로 정상 상태에 도달하는 비율이 100%다(테스트로 검증하는 소실 시나리오 기준).
- **SC-005**: copy 모드 레포 사용자가 갱신을 실행하면 전환 방법을 100% 안내받는다.
- **SC-006**: 임의의 레포에서 상태 점검을 실행하면 현재 배포 모드를 100% 정확히 알 수 있다. (전체 전환 완료 판정은 사람 몫 — Clarifications 참조.)
- **SC-008**: 준비 명령 실행 후 사용자가 "무엇이 바뀌었는지" 를 추가 명령 없이 알 수 있다 — 버전 변화와 조치 필요 항목이 요약에 포함된다.
- **SC-007**: 전 과정에서 기존 회귀 테스트가 계속 통과한다(현재 655건 기준, 감소 없음).

## Assumptions

- 대상 레포는 사내 저장소로 한정되며, 전환 완료 여부를 사람이 열거해 확인할 수 있는 규모(수십 개 이하)다. 관리자가 어떤 레포를 전환해야 하는지 알고 있으므로 판정 자동화는 만들지 않는다.
- 준비 명령의 실행 빈도는 하루 1회 수준이거나 갱신 공지 시점이다. 이 빈도에서는 실행 속도보다 매번 완전한 상태를 보장하는 쪽이 가치가 크며, 빠른 경로 옵션은 "언제 무엇을 쓰나" 라는 판단을 되살리므로 두지 않는다.
- copy 경로 제거는 이 기능의 최종 단계이며, 실제 제거 시점은 전환 완료 확인 이후의 별도 판단이다. 이 스펙은 "제거 가능한 상태로 만드는 것" 과 "제거 절차를 정의하는 것" 까지를 범위로 본다.
- 준비 명령은 현재와 같이 macOS 를 대상으로 한다. 다른 OS 지원은 이 작업의 범위 밖이다.
- 자동화(CI)는 사람이 쓰는 준비 명령과 다른 최소 경로를 계속 사용한다. 두 경로를 통합하는 것은 범위 밖이다.
- 외부 도구(플러그인 등) 설치 실패는 지금처럼 준비 과정을 중단시키지 않고 안내로 처리한다.
- 은퇴 예고의 노출 기간은 정하지 않는다 — 전환 완료 확인이 제거 조건이며 기간은 조건이 아니다.

## Out of Scope

- **copy 경로의 실제 제거(US2 2·3단계)**. 이 스펙이 구현하는 것은 US1, US3, 그리고
  US2 중 은퇴 예고(FR-006/007)와 개별 레포 모드 보고(FR-008)까지다. 제거
  자체(FR-009~011)는 관리자가 전환 완료를 확인한 뒤 별도 작업으로 다룬다 —
  되돌리기 어려운 변경이라 서두를 이유가 없고, 확인 시점에 남은 레포 수가
  제거 방식을 바꿀 수 있다. FR-009~011 은 그때 충족할 요구로 남긴다.
- **신규 프로젝트 생성의 중간 단계 제거(FR-013)**. plan 단계 조사에서 최초 가정이
  틀렸음이 확인됐다: 신규 프로젝트는 하네스 clone 에서 출발하므로 실파일 사본이
  실재하고, 그 사본을 링크로 바꾸는 단계는 불필요한 우회가 아니라 필수다. 이를
  없애려면 clone 대신 패키지에서 직접 배선하도록 생성 절차를 전면 재작성해야 한다 —
  별도 기능으로 분리한다. FR-012(결과 구조 동일)는 이번 범위에 남는다.
- copy 모드와 lock 모드를 동시에 지원하는 하이브리드 구조를 새로 만드는 것.
- 자동화(CI) 준비 경로와 사람용 준비 명령의 통합.
- macOS 외 운영체제 지원.
- 이미 전환된 레포의 과거 잔재를 일괄 정리하는 작업(별도로 처리됨).
