# Feature Specification: Codi Harness 포트폴리오 상세 개선

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-08-20

**Status**: Draft

**Input**: User description: "사내 DX 하네스 v2 작업물을 먼저 완결한다. 데모는 제공하지 않고 두 개의 접근 가능한 스윔레인으로 대체한다. 문제·역할·판단·결과 중심의 공통 상세 구조, 검증 가능한 지표, 현재·역사 도구 구분, 네 개의 분리 인사이트를 제공하며 나머지 7개 작업물은 인터뷰 전까지 보존한다. include test tasks (TDD)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 하네스의 가치와 성과를 빠르게 파악 (Priority: P1)

면접관은 긴 구현 설명을 먼저 읽지 않고도 하네스가 해결한 문제, 작성자의 역할,
핵심 판단과 검증된 결과를 상세 페이지 상단에서 파악하고 싶다.

**Why this priority**: 작업물의 핵심 가치가 첫 화면에서 전달되지 않으면 이후의
스윔레인과 인사이트를 읽을 이유를 만들기 어렵다.

**Independent Test**: 하네스 상세 페이지 상단만 확인해 프로젝트 목적, 기간, 역할,
적용 범위, 사용 인원, 비용 산정, 배포 시간과 환경변수 결과를 구분해 설명할 수 있다.

**Acceptance Scenarios**:

1. **Given** 하네스 상세 페이지를 처음 연 방문자가 있을 때, **When** 상단 요약을 읽으면, **Then** 프로젝트 개요, 역할과 핵심 결과를 장문 본문보다 먼저 확인한다.
2. **Given** 정량 결과가 표시될 때, **When** 방문자가 결과의 근거를 확인하면, **Then** 측정값·보고값·추정값의 종류, 기준 시점과 제한사항을 구분할 수 있다.
3. **Given** Jenkins 서버 비용이 표시될 때, **When** 방문자가 산정 근거를 확인하면, **Then** 현재 공개 가격 기반 컴퓨팅 추정치이며 과거 실제 청구액이나 전체 인프라 비용이 아님을 알 수 있다.

---

### User Story 2 - 개발 운영과 배포 운영의 흐름 이해 (Priority: P1)

면접관은 비공개 소스나 실행 데모 없이도 사용자의 요구가 설계·구현·검증으로
이어지는 과정과, 변경이 검증·시크릿 주입·배포로 이어지는 과정을 이해하고 싶다.

**Why this priority**: 하네스는 눈에 보이는 고객 화면보다 책임 경계와 운영 흐름이
핵심인 작업물이므로 스윔레인이 데모를 대신하는 주요 증거다.

**Independent Test**: 두 스윔레인을 각각 읽고 정상 흐름, 차단 조건, 실패 이후의
복구 또는 중단 결과를 순서대로 설명할 수 있다.

**Acceptance Scenarios**:

1. **Given** 방문자가 설계·개발·검증 스윔레인을 볼 때, **When** 정상 경로를 따라가면, **Then** 사용자 입력부터 계획, 승인, 테스트 우선 구현, 리뷰와 검증까지의 책임 주체를 식별한다.
2. **Given** 중요한 모호성, 미승인 작업, 테스트 실패 또는 검증 불일치가 있을 때, **When** 실패 흐름을 확인하면, **Then** 구현이 차단되거나 이전 단계로 돌아가는 이유와 대상을 알 수 있다.
3. **Given** 방문자가 배포 스윔레인을 볼 때, **When** 정상 경로를 따라가면, **Then** 변경 감지, 품질 검증, 환경 선택, 시크릿 주입과 배포 대상의 순서를 알 수 있다.
4. **Given** 시각 다이어그램을 사용할 수 없는 방문자가 있을 때, **When** 대체 설명을 읽으면, **Then** 시각 다이어그램과 동일한 단계·분기·복구 흐름을 순서대로 이해한다.

---

### User Story 3 - 현재 구조와 발전 과정을 혼동 없이 확인 (Priority: P1)

면접관은 현재 하네스가 사용하는 계획·실행·브라우저 검증 도구와, 초기 버전에서
검토하거나 사용한 도구 및 교체 이유를 구분해서 이해하고 싶다.

**Why this priority**: 역사적 도구가 현재 기술 스택처럼 보이면 작업물의 최신성과
작성자의 실제 판단을 잘못 전달한다.

**Independent Test**: 현재 핵심 도구 목록과 발전 타임라인을 비교해 현재 사용,
역사적 사용, 제거·대체 이유를 서로 섞지 않고 설명할 수 있다.

**Acceptance Scenarios**:

1. **Given** 방문자가 현재 핵심 도구를 확인할 때, **When** 기술 스택과 본문을 읽으면, **Then** 현재 계획·실행·브라우저 검증 역할을 담당하는 도구만 핵심 도구로 인식한다.
2. **Given** 방문자가 발전 타임라인을 읽을 때, **When** 과거 도구 전환 항목을 확인하면, **Then** 문서 통제와 사용자 의견 반영, 실제 사용량 측정이라는 전환 근거를 알 수 있다.
3. **Given** 런타임별 집행 구조를 확인할 때, **When** 소형 계층 구조와 설명을 읽으면, **Then** 공통 정책과 서로 다른 집행 레이어의 책임을 구분한다.

---

### User Story 4 - 본문에서 상세 인사이트로 확장 (Priority: P2)

면접관은 작업물 본문에서는 핵심 판단과 결과에 집중하고, 더 깊은 구현 배경은
관심 있는 주제의 인사이트로 이동해 읽고 싶다.

**Why this priority**: 모든 구현 세부를 한 본문에 유지하면 핵심 서사가 흐려지고
면접관이 필요한 깊이를 선택할 수 없다.

**Independent Test**: 하네스 본문에서 네 개의 상세 주제 링크를 찾고 각 링크가
서로 다른 초점의 인사이트로 이동하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방문자가 패키징, 초기화·검증, 런타임 패리티, 멀티 세션 주제를 읽을 때, **When** 연결된 인사이트를 선택하면, **Then** 해당 주제를 독립적으로 설명하는 글로 이동한다.
2. **Given** 방문자가 하네스 종합 인사이트를 읽을 때, **When** 전체 발전 과정을 확인하면, **Then** 네 개 상세 글과 중복되는 장문 구현 설명 대신 전체 맥락을 파악한다.
3. **Given** 기존 Jenkins·시크릿·네트워크 인사이트가 있을 때, **When** 작업물과 수치·시점을 비교하면, **Then** 서로 충돌하는 비용이나 현재 도구 설명이 없다.

---

### User Story 5 - 기존 작업물을 보존하며 순차 이전 (Priority: P2)

포트폴리오 운영자는 하네스 상세 구조를 먼저 완결하고, 나머지 7개 작업물은 각자의
인터뷰를 마칠 때까지 현재 내용과 접근 경로를 유지하고 싶다.

**Why this priority**: 인터뷰하지 않은 작업물을 동일 구조에 맞추기 위해 임의로
재작성하면 사실성 원칙과 기존 공개 페이지의 안정성을 해친다.

**Independent Test**: 하네스 상세 개선 후에도 전체 8개 작업물 목록과 상세 페이지에
접근하고, 하네스 외 7개 작업물의 기존 본문을 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 하네스만 구조화 상세로 이전됐을 때, **When** 방문자가 다른 7개 작업물을 열면, **Then** 기존 본문이 손실 없이 표시된다.
2. **Given** 모든 작업물이 하나의 상세 템플릿을 사용할 때, **When** 구조화 상세가 없는 작업물을 열면, **Then** 기존 콘텐츠를 지원하되 빈 데모·다이어그램 영역을 표시하지 않는다.
3. **Given** 이후 작업물 인터뷰가 완료될 때, **When** 해당 작업물이 새 상세 구조로 이전되면, **Then** 페이지 템플릿을 새로 만들지 않고 같은 읽기 순서와 선택 증거 규칙을 사용한다.

### Edge Cases

- 데모 URL이 없거나 검증되지 않았으면 외부 데모 CTA와 준비 중 버튼을 모두 숨긴다.
- 정량 결과에 기준 시점, 근거 종류 또는 제한사항이 없으면 공개 가능한 결과로 취급하지 않는다.
- 스윔레인의 lane 또는 step ID가 중복되거나 연결이 존재하지 않는 단계를 참조하면 게시 가능한 데이터로 취급하지 않는다.
- 실패 흐름에 복구 또는 중단 결과가 없으면 불완전한 흐름으로 취급한다.
- 화면 폭보다 넓은 다이어그램은 해당 컨테이너 안에서만 스크롤되고 페이지 전체 폭을 늘리지 않는다.
- 색상을 구분하지 못하는 방문자도 선 스타일, 아이콘과 텍스트로 정상·실패·복구를 식별한다.
- 외부 자료나 가격이 변경돼도 기준 시점이 유지되어 현재 추정치와 과거 실제 비용이 혼동되지 않는다.
- 관련 인사이트가 누락되거나 잘못 연결되면 본문에 끊어진 공개 링크를 노출하지 않는다.
- 구조화 상세가 없는 작업물은 기존 본문을 표시하며 다른 작업물의 데이터로 대체하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 상세 페이지는 프로젝트 개요를 장문 본문 존재 여부와 관계없이 상단에 표시해야 한다.
- **FR-002**: 하네스 상세 페이지는 프로젝트 개요, 역할, 핵심 결과, 문제·제약, 대안·판단, 시스템 흐름, 핵심 설계, 결과·검증, 회고, 관련 인사이트의 공통 읽기 순서를 제공해야 한다.
- **FR-003**: 핵심 결과는 값, 근거 종류, 기준 시점, 근거 설명과 필요한 제한사항을 함께 제공해야 한다.
- **FR-004**: 측정값, 사용자 보고값과 외부 가격 기반 추정값은 서로 다른 근거 종류로 식별돼야 한다.
- **FR-005**: Jenkins 비용은 2026-08-20 기준 서울 리전 `t3.large` Linux On-Demand 2대의 월 730시간 컴퓨팅 비용 `$151.84` 추정치로 표시하고, 부대비용과 과거 실제 청구액이 아님을 밝혀야 한다.
- **FR-006**: 하네스 상세 페이지는 외부 데모 CTA를 제공하지 않아야 한다.
- **FR-007**: 검증된 데모 정보가 없는 모든 작업물은 빈 CTA, 비활성 CTA 또는 준비 중 CTA를 표시하지 않아야 한다.
- **FR-008**: 하네스 상세 페이지는 설계·개발·검증 흐름과 CI/CD·시크릿·배포 흐름을 서로 분리된 두 스윔레인으로 제공해야 한다.
- **FR-009**: 각 스윔레인은 목적, 책임 주체, 단계, 연결, 정상·실패·복구 종류와 순서형 대체 설명을 제공해야 한다.
- **FR-010**: 실패 연결은 복구 또는 중단 결과를 명시해야 한다.
- **FR-011**: 정상·실패·복구 흐름은 색상 외에 선 스타일, 아이콘 또는 명시적 텍스트로 구분돼야 한다.
- **FR-012**: 넓은 스윔레인은 자체 영역 안에서 탐색 가능해야 하며 상세 페이지 전체에 가로 스크롤을 만들지 않아야 한다.
- **FR-013**: 현재 핵심 도구는 Spec Kit, Superpowers, Playwright MCP, Codi skills, GitHub Actions와 Infisical로 한정하고, 초기·과거 도구인 GSD와 GStack은 서로 다른 영역에서 시점과 역할을 구분해 설명해야 한다.
- **FR-014**: GSD에서 Spec Kit으로의 전환은 문서 구조 통제와 사용자 의견 반영을, GStack에서 Playwright MCP로의 전환은 약 5주의 실제 사용량 측정을 검증된 이유로 반영해야 한다.
- **FR-015**: 하네스 본문은 네 개의 독립 인사이트인 패키징·소유권, CLI·진단, 런타임 패리티·회귀 테스트, 멀티 세션·컨텍스트 수명 주제로 직접 연결해야 한다.
- **FR-016**: 하네스 종합 인사이트는 전체 발전 과정의 개요로 압축하고 신규 상세 인사이트와 장문 내용을 중복하지 않아야 한다.
- **FR-017**: 기존 Jenkins, 시크릿, 네트워크 관련 인사이트는 하네스 작업물과 비용·도구 시점·운영 범위가 일치해야 한다.
- **FR-018**: 작업물 분류는 `Backend`, `Frontend`, `DevOps`, `Fullstack`만 허용하고, 상태는 `Production`, `Beta`, `Archived`, `In Progress`만 허용하며 지원되지 않는 값은 공개 전에 차단해야 한다.
- **FR-019**: 하나의 공통 상세 템플릿이 구조화 상세와 아직 이전되지 않은 기존 본문을 모두 표시해야 한다.
- **FR-020**: 하네스 외 7개 작업물의 기존 콘텐츠와 접근 경로는 각 작업물의 인터뷰가 완료될 때까지 보존돼야 한다.
- **FR-021**: 모든 테스트 작업은 구현보다 먼저 수행할 수 있도록 TDD 순서로 계획돼야 한다.

### Key Entities

- **작업물**: 제목, 설명, 기간, 팀, 분류, 상태와 기술 맥락을 가진 포트폴리오 항목이다.
- **작업물 상세**: 역할, 결과, 문제·제약, 대안, 흐름, 핵심 설계, 검증과 회고를 공통 순서로 묶은 서술 단위다.
- **근거 지표**: 값, 측정·보고·추정 종류, 기준 시점, 근거와 제한사항을 가진 결과다.
- **데모 정보**: 검증된 외부 주소, 표시 문구, 운영·포트폴리오 구분, 접근 안내와 현재 접근 가능 상태를 가진 선택 정보다.
- **스윔레인**: 목적, 책임 주체, 단계, 단계 간 연결, 정상·실패·복구 의미와 대체 설명을 가진 흐름 증거다.
- **인사이트**: 작업물의 특정 설계 판단이나 구현 트레이드오프를 독립적으로 설명하고 관련 작업물로 연결되는 장문 글이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 방문자는 하네스 상세 상단에서 프로젝트 목적, 작성자 역할과 핵심 결과 5개 이상을 장문 구현 설명을 읽기 전에 확인할 수 있다.
- **SC-002**: 표시되는 정량 결과의 100%가 근거 종류, 기준 시점과 근거 설명을 제공하며 추정값에는 제한사항이 함께 표시된다.
- **SC-003**: 방문자는 두 스윔레인 각각에서 정상 경로와 최소 한 개의 실패·복구 또는 중단 경로를 식별할 수 있다.
- **SC-004**: 시각 다이어그램을 사용하지 않는 방문자도 대체 설명만으로 두 흐름의 책임 주체, 단계와 분기 결과를 같은 순서로 파악할 수 있다.
- **SC-005**: 320px, 768px, 1024px와 1440px 화면에서 상세 콘텐츠 접근이 유지되고 다이어그램 영역 밖의 페이지 가로 스크롤이 발생하지 않는다.
- **SC-006**: 하네스 상세 페이지에는 외부 데모 CTA, 비활성 데모 CTA와 준비 중 데모 CTA가 0개다.
- **SC-007**: 현재 핵심 도구 목록에는 역사적 도구가 0개이며, 역사적 도구는 전환 시점과 이유가 있는 발전 기록에서만 확인된다.
- **SC-008**: 하네스 본문에서 네 개의 독립 인사이트에 모두 접근할 수 있고 각 링크는 해당 주제의 정상 페이지로 이동한다.
- **SC-009**: 작업물과 관련 인사이트 사이에 서로 다른 Jenkins 비용, 현재 계획 도구 또는 브라우저 QA 도구를 주장하는 공개 문구가 0개다.
- **SC-010**: 하네스 개선 후에도 전체 8개 작업물 상세 페이지에 접근할 수 있고, 하네스 외 7개 작업물의 기존 본문이 유지된다.
- **SC-011**: 키보드만 사용하는 방문자가 상세 페이지의 모든 링크와 외부 링크 안내에 접근할 수 있으며, 정적 흐름 단계가 불필요한 키보드 정지점을 만들지 않는다.
- **SC-012**: 정의된 인수 시나리오와 콘텐츠 계약, 사용자 흐름, 전체 페이지 생성 및 공개 경로의 필수 검증이 100% 통과한 상태에서만 기능 완료로 판정된다.

## Assumptions

- 하네스 작업물은 공개 데모나 실행 가능한 CLI 샌드박스를 제공하지 않는다.
- 두 스윔레인이 하네스의 데모를 대신하는 핵심 흐름 증거다.
- 사내 하네스 전체 소스코드, 고객 데이터와 시크릿은 공개하지 않는다.
- Jenkins 비용은 과거 청구서를 복원한 값이 아니라 2026-08-20 공개 가격을 사용한 현재 컴퓨팅 추정치다.
- 5개 호텔의 약 15분에서 약 3분으로의 배포 시간은 실제 실행 화면 기준의 측정값이다.
- 개발자 `role` 기능은 이번 작업물의 공개 성과 범위에서 제외한다.
- 하네스 외 7개 작업물은 후속 인터뷰에서 데모 공개 범위와 상세 증거를 하나씩 확정한다.
- 기존 공개 작업물 경로와 목록은 유지하며 별도 비교 라우트를 만들지 않는다.
- 기존 작업물에 사용 중인 `In Progress`는 사실성을 유지하기 위해 정식 지원 상태로 포함한다.
- 구현 계획은 테스트 작업을 명시적으로 포함하고 TDD 순서를 유지한다.
