# Feature Specification: 포트폴리오 콘텐츠 작성 규칙과 인사이트 계약

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-08-25

**Status**: Draft

**Input**: 작업물·인사이트·공부 콘텐츠의 공통 편집 계약을 프로젝트 상시 규칙과
재사용 가능한 작성 절차로 규정한다. 인사이트는 프로젝트 사례형과 기술 탐구형 두
유형을 유지하고, 작업물 또는 공부 기록 연결을 원칙으로 한다. 시각 자료는 의무화하지
않되 필요성 판정을 의무화한다. 완료된 세 작업물의 연결 인사이트를 우선 점검하고,
이후 남은 작업물은 상세와 인사이트를 같은 feature에서 진행한다. 테스트 작업을
포함하고 TDD로 구현한다.

## Context

작업물 상세는 하네스, 한마음 과학원, 블랙스톤 벨포레 리조트까지 공통 읽기 구조로
이전됐다. 반면 인사이트는 글의 목적, 목차, 근거 표기, 출처 연결과 시각 자료 사용
기준이 일정하지 않다.

작업물의 사실을 정정할 때 연결 인사이트를 함께 수정하지 않으면 독자가 링크를 따라가
정정 이전 내용을 다시 만나게 된다. 앞으로는 작업물 상세와 연결 인사이트를 하나의
사실 계약으로 관리하고, Claude Code와 Codex가 같은 작성 기준을 반복 적용할 수 있어야
한다.

이번 feature의 초기 적용은 이미 구조화된 세 작업물의 연결 인사이트 6개와 기존 공부
기록에 연결된 기술 탐구형 인사이트 1개였다. 이후 2026-08-26에 사용자가 승인한
The Siena 로그 분리 인사이트 후속을 같은 계약으로 편입했다. 따라서 현재 적용 범위는
프로젝트 사례형 7개와 기술 탐구형 1개, 총 8개이며 나머지 10개 공개 인사이트의 본문과
경로는 보존한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 두 에이전트가 같은 콘텐츠 기준을 따른다 (Priority: P1)

포트폴리오 운영자는 Claude Code와 Codex 중 어느 도구를 사용해도 작업물, 인사이트와
공부 기록이 같은 편집 원칙으로 작성되길 원한다. 세션이 바뀌거나 다른 작업물을
다루더라도 인터뷰 우선, 근거 구분, 연결 콘텐츠 동시 검증과 시각 자료 필요성 판단이
누락되지 않아야 한다.

**Why this priority**: 기준이 채팅이나 일반 문서에만 남으면 다음 세션에서 다시
설명해야 하고, 작업물만 수정한 채 연결 인사이트를 놓치는 문제가 반복된다.

**Independent Test**: 두 지원 에이전트 환경에서 작업물 또는 인사이트 작성 요청을
시작했을 때 동일한 공통 규칙과 상세 작성 절차를 발견하고, 승인된 핵심 판단을 같은
순서로 적용하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 새 세션에서 포트폴리오 작업물 콘텐츠를 수정하는 요청, **When** 에이전트가 작업 범위를 정한다, **Then** 공통 작성 절차를 사용하고 인터뷰·feature 기록·기존 본문의 우선순위를 지킨다
2. **Given** 인사이트를 신규 작성하거나 검토하는 요청, **When** 에이전트가 글의 구조를 정한다, **Then** 두 유형 중 하나를 판정하고 출처 연결과 시각 자료 필요성을 확인한다
3. **Given** 작업물의 역할·수치·원인이 정정된 상태, **When** 에이전트가 변경 대상을 찾는다, **Then** 연결 인사이트까지 같은 변경 단위에 포함한다

---

### User Story 2 - 독자가 인사이트의 목적과 출처를 이해한다 (Priority: P1)

독자는 인사이트가 실제 작업물에서 나온 사례인지, 공부 과정에서 정리한 기술 탐구인지,
그리고 어느 기록에서 출발했는지 빠르게 이해하고 싶다. 독립 글이라면 억지 연결 대신
독립적으로 유지하는 이유를 운영자가 설명할 수 있어야 한다.

**Why this priority**: 출처가 없는 기술 글 모음처럼 보이면 실제 경험과 학습에서 나온
판단이라는 포트폴리오 맥락이 약해진다.

**Independent Test**: 우선 점검 대상 인사이트 각각에서 유형과 유효한 연결 대상을
확인하고, 연결된 상세 화면 양쪽에서 서로 이동할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 실제 작업물에서 나온 인사이트, **When** 글의 분류와 관련 기록을 확인한다, **Then** 프로젝트 사례형이며 존재하는 작업물 하나에 연결돼 있다
2. **Given** 공부 과정에서 나온 인사이트, **When** 글의 분류와 관련 기록을 확인한다, **Then** 기술 탐구형이며 존재하는 공부 기록에 연결돼 있다
3. **Given** 연결할 작업물이나 공부 기록이 없는 기존 기술 글, **When** 독립 유지 여부를 검토한다, **Then** 기술 탐구형으로 분류하고 비어 있지 않은 독립 유지 이유를 남기거나 통합·비공개 후보로 분류한다
4. **Given** 연결된 작업물 또는 공부 기록, **When** 독자가 관련 인사이트를 열고 돌아온다, **Then** 양쪽 공개 화면에서 연결이 끊기지 않는다

---

### User Story 3 - 글마다 같은 판단 품질을 유지한다 (Priority: P1)

기술 면접관은 서로 다른 인사이트를 읽더라도 질문, 배경, 제약, 판단 과정, 결과 또는
적용 기준, 한계와 관련 기록을 일관된 깊이로 이해하고 싶다. 다만 모든 글이 같은
제목의 템플릿 복사본처럼 보여서는 안 된다.

**Why this priority**: 목차 이름만 통일하면 글의 핵심 근거가 빠질 수 있고, 반대로
모든 제목을 강제하면 주제별 흐름과 글의 자연스러움이 손상된다.

**Independent Test**: 우선 점검 대상 8개 인사이트가 공통 의미 계약과 해당 유형의
필수 의미를 모두 제공하면서도 동일한 Markdown 제목을 강제하지 않는지 검토한다.

**Acceptance Scenarios**:

1. **Given** 프로젝트 사례형 인사이트, **When** 글 전체를 읽는다, **Then** 역할, 실제 문제와 시점, 제약, 선택과 구현, 결과 근거, 한계와 회고를 설명할 수 있다
2. **Given** 기술 탐구형 인사이트, **When** 글 전체를 읽는다, **Then** 학습 질문, 참고와 직접 실험의 구분, 개념·대안 비교, 적용 조건, 한계와 연결 공부 기록을 설명할 수 있다
3. **Given** 서로 다른 두 인사이트, **When** 소제목을 비교한다, **Then** 같은 의미 계약을 충족하더라도 주제에 맞는 자연스러운 제목과 순서를 사용할 수 있다
4. **Given** 작업물과 연결 인사이트가 같은 설계를 설명한다, **When** 두 본문을 비교한다, **Then** 작업물은 전체 판단을 요약하고 인사이트는 하나의 질문을 확장하며 장문을 중복하지 않는다

---

### User Story 4 - 필요한 글에만 적합한 시각 증거를 사용한다 (Priority: P2)

독자는 복잡한 주체 이동, 데이터 관계, 상태 변화나 대안 비교가 글만으로 어려울 때
적합한 시각 자료의 도움을 받고 싶다. 단순한 글에는 장식용 스윔레인이나 ERD가 추가돼
읽기 흐름을 방해하지 않아야 한다.

**Why this priority**: 시각 자료의 정보 가치는 높지만 모든 인사이트에 의무화하면
주제와 맞지 않는 그림과 유지보수 비용이 늘어난다.

**Independent Test**: 우선 점검 대상 8개 인사이트에 시각 자료 필요성 판정과 근거가
존재하고, 자료가 있는 경우 질문·텍스트 설명·중복 방지 이유가 함께 제공되는지
확인한다.

**Acceptance Scenarios**:

1. **Given** 세 개 이상의 구성요소, 실패·복구 경로, 데이터 관계 또는 세 개 이상의 대안이 핵심인 글, **When** 시각 자료 필요성을 판정한다, **Then** 스윔레인·ERD·흐름도·상태도·비교표·타임라인 중 목적에 맞는 표현을 검토한다
2. **Given** 단순한 순차 설명으로 충분한 글, **When** 시각 자료 필요성을 판정한다, **Then** `없음`을 유효한 결정으로 남길 수 있다
3. **Given** 시각 자료가 포함된 인사이트, **When** 그림을 이용할 수 없는 독자가 글을 읽는다, **Then** 텍스트 설명만으로도 같은 핵심 관계를 이해할 수 있다
4. **Given** 작업물에 이미 전체 흐름 다이어그램이 있다, **When** 연결 인사이트의 시각 자료를 정한다, **Then** 같은 그림을 복제하지 않고 특정 판단을 확대하거나 `없음`을 선택한다

---

### User Story 5 - 완료된 작업물과 공부 기록의 연결 글을 먼저 정돈한다 (Priority: P1)

포트폴리오 운영자는 새 기준을 한꺼번에 전체 글에 적용해 인터뷰 전 내용을 바꾸지
않고, 이미 구조화된 하네스·한마음·블랙스톤의 연결 인사이트와 기존 공부 기록에
연결된 기술 탐구형 인사이트부터 안전하게 점검하고 싶다.

**Why this priority**: 점진 적용은 기존 사실을 추측으로 재작성하는 위험을 줄이면서도
새 규칙이 실제 콘텐츠에서 작동하는지 검증할 수 있다.

**Independent Test**: 우선 대상 작업물 3개 및 공부 기록 1개와 직접 연결된 인사이트
8개의 정확한 목록, 유형, 연결, 사실 정합성, 중복과 시각 자료 판정을 확인하고 나머지
공개 본문과 경로가 보존되는지 검사한다.

**Acceptance Scenarios**:

1. **Given** 하네스 작업물과 연결된 인사이트, **When** 우선 점검 범위를 확인한다, **Then** 대표 발전 서사와 Jenkins·Infisical·Cloudflare 관련 글 4개가 모두 포함된다
2. **Given** 한마음 작업물, **When** 연결 인사이트를 확인한다, **Then** 77만 자 검색 최적화 글 1개가 포함되고 상세와 검색 사실을 다르게 주장하지 않는다
3. **Given** 블랙스톤 작업물, **When** 연결 인사이트를 확인한다, **Then** API Key와 BFF 글 1개가 포함되고 신규 구축·발견 경위를 상세와 다르게 주장하지 않는다
4. **Given** `ai-dx-harness-starter-kit` 공부 기록, **When** 연결 인사이트를 확인한다, **Then** Vercel 비용 분석 글 1개가 기술 탐구형 계약과 공부 기록 왕복 연결을 검증한다
5. **Given** `the-siena-golf-reservation` 후속 인터뷰와 승인 문안, **When** 현재 적용 범위를 확인한다, **Then** 로그 분리 인사이트 1개가 `project-case`와 해당 작업물의 양방향 연결로 포함된다
6. **Given** 아직 인터뷰하지 않은 작업물과 연결 인사이트, **When** 이번 변경이 완료된다, **Then** 현재 적용 대상 밖 10개의 기존 본문과 공개 경로가 그대로 유지된다

### Edge Cases

- 인사이트가 작업물과 공부 기록 양쪽에 연결돼 있으면 글의 실제 출발점을 기준으로
  하나를 선택하고, 함께 읽을 기록은 관련 링크로만 제공한다.
- 프로젝트 사례형인데 유효한 작업물 연결이 없으면 독립 예외로 우회하지 않고 분류나
  연결을 바로잡기 전까지 완료로 처리하지 않는다.
- 기술 탐구형인데 공부 기록 연결이 없으면 독립 유지 이유가 필요한지 검토하며, 이유가
  없으면 억지 연결 대신 통합·비공개 후보로 남긴다.
- 기존 인사이트의 제목과 목차가 공통 문구와 다르더라도 필수 의미를 충족하면 제목을
  바꾸지 않는다.
- 시각 자료 판정이 `없음`이어도 근거가 있으면 정상적인 완료 상태다.
- 시각 자료가 필요하다고 판단했지만 확인된 관계나 데이터가 부족하면 추측으로 그림을
  만들지 않고 근거 확보가 필요한 상태로 남긴다.
- 작업물 정정이 연결 인사이트와 충돌하면 기존 인사이트를 보존하는 대신 인터뷰와
  feature 근거에 맞춰 함께 정정한다.
- 일반적인 기술 권장사항을 당시 구현 사실이나 검토한 대안으로 바꾸지 않는다.
- 기존 공개 글을 통합하거나 비공개로 바꾸는 결정이 필요하면 이번 feature에서
  자동으로 삭제하지 않고 별도 사용자 승인을 받는다.

## Requirements *(mandatory)*

### Functional Requirements

#### 공통 작성 기준

- **FR-001**: 프로젝트는 Claude Code와 Codex가 모두 발견할 수 있는 하나의 포트폴리오 콘텐츠 작성 기준을 제공해야 한다
- **FR-002**: 공통 기준은 작업물·인사이트·공부 콘텐츠를 작성, 수정, 이전 또는 검토할 때 상세 작성 절차를 사용하도록 안내해야 한다
- **FR-003**: 상세 작성 절차는 인터뷰 근거, 해당 feature 기록, 공통 콘텐츠 기준, 기존 공개 본문의 우선순위를 이 순서로 적용해야 한다
- **FR-004**: 상세 작성 절차는 근거 확인, 콘텐츠 유형 판정, 출처 연결 확인, 의미 계약 적용, 시각 자료 필요성 판정, 중복·사실 충돌 검사와 공개 검증을 포함해야 한다
- **FR-005**: 공통 기준과 상세 절차는 프로젝트가 소유하고, 외부 공용 도구의 업데이트로 덮어쓰거나 다른 프로젝트로 전파되지 않아야 한다
- **FR-006**: 공통 기준과 상세 절차의 규칙 문장은 두 지원 에이전트가 동일한 의미로 해석할 수 있어야 한다

#### 작업물과 인사이트의 역할

- **FR-007**: 작업물 상세는 문제, 역할, 선택, 핵심 구현, 결과와 회고를 빠르게 판단하는 주 진입점 역할을 유지해야 한다
- **FR-008**: 공부 기록은 학습 질문, 참고 자료와 실험, 이해 변화와 적용 기준을 기록하는 역할을 유지해야 한다
- **FR-009**: 인사이트는 작업물 또는 공부 기록에서 나온 하나의 질문을 더 깊게 분석하고 다른 상황에 적용할 판단 기준을 제공해야 한다
- **FR-010**: 작업물과 연결 인사이트는 같은 장문을 반복하지 않아야 하며, 작업물은 전체 판단을 요약하고 인사이트는 특정 질문을 확장해야 한다
- **FR-011**: 남은 작업물은 인터뷰, 구조화 상세, 인사이트 후보 판정, 연결 인사이트 작성·정정과 교차 검증을 하나의 feature 범위로 진행해야 한다
- **FR-012**: 작업물마다 같은 수의 인사이트를 강제하지 않아야 하며 각 인사이트는 독립된 질문과 근거를 가져야 한다

#### 인사이트 유형과 연결

- **FR-013**: 새로 작성하거나 공통 계약으로 점검된 인사이트는 `프로젝트 사례형`과 `기술 탐구형` 두 유형 중 하나로 분류되어야 한다
- **FR-014**: 두 유형은 핵심 질문과 결론, 배경과 문제의식, 제약과 판단 기준, 분석 또는 해결 과정, 결과 또는 적용 기준, 한계와 회고, 관련 기록이라는 공통 의미 계약을 충족해야 한다
- **FR-015**: 공통 의미 계약은 의미의 존재를 요구하되 모든 글에 같은 Markdown 제목이나 같은 순서를 강제하지 않아야 한다
- **FR-016**: 프로젝트 사례형은 역할과 책임, 실제 문제와 당시 시점, 제약, 실제 선택과 구현, 결과 근거, 확인하지 못한 범위와 회고를 제공해야 한다
- **FR-017**: 프로젝트 사례형은 존재하는 작업물 하나에 연결되어야 하며 독립 유지 이유로 연결 요구를 우회하지 않아야 한다
- **FR-018**: 기술 탐구형은 학습 질문, 참고 자료와 직접 실험의 구분, 개념·대안 비교, 적용하기 좋은 조건과 피해야 할 조건, 한계와 추가 검증 범위를 제공해야 한다
- **FR-019**: 기술 탐구형은 존재하는 공부 기록 연결을 원칙으로 하고, 연결 근거가 없는 예외만 비어 있지 않은 독립 유지 이유를 가져야 한다
- **FR-020**: 작업물 또는 공부 기록과 연결된 인사이트는 양쪽 공개 화면에서 서로 탐색할 수 있어야 한다
- **FR-021**: 존재하지 않는 작업물·공부 기록·인사이트 연결은 허용하지 않아야 한다
- **FR-022**: 출처와 독립 유지 이유가 모두 없는 기술 탐구형은 통합 또는 비공개 검토 대상으로 식별해야 한다

#### 사실과 근거

- **FR-023**: 작업물과 연결 인사이트는 역할, 수치, 기준 시점, 문제 원인, 검토 대안과 결과에 대해 하나의 사실 계약을 공유해야 한다
- **FR-024**: 확인하지 않은 수치·비율·대안·원인·운영 결과를 새로 만들지 않아야 한다
- **FR-025**: 사용자 보고값, 직접 측정값과 계산값은 구분되어야 하고 수치에는 기준 시점, 근거 설명과 필요한 관찰 한계가 제공되어야 한다
- **FR-026**: 전달받은 원인은 직접 규명한 사실과 구분하고, 당시 사실과 현재 상태가 다르면 시점을 분리해야 한다
- **FR-027**: 일반적인 모범 사례는 당시 구현 사실이나 실제 검토한 대안으로 표현되지 않아야 한다
- **FR-028**: 작업물의 사실 정정이 연결 인사이트에 영향을 주면 같은 feature에서 함께 정정해야 한다

#### 시각 증거

- **FR-029**: 우선 점검 대상 인사이트마다 시각 자료 필요성 판정과 판정 이유가 존재해야 한다
- **FR-030**: 시각 자료 판정은 `없음`, 스윔레인·시퀀스, ERD, 아키텍처·데이터 흐름, 상태 전이, 비교표·결정 매트릭스, 타임라인을 구분할 수 있어야 한다
- **FR-031**: 세 개 이상의 구성요소, 정상과 실패·복구 경로, 데이터 관계·소유권 경계, 세 개 이상의 대안 또는 시간에 따른 발전이 핵심일 때 적합한 시각 자료를 우선 검토해야 한다
- **FR-032**: 단순한 순차 설명으로 충분한 글은 `없음`을 유효한 판정으로 사용할 수 있어야 한다
- **FR-033**: 시각 자료가 있으면 답하려는 질문, 관계, 정상·예외 또는 선택·기각 구분, 텍스트 설명과 연결 작업물의 자료를 중복하지 않는 이유를 제공해야 한다
- **FR-034**: 시각 자료에 필요한 사실 근거가 부족하면 추측으로 관계를 만들지 않아야 한다

#### 점진 적용과 보존

- **FR-035**: 현재 적용 범위는 하네스 연결 글 4개, The Siena 로그 분리 글 1개, 한마음 연결 글 1개, 블랙스톤 연결 글 1개와 `ai-dx-harness-starter-kit` 공부 기록 연결 글 1개인 정확히 8개의 인사이트여야 한다. The Siena 항목은 2026-08-26 사용자 승인 후속으로 초기 7개 범위를 확장한 것이다.
- **FR-036**: 현재 적용 대상 8개는 유형, 유효한 연결, 공통·유형별 의미, 출처 기록과의 사실 정합성, 중복과 시각 자료 필요성을 모두 점검해야 한다
- **FR-037**: 첫 적용 대상의 기존 글은 새 계약에 필요한 경우만 수정하고 같은 목차를 만들기 위한 전면 재작성은 하지 않아야 한다
- **FR-038**: 아직 인터뷰하지 않은 작업물과 연결 인사이트의 기존 본문은 후속 feature까지 보존해야 한다
- **FR-039**: 기존 작업물·공부·인사이트 공개 경로를 변경하거나 제거하지 않아야 한다
- **FR-040**: 통합 또는 비공개 후보를 자동으로 삭제하지 않고 별도 사용자 승인 대상으로 남겨야 한다

#### 검증

- **FR-041**: 상세 작성 절차는 작업물만 수정하고 연결 인사이트를 누락하는 상황, 동일 목차 강제, 공부 기록과 인사이트 중복, 근거 없는 독립 유지, 불필요한 시각 자료, 사실 불일치 상황을 포함한 대표 평가를 가져야 한다
- **FR-042**: 각 대표 평가는 상세 작성 절차가 없는 기준 결과와 절차를 사용한 결과를 함께 남겨야 한다
- **FR-043**: 상세 작성 절차를 사용한 결과는 유형, 출처, 의미 계약, 시각 자료 판단, 교차 검증과 근거 보존 요구를 모두 충족해야 한다
- **FR-044**: 구현 작업 목록에는 테스트를 먼저 작성하고 예상한 이유로 실패를 확인한 뒤 최소 변경으로 통과시키는 TDD 단계가 포함되어야 한다
- **FR-045**: 사용자에게 보이는 콘텐츠 흐름이 변경되므로 공개 경로, 양방향 연결과 좁은 화면을 포함한 브라우저 검증 증거를 남겨야 한다

### Key Entities

- **포트폴리오 콘텐츠 작성 기준**: 두 지원 에이전트가 항상 적용하는 핵심 불변 조건과 상세 작성 절차의 사용 조건
- **상세 작성 절차**: 근거 확인부터 유형·연결·의미·시각 자료·교차 검증까지 반복 수행하는 프로젝트 전용 작성 지침
- **인사이트 유형**: 프로젝트 사례형 또는 기술 탐구형이라는 글의 목적 분류
- **출처 연결**: 인사이트가 출발한 작업물 또는 공부 기록과의 유효한 관계
- **독립 유지 이유**: 공부 기록에 연결할 근거가 없는 기술 탐구형을 독립 글로 유지하는 명시적 근거
- **시각 자료 판정**: 자료 필요 여부, 선택 유형, 판정 이유와 자료가 있을 때의 대체 설명·중복 방지 근거
- **사실 계약**: 작업물과 연결 인사이트가 공유하는 역할, 수치, 시점, 원인, 검토 대안과 결과의 확정 범위
- **우선 점검 집합**: 하네스·The Siena·한마음·블랙스톤 작업물 및 기존 공부 기록 하나와 직접 연결된 8개 인사이트의 정확한 목록
- **작성 절차 평가**: 같은 콘텐츠 상황에서 상세 절차가 없는 결과와 적용한 결과를 비교하는 검증 기록

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Claude Code와 Codex 두 환경 모두 새 세션에서 동일한 포트폴리오 작성 기준과 상세 작성 절차를 발견할 수 있다
- **SC-002**: 대표 평가 6개가 기준 결과와 상세 절차 적용 결과를 모두 보유하고, 적용 결과는 각 평가의 필수 판정 항목을 100% 충족한다
- **SC-003**: 우선 점검 대상이 하네스 4개, The Siena 1개, 한마음 1개, 블랙스톤 1개, 공부 기록 연결 1개인 정확히 8개이며 누락이나 추가가 0개다
- **SC-004**: 우선 점검 대상 8개의 100%가 승인된 인사이트 유형, 유효한 출처 연결과 시각 자료 필요성 판정 이유를 가진다
- **SC-005**: 우선 점검 대상 8개와 연결 작업물 또는 공부 기록 사이에 확정된 역할·수치·시점·원인·대안·결과 충돌이 0건이다
- **SC-006**: 우선 점검 대상에서 작업물 본문을 장문으로 반복하거나 불필요한 동일 다이어그램을 복제한 사례가 0건이다
- **SC-007**: 존재하지 않는 작업물·공부 기록·인사이트를 가리키는 내부 연결이 0건이고, 적용 대상의 양방향 연결 성공률이 100%다
- **SC-008**: 기존 작업물 8개와 현재 공개 중인 인사이트 18개의 경로가 모두 유지되며, 인터뷰 전 작업물과 연결 글의 본문 손실이 0건이다
- **SC-009**: 시각 자료가 없는 적용 대상도 판정 이유를 100% 제공하고, 시각 자료가 있는 적용 대상은 텍스트 설명을 100% 제공한다
- **SC-010**: 지원 화면 너비에서 인사이트 목록·상세와 관련 기록 탐색 중 문서 전체 가로 넘침이 0건이다

## Assumptions

- 승인된 설계 문서 `docs/superpowers/specs/2026-08-25-portfolio-content-authoring-design.md`가 이 명세의 입력 근거다.
- 현재 공개 중인 인사이트는 18개이며, 현재 적용 대상 8개 외의 10개는 본문과 기존 분류를 이번 feature에서 전면 재작성하지 않는다. 초기 7개/11개 수치는 후속 Siena 승인이 일어나기 전 RED·실행 증거의 역사적 범위다.
- 프로젝트 사례형은 작업물 연결이 필수이고 독립 유지 예외를 허용하지 않는다.
- 기술 탐구형은 공부 기록 연결을 원칙으로 하되, 근거가 없는 기존 독립 기술 글만 명시적 이유와 함께 예외로 유지할 수 있다.
- 인사이트 유형은 글의 출발점과 목적을 표현하며 태그나 기술 분야 분류를 대체하지 않는다.
- 시각 자료 `없음`은 실패나 미완료 상태가 아니라 근거가 있는 정상 판정이다.
- 기존 공개 경로의 삭제, redirect, 통합과 비공개 전환은 별도 사용자 승인 없이는 수행하지 않는다.
- 아직 인터뷰하지 않은 작업물은 현재 legacy 본문을 유지하며 후속 feature에서 하나씩 이전한다. The Siena는 2026-08-26 후속 인터뷰·명시적 공개 문안 승인으로 이 가정의 예외가 아니라 현재 승인 적용 대상이다.
- 저장소 전역 검사에 기존 baseline 문제가 있으면 변경 범위 검사와 관련 빌드·브라우저 검증을 완료하고, 관련 없는 파일을 포맷하지 않는다.
