# Feature Specification: 행사 호텔 예약·결제 통합 플랫폼 구조화 상세

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-09-15

**Status**: Draft

**Input**: 2026-09-15 사용자 인터뷰와 두 원본 저장소의 `dev` 브랜치에서 승인·확인된 행사 호텔 예약·결제 통합 플랫폼을 공통 구조화 상세로 이전한다. 고객사 UAT 흐름과 Core Product 관계를 시각화하고, 연결된 인사이트를 사실에 맞게 3건으로 정리하며 기존 공개 경로를 보존한다. 작업 목록에는 테스트 우선 개발(TDD) 항목을 포함한다.

## Context

`integrated-reservation-platform`은 현재 공개 목록과 상세 경로가 있지만 장문 본문만 제공한다. 본문에는 실제와 다른 단일 트랜잭션·결제 보상 성과, 근거 없는 JOIN 단계 수치, 과도한 BFF·Cloudflare 결과와 Middleware 선택의 회고가 포함되어 있다. 연결 인사이트 4건도 작업물과 같은 사실 계약으로 다시 검토해야 하며, 그중 BFF 인사이트 2건은 내용이 중복된다.

승인된 인터뷰:
`docs/portfolio-interviews/2026-09-15-integrated-reservation-platform.md`

핵심 공개 경계는 다음과 같다.

- 프로젝트는 기존 시스템 교체가 아니라 행사별 호텔 예약·결제 운영을 위한 신규 구축이며, 2025년 12월 요구사항·설계부터 2026년 3월까지 진행됐다.
- 사용자는 1인 백엔드로 전반을 담당하면서 PM·PL을 겸임해 고객사 요구사항·일정과 FE 3명의 우선순위·분담·API 계약을 조율했다.
- 고객사는 스테이징에서 행사 생성부터 호텔·객실·재고 등록, 사용자 조회·예약·PG 테스트 결제, 관리자 확인·취소까지 UAT로 검증했다.
- 프로젝트는 고객사 측 사업 여건으로 보류됐으며 정식 운영, 운영 결제와 운영 지표는 없다.
- Core Product 구조와 `version` 기반 재고 충돌 감지는 구현됐지만 실제 병렬 DB 통합 테스트와 불일치 0건을 주장하지 않는다.
- PG 승인 실패 시 차감 재고의 즉시 복구는 미완성이므로 단일 원자적 트랜잭션이나 완성된 보상 흐름으로 서술하지 않는다.
- 실제 도메인은 `A-domain.com`, `api.A-domain.com`으로 익명화하고, Next.js reverse proxy와 Cloudflare 고정 IP 허용 대응의 스테이징 범위만 공개한다.
- Middleware 선택은 Express 경험에서 출발했으며 현재는 Global Auth Guard를 기본 적용하는 구성이 더 알맞다는 회고로 정정한다.
- 비밀번호 전송용 클라이언트 암호화는 구현 후 제거했지만 예약 임시 데이터용 AES까지 전부 제거했다고 쓰지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채용 담당자가 실제 역할과 완료 범위를 이해한다 (Priority: P1)

채용 담당자가 작업물 상세를 열었을 때 1인 백엔드와 PM·PL로 수행한 책임, 고객사 UAT까지 완료한 핵심 객실 예약 흐름, 보류 시점의 미완성 범위와 운영되지 않은 상태를 과장 없이 구분해 이해한다.

**Why this priority**: 역할과 결과가 가장 먼저 정확해야 설계 판단과 회고가 신뢰를 얻고, 고객사 사정으로 보류된 프로젝트가 기술 실패나 운영 성과로 잘못 읽히지 않는다.

**Independent Test**: 작업물 상세의 역할, 기간, 상태, 문제, 제약, 구현, 결과와 회고를 승인 인터뷰와 항목별로 대조한다.

**Acceptance Scenarios**:

1. **Given** 작업물 상세, **When** 역할을 읽는다, **Then** 1인 백엔드와 고객사·FE 협업을 포함한 PM·PL 책임이 구분된다
2. **Given** 기간과 상태, **When** 프로젝트 결과를 읽는다, **Then** `2025.12 – 2026.03`, 고객사 UAT, 고객사 측 사업 여건에 따른 보류와 비운영 상태가 함께 드러난다
3. **Given** 결과 섹션, **When** 검증 범위를 판단한다, **Then** PG 테스트 환경과 실제 운영 결제가 명확히 구분된다
4. **Given** 미완성 범위, **When** 결제 실패 흐름을 읽는다, **Then** 재고 즉시 복구가 완료된 성과로 표현되지 않는다

---

### User Story 2 - 독자가 도메인 구조와 예약·결제 흐름을 시각적으로 이해한다 (Priority: P1)

독자가 작업물의 스윔레인과 관계 다이어그램을 통해 운영자의 행사·재고 설정부터 사용자의 예약·결제와 관리자 확인·취소까지의 책임 경계, 공통 Product와 객실·관광·주문·재고 관계를 이해한다.

**Why this priority**: 순차적인 사용자 흐름과 데이터 관계는 서로 다른 질문이며, 두 시각 자료가 있어야 장문을 반복하지 않고 핵심 설계를 검증할 수 있다.

**Independent Test**: 스윔레인의 정상·예외 흐름과 관계 다이어그램의 엔터티·관계를 승인 인터뷰 및 텍스트 설명과 대조한다.

**Acceptance Scenarios**:

1. **Given** 작업물 스윔레인, **When** 정상 경로를 따라간다, **Then** 행사·재고 등록, 사용자 조회·예약, PG 테스트 승인, 관리자 확인·취소 순서를 이해한다
2. **Given** 재고 충돌, **When** 예외 경로를 따라간다, **Then** 조건부 갱신 실패가 재시도 안내로 이어지는 위치를 이해한다
3. **Given** PG 승인 실패, **When** 예외 경로를 따라간다, **Then** 주문·결제 실패 기록과 재고 자동 복구 미완성 범위가 구분된다
4. **Given** Core Product 관계 다이어그램, **When** 상품과 주문 관계를 읽는다, **Then** 객실·관광의 세부 모델과 공통 주문 참조를 혼동하지 않는다
5. **Given** 시각 자료를 볼 수 없는 독자, **When** 동등한 텍스트 설명을 읽는다, **Then** 같은 흐름과 관계 및 한계를 이해한다

---

### User Story 3 - 연결 인사이트가 실제 경험과 현재 판단을 분리한다 (Priority: P1)

독자가 작업물과 연결 인사이트를 오가며 Middleware·Guard, BFF·쿠키·Cloudflare, HTTPS·비밀번호 전송이라는 세 질문을 각각 깊게 읽고 당시 구현과 현재 개선 판단을 구분한다.

**Why this priority**: 기존 글은 합리화된 당시 판단, 중복 BFF 설명과 검증되지 않은 일반화를 포함하므로 같은 사실 계약 안에서 정정해야 한다.

**Independent Test**: 작업물과 세 인사이트의 역할, 원인, 구현, 결과, 현재 판단, 시각 자료와 양방향 링크를 서로 대조한다.

**Acceptance Scenarios**:

1. **Given** Middleware·Guard 인사이트, **When** 결론을 읽는다, **Then** Express에 익숙해 Middleware를 선택한 당시 배경과 현재의 Global Guard 개선 판단이 구분된다
2. **Given** BFF 인사이트, **When** 네트워크 경계를 읽는다, **Then** 브라우저 직접 호출의 쿠키 실패, reverse proxy 전환과 Cloudflare 고정 IP 허용 대응이 순서대로 드러난다
3. **Given** 기존 BFF 인사이트 주소 2개, **When** 어느 주소로 접근한다, **Then** 중복되지 않은 통합 인사이트를 계속 읽을 수 있다
4. **Given** HTTPS 인사이트, **When** 암호화 범위를 읽는다, **Then** 비밀번호 전송용 클라이언트 암호화 제거와 예약 임시 데이터용 AES 유지가 구분된다
5. **Given** 작업물 또는 인사이트 상세, **When** 출처 링크를 활성화한다, **Then** 의미 있는 링크 이름으로 연결 기록에 이동하고 다시 돌아올 수 있다

---

### User Story 4 - 기존 공개 경로와 주변 콘텐츠가 회귀 없이 유지된다 (Priority: P2)

독자가 기존 작업물·인사이트 주소와 공개 목록을 계속 사용하고, 지원 화면 크기와 키보드 환경에서 구조화 본문과 시각 자료를 읽고 이동할 수 있다.

**Why this priority**: 구조화 이전과 인사이트 통합이 기존 북마크, 목록, 연결 관계, 공통 시각 계약 또는 완료된 다른 작업물의 표현을 깨뜨리면 안 된다.

**Independent Test**: 기존 작업물 및 인사이트 경로, 공개 목록 진입, 키보드 이동, 지원 화면 크기와 완료된 구조화 상세를 실제 화면에서 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 작업물과 인사이트 주소, **When** 각각 연다, **Then** 승인된 콘텐츠 또는 호환 연결로 정상 응답한다
2. **Given** 공개 작업물·인사이트 목록, **When** 대상 항목을 활성화한다, **Then** 올바른 구조화 상세 또는 통합 인사이트로 이동한다
3. **Given** 키보드 사용자, **When** 작업물·인사이트 링크와 시각 자료 확대 기능을 탐색한다, **Then** 초점을 확인하고 기능을 활성화할 수 있다
4. **Given** 320·768·1024·1440px 화면, **When** 본문과 시각 자료를 읽는다, **Then** 문서 전체 가로 넘침과 핵심 텍스트 잘림 없이 내용을 확인할 수 있다

### Edge Cases

- 고객사 자금 문제가 구체적으로 노출되는가? → `고객사 측 사업 여건`으로만 공개한다.
- `On Hold`가 현재도 개발 중이라는 뜻으로 읽히는가? → 2026년 3월 보류와 미운영 상태를 함께 설명한다.
- 2026년 4월 프론트엔드 의존성 수정이 개발 기간 연장으로 읽히는가? → 공개 기간은 승인된 `2025.12 – 2026.03`을 유지한다.
- 프론트엔드 개발자의 백엔드 커밋 1건 때문에 1인 백엔드 서술이 거짓이 되는가? → 일시적 기여와 전체 책임 범위를 구분한다.
- 고객사 UAT가 운영 검증이나 실제 PG 결제로 읽히는가? → 스테이징 및 PG 테스트 환경을 함께 표시한다.
- Core Product가 임의의 모든 상품으로 무변경 확장된다고 읽히는가? → 객실·관광 통합 범위로 제한한다.
- 기억나지 않는 JOIN 단계 수치가 다시 등장하는가? → 단계 수치와 성능 개선률을 모두 제외한다.
- 단위 테스트가 실제 병렬 DB 통합 테스트나 불일치 0건으로 확대되는가? → 성공·충돌 분기 검증으로만 설명한다.
- PG 승인 실패가 주문 상태만 바꾸고 재고를 복구하지 않는 사실이 숨겨지는가? → 보류 시점의 미완성 범위를 결과와 회고에 명시한다.
- Next.js rewrite가 응답 가공·성능 최적화까지 갖춘 완성형 BFF로 표현되는가? → reverse proxy로 BFF 경계를 만든 단계로 제한한다.
- 실제 회사 도메인이나 서버 IP가 노출되는가? → 익명 도메인과 역할 수준의 설명만 사용한다.
- Middleware를 충분한 비교 끝에 Guard보다 선택한 것으로 읽히는가? → Express 경험에서 출발했고 현재는 Global Guard를 선호한다는 변화를 밝힌다.
- 비밀번호 클라이언트 암호화 제거가 모든 브라우저 저장 데이터의 암호화 제거로 읽히는가? → 비밀번호 전송 범위로 한정한다.
- BFF 통합 전의 두 공개 주소 중 하나가 사라지는가? → 기존 주소 모두 호환 연결을 제공한다.
- 작업물과 인사이트 시각 자료가 같은 흐름을 반복하는가? → 각 시각 자료의 질문과 필요성 판정을 검증한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 작업물 구조화 상세와 근거

- **FR-001**: 행사 호텔 예약·결제 작업물은 기존 구조화 상세와 같은 공통 읽기 순서로 제공되어야 한다
- **FR-002**: 작업물의 기존 공개 경로와 공개 목록 항목을 유지해야 한다
- **FR-003**: 제목은 행사 단위의 호텔 예약·결제 신규 구축임을 드러내야 한다
- **FR-004**: 기간은 `2025.12 – 2026.03`, 상태는 고객사 측 사업 여건에 따른 `On Hold`로 표시해야 한다
- **FR-005**: 고객사의 구체적인 자금 상황을 공개하지 않아야 한다
- **FR-006**: 역할은 1인 백엔드의 전반 책임과 고객사 요구사항·일정 및 FE 3명의 우선순위·분담·API 계약을 조율한 PM·PL 책임을 함께 설명해야 한다
- **FR-007**: 프론트엔드 개발자의 일시적 백엔드 기여 1건을 공동 백엔드 담당자나 사용자의 단독 구현 과장으로 왜곡하지 않아야 한다
- **FR-008**: 공개 근거에는 고객사 스테이징 UAT, PG 테스트 환경, 비운영 상태의 근거 종류·기준 시점·관찰 한계를 제공해야 한다
- **FR-009**: 고객 거래 데이터, 실제 회사 도메인·서버 IP, 인증값, 시크릿, 비공개 소스와 고객사 자금 세부 상황을 공개하지 않아야 한다

#### Core Product와 재고·결제 구현

- **FR-010**: 공통 Product가 객실과 관광 세부 모델을 같은 주문·결제 구조에 연결한 목적을 설명해야 한다
- **FR-011**: 주문 항목이 공통 상품을 참조하고 객실 재고가 객실·옵션을 직접 참조하는 관계를 설명해야 한다
- **FR-012**: 확인되지 않은 JOIN 단계 수치, 성능 개선률, 임의 상품의 무변경 확장과 다른 작업물의 구조를 이 작업의 성과로 주장하지 않아야 한다
- **FR-013**: 재고의 버전을 조건으로 갱신하고 갱신 건수가 0이면 충돌로 처리한 구현을 설명해야 한다
- **FR-014**: 재고 충돌 검증을 단위 테스트의 정상·충돌 분기 확인 범위로 제한해야 한다
- **FR-015**: 실제 병렬 DB 통합 테스트, 불일치 0건, 초과 예약 완전 방지 또는 운영 정합성을 주장하지 않아야 한다
- **FR-016**: 주문·재고의 사전 기록, 외부 PG 승인, 주문·결제 확정이 서로 다른 단계였음을 설명해야 한다
- **FR-017**: 예약·결제·재고를 하나의 DB 트랜잭션에 묶었다고 표현하지 않아야 한다
- **FR-018**: 최종 내부 반영 실패 시 PG 취소 시도는 구현 범위로, PG 승인 실패 시 차감 재고의 즉시 복구는 미완성 범위로 구분해야 한다
- **FR-019**: 고아 재고 0건이나 완성된 보상 흐름을 주장하지 않아야 한다

#### BFF·Cloudflare와 인증 회고

- **FR-020**: 실제 주소 대신 `A-domain.com`과 `api.A-domain.com`을 사용하고 같은 기본 도메인의 서로 다른 Origin 관계로 설명해야 한다
- **FR-021**: 브라우저의 API 직접 호출에서 쿠키 저장·전달 실패를 실제 확인한 사실을 설명해야 한다
- **FR-022**: Next.js reverse proxy가 브라우저 요청 Origin을 프론트엔드로 통일한 경계를 설명해야 한다
- **FR-023**: reverse proxy를 응답 가공·프론트 전용 정책·검증된 성능 개선까지 갖춘 완성형 BFF로 표현하지 않아야 한다
- **FR-024**: BFF 서버 요청의 Cloudflare 차단 원인을 사용자가 직접 확인하고 고정 IP 허용 규칙으로 스테이징 통신을 복구한 범위를 설명해야 한다
- **FR-025**: Cloudflare 대응을 전 환경, 운영 장애나 운영 성과로 확대하지 않아야 한다
- **FR-026**: 당시 Middleware 선택이 Express 경험에서 출발했으며 NestJS 권장 패턴을 충분히 비교한 결론은 아니었음을 설명해야 한다
- **FR-027**: 당시의 인증 Middleware와 관리자 등급 Guard 책임을 구분해야 한다
- **FR-028**: 현재 개선 판단은 Global Auth Guard로 인증을 기본 적용하고 공개 경로를 제외하며 세부 권한 Guard를 분리하는 방향으로 설명해야 한다
- **FR-029**: Middleware가 Guard보다 항상 견고하거나 인증 선언 누락을 완전히 제거했다는 결론을 사용하지 않아야 한다

#### 결과와 회고

- **FR-030**: 고객사 UAT의 핵심 흐름을 행사 생성, 호텔·객실·재고 등록, 사용자 조회·예약·PG 테스트 결제, 관리자 확인·취소 순서로 설명해야 한다
- **FR-031**: 관광 예약, 결제 링크, 일부 엑셀·문서 기능이 보류 시점에 미완성이었음을 핵심 객실 예약 UAT와 구분해야 한다
- **FR-032**: 정식 운영, 실제 결제, 운영 건수, 운영 장애율, 성능 개선률 또는 전환율을 주장하지 않아야 한다
- **FR-033**: 회고는 외부 결제의 실패 지점별 상태 전이·보상·재시도·운영자 확인 절차, 실제 DB 동시성 통합 테스트와 인증 기본 거부 구조를 다음 개선으로 다뤄야 한다

#### 작업물 시각 자료

- **FR-034**: 작업물은 고객사 UAT 핵심 흐름을 보여 주는 스윔레인 정확히 하나를 제공해야 한다
- **FR-035**: 스윔레인은 고객사 운영자, 사용자, 프론트엔드 경계, API·데이터 경계와 PG 테스트 환경을 구분해야 한다
- **FR-036**: 스윔레인은 정상 UAT 경로, 재고 버전 충돌과 PG 승인 실패를 구분해야 한다
- **FR-037**: PG 승인 실패 예외는 주문·결제 실패 기록과 재고 자동 복구 미완성 범위를 숨기지 않아야 한다
- **FR-038**: 작업물은 공통 Product, 객실, 관광, 주문 항목과 객실 재고의 승인된 관계만 보여 주는 소형 관계 다이어그램을 제공해야 한다
- **FR-039**: 작업물의 두 시각 자료는 순차 흐름과 데이터 관계라는 서로 다른 질문을 답하고 동등한 텍스트 설명을 제공해야 한다

#### 연결 인사이트와 시각 자료

- **FR-040**: Middleware·Guard 인사이트는 기존 경로를 유지하고 승인된 새 제목·메시지로 다시 작성해야 한다
- **FR-041**: Middleware·Guard 인사이트는 당시 구조와 현재 Global Guard 개선 판단을 비교하는 요청 생명주기 시각 자료를 제공해야 한다
- **FR-042**: 두 BFF 인사이트의 중복 본문은 하나의 프로젝트 사례로 통합해야 한다
- **FR-043**: 통합 BFF 인사이트는 쿠키 실패, reverse proxy, CSRF 방어와 Cloudflare 허용 대응을 실제 발생 순서와 검증 범위로 설명해야 한다
- **FR-044**: 통합 BFF 인사이트는 브라우저 직접 호출과 reverse proxy 이후의 경계를 비교하는 네트워크 시각 자료를 제공해야 한다
- **FR-045**: 통합 전 BFF 인사이트의 기존 공개 주소 2개는 모두 유지하며 기본 통합 인사이트로 도달할 수 있어야 한다
- **FR-046**: BFF 인사이트에서 대기업 일반화, 다른 최상위 도메인, rewrite 스트리밍 성능과 완성형 BFF 주장을 제거해야 한다
- **FR-047**: HTTPS 인사이트는 기존 경로를 유지하고 비밀번호 전송용 클라이언트 암호화의 구현·제거 경험으로 다시 작성해야 한다
- **FR-048**: HTTPS 인사이트는 애플리케이션 Payload와 TLS 전송 구간, 프론트엔드 키 노출, 외부 서비스 확인, 서버 bcrypt 저장을 승인 범위로 설명해야 한다
- **FR-049**: HTTPS 인사이트는 예약 임시 데이터용 AES까지 전부 제거했다고 주장하지 않아야 한다
- **FR-050**: HTTPS 인사이트에는 다이어그램을 의무적으로 추가하지 않고 동등한 텍스트로 경계를 설명해야 한다
- **FR-051**: 작업물은 세 기본 인사이트로, 각 기본 인사이트는 작업물로 돌아가는 의미 있는 양방향 링크를 제공해야 한다
- **FR-052**: 작업물과 인사이트의 장문 및 시각 자료 비중복 판정을 각각 기록해야 한다

#### 접근성·회귀·검증

- **FR-053**: 작업물·인사이트 본문과 시각 자료는 320·768·1024·1440px에서 문서 전체 가로 넘침과 핵심 텍스트 잘림 없이 읽을 수 있어야 한다
- **FR-054**: 시각 자료는 키보드로 접근·확대·종료할 수 있고 의미 있는 텍스트 대안을 제공해야 한다
- **FR-055**: 시각적 관계, 정상·예외 또는 현재·개선 차이를 색상만으로 구분하지 않아야 한다
- **FR-056**: 작업물과 네 인사이트의 기존 경로, 공개 목록, 양방향 링크, 통합 호환 경로와 완료된 구조화 상세의 공통 계약을 실제 화면에서 검증해야 한다
- **FR-057**: 관련 없는 작업물·인사이트의 공개 내용, Feature 013 미완료 상태와 사용자 소유 변경을 수정하거나 다시 포맷하지 않아야 한다
- **FR-058**: 변경 파일에 대한 콘텐츠 계약, 타입, 린트, 프로덕션 빌드와 사용자 흐름 E2E 검증을 수행해야 한다

### Key Entities

- **행사 호텔 예약·결제 작업물 상세**: 역할, 근거 카드, 문제, 제약, 선택, 구현, 고객사 UAT 결과와 회고를 공통 순서로 제공하는 원본 기록
- **UAT 예약·결제 스윔레인**: 운영자의 행사·재고 설정부터 사용자 예약·PG 테스트 결제와 관리자 확인·취소, 재고 충돌·PG 실패를 표시하는 흐름 자료
- **Core Product 관계 다이어그램**: 공통 상품, 객실·관광 세부 모델, 주문 항목과 객실 재고의 승인된 관계를 설명하는 자료
- **Middleware·Guard 인사이트**: Express 경험에서 출발한 당시 구조와 현재 Global Guard 개선 판단을 다루는 프로젝트 사례
- **통합 BFF 인사이트**: 교차 Origin 쿠키 실패, Next.js reverse proxy, CSRF 방어와 Cloudflare 서버 요청 차단 대응을 다루는 프로젝트 사례
- **HTTPS 인사이트**: 비밀번호 전송용 클라이언트 암호화의 구현·제거와 TLS·서버 저장 경계를 다루는 프로젝트 사례
- **호환 인사이트 경로**: 통합되는 기존 BFF 글의 공개 주소를 보존하고 기본 인사이트로 연결하는 관계
- **근거 카드**: 1인 백엔드·PM/PL 책임, 고객사 스테이징 UAT, PG 테스트·비운영 범위의 근거 종류와 한계를 표시하는 정보

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 행사 호텔 예약·결제 작업물 1개가 승인된 문구와 공통 읽기 순서의 구조화 상세로 공개된다
- **SC-002**: 공개하는 근거 카드의 100%가 값, 근거 종류, 기준 시점, 설명과 필요한 관찰 한계를 함께 제공한다
- **SC-003**: JOIN 단계 수치, 불일치·고아 재고 0건, 단일 원자적 트랜잭션, 완성형 BFF, 전 환경 정상화와 운영 성과 주장이 작업물과 연결 인사이트에서 0건이다
- **SC-004**: 작업물 스윔레인 1개가 승인된 정상 UAT 경로 1개와 재고 충돌·PG 승인 실패 예외 2개를 서로 구분하고 동등한 텍스트 설명을 제공한다
- **SC-005**: Core Product 관계 다이어그램 1개가 승인된 핵심 엔터티와 관계만 제공하며 임의 상품 확장이나 확인되지 않은 JOIN 수치를 0건 포함한다
- **SC-006**: 기존 인사이트 4개는 기본 콘텐츠 3개로 정리되고, 기존 공개 주소 4개가 모두 정상 콘텐츠 또는 호환 연결로 응답한다
- **SC-007**: 작업물과 기본 인사이트 3개 사이의 정방향·역방향 출처 링크가 실제 화면과 키보드 환경에서 모두 동작한다
- **SC-008**: Middleware·Guard와 BFF 인사이트는 필요성이 승인된 시각 자료를 각각 1개 제공하고, HTTPS 인사이트는 불필요한 다이어그램 없이 승인된 텍스트 경계를 제공한다
- **SC-009**: 작업물과 인사이트의 장문 중복 및 시각 중복 검토에서 각각 0개의 미해결 중복이 남는다
- **SC-010**: 320·768·1024·1440px에서 대상 본문과 시각 자료를 읽을 수 있고 문서 전체 가로 넘침, 핵심 텍스트 잘림과 색상만으로 전달되는 핵심 관계가 0건이다
- **SC-011**: 대상 작업물·인사이트 경로, 공개 목록, 통합 호환 경로, 완료된 구조화 상세에 대한 관련 회귀 검사가 모두 통과한다
- **SC-012**: 변경 파일 범위의 콘텐츠 테스트, 타입 검사, 린트, 프로덕션 빌드와 사용자 흐름 E2E 검증이 모두 통과한다

## Assumptions

- 승인된 인터뷰 기록이 작업물과 연결 인사이트의 최우선 사실·문구 근거다.
- 두 원본 저장소는 계획 단계의 읽기 전용 보조 근거이며 포트폴리오 빌드나 테스트가 외부 저장소 접근에 의존하지 않는다.
- `CODI-RS-SYSTEM`은 별도 신규 프로젝트이며 이 작업물의 구현·성과 근거로 사용하지 않는다.
- 통합 BFF 인사이트의 기본 공개 경로는 `nextjs-nestjs-domain-separation-and-bff`로 유지하고 `enterprise-bff-architecture-and-cors`는 기본 글로 연결되는 호환 경로로 보존한다.
- 공개 작업물에는 별도 데모 주소를 추가하지 않는다.
- 시각 자료는 승인된 사실 관계만 표현하며 실제 회사 도메인, 서버 IP, 고객 데이터와 인증값을 포함하지 않는다.
- 기존 구조화 상세와 Archify 기반 확대 경험을 재사용하되 Core Product 관계 자료에 필요한 최소한의 공통 표현만 확장한다.
- 저장소 전역 lint의 기존 baseline은 이 기능의 결과로 정리하지 않고 변경 파일만 검사한다.
- 포트 1104의 사용자 소유 개발 서버는 중단하지 않는다. 사용자 흐름 검증은 프로덕션 빌드를 별도 포트에서 실행하고 임시 설정과 프로세스를 종료한다.
- Feature 013의 미완료 T045·T047·T048은 별도 상태로 보존하며 이 기능에서 체크하거나 수정하지 않는다.
