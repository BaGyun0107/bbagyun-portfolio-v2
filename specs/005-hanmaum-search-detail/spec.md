# Feature Specification: 한마음과학원 법문검색 구조화 상세 이전

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-08-24

**Status**: Draft

**Input**: 한마음과학원 법문검색 엔진 작업물을 하네스와 동일한 구조화 상세로 이전하고, 인터뷰(2026-08-24)에서 확인한 사실 오류를 정정한다.

## Context

`hanmaum-science-institute`는 현재 `Feature.content` 장문 마크다운으로만 제공된다.
2026-08-24 인터뷰에서 다음을 확정했다.

- 백엔드 단독 담당이며 기술 선택도 본인 판단이었다. 역할 서술은 낮출 필요가 없다.
- 검색 응답 개선은 브라우저 네트워크 탭 기준으로 동일 검색어를 여러 날짜에 걸쳐
  반복 관측한 값이다.
- 본문에 사실과 다른 서술 두 건이 있다(파싱 대안 비교표, 최소 토큰 길이 강제).
- 제공된 실제 코드에서 예외 롤백과 구분되는 검증 롤백을 확인했다.

인터뷰 전문: `docs/portfolio-interviews/2026-08-24-hanmaum-science-institute.md`

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채용 담당자가 작업물 간 같은 기준으로 비교한다 (Priority: P1)

채용 담당자가 하네스 상세를 읽은 뒤 한마음 상세를 열었을 때, 같은 읽기 순서와
같은 근거 표기 방식을 만난다. 두 작업물을 같은 기준으로 비교할 수 있다.

**Why this priority**: 형식이 통일되지 않으면 독자는 작업물마다 다른 방식으로
정보를 찾아야 하고, 근거 등급이 없는 수치는 검증 없이 주장한 값으로 읽힌다.

**Independent Test**: 한마음 상세 경로에서 하네스와 동일한 공통 제목이 승인된
순서로 렌더링되는지, 결과 지표에 근거 종류와 기준 시점이 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 한마음 작업물 상세 페이지, **When** 페이지를 연다, **Then** 하네스와
   동일한 공통 `h2` 제목이 승인된 읽기 순서로 표시된다
2. **Given** 핵심 결과 요약 영역, **When** 검색 응답 지표를 본다, **Then** 근거
   종류·기준 시점·근거 설명이 함께 표시된다
3. **Given** 검증된 데모 URL이 없는 상태, **When** 페이지 전체를 본다, **Then**
   데모 CTA, 비활성 버튼, "준비 중" 문구가 존재하지 않는다

---

### User Story 2 - 독자가 검증 가능한 근거로 성능 개선을 이해한다 (Priority: P1)

독자가 검색 응답 개선 수치를 볼 때, 그 값이 무엇을 잰 것이고 어떤 조건에서
비교한 것인지 함께 확인한다.

**Why this priority**: 이 수치는 작업물에서 가장 강한 주장이므로 측정 대상이
모호하면 전체 서술의 신뢰도가 떨어진다.

**Independent Test**: 검색 응답 지표의 근거 문구가 측정 도구와 비교 조건을
명시하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검색 응답 지표, **When** 근거 설명을 읽는다, **Then** 브라우저
   네트워크 응답 기준임이 드러나고 DB 쿼리 단독 시간으로 오해되지 않는다
2. **Given** 검색 응답 지표, **When** 근거 설명을 읽는다, **Then** 동일 검색어와
   데이터 전량 적재 조건에서 반복 관측했다는 비교 조건이 드러난다
3. **Given** 적재 소요 시간 정보, **When** 근거 종류를 본다, **Then** 계측 기록이
   아닌 회고 기반임이 구분된다

---

### User Story 3 - 독자가 사실과 일치하는 구현 서술을 읽는다 (Priority: P1)

독자가 파싱·적재 구현과 인덱스 제약 설명을 읽을 때, 실제 구현 및 확인된
기술 사실과 일치하는 내용을 만난다.

**Why this priority**: 사실과 다른 서술은 면접에서 드러나면 다른 작업물의
서술까지 의심받게 만든다.

**Independent Test**: 공개 본문에 사실과 어긋나는 것으로 확인된 서술이 남아
있지 않은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 파싱·적재 서술, **When** 실행 위치를 읽는다, **Then** 서버 업로드
   엔드포인트로 서술되고 로컬 스크립트 채택으로 서술되지 않는다
2. **Given** 인덱스 제약 서술, **When** 최소 토큰 길이 설명을 읽는다, **Then**
   버전이 값을 강제했다고 주장하지 않는다
3. **Given** 외부 검색 엔진 언급, **When** 배제 사유를 읽는다, **Then** 검토 후
   기각이 아니라 비용으로 시도하지 못했다는 사실로 서술된다

---

### User Story 4 - 독자가 실패 대응 흐름을 이해한다 (Priority: P2)

독자가 데이터 적재 과정에서 무엇이 잘못될 수 있고 시스템이 어떻게 대응했는지
이해한다.

**Why this priority**: 정상 경로만 있는 서술은 운영 경험을 보여주지 못한다.
다만 P1 항목이 사실 정확성을 다루는 데 비해 이는 깊이 보강에 해당한다.

**Independent Test**: 예외 롤백과 검증 롤백이 구분되어 서술되는지, 실패 후
대응 방식이 드러나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 적재 서술, **When** 롤백 설명을 읽는다, **Then** 예외 발생 롤백과
   검증 실패 롤백이 서로 다른 장치로 구분된다
2. **Given** 검증 롤백 서술, **When** 도입 경위를 읽는다, **Then** 실패를 겪은
   뒤 원인 지점 파악을 위해 추가했다는 순서가 드러난다
3. **Given** 실패 대응 서술, **When** 수정 대상을 읽는다, **Then** 원본 문서가
   아니라 파싱 규칙을 보완했다는 선택이 드러난다

---

### User Story 5 - 기존 공개 계약이 손상되지 않는다 (Priority: P1)

한마음 작업물을 이전한 뒤에도 하네스 상세와 아직 이전하지 않은 작업물들의
공개 내용이 그대로 유지된다.

**Why this priority**: 회귀가 발생하면 이미 완결한 작업의 신뢰도가 무너진다.

**Independent Test**: 전체 작업물 경로와 유지 대상 인사이트를 확인한다.

**Acceptance Scenarios**:

1. **Given** 전체 작업물 목록, **When** 각 경로를 연다, **Then** 8개 작업물
   경로가 모두 성공한다
2. **Given** 아직 이전하지 않은 6개 작업물, **When** 본문을 확인한다, **Then**
   기존 장문 본문이 보존된다
3. **Given** 하네스 상세, **When** 지표·스윔레인·연결 인사이트를 확인한다,
   **Then** 기존 계약이 유지된다

### Edge Cases

- 구조화 상세를 가진 작업물이 둘로 늘어날 때, "하네스 하나뿐"을 고정한 기존
  테스트와 fixture는 어떻게 되는가? → 새 상태를 정확한 목록으로 다시 고정한다.
  단순히 assertion을 삭제하지 않는다.
- 한마음에 연결된 인사이트가 본문에서도 링크될 때 목록에 중복 노출되는가?
  → 하네스와 동일하게 연결된 인사이트를 사이드바와 본문 하단에 모두 노출한다.
- 스윔레인 다이어그램이 좁은 화면에서 페이지 전체를 넘치게 하는가?
  → 다이어그램 영역 내부에서만 가로 스크롤한다.
- 인터뷰로 복원되지 않은 값(단락 레코드 수)을 어떻게 다루는가? → 추정치를
  만들지 않고 생략한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 구조화 이전

- **FR-001**: 한마음 작업물은 하네스와 동일한 구조화 상세 계약으로 제공되어야 한다
- **FR-002**: 한마음 작업물 상세는 공통 10개 제목을 승인된 읽기 순서로 표시해야 한다
- **FR-003**: 이전 후 한마음의 legacy 장문 본문은 공개 경로에서 중복 제공되지 않아야 한다
- **FR-004**: 아직 이전하지 않은 6개 작업물의 기존 본문은 보존되어야 한다

#### 근거 표기

- **FR-005**: 검색 응답 개선 지표는 측정값으로 표기하고, 근거에 측정 도구와 비교
  조건(동일 검색어, 데이터 전량 적재, 반복 관측)을 명시해야 한다
- **FR-006**: 검색 응답 지표의 근거는 측정 대상이 엔드투엔드 응답임을 밝혀
  데이터베이스 쿼리 단독 시간으로 읽히지 않아야 한다
- **FR-007**: 적재 소요 시간은 계측 기록이 아닌 회고 기반임이 구분되는 근거
  종류로 표기해야 한다
- **FR-008**: 인터뷰로 복원되지 않은 수치는 추정치를 만들지 않고 생략해야 한다

#### 사실 정정

- **FR-009**: 파싱·적재는 서버 업로드 처리로 서술하고, 이를 기각했다고 적은
  대안 비교표는 제거해야 한다
- **FR-010**: 최소 토큰 길이 제약은 버전이 값을 강제했다고 주장하지 않아야 하며,
  낮추려 시도했으나 적용되지 않았고 성공했더라도 기본 토큰화 방식 때문에 한국어
  한 글자 검색은 해결되지 않았을 것이라는 이해를 함께 제공해야 한다
- **FR-011**: 외부 검색 엔진은 검토 후 기각이 아니라 비용 때문에 시도하지 못한
  것으로 서술해야 한다
- **FR-011a**: 작업물 상세에서 직접 연결하는 인사이트도 같은 사실 정정을 반영해야
  한다. 상세와 인사이트가 같은 사실을 다르게 주장해서는 안 된다

#### 실패 흐름

- **FR-012**: 적재 서술은 예외 발생 롤백과 검증 실패 롤백을 서로 다른 장치로
  구분해야 한다
- **FR-013**: 검증 롤백은 실패를 겪은 뒤 원인 지점을 파악하기 위해 추가되었다는
  경위와, 원본 문서가 아닌 파싱 규칙을 보완했다는 대응 방식을 함께 제공해야 한다

#### 선택 증거

- **FR-014**: 검증된 공개 데모 URL이 없으므로 데모 관련 요소를 만들지 않아야 한다
- **FR-015**: 시스템 흐름을 제공하는 경우 정상 경로와 실패·복구 경로를 구분하고,
  흐름을 보지 못하는 독자를 위한 텍스트 설명을 함께 제공해야 한다

#### 회귀 보호

- **FR-016**: 구조화 상세를 가진 작업물 목록과 legacy 본문을 유지하는 작업물
  목록은 새 상태에 맞는 정확한 목록으로 다시 고정되어야 한다
- **FR-017**: 전체 작업물 경로와 하네스의 기존 공개 계약이 유지되어야 한다
- **FR-018**: 연결된 인사이트는 하네스와 동일한 방식으로 노출되어야 한다

### Key Entities

- **작업물 구조화 상세**: 역할, 결과 지표, 문제, 제약, 대안, 시스템 흐름,
  핵심 구현, 결과, 회고를 담는 재사용 계약
- **결과 지표**: 값과 함께 근거 종류, 기준 시점, 근거 설명, 필요 시 유의 범위를
  갖는 항목
- **시스템 흐름**: 주체 구분, 단계, 정상 연결, 예외 연결과 예외 설명을 갖는
  선택적 표현

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 구조화 상세를 가진 작업물이 2개가 되고, 두 상세 모두 동일한 공통
  제목을 동일한 순서로 제공한다
- **SC-002**: 한마음 상세의 모든 수치 지표가 근거 종류와 기준 시점을 100% 포함한다
- **SC-003**: 인터뷰에서 사실과 다르다고 확인된 서술 3건이 공개 경로에 0건 남는다.
  작업물 상세뿐 아니라 상세가 직접 링크하는 인사이트까지 포함해 측정한다
- **SC-004**: 전체 8개 작업물 경로가 모두 성공하고, 이전하지 않은 6개 작업물의
  본문이 이전과 동일하게 보존된다
- **SC-005**: 검증된 데모가 없는 작업물에 데모 관련 요소가 0개 존재한다
- **SC-006**: 320/768/1024/1440px에서 문서 전체 가로 넘침이 발생하지 않는다

## Assumptions

- 한마음에 연결된 기존 인사이트는 **이번 범위에 포함한다** (2026-08-24 리뷰 결과
  반영). 초안에서는 변경하지 않는다고 가정했으나, 리뷰에서 그 인사이트가 이번에
  정정하는 사실 3건을 반대로 주장하고 있음이 확인되었다. 상세 본문에서 직접
  링크하는 글이므로 정정하지 않으면 독자가 링크를 따라가 정정 이전 서술을
  만나게 되어 정정의 실효가 사라진다.
  - 최소 토큰 길이가 "2로 제한"되어 있었다는 서술
  - 외부 검색 엔진 도입을 "고려했다"는 서술
  - "로컬 스크립트로" 마이그레이션했다는 서술과 그것을 전제로 한 회고
- 본문과 인사이트의 역할 분담은 하네스와 동일하게 적용한다. 인사이트는 기술적
  깊이를 담당하되 사실 자체는 상세와 일치해야 한다.
- 시스템 흐름은 두 개를 제공한다(2026-08-24 사용자 확정).
  1. 파싱·적재 실패와 복구 — 코드로 검증된 사실이며 예외 롤백과 검증 롤백이
     서로 다른 장치임을 텍스트보다 명확히 전달한다.
  2. 검색 요청 처리 — 후보군 압축과 정밀 검증의 2단계 역할 분리를 전달한다.
     검색 구현 코드는 확인하지 않았으므로 단계 수준으로만 표현하고, 분기의
     구체적 임계값은 명시하지 않는다.
- 사용자가 제공한 실제 코드는 사실 확인 근거로만 사용하고, 코드 자체나 고객
  데이터는 공개하지 않는다.
