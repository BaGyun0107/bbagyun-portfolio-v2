# Phase 0 Research: 한마음과학원 구조화 상세 이전

**Date**: 2026-08-24

Technical Context에 NEEDS CLARIFICATION 항목은 없다. 인터뷰(2026-08-24)와
사용자 제공 코드로 사실이 확정되었고, 재사용할 계약은 저장소에서 직접 확인했다.
아래는 구현 전에 확정한 결정과 근거다.

## D-001. 렌더러를 신규 개발하지 않고 재사용한다

**Decision**: `ProjectDetailContent`, `ProjectSwimlane`, `ProjectHighlights`,
`ProjectDemoLink`를 그대로 사용한다. 신규 컴포넌트를 만들지 않는다.

**Rationale**: 이 렌더러들은 `FeatureDetailDto`만 받으면 동작하도록 이미
구현·검증되어 있다. 한마음 이전은 데이터 추가 문제이지 표현 문제가 아니다.
컴포넌트를 새로 만들면 형식 통일이라는 목표와 정면으로 어긋난다.

**Alternatives considered**:
- 한마음 전용 렌더러: 기각. 작업물마다 표현이 달라져 비교 가능성이 사라진다.
- 렌더러 일반화 리팩터링: 기각. 현재 계약으로 충분하며 하네스 회귀 위험만 늘린다.

## D-002. 지표 근거 등급을 값별로 분리한다

**Decision**:

| 지표 | 값 | kind | evidence 요지 |
| --- | --- | --- | --- |
| 검색 응답 시간 | 약 1500ms → 약 400ms | `measured` | 브라우저 네트워크 응답 기준. 동일 검색어, 데이터 전량 적재 상태, 구/신 도메인 동시 존재로 직접 비교, 날짜를 달리해 반복 관측 |
| 원문 규모 | 약 77만 자 / 최대 454페이지 | `reported` | 이관 대상 교재 원본 기준 |
| 적재 소요 | 5분 이내 | `reported` | 실행 당시 회고 기준이며 계측 기록 없음 |

**Rationale**: 헌법 원칙 I은 measured/reported/estimated 구분을 요구한다.
검색 응답만 반복 관측과 비교 조건이 확보되어 `measured` 요건을 만족한다.
적재 소요는 기억 기반이므로 같은 등급을 줄 수 없다.

**주의**: 검색 응답은 DB 쿼리 단독이 아니라 엔드투엔드 응답이다. `evidence`에
측정 대상을 명시해 쿼리 실행 시간으로 오해되지 않게 한다(FR-006).

**Alternatives considered**:
- 적재 소요를 `measured`로 표기: 기각. 계측 기록이 없어 근거를 댈 수 없다.
- 단락 레코드 수 추가: 기각. 인터뷰로 복원되지 않았고 추정치를 만들지 않는다(FR-008).

## D-003. 최소 토큰 길이 서술을 정정한다

**Decision**: "버전이 값을 2로 강제했다"는 서술을 제거하고, 다음 사실로 대체한다.

1. 값을 1로 낮추려 시도했으나 적용되지 않았다.
2. 적용에 성공했더라도 한국어 한 글자 검색은 해결되지 않았을 것이다.
3. 이유는 기본 토큰화가 공백·구두점 기준이라 한 글자 토큰 자체가 생성되지
   않기 때문이다. 최소 길이 설정은 잘라낸 토큰의 인덱싱 기준일 뿐 자르는
   방식을 바꾸지 못한다.
4. 자르는 방식을 바꾸는 것은 N-gram 방식이며 상위 버전과 특정 엔진을 요구한다.

**Rationale**: 최소 길이 하한은 1이며 버전 제약이 아니다. 현재 서술은 사실이
아니므로 원칙 I 위반이다. 다만 정정하면 서술이 약해지는 것이 아니라, 설정과
토큰화 방식의 차이를 구분한다는 이해가 드러나 오히려 강해진다.

**Alternatives considered**:
- 제약 언급을 통째로 삭제: 기각. 하이브리드를 택한 이유가 사라진다.
- 기존 서술 유지: 기각. 사실이 아니다.

## D-004. 파싱 실행 위치를 실제 구현으로 정정한다

**Decision**: "로컬 스크립트 채택 / 서버 파이프라인 기각" 비교표를 제거하고,
서버 업로드 처리로 서술한다. 하나의 처리 경로가 최초 적재와 갱신을 모두
담당한다는 사실을 포함한다.

**Rationale**: 사용자 제공 코드(`bub_w_upload.js`)는 요청 객체와 업로드 파일을
받는 서버 핸들러다. 기각했다고 적은 쪽이 실제 구현이므로 비교표는 사실과
반대다.

**Alternatives considered**:
- 비교표를 유지하고 채택 항목만 교체: 기각. 나머지 기각 사유도 당시 검토
  기록인지 확인되지 않았다. 골프 작업물에서 적용한 기준과 동일하게 처리한다.

## D-004b. 외부 검색 엔진 배제 사유를 실제 사실로 서술한다

**Decision**: "프로젝트 일정·인프라 예산 제약으로 검토 후 기각"이라는 서술을
"비용이 발생해 시도조차 하지 못했다"로 바꾼다.

**Rationale**: 인터뷰 답변이 "엘라스틱서치를 쓰자니 비용이 발생하는 이슈가
있어서 시도조차 못 했다"였다. 검토 과정을 거쳐 기각한 것과 애초에 선택지에서
빠진 것은 다르다. 후자를 전자로 쓰면 하지 않은 검토를 했다고 주장하게 된다.

**보완**: 배제 사유를 낮추는 대신, 그 제약 안에서 무엇을 했는지가 드러나므로
서술이 약해지지 않는다. 회고에서 "대규모 검색이라면 외부 엔진을 도입해
토큰화와 스코어링을 직접 제어하겠다"는 현재 시점 판단은 유지한다.

## D-005. 검증 롤백을 예외 롤백과 분리해 서술한다

**Decision**: 롤백을 두 장치로 나눠 서술한다.

- 예외 롤백: 처리 중 오류가 나면 전체를 되돌린다.
- 검증 롤백: 오류가 없어도 커밋 직전에 미매칭 항목이 남아 있으면 스스로
  되돌리고, 어떤 항목이 남았는지 함께 알린다.

도입 경위(실패를 겪은 뒤 원인 지점을 알기 위해 추가)와 대응 방식(원본 문서가
아니라 파싱 규칙을 보완)을 함께 남긴다.

**Rationale**: 코드에서 두 경로를 확인했다. 검증 롤백은 "오류가 없다"와
"데이터가 올바르다"를 구분한 장치이며, 실제로 여러 번 작동했다. 현재 본문의
"중간 실패 시 롤백"은 이 차이를 전달하지 못한다.

## D-006. 스윔레인 2개, 표현 깊이를 다르게 한다

**Decision**: 사용자 확정에 따라 2개를 제공하되 근거 강도에 맞춰 깊이를 조절한다.

| 흐름 | 근거 | 표현 깊이 |
| --- | --- | --- |
| 파싱·적재 실패와 복구 | 코드 확인 | decision 노드와 두 갈래 실패 경로, 복구 경로까지 표현 |
| 검색 요청 처리 | 본문 서술만 | 단계 수준. 분기의 구체적 임계값은 명시하지 않음 |

**Rationale**: 검색 구현 코드는 확인하지 않았다. 임계값 같은 세부를 그리면
근거 없는 정밀도가 되어 원칙 I에 어긋난다.

**검증기 제약**(`validateFeatureDetail`에서 확인):
- normal edge는 `outcome: 'continue'`이고 더 큰 row로만 진행
- exception edge는 `outcome`이 `recover` 또는 `stop`이며 조건 label 필수
- decision에서 나가는 edge는 결과 label 필수
- `stop` outcome은 `stop` node를 대상으로 해야 함
- lane·step·edge·exception ID 중복 금지, lane 내 row 중복 금지

## D-007. 회귀 계약을 재고정한다

**Decision**: 다음 fixture를 새 상태로 원자적으로 갱신한다.

1. 구조화 상세 보유 목록: `['codi-harness-dx-platform']` →
   `['codi-harness-dx-platform', 'hanmaum-science-institute']`
2. legacy 본문 fixture: 한마음 항목 제거, 나머지 6개 유지
3. "구조화 상세은 하네스 하나뿐" 테스트 제목과 assertion을 새 계약에 맞게 수정

**Rationale**: 핸드오프 문서의 지침이다. assertion을 단순 삭제하면 회귀
보호가 사라진다. 이전된 작업물과 남은 legacy 작업물의 정확한 목록을 새
계약으로 고정해야 한다.

**Alternatives considered**:
- 목록 검사를 개수 검사로 완화: 기각. 어떤 작업물이 어느 형식인지 고정하지
  못해 보호 강도가 떨어진다.

## D-008. 데모 요소를 만들지 않는다

**Decision**: `demo` 필드를 설정하지 않는다.

**Rationale**: 공개 가능한 URL을 확인하지 않았다. 인터뷰에서도 데모 관련
확정이 없었다. 검증 전 추가 금지 원칙에 따른다(FR-014).
