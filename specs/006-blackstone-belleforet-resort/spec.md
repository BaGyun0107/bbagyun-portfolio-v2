# Feature Specification: 블랙스톤 벨포레 리조트 구조화 상세 이전

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-08-24

**Status**: Complete

**Input**: 블랙스톤 벨포레 리조트 작업물을 기존 구조화 상세와 같은 형식으로 이전하고, 2026-08-24 인터뷰에서 확인한 사실 오류 6종을 정정한다. 이후 작업 목록에는 테스트 우선 개발(TDD) 항목을 포함한다.

## Context

`blackstone-belleforet-resort`는 현재 장문 본문으로만 제공된다. 2026-08-24
인터뷰에서 다음 사실을 확정했다.

- 모든 설계를 혼자 했으며, 1인 백엔드로 아키텍처와 프로젝트 전반을 주도했다.
  현재 역할 서술은 사실과 일치하므로 낮추지 않는다.
- 기존 그누보드 자산 위에 PHP와 React를 결합한 신규 구축이었다. 운영 중
  서비스를 무중단 전환한 작업이 아니다.
- 결제·예약 불일치의 원인을 순서대로 추적해 자동 보상취소, 로그,
  timeout 정책을 보강했다. 결제 식별자 fallback은 직접 확인되지 않아 공개
  서술에서 제외한다.
- 현재 본문에는 인터뷰와 다른 서술 6종이 있으며, 정정 전 표현을 구조화 상세로
  옮기지 않는다.
- 시스템 흐름은 사용자가 확정한 결제·보상취소 흐름 하나만 제공한다.

인터뷰 전문:

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채용 담당자가 작업물을 같은 기준으로 비교한다 (Priority: P1)

채용 담당자가 이미 구조화된 하네스·한마음 상세와 블랙스톤 상세를 차례로
열었을 때, 같은 읽기 순서와 같은 근거 표기 방식을 만나 작업물을 같은 기준으로
비교할 수 있다.

**Why this priority**: 형식이 다르면 독자는 작업물마다 역할, 판단, 결과의 위치를
다시 찾아야 하며, 근거 등급이 없는 수치는 검증되지 않은 성과로 읽힌다.

**Independent Test**: 블랙스톤 상세 경로에서 기존 구조화 상세와 같은 공통 제목이
승인된 순서로 표시되고, 모든 결과 지표에 근거 종류·기준 시점·근거 설명이 함께
표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 블랙스톤 작업물 상세 페이지, **When** 페이지를 연다, **Then** 기존
   구조화 상세와 같은 공통 10개 제목이 승인된 순서로 표시된다
2. **Given** 핵심 결과 요약 영역, **When** 수치 지표를 본다, **Then** 값과 함께
   근거 종류·기준 시점·근거 설명 및 필요한 유의 범위가 표시된다
3. **Given** 검증된 공개 데모 주소가 없는 상태, **When** 페이지 전체를 본다,
   **Then** 데모 CTA, 비활성 버튼, "준비 중" 문구가 존재하지 않는다

---

### User Story 2 - 독자가 근거 범위 안에서 결제 안정화 결과를 이해한다 (Priority: P1)

독자가 결제·예약 불일치와 운영 관찰 기간을 볼 때, 무엇을 어떤 범위에서
확인한 값인지, 그리고 그 값이 보장하지 않는 범위까지 함께 이해한다.

**Why this priority**: 이 작업물의 가장 강한 성과는 결제 장애 대응이다. 고객
컴플레인과 시스템 집계를 구분하지 않으면 실제보다 강한 보증으로 읽혀 서술
전체의 신뢰도가 떨어진다. PMS 응답 지연과 장애 지속 시간은 결과 카드보다
timeout 설계 교훈의 맥락에 가깝다.

**Independent Test**: 두 개의 결과 지표가 확정한 등급과 근거를 사용하고 PMS
응답·장애 카드를 만들지 않는지, 확인할 수 없는 총 결제 건수·누적 건수·비율을
만들지 않았는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `10건 미만` 지표, **When** 근거를 읽는다, **Then** 시스템 집계가
   아니라 고객 컴플레인으로 접수된 불일치이며 실제 불일치의 하한임을 알 수 있다
2. **Given** 운영 관찰 기간 지표, **When** 값을 본다, **Then** `2024년 오픈 ~
   현재 진행 중`으로 유지보수가 계속되는 상태를 알 수 있다
3. **Given** 핵심 결과 요약, **When** 카드 목록을 본다, **Then** 당시 API 문제로
   지연된 약 20초와 약 1시간의 PMS 장애 지속 시간은 성과 지표로 표시되지 않는다
4. **Given** 결제 규모 설명, **When** 공개 수치를 읽는다, **Then** 확인 불가능한
   총 결제 건수나 이를 분모로 한 비율·누적 계산이 존재하지 않는다

### User Story 3 - 독자가 사실과 일치하는 판단 과정을 읽는다 (Priority: P1)

독자가 아키텍처, 인증, 결제, API Key 대응을 읽을 때 실제로 검토하고 선택한 것과
잘못 알고 있다가 발견해 고친 것을 구분할 수 있다.

**Why this priority**: 하지 않은 대안 검토나 해당하지 않는 무중단 성과를 남기면
면접에서 사실관계가 어긋나고 다른 작업물의 신뢰까지 손상된다.

**Independent Test**: 인터뷰에서 사실과 다르다고 확인된 6종의 서술이 공개
상세와 직접 연결된 인사이트에 남아 있지 않고, 각 정정 사실이 문장 단위로
존재하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 역할 서술, **When** 담당 범위를 읽는다, **Then** 모든 설계를 혼자
   했고 1인 백엔드로 아키텍처와 프로젝트 전반을 주도한 사실이 유지된다
2. **Given** PHP와 React의 공존 설명, **When** 전환 배경과 결과를 읽는다,
   **Then** 신규 구축으로 서술되며 운영 중 서비스의 무중단 전환을 성과로
   주장하지 않는다
3. **Given** timeout 장애 설명, **When** 발생 순서를 읽는다, **Then** 12초를
   임의 설정한 뒤 실패로 오판했고 당시 약 20초 지연은 API 문제로 발생한 상태였으며,
   현재는 해당 API가 수정되어 같은 수준의 지연이 아니라는 범위가 드러난다
4. **Given** 60초 선택 설명, **When** 판단 근거를 읽는다, **Then** 사용자 경험상
   30초가 낫다는 고려와 결제 안전성 사이에서 60초를 택한 트레이드오프가 드러난다
5. **Given** 결제 대안 설명, **When** 선택 배경을 읽는다, **Then** 2PC·이벤트
   소싱을 검토했다고 주장하지 않고, Node.js에서 쓰던 ORM 트랜잭션 방식을 PHP
   결제 흐름에 그대로 적용하기 어려워 보상 방식을 택한 사실을 설명한다
6. **Given** API Key 대응 설명, **When** 발견 경위를 읽는다, **Then** 환경변수
   난독화를 검토했다고 주장하지 않고 React 환경변수가 빌드 산출물에 포함되는
   사실을 프로젝트 중간에 발견해 서버 프록시로 대응한 순서를 설명한다
7. **Given** WebView 세션 설명, **When** 원인을 읽는다, **Then** 앱 개발자에게
   전달받은 내용임이 드러나며 직접 규명한 사실처럼 단정하지 않는다

---

### User Story 4 - 독자가 결제 실패와 보상취소 흐름을 한눈에 이해한다 (Priority: P2)

독자가 결제 승인부터 예약·티켓 생성, 실패 시 보상취소까지의 정상 흐름과 장애
분기를 하나의 시스템 흐름에서 이해한다.

**Why this priority**: 라우팅·인증은 단계가 단순하지만 결제는 응답 미도달, 외부
장애 중 보상취소 실패, timeout 오판처럼 여러 실패 경로가 있어 시각적 흐름의
정보 가치가 높다. 다만 사실 정확성을 다루는 P1 항목 다음의 깊이 보강이다.

**Independent Test**: 결제·보상취소 흐름 하나가 정상 경로와 확인된 실패·복구
경로를 구분하고, 그림을 보지 못하는 독자를 위한 텍스트 요약을 제공하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 결제·보상취소 흐름, **When** 정상 경로를 따라간다, **Then** 결제
   승인에서 예약·티켓 생성 완료까지 도달할 수 있다
2. **Given** 예약·티켓 생성 실패 또는 응답 미도달, **When** 예외 경로를
   따라간다, **Then** 서버 보상취소와 결과 추적이 구분되어 표시된다
3. **Given** 외부 PMS 장애 또는 timeout 오판, **When** 예외 설명을 읽는다,
   **Then** 로그로 확인한 장애 구간과 timeout 보강 범위를 넘는 fallback 단계를
   만들지 않는다
4. **Given** 시각적 흐름을 이용할 수 없는 독자, **When** 텍스트 요약을 읽는다,
   **Then** 정상 경로와 주요 실패 대응을 이해할 수 있다

---

### User Story 5 - 기존 공개 계약이 손상되지 않는다 (Priority: P1)

블랙스톤 작업물을 이전한 뒤에도 기존 구조화 상세 두 개와 아직 이전하지 않은
작업물 다섯 개의 공개 내용이 유지된다.

**Why this priority**: 회귀 계약을 느슨하게 만들거나 경로 하나를 빠뜨리면 이미
완료한 이전 작업과 남은 인터뷰 대상의 공개 내용이 조용히 손상될 수 있다.

**Independent Test**: 전체 작업물 경로, 구조화 상세 목록, legacy 본문 보존 목록,
연결 인사이트를 새 상태의 정확한 목록으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 전체 작업물 목록, **When** 각 상세 경로를 연다, **Then** 8개
   작업물 경로가 모두 성공한다
2. **Given** 구조화 상세 목록, **When** 이전 후 목록을 확인한다, **Then** 하네스,
   한마음, 블랙스톤 세 작업물만 정확히 포함된다
3. **Given** 아직 이전하지 않은 다섯 작업물, **When** 본문을 확인한다, **Then**
   기존 장문 본문이 보존된다
4. **Given** 블랙스톤에 연결된 인사이트, **When** 상세에서 링크를 따라간다,
   **Then** API Key 발견 경위와 신규 구축 전제를 상세와 다르게 주장하지 않는다

### Edge Cases

- 구조화 상세가 셋으로 늘어날 때 기존의 "둘뿐" 계약을 어떻게 다루는가? →
  assertion을 삭제하거나 개수 검사로 완화하지 않고 구조화 3개·legacy 5개의
  정확한 목록으로 원자적으로 다시 고정한다.
- `10건 미만`이 실제 불일치 전체로 읽히는가? → 지표 이름과 근거에서 고객
  컴플레인 접수 기준, 시스템 집계 아님, 실제 불일치의 하한을 함께 밝힌다.
- 부정확한 일별 결제량으로 누적 건수나 비율을 만들 수 있는가? → 만들지 않는다.
  규모를 언급할 필요가 있으면 회고 기반의 대략적 일 단위 범위와 불확실성만
  밝히고 성과 분모로 사용하지 않는다.
- `현재 진행 중`이 시스템 무결성 보장으로 읽히는가? → 2024년 오픈 이후 현재까지
  유지보수 과정에서 확인한 관찰 범위이며 전수 집계가 아님을 함께 밝힌다.
- 신규 구축인데 "전환", "무중단", "핫픽스" 같은 표현이 운영 중 서비스로
  오해되게 하는가? → 문맥을 검토해 운영 중 서비스였다는 주장을 만들지 않는다.
- 직접 연결된 인사이트가 정정 전 사실을 다시 주장하는가? → 공개 상세와 연결
  인사이트를 함께 검사하되, 이미 일치하는 문장은 근거 없이 다시 쓰지 않는다.
- 스윔레인이 좁은 화면에서 페이지 전체를 넘치게 하는가? → 흐름 영역 내부에서만
  가로 이동이 가능하고 문서 전체에는 가로 넘침이 없어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 구조화 이전

- **FR-001**: 블랙스톤 작업물은 기존 구조화 상세와 같은 구조화 상세 계약으로
  제공되어야 한다
- **FR-002**: 블랙스톤 상세는 공통 10개 제목을 승인된 읽기 순서로 표시해야 한다
- **FR-003**: 이전 후 블랙스톤의 legacy 장문 본문은 공개 경로에서 중복 제공되지
  않아야 한다
- **FR-004**: 역할은 모든 설계를 혼자 했으며 1인 백엔드로 아키텍처와 프로젝트
  전반을 주도한 사실을 유지해야 한다

#### 근거 표기

- **FR-005**: 블랙스톤 상세는 다음 두 지표를 근거와 함께 제공해야 한다:
  컴플레인으로 접수된 불일치 10건 미만, 2024년 오픈부터 현재 진행 중인 운영
  관찰 기간
- **FR-006**: 컴플레인 접수 불일치와 운영 관찰 기간은 회고에 기반한
  `reported` 값으로 구분해야 한다
- **FR-007**: 외부 PMS 약 20초 응답 지연과 약 1시간 장애 지속 시간은 결과
  카드에서 제외해야 한다
- **FR-008**: 모든 공개 지표는 근거 종류, 기준 시점, 근거 설명을 가져야 하고,
  근거 한계가 있으면 유의 범위를 함께 제공해야 한다
- **FR-009**: 확인할 수 없는 총 결제 건수, 누적 결제 건수, 이를 분모로 한 비율은
  공개하거나 계산하지 않아야 한다
- **FR-010**: 인터뷰로 복원되지 않은 수치는 추정치를 만들지 않고 생략해야 한다
- **FR-011**: 평일 10건 이상·주말 30건 이상이라는 결제량을 언급하는 경우 정확한
  집계가 아닌 회고 기반의 대략적 규모임을 밝히고 성과 지표의 분모로 쓰지 않아야 한다

#### 사실 정정

- **FR-012**: `10건 미만`은 결제·예약 불일치 전체가 아니라 고객 컴플레인으로
  접수된 불일치로 서술하고, 실제 불일치의 하한임을 밝혀야 한다
- **FR-013**: PHP와 React의 결합은 기존 그누보드 자산을 활용한 신규 구축으로
  서술하고, 운영 중 서비스의 무중단 전환을 선택 근거나 성과로 주장하지 않아야 한다
- **FR-014**: timeout 장애는 12초 임의 설정, 정상 처리 중 요청의 실패 오판,
  당시 API 문제로 약 20초까지 지연된 상태, 장애 대응 중 60초 선택, 이후 API
  수정으로 현재는 같은 수준으로 오래 걸리지 않는 상태를 구분해 서술해야 한다.
  약 20초를 PMS의 정상 평균 응답 속도로 일반화하지 않아야 한다
- **FR-015**: 결제 대안에서 근거 없는 2PC·이벤트 소싱 비교를 제거하고,
  Node.js에서 사용하던 ORM 트랜잭션 방식을 PHP 결제 흐름에 그대로 적용하기
  어려워 보상 방식을 택한 실제 고민으로 대체해야 한다
- **FR-016**: API Key 대안에서 근거 없는 환경변수 난독화 비교를 제거하고,
  React 환경변수가 빌드 산출물에 포함되는 사실을 프로젝트 중간에 발견해 서버
  프록시로 대응한 실제 순서로 대체해야 한다
- **FR-017**: WebView 자동로그인 토큰 유실 원인은 앱 개발자에게 전달받은 내용임을
  밝히고 직접 확인한 원인처럼 단정하지 않아야 한다. 브릿지로 토큰을 전달한 구현
  사실은 유지해야 한다. 문제·제약과 직접 관련 없는 `고객 거래 데이터, 시크릿,
  비공개 소스도 공개하지 않습니다`라는 일반 공개 제한 문장은 포함하지 않아야 한다
- **FR-018**: 직접 연결된 `spa-api-key-exposure-and-bff-architecture` 인사이트는
  상세와 API Key 발견 경위 및 신규 구축 전제를 다르게 주장하지 않아야 한다.
  이미 일치하는 내용은 근거 없이 변경하지 않는다

#### 시스템 흐름과 선택 증거

- **FR-019**: 시스템 흐름은 결제·보상취소 흐름 정확히 하나만 제공하고, 정상
  경로와 확인된 실패·복구 경로를 구분하며 텍스트 요약을 함께 제공해야 한다.
  직접 확인되지 않은 `resvId`·`tid`·fallback 구현은 스윔레인뿐 아니라 핵심
  구현, 결과, 회고를 포함한 공개 상세 전체에 포함하지 않아야 한다
- **FR-020**: 검증된 공개 데모 주소가 없으므로 데모 관련 요소를 만들지 않아야 한다

#### 회귀 보호

- **FR-021**: 구조화 상세 목록은 하네스·한마음·블랙스톤 3개로, legacy 본문
  유지 목록은 나머지 5개로 새 상태에 맞게 정확히 다시 고정되어야 한다
- **FR-022**: 전체 8개 작업물 경로, 기존 구조화 상세 두 개의 공개 계약, 아직
  이전하지 않은 다섯 작업물의 장문 본문이 유지되어야 한다
- **FR-023**: 연결된 인사이트는 기존 구조화 상세와 같은 방식으로 노출되어야 한다

### Key Entities

- **작업물 구조화 상세**: 역할, 결과 지표, 문제, 제약, 대안, 시스템 흐름,
  핵심 구현, 결과, 회고를 공통 읽기 순서로 담는 공개 콘텐츠
- **결과 지표**: 값과 함께 근거 종류, 기준 시점, 근거 설명, 필요 시 유의 범위를
  갖는 항목
- **결제·보상취소 흐름**: 결제 승인부터 예약·티켓 생성, 실패 판단, 보상취소,
  추적과 복구를 정상·예외 경로로 구분한 선택 증거
- **연결 인사이트**: 구조화 상세에서 더 깊은 기술 회고로 연결되며 상세와 같은
  사실 전제를 유지해야 하는 공개 콘텐츠

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 구조화 상세를 가진 작업물이 정확히 3개가 되고, 세 상세 모두 같은
  공통 10개 제목을 같은 순서로 제공한다
- **SC-002**: 블랙스톤 상세의 두 결과 지표가 근거 종류·기준 시점·근거 설명을
  100% 포함하고 PMS 응답·장애 카드는 0개이며, 총 결제 건수·누적 건수·비율
  주장은 0건이다
- **SC-003**: 인터뷰에서 사실과 다르다고 확인된 서술 6종이 공개 상세에 0건
  남고, 직접 연결된 인사이트에도 상세와 충돌하는 주장이 0건이다
- **SC-004**: 결제·보상취소 스윔레인이 정확히 1개 제공되고, 정상 완료 경로와
  응답 미도달·외부 장애·timeout 오판에 대응하는 확인된 예외 설명을 포함하며
  공개 상세 전체의 `resvId`·`tid`·fallback 주장은 0건이다
- **SC-005**: 전체 8개 작업물 경로가 모두 성공하고, 이전하지 않은 5개 작업물의

- **SC-006**: 검증된 데모가 없는 블랙스톤 상세에 데모 관련 요소가 0개 존재한다
- **SC-007**: 320/768/1024/1440px에서 문서 전체 가로 넘침이 발생하지 않고,
  결제 흐름은 자체 영역 안에서만 가로 이동한다

## Assumptions

- 인터뷰와 2026-08-25 후속 정정으로 역할, 사실 정정, 지표 범위, 현재 진행 중인
  관찰 기간, timeout 교훈, 스윔레인 개수가 확정되었다.
- `운영 관찰 기간`은 2024년 오픈부터 현재까지 유지보수하며 같은 유형의 문제를
  파악하지 못했다는 회고 범위다. 시스템 무결성을 전수 집계한 보증으로 확대하지 않는다.
- 약 20초는 PMS의 정상 평균 응답 속도가 아니라 당시 해당 API에 문제가 있어
  지연된 상태다. 현재는 API가 수정되어 과거처럼 오래 걸리지 않는다.
- `resvId`·`tid`·fallback 구현은 Q&A에서 직접 확인되지 않았으므로 공개 상세와
  스윔레인에서 제외한다.
- 연결 인사이트는 사실 일관성 검증 범위에 포함한다. 사전 점검에서 API Key를
  잘못 이해했다가 발견한 순서는 상세 정정 방향과 일치하고 무중단을 명시적으로
  주장하지 않는 것으로 확인했다. 후속 검토에서 문맥 충돌이 발견될 때만 정정한다.
- 시스템 흐름은 사용자가 확정한 결제·보상취소 흐름 하나만 제공한다. 라우팅·인증
  흐름은 단계가 단순하고 추가 시각 증거의 가치가 낮아 범위에서 제외한다.
- 현재 확인된 공개 데모 주소가 없으므로 선택 증거에서 제외한다.
- 아직 인터뷰하지 않은 5개 작업물은 이번 범위에서 내용을 수정하지 않는다.
