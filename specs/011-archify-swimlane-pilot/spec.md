# Feature Specification: Archify 스윔레인 파일럿

**Feature Branch**: `chore/cleanup-downstream-harness`

**Created**: 2026-09-09

**Status**: Complete

**Input**: 호텔 예약 시스템 작업물의 기존 스윔레인을 유지하면서, 승인된 동일 흐름을 Archify standalone viewer로 새 탭에서 제공하는 파일럿을 만든다. 기존 작은 미리보기와 크게 보기는 보존하고, 파일럿이 승인된 뒤에만 후속 전환을 검토한다. 작업 목록에는 테스트 우선 개발(TDD) 항목을 포함한다.

## Context

Feature 010에서 `hotel-reservation-platform` 작업물의 `플랫폼 변경·검증·배포 흐름`은 승인된 10개 단계와 12개 관계를 사용하는 React 스윔레인으로 공개됐다. 현재 시각 자료는 반응형 미리보기와 `크게 보기`를 제공하지만, 사용자는 같은 의미를 더 풍부하게 탐색하고 내보낼 수 있는 Archify 표현을 직접 비교해보고 싶어 한다.

이 파일럿은 기존 시각 자료를 교체하거나 새로운 프로젝트 사실을 추가하지 않는다. 현재 스윔레인을 그대로 유지한 채, 같은 질문과 관계를 별도의 standalone viewer로 열어 표현 품질과 후속 전환 가치를 판단할 수 있게 한다.

승인된 설계 근거:

- `docs/superpowers/specs/2026-09-09-archify-swimlane-pilot-design.md`
- `specs/010-hotel-reservation-platform/`
- 2026-09-09 사용자 승인: 기존 미리보기·크게 보기 유지, 새 탭 viewer, 기존 노드·관계만 사용, 원본 명세와 결과물 함께 관리

### Visual Evidence Decision

- **Visual decision: provided** — 책임 이동, 세 갈래 코드 배치, 검증·배포와 복구가 여러 lane에 걸쳐 있어 스윔레인이 필요하다.
- **Existing visual disposition: retain existing swimlane** — 현재 React 미리보기와 크게 보기는 제거하거나 변경하지 않는다.
- Archify viewer는 새로운 기술 관계를 추가하는 두 번째 증거가 아니라, 같은 승인 흐름을 다른 viewer에서 비교하기 위한 선택적 표현이다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 독자가 같은 흐름을 확장 viewer에서 탐색한다 (Priority: P1)

호텔 예약 시스템 작업물을 읽는 독자는 기존 스윔레인 카드에서 선택적 Archify 보기 동작을 발견하고, 새 탭에서 동일한 플랫폼 변경·검증·배포 흐름을 확대하거나 관계를 따라가며 읽을 수 있다.

**Why this priority**: 파일럿의 직접 가치는 기존 의미를 유지하면서 더 풍부한 탐색 경험이 실제로 유용한지 비교하는 데 있다.

**Independent Test**: 호텔 예약 시스템 상세에서 Archify 보기 동작을 활성화하고, 열린 standalone viewer에서 기존 스윔레인의 모든 단계·관계·정상 및 복구 경로를 확인한다.

**Acceptance Scenarios**:

1. **Given** 호텔 예약 시스템의 플랫폼 변경·검증·배포 스윔레인, **When** 독자가 `Archify로 보기`를 활성화한다, **Then** 같은 출처의 standalone viewer가 새 탭에서 열린다
2. **Given** 열린 Archify viewer, **When** 독자가 주 흐름을 따라간다, **Then** 변경 요청, 세 코드 배치 경계, 플랫폼별 빌드, 계약·동작 검증과 호텔별 배포를 순서대로 이해한다
3. **Given** 계약·동작 검증 단계, **When** 독자가 예외 경로를 따라간다, **Then** 패리티 누락에서 운영 브랜치 감사와 수동 이식을 거쳐 재검증하는 복구 경로를 이해한다
4. **Given** 세 코드 배치 분기, **When** 독자가 관계를 비교한다, **Then** `core`, `rsConfig`, `platform`이 순위가 아닌 변경 성격에 따른 동등한 선택으로 보인다

---

### User Story 2 - 기존 스윔레인 경험이 보존된다 (Priority: P1)

기존 작업물을 읽는 독자는 Archify 파일럿 사용 여부와 관계없이 현재 React 미리보기와 `크게 보기`를 이전과 동일하게 사용할 수 있다. 다른 작업물에는 파일럿과 무관한 버튼이나 빈 영역이 생기지 않는다.

**Why this priority**: 파일럿이 기존에 검증된 읽기 경험을 대체하거나 다른 작업물까지 암묵적으로 확장하면 안전한 비교가 불가능하다.

**Independent Test**: 호텔 예약 시스템에서 기존 미리보기·Dialog를 사용하고, 다른 모든 구조화 작업물에서 Archify 전용 동작이 나타나지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 호텔 예약 시스템 스윔레인 카드, **When** 독자가 기존 `크게 보기`를 활성화한다, **Then** 기존 React 기반 전체 흐름 Dialog가 열리고 닫힌 뒤 초점이 원래 동작으로 돌아온다
2. **Given** 호텔 예약 시스템 상세, **When** 파일럿이 추가된다, **Then** 기존 작은 미리보기의 단계·관계·요약·예외 설명은 그대로 유지된다
3. **Given** Archify 자료가 연결되지 않은 다른 스윔레인, **When** 독자가 해당 카드를 연다, **Then** Archify 버튼·빈 placeholder·비활성 동작이 표시되지 않는다
4. **Given** Archify standalone 자료를 사용할 수 없는 상황, **When** 독자가 원본 작업물을 읽는다, **Then** 기존 미리보기·크게 보기·텍스트 설명으로 전체 흐름을 계속 이해할 수 있다

---

### User Story 3 - 포트폴리오 소유자가 동일 의미와 검증 근거를 확인한다 (Priority: P2)

포트폴리오 소유자는 Archify viewer가 현재 공개 스윔레인의 표현만 바꿨으며, 승인되지 않은 구성요소·성과·자동화를 추가하지 않았다는 사실을 검증 기록으로 확인할 수 있다.

**Why this priority**: 더 화려한 viewer가 사실 범위를 강화하거나 관계를 새로 만들어내면 포트폴리오의 신뢰성이 떨어진다.

**Independent Test**: 기존 스윔레인과 Archify 원본·결과물을 대조하고, 단계·관계 수, label, 방향, 복구 의미와 생성·브라우저 검증 증거를 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 스윔레인과 Archify 원본, **When** 단계와 관계를 대조한다, **Then** 기존 10개 단계와 12개 관계가 모두 대응되고 추가 기술 주장이 없다
2. **Given** 최종 Archify 결과물, **When** 생성 검증 기록을 확인한다, **Then** 고품질 검사, 결정적 산출물 receipt와 실제 브라우저 검사가 서로 구분되어 기록된다
3. **Given** 시각적 복구 경로, **When** 기존 인터뷰와 Feature 010 사실 계약을 대조한다, **Then** 운영 배포 전 패리티 누락 발견과 수동 이식 후 재검증 범위를 넘지 않는다
4. **Given** 파일럿 결과, **When** 작은 미리보기 전환 여부를 판단한다, **Then** 이번 기능은 자동 전환하지 않고 별도의 사용자 승인과 후속 설계를 요구한다

---

### User Story 4 - 다양한 입력과 화면 환경에서 파일럿을 사용할 수 있다 (Priority: P2)

키보드 사용자와 서로 다른 크기의 화면을 사용하는 독자는 기존 카드에서 새 동작을 식별하고 활성화할 수 있으며, 새 탭의 viewer에서도 핵심 노드와 관계를 가림 없이 읽을 수 있다.

**Why this priority**: 확장 viewer가 마우스나 특정 데스크톱 크기에서만 동작하면 기존 접근성·반응형 계약보다 후퇴한다.

**Independent Test**: 키보드와 지원 화면 크기에서 링크의 이름·초점·새 탭 동작, 원본 페이지의 overflow와 standalone viewer의 가시성을 확인한다.

**Acceptance Scenarios**:

1. **Given** 키보드 사용자, **When** 스윔레인 카드의 두 동작 사이를 이동한다, **Then** 기존 크게 보기와 Archify 새 탭 보기를 서로 구분해 식별하고 활성화할 수 있다
2. **Given** 320px, 768px, 1024px 또는 1440px 폭의 작업물 화면, **When** 스윔레인 카드 header를 읽는다, **Then** 제목과 두 동작이 서로를 가리거나 문서 전체 가로 넘침을 만들지 않는다
3. **Given** 일반적인 데스크톱 화면에서 열린 standalone viewer, **When** 독자가 전체 흐름을 탐색한다, **Then** 필요한 핵심 노드·관계·label이 화면 밖으로 잘리거나 다른 요소에 가려지지 않는다
4. **Given** 새 탭 동작, **When** 독자가 링크의 접근 가능한 이름을 확인한다, **Then** 대상 스윔레인과 새 탭으로 열린다는 사실을 이해할 수 있다

### Edge Cases

- Archify 연결 정보가 비어 있거나 허용된 정적 다이어그램 경로가 아니면 어떻게 되는가? → 잘못된 연결을 거부하고 새 동작을 공개하지 않는다.
- 연결 정보는 있지만 결과 파일이 없거나 응답하지 않으면 어떻게 되는가? → 공개 전 검증이 실패하며 기존 React 스윔레인만 유지한다.
- 다른 작업물의 스윔레인이 선택 필드를 제공하지 않으면 어떻게 되는가? → 현재 UI만 표시하고 Archify placeholder를 만들지 않는다.
- 두 action이 320px 카드 header에 함께 들어가지 않으면 어떻게 되는가? → action 영역이 자연스럽게 줄바꿈되며 제목·버튼·문서 폭을 침범하지 않는다.
- 새 탭이 차단되거나 사용자가 닫으면 어떻게 되는가? → 원본 작업물 상태는 바뀌지 않고 기존 크게 보기 기능을 계속 사용할 수 있다.
- 세 코드 배치 분기가 배열 순서 때문에 1·2·3순위처럼 보이면 어떻게 되는가? → 동등한 분기 의미를 label과 배치로 보존한다.
- 복구선이나 label이 노드 위를 지나가면 어떻게 되는가? → 공개 전 시각 검사가 실패하며 관계 label을 삭제하지 않고 경로·간격을 조정한다.
- 더 보기 좋은 구성을 위해 노드나 관계를 줄이고 싶으면 어떻게 되는가? → 기존 의미 계약의 10개 단계와 12개 관계를 유지하며 단순화를 이유로 삭제하지 않는다.
- Archify 실행 환경이 CI나 앱 런타임에 없으면 어떻게 되는가? → 이미 검증된 정적 결과물을 제공하므로 원본 작업물과 공개 viewer는 계속 동작한다.
- 한국어 locale을 지원하지 않는 고정 Viewer UI는 어떻게 표시되는가? → 작성된 노드·관계는 한국어를 유지하고 고정 Viewer UI와 문서 언어 fallback이 영어임을 공개 범위에서 분명히 한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 파일럿 범위와 기존 경험

- **FR-001**: 파일럿은 `hotel-reservation-platform`의 플랫폼 변경·검증·배포 스윔레인 하나에만 적용되어야 한다
- **FR-002**: 기존 React 미리보기, 크게 보기, 전체 흐름 설명과 예외 설명은 변경 없이 유지되어야 한다
- **FR-003**: 대상 스윔레인은 기존 동작과 구분되는 `Archify로 보기` 동작을 하나 제공해야 한다
- **FR-004**: Archify 연결이 없는 다른 모든 스윔레인은 새 동작, 빈 영역 또는 비활성 placeholder를 표시하지 않아야 한다
- **FR-005**: Archify viewer가 응답하지 않더라도 원본 작업물과 기존 React 시각·텍스트 설명은 독립적으로 사용 가능해야 한다
- **FR-006**: 작은 미리보기의 Archify 전환은 이번 범위에 포함하지 않으며 별도의 사용자 승인 없이 수행되지 않아야 한다

#### 동일 의미와 공개 경계

- **FR-007**: Archify viewer는 기존 10개 단계와 12개 관계를 모두 표현해야 한다
- **FR-008**: 정상 흐름은 변경 요청, 차이 분류, 코드 경계 배치, 플랫폼별 빌드, 계약·동작 검증, 호텔별 운영 폴더 배포 순서를 유지해야 한다
- **FR-009**: 세 코드 배치 경로는 모든 플랫폼 공통, 값만 다름, 화면·로직 차이라는 선택 기준과 각각의 `core`, `rsConfig`, `platform` 도착을 유지해야 한다
- **FR-010**: 예외 흐름은 패리티 누락, 운영 브랜치 감사, `core·platform` 수동 이식, 계약·동작 재검증의 방향을 유지해야 한다
- **FR-011**: 세 코드 배치 경로를 우선순위·성숙도·단계 순서로 표현하지 않아야 한다
- **FR-012**: 새 viewer는 승인되지 않은 수치, 시스템 구성요소, 자동화, 운영 성과, 단일 산출물 배포나 무수정 신규 호텔 추가를 암시하지 않아야 한다
- **FR-013**: 프로젝트 본문과 연결 인사이트의 역할·기간·수치·원인·대안·구현·결과 문구는 이번 파일럿으로 변경되지 않아야 한다
- **FR-014**: 현재 시각 상태는 `provided`로 기록하고 기존 스윔레인은 `retain existing swimlane`으로 명시해야 한다
- **FR-015**: Archify viewer는 같은 질문에 대한 대체 표현임을 유지하며 작업물이나 인사이트에 새로운 시각 증거로 중복 삽입되지 않아야 한다

#### 링크와 독립 산출물

- **FR-016**: 새 동작은 같은 출처의 허용된 정적 다이어그램 문서만 열어야 한다
- **FR-017**: 새 동작은 원본 작업물의 탐색 상태를 바꾸지 않고 별도 탭에서 열려야 한다
- **FR-018**: 새 탭 문서는 앱의 실행 중 생성 과정에 의존하지 않고 독립적으로 응답해야 한다
- **FR-019**: 편집 가능한 의미 원본과 독자가 여는 최종 결과물이 함께 보존되어야 한다
- **FR-020**: 최종 결과물은 어떤 의미 원본에서 생성됐는지 식별 가능한 검증 receipt를 가져야 한다
- **FR-021**: 검증을 통과하지 못했거나 결과 파일이 없는 연결은 공개되지 않아야 한다

#### 접근성·반응형·검증

- **FR-022**: 새 동작은 보이는 이름과 접근 가능한 이름으로 대상 스윔레인과 새 탭 동작을 구분해야 한다
- **FR-023**: 키보드만으로 기존 크게 보기와 Archify 보기를 각각 식별하고 활성화할 수 있어야 한다
- **FR-024**: 새 탭 연결은 열린 문서가 원본 페이지 제어 권한을 얻지 않는 안전한 관계를 사용해야 한다
- **FR-025**: 원본 카드의 제목과 두 action은 320px, 768px, 1024px, 1440px에서 서로의 핵심 내용을 가리거나 문서 전체 가로 넘침을 만들지 않아야 한다
- **FR-026**: standalone viewer는 1440×900, 1600×1000, 1920×1080에서 문서 전체 가로·세로 넘침 없이 필요한 전체 흐름을 읽을 수 있어야 한다
- **FR-027**: 작성된 노드·관계·설명은 한국어를 유지하고, 고정 Viewer UI와 문서 언어 fallback이 영어라는 한계를 숨기지 않아야 한다
- **FR-028**: 관계 차이는 색상만이 아니라 방향, label, 구조로 구분되어야 한다
- **FR-029**: 공개 전 고품질 구조 검사, 결정적 결과물 receipt, 실제 브라우저 검사와 이미지 기반 시각 검토가 서로 구분되어 기록되어야 한다
- **FR-030**: 고품질 구조 검사는 9개 artifact check, composition error 0건, warning 0건을 만족해야 한다
- **FR-031**: 기존 작업물 스윔레인, 다른 구조화 작업물, 연결 인사이트와 공개 경로의 회귀 검사가 통과해야 한다
- **FR-032**: 고객 정보, 예약·결제 식별자, 시크릿, 비공개 소스·로그와 내부 감사 수치는 의미 원본·결과물·검증 산출물에 포함되지 않아야 한다

### Key Entities

- **대상 스윔레인**: 호텔 예약 시스템 작업물에 이미 공개된 플랫폼 변경·검증·배포 흐름. 기존 React 표현과 Archify 표현이 공유하는 사실 기준이다.
- **Archify 의미 원본**: 대상 스윔레인의 승인된 단계, 관계, label과 복구 의미를 편집 가능한 형태로 보존하는 파일럿 원본이다.
- **Standalone viewer**: 의미 원본에서 생성돼 새 탭에서 독립적으로 열리는 확장 다이어그램 문서다.
- **선택적 연결**: 대상 스윔레인에만 standalone viewer의 존재와 보이는 이름을 연결하는 정보다.
- **검증 receipt**: 의미 원본과 결과물의 동일성, 구조 검사와 생성 결과를 식별하는 증거다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 호텔 예약 시스템의 대상 스윔레인 카드에 기존 크게 보기 1개와 Archify 보기 1개가 함께 표시되고, 기존 미리보기·요약·예외 설명이 모두 유지된다
- **SC-002**: Archify 의미 원본과 standalone viewer에서 기존 단계 10개와 관계 12개의 누락·추가·방향 불일치가 0건이다
- **SC-003**: 세 코드 배치 분기와 패리티 복구 경로에 대한 의미 오독 finding이 자동 검사와 이미지 기반 검토에서 0건이다
- **SC-004**: 고품질 구조 검사 9개가 모두 통과하고 composition error와 warning이 각각 0건이다
- **SC-005**: 대상 새 탭 문서는 실제 브라우저 요청의 100%에서 성공 응답하며, 키보드 활성화로 올바른 문서가 열린다
- **SC-006**: 320px, 768px, 1024px, 1440px의 원본 작업물에서 문서 전체 가로 넘침과 카드 제목·action 겹침이 각각 0건이다
- **SC-007**: 1440×900, 1600×1000, 1920×1080의 standalone viewer에서 문서 전체 가로·세로 넘침과 핵심 노드·관계·label 겹침이 각각 0건이다
- **SC-008**: Archify 연결이 없는 기존 스윔레인의 새 Archify action과 빈 placeholder가 0건이다
- **SC-009**: 기존 React 크게 보기의 마우스·터치·키보드 활성화, 닫기와 초점 복귀 회귀 검사가 모두 통과한다
- **SC-010**: 프로젝트 본문·연결 인사이트·다른 작업물의 공개 문구 변경이 0건이며, 승인되지 않은 기술·수치·성과 주장이 결과물에서 0건이다
- **SC-011**: 의미 원본, 최종 결과물, 구조 검사, delivery receipt, 브라우저 검사와 시각 검토의 증거가 한 검증 기록에서 모두 추적 가능하다

## Assumptions

- Feature 010에서 승인·검증된 `platform-change-verification-deployment`의 10개 단계, 12개 관계, 목적과 요약이 이번 파일럿의 최우선 사실 기준이다.
- 사용자는 기존 React 미리보기·크게 보기 유지, Archify 새 탭 보기, 기존 관계만 사용, 원본과 결과물의 동시 보존을 명시적으로 승인했다.
- standalone viewer의 고정 UI와 문서 언어는 영어 fallback을 사용하며, 이번 기능에서 한국어 locale이나 viewer 내부 구현을 추가하지 않는다.
- 새 viewer는 인증 없이 같은 출처의 정적 공개 문서로 제공된다.
- 파일럿의 비교 결과가 긍정적이어도 작은 미리보기나 다른 스윔레인을 자동 전환하지 않는다.
- Archify 실행 환경은 제작·검증 시점에만 필요하며 배포된 앱의 build와 runtime은 생성 도구에 의존하지 않는다.
- 기존 1104 개발 서버는 임의로 종료·재시작하지 않고, 최종 브라우저 검증은 별도 production server에서 수행한다.
- 저장소 전역 lint의 기존 baseline과 관련 없는 파일 포맷은 이번 기능 범위에 포함하지 않는다.
