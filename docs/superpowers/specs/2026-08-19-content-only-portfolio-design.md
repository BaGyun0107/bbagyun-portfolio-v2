# 상세 콘텐츠 중심 포트폴리오 개편 설계

## 목표

기존 포트폴리오의 화면 디자인과 공개 라우트를 유지하면서 작업물·공부·인사이트 상세 페이지의 콘텐츠만 강화한다. 화면을 새로 디자인하거나 기존 레이아웃을 교체하지 않고, 면접관이 작성자의 문제 정의·제약·판단·해결·결과·회고를 충분히 읽을 수 있도록 콘텐츠 원본과 상세 페이지의 표시 계약을 정리한다.

## 확정된 범위

- 기존 `/`, `/projects`, `/projects/[slug]`, `/study`, `/study/[slug]`, `/insights`, `/insights/[slug]`의 시각 디자인을 유지한다.
- Apple 스타일 또는 새로운 시각 시스템은 이번 작업의 기준에서 제외한다.
- 소스코드 링크와 검증되지 않은 데모 링크를 추가하지 않는다.
- 실제 경험과 현재 데이터에 근거하지 않는 수치·기술·관계를 만들어내지 않는다.
- 상세 콘텐츠는 기존 Markdown 원본을 활용하고, 필요한 경우 데이터 파일의 본문만 수정한다.

## 콘텐츠 구조

### 작업물

각 작업물은 다음 순서를 기본으로 한다.

1. 프로젝트 개요와 담당 역할
2. 문제 상황과 비즈니스·기술 제약
3. 고려한 대안과 선택하지 않은 이유
4. 선택한 설계와 핵심 구현
5. 데이터·API·외부 시스템·운영 관점의 결과
6. 확인 가능한 결과와 한계
7. 회고와 다음 단계

### 공부

학습 목적, 핵심 개념, 직접 검증한 내용, 기존 생각과 달라진 점, 실무 적용 기준, 남은 질문 순서로 작성한다.

### 인사이트

문제의식, 실제 상황 또는 근거, 선택지 비교, 나의 판단, 실무 적용 기준, 반대 조건과 후속 질문을 포함한다.

## 구현 경계

- 콘텐츠 표시를 이미 담당하는 `MarkdownViewer`와 기존 상세 라우트를 우선 재사용한다.
- 디자인 토큰·전역 CSS·기존 레이아웃 컴포넌트는 변경하지 않는다.
- 이전에 만들었던 `/preview` 구현은 폐기하고, 공개 라우트만 콘텐츠 원본의 대상 범위로 유지한다.
- 검증은 데이터 품질 테스트, 기존 상세 라우트 E2E, TypeScript, production build로 수행한다.

## 완료 기준

- 공개 상세 라우트의 레이아웃과 기존 네비게이션이 유지된다.
- 작업물·공부·인사이트 상세 콘텐츠가 축약 카드가 아니라 장문 원문으로 표시된다.
- 작업물 본문에서 문제 → 판단 → 구현 → 결과 → 회고의 흐름을 확인할 수 있다.
- 콘텐츠가 없는 경우 빈 페이지 대신 기존 fallback이 유지된다.
- 데모·소스코드·수치는 실제 데이터가 없는 경우 노출되지 않는다.
