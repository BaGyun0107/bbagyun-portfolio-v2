# 백엔드 중심 풀스택 포트폴리오 개편 설계

## 상태

- 설계 방향: 사용자 승인 — Apple-inspired visual direction
- 구현 상태: Apple 스타일 재설계 진행
- 우선 적용 대상: 대표 작업물 1개를 파일럿으로 선정해 검증
- 작업 크기: Large

## 목표

이 포트폴리오는 작업물·공부·인사이트를 단순한 게시글 목록으로 보여주는 대신, 백엔드 중심 풀스택 개발자가 어떤 문제를 발견하고, 어떤 제약 안에서 설계 판단을 내리고, 실제 운영 가능한 시스템으로 만든 과정을 보여준다.

면접관은 첫 화면에서 대표 작업물을 빠르게 찾고, 작업물 상세 페이지에서 데모 또는 아키텍처 증거를 확인한 뒤, 사용자의 문제 정의·데이터 모델링·API 설계·장애 대응·운영 결과를 원하는 깊이로 탐색할 수 있어야 한다.

## 설계 원칙

1. 데모보다 판단을 우선한다.
   - 프론트엔드가 있는 작업물은 데모와 아키텍처 흐름을 함께 제공한다.
   - 백엔드·인프라 작업물은 데모를 억지로 만들지 않고 다이어그램, API 계약, ERD, 실행 흐름, 운영 결과를 증거로 제공한다.
2. 요약과 본문을 분리한다.
   - 상단 요약은 빠른 판단을 돕는다.
   - 본문은 사용자의 실제 생각과 구현 과정을 축약하지 않는다.
3. 모든 작업물의 공통 골격은 유지하되 증거 블록은 작업물 특성에 따라 구성한다.
4. 다이어그램은 장식 이미지가 아니라 시스템의 책임·시간·데이터를 설명하는 기술 산출물로 취급한다.
5. 공개 콘텐츠와 원본 작업 기록을 분리한다.
   - 매일의 Claude Code·Codex 작업 이력은 먼저 개발 기록으로 보존한다.
   - 사용자의 확인과 보완을 거친 뒤 작업물·공부·인사이트로 승격한다.
6. 출처가 불명확한 수치나 과장된 성과를 만들지 않는다.

## Apple 스타일 시각 방향

사용자가 승인한 `apple/` 디자인 자료를 기준으로 preview 화면의 시각 계층을 재구성한다. Apple의 구조를 그대로 복제하지 않고, 포트폴리오 콘텐츠에 맞는 editorial case-study 화면으로 번역한다.

- 캔버스는 `#f5f5f7`, `#ffffff`, `#000000` 세 장면을 중심으로 구성한다.
- 색상 포인트는 인터랙션에만 Apple Blue(`#0071e3`)를 사용한다.
- 청록·주황 등 다중 강조색, 과도한 테두리, 촘촘한 작은 카드, 장식용 그림자는 제거한다.
- 히어로는 중앙 정렬의 큰 제목과 짧은 설명을 사용하고, 대표 작업물은 검정색 몰입형 섹션으로 분리한다.
- 카드보다 섹션의 여백과 배경 전환으로 정보 우선순위를 만든다.
- CTA는 pill 형태를 사용하되, 일반 텍스트 링크는 버튼처럼 감싸지 않는다.
- 상세 페이지는 좌측 목차와 우측 본문을 유지하되, 본문을 넓은 editorial reading column으로 표현한다.
- 기존 데이터, 8개 작업물, 다이어그램/ERD, 다크모드, 별도 라우트는 유지하고 시각 표현만 교체한다.

## 홈 화면

홈 화면은 다음 순서로 유지한다.

`소개 메시지 → 대표 작업물 → 핵심 지표 → 최근 개발 기록 → 공부/인사이트 → 문의`

대표 작업물 카드에는 기술 스택보다 다음 정보를 우선 노출한다.

- 해결한 문제
- 핵심 설계 주제
- 실제 결과 또는 적용 범위
- 데모 실행 또는 아키텍처 흐름 보기

홈 화면의 포지셔닝 문구는 백엔드 중심 풀스택 정체성을 분명히 한다. 예시 문구는 “사용자 경험을 이해하고, 그 뒤에서 오래 버티는 시스템을 설계합니다.”이다.

헤더 우측에는 다크모드 전환 버튼을 제공한다. 전환 상태는 사용자의 시스템 테마를 기본값으로 존중하고, 사용자가 직접 선택한 값은 다음 방문에도 유지한다. 다크모드에서도 장문 본문, SVG 다이어그램, ERD, 코드 블록, 상태 배지의 대비와 가독성이 유지되어야 한다.

## 작업물 상세 페이지

작업물 상세 페이지의 공통 순서는 다음과 같다.

1. 프로젝트 스냅샷
   - 제목, 한 줄 요약, 기간, 역할, 팀, 상태, 핵심 결과
   - 데모가 존재할 때만 데모 버튼을 노출
   - 모든 작업물에 아키텍처 흐름 보기 버튼을 노출
   - 소스 코드 버튼은 노출하지 않음
2. 개요와 역할
   - 누구를 위한 시스템인지
   - 사용자의 역할과 책임 범위
   - 본인이 직접 설계·구현·운영한 범위
3. 문제 상황
   - 기존 흐름
   - 실제 비용이나 장애
   - 문제가 중요한 이유
4. 제약과 설계 판단
   - 일정, 비용, 팀 규모, 레거시, 외부 API, 운영 환경
   - 선택한 대안과 선택하지 않은 대안
   - 트레이드오프
5. 시스템 개요도
   - 외부 사용자·시스템·서비스·저장소의 관계
6. 시퀀스/스윔레인 다이어그램
   - 정상 흐름
   - 필요한 경우 실패 흐름과 복구 흐름
   - 각 주체의 책임과 데이터 이동
7. ERD 및 데이터 설계
   - 핵심 도메인만 표시
   - 관계, 상태 생명주기, 제약, 인덱스, 트랜잭션 경계
8. API 계약
   - 주요 엔드포인트, 요청·응답 예시, 인증·인가, 오류 응답, 멱등성
   - 소스 코드는 공개하지 않고 읽을 수 있는 API 계약만 제공
9. 구현 세부
   - 실제로 부딪힌 문제
   - 적용한 구현 방식
   - 실패한 시도와 변경 이유
10. 안정성·보안·운영
    - 로깅, 메트릭, 알림, 재시도, 타임아웃, fallback, 배포, 롤백, 장애 대응
11. 결과와 검증
    - 성능, 처리량, 비용, 장애 감소, 적용 범위, 운영 상태
12. 회고와 다음 단계
    - 다시 설계한다면 바꿀 점
    - 현재 남아 있는 위험
    - 확장 계획
13. 관련 콘텐츠
    - 관련 인사이트, 공부 기록, 다른 작업물

왼쪽 또는 상단에 목차를 제공해 긴 글을 빠르게 탐색할 수 있게 한다. 다이어그램은 이미지처럼 선명하게 표시하되, 단계나 영역을 선택하면 해당 설명으로 이동할 수 있게 한다.

## 작업물별 증거 규칙

### 프론트엔드·제품 작업물

- 라이브 데모
- 주요 사용자 시나리오
- 화면 흐름과 API/상태 흐름을 연결한 시퀀스 다이어그램
- ERD 또는 핵심 데이터 모델
- 결과 지표와 운영 정보

### 백엔드·인프라 작업물

- 아키텍처 흐름을 첫 번째 증거로 제공
- 시퀀스/스윔레인 다이어그램
- ERD 또는 데이터 저장 구조
- API 계약 또는 작업 실행 계약
- 배포·운영·장애 대응 흐름
- 실제 결과 수치와 적용 범위

프론트엔드가 있는 작업물에도 아키텍처 흐름은 반드시 제공한다. 데모는 사용 경험을 보여주고, 아키텍처 흐름은 설계 사고를 보여준다.

## 다이어그램 산출물

다이어그램은 AI가 만든 래스터 이미지보다 SVG, Mermaid 또는 동등한 구조화된 원본으로 관리한다.

### 필수 유형

- 시스템 개요도: 시스템·외부 의존성·저장소의 관계
- 시퀀스/스윔레인: 시간 순서·책임·정상/실패 흐름
- ERD: 핵심 데이터 모델·관계·정합성

### 다이어그램 품질 기준

- 모든 화살표에 방향과 의미가 있다.
- 주체별 책임이 명확하다.
- 인증·인가 경계와 트랜잭션 경계가 표시된다.
- 외부 API, 큐, 버퍼, 저장소, 모니터링 지점이 구분된다.
- 모바일에서 확대 또는 가로 스크롤이 가능하다.
- 이미지 대체 텍스트와 설명 문장이 제공된다.
- 다이어그램 아래에 핵심 판단 2~4개를 설명한다.
- 라이트·다크 테마 모두에서 선, 텍스트, 범례, 상태 색상의 대비가 유지된다.

## 개발 기록과 공개 콘텐츠

공개 분류인 작업물·공부·인사이트 앞에 비공개 또는 검토 대기 상태의 `Development Log` 계층을 둔다.

### Development Log 필드

- 작업 날짜
- 관련 작업물
- 작업 출처(Claude Code, Codex, 직접 작업 등)
- 변경한 내용
- 만난 문제
- 처음 세운 가설
- 실제 선택
- 선택하지 않은 대안
- 검증 방법
- 결과
- 남은 문제
- 사용자가 추가한 생각과 감정
- 공개 상태

### 공개 승격 규칙

- 특정 프로젝트의 구현·장애·설계 변경 → 작업물 상세 페이지
- 개념 학습·실험·정리 → 공부
- 문제 해결 과정·판단·회고 → 인사이트
- 아직 정리되지 않은 작업 → Development Log에 보관

LLM은 로컬 Claude Code·Codex 작업 이력에서 사실과 후보 요약을 추출하지만, 사용자의 의도·감정·최종 판단을 대신 확정하지 않는다. 사용자가 내용을 확인하고 보완한 뒤에만 공개 상태로 전환한다.

## 데이터 모델 방향

현재 `FeatureDto`를 확장해 작업물과 기술 산출물을 명시적으로 연결한다.

예상 개념은 다음과 같다.

- `Feature`: 대표 작업물의 기본 정보와 장문 본문
- `Artifact`: 다이어그램, ERD, API 계약, 성능 차트, 운영 증거
- `Demo`: 데모 URL, 접근 안내, 제한 사항, 상태
- `Decision`: 문제, 선택, 대안, 근거, 결과
- `Metric`: 측정 항목, 전후 값, 측정 조건, 출처
- `DevelopmentLog`: 원본 작업 기록과 공개 상태

기존 `Study`와 `Insight`는 유지하되 `Feature`, `Artifact`, `DevelopmentLog`와 연결한다.

## 전체 작업물 적용과 파일럿 검증

현재 작업물 8개는 모두 새 비교 라우트에서 노출하고, 8개 모두 동일한 상세 페이지 템플릿으로 접근할 수 있어야 한다. 작업물별로 데모·시스템 개요도·스윔레인·ERD·API 계약·운영 지표 중 실제로 존재하는 증거만 표시한다.

파일럿은 적용 범위를 줄이는 단계가 아니다. 외부 예약 API와 로깅 병목 작업물을 가장 내용이 풍부한 대표 사례로 먼저 다듬어 템플릿과 콘텐츠 표현을 검증한 뒤, 같은 템플릿을 나머지 7개 작업물에 적용한다.

## 파일럿 적용 순서

1. 대표 작업물 1개 선정
2. 해당 작업물의 장문 서술을 사용자의 관점으로 재정리
3. 시스템 개요도·스윔레인·ERD 제작
4. 데모 유무에 따른 상단 CTA 적용
5. 상세 페이지에 본문·목차·증거 블록 구현
6. 면접관 관점에서 3분 안에 핵심을 파악할 수 있는지 검토
7. 개발 기록 한 건을 작업물 또는 인사이트로 승격하는 흐름 검증
8. 템플릿을 다른 작업물로 확장

기존 화면과의 비교 가능성을 보장하기 위해 현재 공개 라우트는 유지한다. 새로운 홈·작업물 상세 경험은 별도 비교 라우트 아래에 추가하고, 파일럿 검증이 끝난 뒤에만 기존 라우트로 승격 여부를 결정한다. 기존 라우트와 새 라우트는 동일한 원본 콘텐츠를 사용할 수 있지만, 새 라우트의 화면 구조나 표현 방식이 기존 화면을 덮어쓰지 않아야 한다.

첫 파일럿 후보는 외부 예약 API와 로깅 병목을 해결한 작업물이다. 이 작업물은 외부 연동, 데이터 흐름, 로그 분리, 버퍼링, 장애 대응, 성능과 운영 결과를 동시에 보여줄 수 있어 ERD와 스윔레인 구조를 검증하기에 적합하다.

## 범위에서 제외하는 것

- 작업물별 소스 코드 공개
- 모든 작업물에 실행 가능한 데모 강제
- 근거 없는 성능·사용자 수·비용 수치 생성
- 모든 일일 기록의 자동 공개
- 다이어그램을 장식 이미지로만 사용하는 것
- 첫 파일럿 전에 전체 콘텐츠를 일괄 마이그레이션하는 것

## 검증 기준

- 면접관이 홈 화면에서 대표 작업물과 데모/아키텍처 진입점을 10초 이내에 찾을 수 있다.
- 사용자가 헤더에서 라이트·다크 테마를 즉시 전환할 수 있고, 선택한 테마가 새로고침 후에도 유지된다.
- 대표 작업물 상세 페이지에서 문제·역할·설계 판단·데이터 구조·운영 결과를 3분 이내에 파악할 수 있다.
