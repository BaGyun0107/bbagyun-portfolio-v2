# Codi Harness 작업물 본문 보강 및 인사이트 통합 설계

- 작성일: 2026-08-21
- 대상 작업물: `codi-harness-dx-platform`
- 상태: 사용자 승인 완료
- 범위: 작업물 상세 콘텐츠 재구성, 대표 인사이트 통합, 중복 정본 제거

## 1. 목표

`사내 DX 하네스 v2 구축` 작업물은 현재 구조와 스윔레인만으로 전체 운영 흐름을
이해하기 쉬워졌지만, 핵심 구현을 짧은 인사이트 네 개로 과도하게 분리해 작업물
상세만 읽으면 도구를 조합한 프로젝트처럼 보일 수 있다.

이번 변경은 연결형 스윔레인과 근거 지표를 유지하면서 작업물 상세에 대표 설계 결정의
기술적 실체를 복원한다. 동시에 짧은 인사이트 네 개와 얇은 종합 글을 하나의 발전
과정 중심 대표 인사이트로 통합한다.

완료 후 방문자는 다음을 수행할 수 있어야 한다.

- 작업물 상세만 읽고 문제, 작성자의 역할, 대표 설계 결정 네 개와 결과를 설명한다.
- 대표 인사이트를 읽고 복사형 v1에서 멀티 세션 실험까지 설계가 발전한 이유를 설명한다.
- 현재 운영 구조, 실제 적용 결과와 실험 단계의 확장 범위를 혼동하지 않는다.
- 제거된 인사이트를 참조하는 끊어진 내부 링크를 만나지 않는다.

## 2. 승인된 콘텐츠 전략

균형형 구성을 사용한다.

- 작업물 상세는 약 5~7분 분량으로 유지한다.
- 작업물 상세에는 문제, 결과와 대표 설계 결정 네 개를 직접 제공한다.
- 통합 대표 인사이트는 약 8~10분 분량으로 발전 과정과 트레이드오프를 설명한다.
- Jenkins, Infisical, Cloudflare처럼 독립적인 인프라 문제 해결 글은 유지한다.
- 제거되는 짧은 인사이트 네 개는 redirect 없이 공개 경로에서도 제거한다.

작업물 상세는 결론과 현재 구조를 담당하고, 대표 인사이트는 시간에 따른 판단 과정과
설계 변화의 인과관계를 담당한다. 같은 사실을 양쪽에 사용할 수 있지만, 같은 장문을
복제하지 않는다.

## 3. 작업물 상세 콘텐츠 설계

### 3.1 제목 아래 설명

도구 이름을 나열하는 기존 설명 대신 프로젝트 가치를 한 문장으로 정의한다.

> 팀원과 AI 에이전트가 프로젝트마다 다르게 수행하던 설계·검증·배포 절차를 공통 정책,
> CLI와 CI/CD로 집행하는 사내 개발 운영 플랫폼입니다.

### 3.2 프로젝트 개요

Jenkins 비용과 운영 부담에서 출발했지만 실제 문제는 개발 운영 기준의 불일치였다는
발전 과정만 설명한다. 적용 프로젝트, 운영 프로젝트와 사용자 수는 바로 뒤의 지표에서
제공하므로 개요에서 반복하지 않는다.

### 3.3 나의 역할과 책임 범위

구현 항목을 길게 나열하지 않고 다음 세 책임 묶음으로 설명한다.

1. 하네스 아키텍처와 파일 소유권 정책
2. 초기화·진단·AI 작업 규칙 자동화
3. CI/CD·시크릿·실제 프로젝트 적용과 운영 검증

### 3.4 핵심 결과 요약

기존 여섯 지표와 값은 변경하지 않는다.

- 적용 프로젝트 11개
- 실제 운영 프로젝트 8개
- 팀 사용자 3명
- Jenkins 컴퓨팅 비용 추정 `$151.84/월`
- 5개 호텔 배포 시간 `약 15분 → 약 3분`
- 동일 유형 환경 혼입 `전환 후 미발생`

측정값, 사용자 보고값과 공개 가격 추정값의 구분, 기준 시점, 근거와
산정·측정·관찰 범위도 유지한다.

### 3.5 문제 상황과 제약 조건

문제 상황은 다음 세 가지 실제 문제로 압축한다.

1. 프로젝트마다 반복되는 초기화·배포 설정
2. 팀원과 AI 에이전트마다 달라지는 설계·TDD·코드 영역 규칙
3. 여러 호텔 배포에서 환경과 대상이 섞일 수 있었던 운영 위험

제약 조건은 별도로 구분한다.

- 사내 하네스 원본, 고객 코드와 시크릿은 공개할 수 없다.
- Claude Code와 Codex는 서로 다른 hook·규칙 형식으로 같은 정책 의미를 집행해야 한다.
- 하네스 업데이트는 프로젝트 소유 파일과 진행 중인 작업을 덮어써서는 안 된다.

### 3.6 대안 검토와 선택

다음 세 대안을 비교한다.

1. Jenkins를 유지하고 설정만 개선한다.
2. GitHub Actions workflow를 프로젝트마다 복사한다.
3. 공통 정책·CLI·검증 게이트를 포함한 하네스를 만든다.

선택 기준은 초기 도입 속도가 아니라, 프로젝트가 늘어나도 같은 기준을 안전하게
반복할 수 있는지로 둔다.

### 3.7 시스템 흐름

현재 연결형 스윔레인 두 개의 데이터, 렌더링과 문구는 변경하지 않는다.

- 설계·개발·검증
- CI/CD·시크릿·배포

### 3.8 핵심 설계와 구현

링크를 열지 않아도 구현 범위를 설명할 수 있도록 다음 네 설계 결정을 작업물 상세에
직접 제공한다.

#### `./harness`와 `doctor`

사람이 기억하던 프로젝트 초기화 체크리스트를 실행 명령과 재진단 가능한 계약으로
전환한 과정을 설명한다. CLI는 원하는 상태를 만들고 doctor는 현재 상태가 계약과
일치하는지 확인한다.

#### `harness.lock`과 소유권 경계

shared 업데이트와 project-owned 파일 보존을 함께 처리하는 구조를 설명한다. manifest와
lock을 기준으로 공통 파일을 materialize하되 로컬 변경과 프로젝트 자산을 자동으로
덮어쓰지 않는 트레이드오프를 포함한다.

#### 공통 정책과 런타임 어댑터

공통 정책 의미를 한곳에서 관리하고 Claude Code와 Codex의 서로 다른 규칙·hook 형식은
런타임 어댑터에서 집행하는 구조를 설명한다. 파일 내용의 동일성이 아니라 같은 입력에
대한 허용·차단 결과를 패리티로 정의한다.

#### 변경 범위 기반 배포와 Infisical 경계

공통 변경은 전체 호텔, 호텔별 변경은 해당 대상만 배포하는 matrix와 환경별 시크릿 조회
경계를 설명한다. 이 결정이 배포 시간과 환경 혼입 관찰 결과에 어떻게 연결되는지 함께
제공한다.

각 설계 결정은 `발생한 문제 → 선택한 구조 → 실제 검증 또는 트레이드오프` 순서의
짧은 2~3문단으로 작성한다.

### 3.9 결과와 검증 근거

지표를 단순 반복하지 않고 설계 결정과 결과의 인과관계를 연결한다.

- 변경 범위 계산과 병렬 matrix → 약 15분에서 약 3분
- Infisical 환경 경계 → 동일 유형 환경 혼입 전환 후 미발생
- CLI·doctor·공통 정책 → 11개 적용, 8개 운영, 3명 사용
- Jenkins 제거 → 공개 가격 기준 월 `$151.84` 컴퓨팅 추정 범위 제거

### 3.10 회고와 다음 개선

다음 두 판단을 회고의 중심으로 사용한다.

> 재사용성은 파일을 복사하기 쉽게 만드는 것이 아니라, 공통 변경을 프로젝트 소유권을
> 침범하지 않고 안전하게 전파하는 능력이다.

> guardrail은 개발자와 AI 에이전트를 느리게 만드는 장치가 아니라, 빠르게 작업하더라도
> 반드시 지켜야 하는 경계를 제공하는 장치다.

멀티 세션과 컨텍스트 수명 자동화는 완료된 핵심 기능이 아니라 다음 운영 확장 실험으로
구분한다.

### 3.11 관련 인사이트

작업물 본문의 `핵심 설계와 구현`에서는 통합 대표 인사이트 하나만 직접 연결한다.
Jenkins, Infisical, Cloudflare 등 독립 글은 기존 하단 관련 인사이트 목록에서 탐색하게
해 본문 안의 링크 나열을 줄인다.

## 4. 통합 대표 인사이트 설계

### 4.1 정체성

- 대표 slug: `codi-harness-dx-platform-design`
- 제목: `DX 하네스 v2: 복사형 도구에서 사내 개발 운영 플랫폼까지`
- 공개 읽기 시간: `9 min`
- 서사 방식: 발전 과정 중심

### 4.2 본문 순서

#### 1. Jenkins 제거가 출발점이었다

Jenkins 비용과 운영 부담, GitHub Actions·Infisical 전환을 짧게 설명한다. workflow를
프로젝트마다 복사하는 것만으로는 반복 설정과 운영 기준 문제가 남는다는 발견으로 다음
단계를 연결한다. Jenkins·Infisical 상세 구현은 기존 독립 인사이트에 맡긴다.

#### 2. v1: 복사는 설치를 쉽게 했지만 업데이트를 어렵게 했다

공통 정책과 skill을 프로젝트마다 복사했던 초기 구조, 프로젝트별 버전 드리프트와
공통 변경 전파 비용을 설명한다. 문제를 저장소 용량이 아니라 업데이트 전파와 소유권으로
재정의한다.

#### 3. `harness.lock`: 재사용성을 안전한 변경 전파로 다시 정의하다

shared/project-owned 경계, manifest·lock 기반 materialize, 로컬 변경 덮어쓰기 차단과
stale 파일 정리 범위를 설명한다. 업데이트 로직의 복잡성과 프로젝트 자산 보호의
트레이드오프를 함께 기록한다.

#### 4. `./harness`와 `doctor`: 체크리스트를 내부 제품으로 만들다

저장소, profile, Infisical, workflow와 브랜치 설정을 사람이 기억하던 문제에서 출발한다.
CLI의 상태 생성과 doctor의 계약 재진단을 분리하고, 자동화 가능한 범위와 사용자 승인이
필요한 외부 상태 변경의 경계를 설명한다.

#### 5. AI 작업 규칙: 문서를 복사하는 것에서 행동을 검증하는 것으로

Spec 문서화, TDD, 코드 소유권, 스킬 선택, 위험 명령과 PR 규칙을 공통 정책으로 묶은
이유를 설명한다. Claude/Codex 런타임 어댑터, `context-check`, `rule-check`, hook payload와
transcript replay를 통해 규칙의 존재가 아니라 관찰 가능한 집행 결과를 검증한 과정을
다룬다. GSD→Spec Kit과 GStack→Playwright MCP 전환 이유도 이 발전 단계에 포함한다.

#### 6. 멀티 세션: 규칙 통일에서 실행 환경 격리로 확장하다

모든 프로젝트의 기본 기능이 아니라 약 2주 동안 수행한 운영 확장 실험임을 명시한다.
planner·worker·shipper, worktree·container·database schema·port 격리, spec·plan·미완료
task를 durable state로 사용하는 방식을 설명한다. context clear·compact 시점 자동화는
해결되지 않은 과제로 남긴다.

#### 7. 결과: 하네스가 관리하는 것은 파일이 아니라 반복 가능한 작업 방식이다

11개 프로젝트 적용, 8개 운영 프로젝트와 팀원 3명 사용을 한 번만 인용한다. 운영 중인
핵심 구조와 멀티 세션 확장 실험을 구분한다.

#### 8. 회고

다음 문장으로 글을 수렴한다.

> 내부 도구의 가치는 기능 수가 아니라, 팀이 같은 기준으로 안전하게 반복할 수 있는 일을
> 얼마나 늘렸는가로 판단해야 한다.

### 4.3 운영 성숙도 구분

- 운영 중인 핵심 구조: lock·소유권 경계, CLI·doctor, 정책·런타임 집행
- 실제 적용 결과: 11개 적용, 8개 운영, 3명 사용
- 운영 확장 실험: 멀티 세션과 컨텍스트 수명주기 자동화

## 5. 콘텐츠 정본

### `features.ts`

제목, 한 문장 설명, 개요, 기간, 팀과 기술 스택만 관리한다. 하네스의 사용되지 않는 긴
`content`는 제거한다.

### `feature-details/codi-harness-dx-platform.ts`

역할, 지표, 문제·제약, 대안, 스윔레인, 대표 설계 결정, 결과와 회고를 관리하는 작업물
상세의 유일한 정본으로 사용한다.

### `insights.ts`

`codi-harness-dx-platform-design`을 통합 대표 인사이트로 사용한다. 이 객체의 오래된
`legacyContent`를 제거하고 새 발전 과정 본문을 유일한 `content` 정본으로 사용한다.

다음 네 인사이트 객체와 공개 경로는 제거한다.

- `harness-lock-and-project-ownership-boundary`
- `harness-cli-and-doctor-productization`
- `claude-codex-policy-parity-and-regression-testing`
- `multi-session-testbed-and-context-lifecycle`

## 6. 링크와 경로 처리

- 제거된 네 slug에는 redirect를 만들지 않는다.
- 제거된 네 slug를 참조하는 작업물, 인사이트와 테스트의 내부 링크를 모두 제거한다.
- 대표 인사이트의 기존 `codi-harness-dx-platform-design` URL은 유지한다.
- 작업물 본문은 대표 인사이트 하나만 강하게 연결한다.
- 하단 관련 인사이트 목록은 유지된 독립 인프라 글을 계속 제공한다.
- 제거된 네 URL에 직접 접근하면 404를 반환하는 것을 의도된 결과로 검증한다.

## 7. 변경하지 않는 범위

- 연결형 스윔레인 데이터, 문구와 SVG 구조
- 지표 값, 근거 종류와 Jenkins 비용 산정 범위
- 하네스의 데모 없음 정책
- 하네스 외 7개 작업물의 본문과 경로
- Jenkins·Infisical·Cloudflare 독립 인사이트
- 작업물 상세의 공통 10개 제목 순서
- 구조화 상세이 없는 작업물의 legacy fallback

## 8. 검증 설계

콘텐츠 변경도 실패 테스트를 먼저 확인하는 TDD 순서로 진행한다.

### 8.1 데이터 계약

- 하네스 `features.ts.content`가 제거됐는지 확인한다.
- 대표 인사이트에 `legacyContent`가 없는지 확인한다.
- 제거 대상 네 slug가 insight registry에 없는지 확인한다.
- 통합 인사이트가 승인된 발전 단계 여덟 개를 순서대로 포함하는지 확인한다.
- 대표 인사이트의 읽기 시간이 `9 min`으로 갱신됐는지 확인한다.

### 8.2 서버 렌더링

- 작업물 상세에 대표 설계 결정 네 개가 표시되는지 확인한다.
- 설명·개요·문제 상황이 같은 역할의 문장을 반복하지 않는지 확인한다.
- 기존 두 스윔레인과 여섯 지표가 유지되는지 확인한다.
- 회고의 두 핵심 판단이 표시되는지 확인한다.
- 제거된 네 인사이트 링크가 공개 HTML에 남지 않는지 확인한다.

### 8.3 브라우저 회귀

- 하네스 작업물에서 통합 대표 인사이트로 이동할 수 있어야 한다.
- 대표 인사이트가 새 제목과 승인된 발전 순서를 제공해야 한다.
- 제거된 네 URL은 404를 반환해야 한다.
- Jenkins·Infisical·Cloudflare 인사이트는 정상 접근해야 한다.
- 전체 작업물 8개와 하네스 외 7개 본문이 유지돼야 한다.
- 320, 768, 1024, 1440px에서 페이지 overflow와 스윔레인 키보드 탐색 계약이 유지돼야
  한다.

### 8.4 완료 조건

- 작업물 상세만 읽어도 문제, 본인 역할, 대표 구현 네 개와 결과를 설명할 수 있다.
- 대표 인사이트만 읽어도 v1 복사 구조에서 멀티 세션 실험까지의 발전 이유를 설명할 수
  있다.
- 같은 사실을 가진 숨은 장문 정본이 남지 않는다.
- 제거된 slug를 참조하는 내부 링크는 0개다.
- 기존 공개 지표의 값과 근거 범위는 변경되지 않는다.
- 스윔레인, 다른 작업물과 유지 대상 인사이트에 회귀가 없다.

## 9. 설계 자체 검토 기준

- 미정 표현이나 후속 구현자가 선택해야 하는 분기 없이 파일별 정본이 확정돼야 한다.
- 작업물 상세과 대표 인사이트가 같은 장문을 중복하지 않아야 한다.
- 운영 중 구조와 멀티 세션 실험을 같은 성숙도로 표현하지 않아야 한다.
- 제거되는 공개 경로와 유지되는 대표 경로가 명확해야 한다.
- 사용자가 승인한 균형형 분량과 발전 과정 중심 서사를 유지해야 한다.
