# 포트폴리오 콘텐츠 작성 규칙·스킬 설계

날짜: 2026-08-25

상태: 사용자 설계 승인 완료, 구현 전 검토 대기

Size: Large

## 1. 목표

작업물 상세만 공통 구조로 이전하고 인사이트는 기존 형식에 맡기는 방식을 중단한다.
앞으로는 작업물 하나를 정리할 때 연결 인사이트까지 같은 근거와 편집 기준으로 함께
완결한다.

Claude Code와 Codex가 이 기준을 세션마다 일관되게 적용하도록 다음 세 요소를
프로젝트 소유 영역에 둔다.

1. 상시 규칙: 포트폴리오 콘텐츠 작업에서 전용 스킬을 반드시 사용하게 한다.
2. 프로젝트 로컬 스킬: 작업물·인사이트·공부 기록의 작성 및 검토 절차를 제공한다.
3. 앱 데이터 계약 테스트: 연결, 사실 일치와 시각 증거 계약을 기계적으로 검증한다.

별도의 `docs/portfolio-content-standard.md`는 만들지 않는다. 사람이 필요할 때만 읽는
문서는 에이전트 행동을 안정적으로 유도하지 못하므로, 상세 편집 기준은 스킬과 그
참조 자료가 소유한다.

## 2. 범위

### 포함

- 작업물 구조화 상세의 공통 의미 계약
- 인사이트 두 유형과 공통·유형별 의미 계약
- 작업물·공부 기록·인사이트 사이의 연결 원칙
- 독립 인사이트 예외 정책
- 작업물과 연결 인사이트의 사실·수치·시점 교차 검증
- 스윔레인, ERD 등 시각 자료의 필요성 판정 계약
- 완료된 하네스·한마음·블랙스톤 작업물의 연결 인사이트와 기존 공부 기록 연결
  인사이트 우선 점검
- 이후 남은 작업물을 상세와 인사이트가 포함된 단일 feature로 진행하는 방식
- Claude Code와 Codex가 함께 읽을 수 있는 프로젝트 로컬 배선

### 제외

- 모든 인사이트에 동일한 제목이나 동일한 목차 문구 강제
- 작업물 또는 인사이트마다 같은 수의 시각 자료 강제
- 아직 인터뷰하지 않은 작업물의 사실 재작성
- 연결 근거가 없는 인사이트를 임의로 작업물이나 공부 기록에 귀속
- 공용 `.harness/skills/**` 또는 `.harness/policies/**` 수정
- 명령 차단용 hook이나 `.codex/rules` 추가
- 기존 전체 인사이트 18개의 일괄 재작성

## 3. 현재 상태와 문제

구조화 상세는 하네스, 한마음 과학원, 블랙스톤 벨포레 리조트까지 같은 렌더링 계약과
읽기 순서를 사용한다. 그러나 인사이트는 프로젝트별 개수, 목적, 목차, 근거 표기와
연결 수준에 편차가 있다.

기존 작업에서 작업물의 사실을 정정할 때 연결 인사이트도 함께 수정해야 했다. 한마음
검색과 블랙스톤 API Key 사례처럼 상세만 수정하면 링크를 따라간 독자가 정정 전
서술을 다시 만나게 된다. 따라서 작업물 상세와 연결 인사이트는 별도 콘텐츠가 아니라
하나의 사실 계약을 공유하는 두 표현으로 취급해야 한다.

## 4. 정보 구조 결정

### 4.1 작업물, 공부 기록, 인사이트의 역할

- **작업물**: 문제, 본인의 역할, 선택, 핵심 구현, 결과와 회고를 빠르게 판단하는
  포트폴리오의 주 진입점이다.
- **공부 기록**: 무엇을 학습했고 어떤 자료와 실험을 거쳐 이해가 바뀌었는지 기록한다.
- **인사이트**: 작업물 또는 공부 기록에서 나온 하나의 질문을 더 깊게 분석하고,
  다른 상황에서도 사용할 수 있는 판단 기준으로 정리한다.

작업물과 공부 기록은 출발점이고 인사이트는 그 출발점에서 확장된 발행물이다. 같은
문장을 반복하지 않고 각각의 독자가 얻어야 할 답을 구분한다.

### 4.2 인사이트 유형

인사이트는 다음 두 유형을 유지한다.

#### 프로젝트 사례형

실제 작업물에서 발생한 문제, 판단, 구현과 결과를 깊게 확장한다.

필수 의미:

- 본인이 맡은 역할과 책임 범위
- 실제 발생한 문제와 당시 시점
- 당시 환경과 제약
- 검토하거나 실제로 시도한 접근
- 선택한 설계와 구현 방식
- 결과와 검증 근거
- 확인하지 못한 범위와 회고

#### 기술 탐구형

공부 과정에서 출발한 기술 원리, 대안, 실험과 적용 기준을 정리한다.

필수 의미:

- 학습을 시작한 질문
- 참고 자료와 직접 확인한 실험의 구분
- 핵심 개념과 대안 비교
- 적용하기 좋은 조건과 피해야 할 조건
- 한계, 반례와 추가 검증 범위
- 연결된 공부 기록에서 확인할 수 있는 학습 맥락

### 4.3 공통 의미 계약

두 유형 모두 다음 질문에 답해야 한다. 실제 Markdown 제목은 글의 흐름에 맞게 바꿀
수 있고 아래 문구를 그대로 복사할 필요는 없다.

1. 이 글이 답하려는 질문과 먼저 전달할 결론은 무엇인가?
2. 왜 이 주제를 다루게 됐으며 어느 작업물 또는 공부 기록에서 출발했는가?
3. 당시 또는 실험 환경의 제약과 판단 기준은 무엇인가?
4. 어떤 접근을 분석·선택·배제했고 그 이유는 무엇인가?
5. 실제 결과 또는 실무 적용 기준은 무엇인가?
6. 확인하지 못한 범위와 현재의 회고는 무엇인가?
7. 독자가 함께 읽어야 할 관련 기록은 무엇인가?

통일 대상은 의미와 근거 수준이다. 모든 글이 같은 목차의 복사본처럼 보이게 만들지
않는다.

## 5. 연결과 출처 계약

모든 인사이트는 원칙적으로 작업물 또는 공부 기록 중 하나에 연결한다.

```text
작업물 ── 프로젝트 사례형 인사이트
공부 기록 ── 기술 탐구형 인사이트
```

연결은 단순 분류 태그가 아니라 글의 출발 근거다. 연결된 양쪽 상세 화면에서 서로
왕복할 수 있어야 한다.

기존 독립 인사이트는 다음 순서로 처리한다.

1. 내용과 발생 배경을 검토한다.
2. 적절한 작업물 또는 공부 기록이 있으면 근거와 함께 연결한다.
3. 연결 근거가 없다면 억지로 귀속하지 않는다.
4. 독립 글로 유지할 가치가 있으면 그 이유를 데이터에 기록한다.
5. 출처와 독립 유지 이유가 모두 없으면 통합 또는 비공개 후보로 분류한다.

연결 대상과 실제 글의 유형이 다른 경우 자동으로 고치지 않는다. 글의 내용이 잘못
분류됐는지, 출발 기록이 잘못 연결됐는지 편집 판단을 먼저 남긴다.

프로젝트 사례형은 실제 작업물 사례를 전제로 하므로 유효한 작업물 연결이 반드시
필요하다. 기술 탐구형은 공부 기록 연결을 원칙으로 하되, 기존 독립 기술 글처럼 연결할
근거가 없는 예외만 독립 유지 이유를 사용할 수 있다. 작업물 연결도 독립 유지 이유도
없는 프로젝트 사례형은 허용하지 않는다.

## 6. 작업물과 인사이트의 동시 진행 계약

앞으로 남은 작업물은 다음 단위를 하나의 feature로 취급한다.

```text
인터뷰
→ 작업물 구조화 상세
→ 인사이트 후보 판정
→ 기존 인사이트 유지·수정·통합·삭제·신규 작성 결정
→ 연결 인사이트 작성 또는 정정
→ 상세·인사이트 교차 검증
```

작업물 상세를 먼저 뼈대로 작성하되, 연결 인사이트를 별도 후속 프로젝트로 미루지
않는다. 작업물에는 전체 판단 흐름을 남기고, 특정 판단의 원리·구현·트레이드오프가
길어질 때만 인사이트로 확장한다.

작업물마다 같은 수의 인사이트를 만들지 않는다. 하나의 강한 인사이트로 충분할 수
있고, 독립적인 판단이 여러 개라면 복수 글을 허용한다. 인사이트 수보다 각 글의
독립된 질문과 근거가 중요하다.

## 7. 사실과 근거 계약

우선순위는 다음과 같다.

```text
사용자가 확정한 인터뷰 사실
→ 해당 feature의 spec·research·data model
→ 포트폴리오 콘텐츠 공통 규칙과 스킬
→ 기존 공개 본문
```

작업물과 연결 인사이트는 역할, 수치, 기준 시점, 문제 원인, 검토 대안과 결과의 사실
계약을 공유한다.

- 확인하지 않은 수치나 비율을 만들지 않는다.
- 사용자가 전달한 값, 직접 측정값과 계산값을 구분한다.
- 수치에는 기준 시점, 근거 설명과 필요한 관찰 한계를 둔다.
- 하지 않은 대안 검토를 설계 판단처럼 추가하지 않는다.
- 전달받은 원인을 직접 규명한 사실처럼 단정하지 않는다.
- 당시 사실과 현재 상태가 달라졌다면 시점을 분리한다.
- 일반론이나 모범 사례를 당시 구현 사실로 바꾸지 않는다.
- 작업물 정정이 연결 인사이트에 영향을 주면 같은 feature에서 함께 수정한다.

## 8. 시각 증거 계약

원칙은 **“인사이트당 다이어그램 의무화”가 아니라 “필요성 판정 의무화”**다.

각 인사이트는 다음 중 하나를 명시적으로 판정한다.

- 없음
- 스윔레인 또는 시퀀스 다이어그램
- ERD
- 아키텍처 또는 데이터 흐름도
- 상태 전이도
- 비교표 또는 결정 매트릭스
- 타임라인

### 선택 기준

| 설명 대상 | 우선 표현 | 사용하는 조건 |
| --- | --- | --- |
| 여러 주체의 요청·응답·실패·복구 | 스윔레인·시퀀스 | 주체가 3개 이상이거나 예외 경로가 핵심일 때 |
| 테이블 관계와 정합성 제약 | ERD | 데이터 관계가 결론의 근거일 때 |
| 시스템 경계와 데이터 이동 | 아키텍처·데이터 흐름도 | 프론트·백엔드·외부 시스템 경계가 중요할 때 |
| 상태와 재시도 | 상태 전이도 | 정상·실패·복구 상태를 구분해야 할 때 |
| 복수 대안의 선택 | 비교표·결정 매트릭스 | 세 개 이상의 대안을 같은 기준으로 비교할 때 |
| 설계 발전 과정 | 타임라인 | 문제 발견과 개선 순서가 핵심일 때 |
| 단순한 순차 설명 | 번호 목록 | 복잡한 관계나 분기가 없을 때 |

아래 중 하나에 해당하면 시각 자료를 우선 검토한다.

- 세 개 이상의 구성요소가 서로 영향을 준다.
- 정상 경로와 실패·복구 경로가 함께 존재한다.
- 데이터 관계나 소유권 경계가 결론의 근거다.
- 세 개 이상의 대안을 동일 기준으로 비교한다.
- 글만으로 설명하면 독자가 앞부분을 다시 읽어야 한다.

시각 자료를 사용하면 다음 정보가 필요하다.

- 자료 유형
- 이 자료가 답하는 질문
- 노드와 연결 관계
- 정상·예외 또는 선택·기각 구분
- 그림을 보지 못하는 독자를 위한 텍스트 설명
- 연결 작업물의 시각 자료와 중복되지 않는 이유

작업물의 시각 자료는 전체 시스템의 핵심 흐름을 요약하고, 인사이트의 시각 자료는
특정 판단을 확대한다. 같은 다이어그램을 양쪽에 복제하지 않는다.

## 9. 에이전트 배선

### 9.1 상시 규칙

프로젝트 소유 경로에 다음 파일을 둔다.

```text
.harness/rules-local/portfolio-editorial-standard.md
```

이 파일은 상세 절차를 반복하지 않고 다음 역할만 맡는다.

- 작업물·인사이트·공부 콘텐츠 작업에서 전용 스킬 사용을 요구한다.
- 인터뷰와 feature 기록을 기존 본문보다 우선한다.
- 작업물과 연결 인사이트를 같은 변경 단위에서 검증한다.
- 확인되지 않은 사실을 만들지 않는다.
- 시각 자료 필요성 판정을 생략하지 않는다.

이 규칙은 콘텐츠 판단에 관한 프로젝트 전역 불변 조건이므로 unscoped
`rules-local` 규칙이 적합하다. Claude Code는 `.claude/rules/local/` 링크로 읽고,
Codex는 루트 `AGENTS.md`의 기존 `rules-local` 로딩 계약을 따른다.

### 9.2 프로젝트 로컬 스킬

프로젝트 소유 경로에 다음 스킬을 둔다.

```text
.harness/skills-local/portfolio-content-authoring/
├── SKILL.md
├── evals/
│   └── evals.json
└── references/
    ├── project-detail-contract.md
    ├── insight-contract.md
    ├── evidence-and-linking.md
    └── visual-evidence.md
```

스킬은 다음 상황에서 사용한다.

- 작업물 인터뷰를 준비·진행·정리할 때
- legacy 작업물을 구조화 상세로 이전할 때
- 인사이트를 신규 작성, 수정, 통합 또는 검토할 때
- 공부 기록과 기술 탐구형 인사이트를 연결할 때
- 작업물과 연결 인사이트의 사실 충돌을 검토할 때
- 시각 자료 필요성과 유형을 판단할 때
- 포트폴리오 콘텐츠를 리뷰할 때

`SKILL.md`는 전체 흐름과 참조 선택 기준만 제공한다. 상세 계약은 필요한 reference만
읽게 해 컨텍스트 사용량을 제한한다.

`./harness skills-link`가 로컬 스킬을 Claude Code와 Codex의 스킬 트리에 연결한다.
공용 `.harness/skills/**`는 수정하지 않는다.

`.harness/rules-local/**`와 `.harness/skills-local/**`는 AI가 직접 읽는 파일이므로
규칙과 스킬의 설명 문장은 영어로 작성한다. 사용자에게 노출되는 예시 문구와 실제
포트폴리오 콘텐츠는 한국어를 유지한다.

### 9.3 배치 근거

새 구성요소의 steering 분류는 다음과 같다.

1. **Compaction 생존**: 핵심 트리거는 상시 규칙으로 유지해야 한다.
2. **지속성**: 이 저장소 전체에서 지속되는 팀 규칙이다.
3. **Trigger**: 포트폴리오 작업물·인사이트·공부 콘텐츠를 작성하거나 검토할 때다.
4. **Scope**: 상시 규칙은 프로젝트 전체, 상세 절차는 요청 시 로드되는 스킬이다.
5. **Override**: 사용자 확정 인터뷰와 feature spec이 일반 편집 규칙보다 우선한다.

이 규칙은 명령 prefix나 파일 쓰기를 차단하는 정책이 아니다. `.codex/rules`와 hook은
편집 판단을 강제할 수 없으므로 추가하지 않는다. Codex의 스킬 자동 선택이 완전한
결정론은 아니라는 한계는 상시 `rules-local` 트리거와 데이터 계약 테스트로 보완한다.

## 10. 스킬 작성과 평가

새 스킬은 skill TDD 방식으로 작성한다. 스킬을 먼저 쓰지 않고, 기존 규칙만 받은
에이전트가 대표 상황에서 어떤 판단을 누락하는지 baseline을 확인한다.

### 평가 시나리오

1. 작업물 상세만 정정하고 연결 인사이트를 누락하려는 상황
2. 모든 인사이트에 동일한 목차를 강제하려는 상황
3. 공부 기록과 기술 탐구형 인사이트가 같은 내용을 반복하는 상황
4. 연결 근거 없이 독립 인사이트를 유지하는 상황
5. 단순한 글에 ERD나 스윔레인을 장식처럼 추가하려는 상황
6. 작업물과 인사이트가 같은 수치·원인·시점을 다르게 표현하는 상황

각 시나리오는 스킬 없는 baseline과 스킬 적용 결과를 비교한다. 성공 여부는 다음으로
판단한다.

- 두 인사이트 유형을 올바르게 구분한다.
- 공통 의미 계약과 유형별 의미 계약을 함께 적용한다.
- 작업물 또는 공부 기록 연결을 확인한다.
- 독립 유지 예외에는 이유를 요구한다.
- 시각 자료 필요성을 판단하고 불필요한 자료를 거부할 수 있다.
- 작업물과 연결 인사이트의 교차 검증을 작업 범위에 포함한다.
- 확인되지 않은 사실을 만들지 않는다.

## 11. 데이터 계약과 검증

구현 단계에서는 먼저 실패하는 계약 테스트를 작성한 뒤 최소 데이터·타입·UI 변경으로
통과시킨다.

검증 대상:

- 인사이트 유형이 승인된 두 값 중 하나다.
- 프로젝트 사례형은 유효한 작업물 연결을 가진다.
- 기술 탐구형은 유효한 공부 기록 연결 또는 비어 있지 않은 독립 유지 이유를 가진다.
- 작업물·공부 기록 연결이 없는 기술 탐구형만 독립 유지 예외를 사용할 수 있다.
- 존재하지 않는 작업물·공부·인사이트를 연결하지 않는다.
- 양방향 탐색 링크가 끊기지 않는다.
- 작업물과 연결 인사이트의 금지 표현 및 정정 사실이 일치한다.
- 시각 자료 필요성 판정이 존재한다.
- 시각 자료가 있으면 질문, 텍스트 설명과 중복 방지 근거가 존재한다.
- 기존 공개 경로와 인터뷰 전 legacy 본문이 보존된다.

이 계약은 콘텐츠 의미 전체를 자동 판정하려는 것이 아니다. 타입, 연결, 필수 근거와
이미 확정된 사실처럼 기계적으로 검증 가능한 경계를 맡는다. 편집 품질과 사실 해석은
스킬 절차와 사용자 리뷰가 담당한다.

## 12. 점진 적용 순서

사용자가 승인한 A안을 따른다.

### 1단계: 공통 기반

- 상시 규칙 작성
- 프로젝트 로컬 스킬과 reference 작성
- baseline·with-skill 평가
- 인사이트 유형, 연결과 시각 자료 판정 데이터 계약 설계

### 2단계: 완료된 작업물 우선 점검

이미 구조화된 다음 세 작업물의 직접 연결 인사이트와 기존 공부 기록에 연결된 기술
탐구형 인사이트 하나를 계약에 맞춰 점검한다.

- Codi Harness DX Platform
- 한마음 과학원
- 블랙스톤 벨포레 리조트
- AI DX Harness Starter Kit 공부 기록

기존 글을 전면 재작성하지 않는다. 유형, 연결, 사실 정합성, 중복과 시각 자료 필요성만
판정하고 필요한 범위에서 수정한다.

### 3단계: 남은 작업물

남은 작업물은 하나씩 인터뷰한 뒤 작업물 상세와 연결 인사이트를 같은 feature로
완결한다. 아직 인터뷰하지 않은 작업물과 연결 글은 추측으로 먼저 구조화하지 않는다.

### 4단계: 독립 인사이트 정리

작업물 이전이 진행되며 충분한 출처 맥락이 확보된 뒤, 남은 독립 인사이트를 연결,
독립 유지, 통합 또는 비공개 후보로 분류한다.

## 13. 오류 처리와 보존 원칙

- 연결 대상이 모호하면 임의 연결하지 않고 사용자 판단 항목으로 남긴다.
- 인터뷰와 기존 인사이트가 충돌하면 기존 글을 정본으로 취급하지 않는다.
- 시각 자료 판정이 `없음`이어도 정상적인 완료 상태로 인정한다.
- 기존 공개 URL 변경이나 글 삭제는 별도 승인 없이 수행하지 않는다.
- 완료된 작업물의 확정 사실을 새 공통 템플릿에 맞춘다는 이유로 약화하지 않는다.
- 저장소 전역 lint baseline과 무관한 파일은 포맷하지 않는다.
- 사용자 작업과 관련 없는 dirty worktree 변경을 보존한다.

## 14. 완료 기준

다음 조건을 모두 만족하면 공통 기반 feature가 완료된다.

1. 상시 규칙이 프로젝트 소유 경로에 존재하고 양 런타임에서 발견된다.
2. 프로젝트 로컬 스킬이 작업물·인사이트·공부 콘텐츠 요청에 맞게 trigger된다.
3. baseline 실패와 스킬 적용 개선이 대표 평가 시나리오에서 확인된다.
4. 두 인사이트 유형, 연결과 독립 예외를 데이터가 표현할 수 있다.
5. 시각 자료 필요성 판정과 선택적 증거가 데이터로 표현된다.
6. 완료된 세 작업물의 연결 인사이트가 새 계약으로 분류·점검된다.
7. 작업물과 연결 인사이트 사이에 확정된 사실 충돌이 없다.
8. 기존 작업물·공부·인사이트 공개 경로가 보존된다.
9. 변경 범위의 타입 검사, 단위 테스트, lint, 빌드와 E2E가 통과한다.
10. feature spec의 verification 기록과 `ROADMAP.md` 상태가 수렴한다.

## 15. 후속 계획 경계

이 문서는 설계 결정만 소유한다. 구현 계획의 정본은 새
`specs/<NNN-portfolio-content-authoring>/` feature에서 만든다.

설계 검토 승인 후 다음 순서로 진행한다.

1. `speckit-specify`로 공통 기반 feature 명세 작성
2. clarify 필요 여부 보고 후 사용자 handoff
3. 사용자의 명시적 `codi-auto-loop` 시작 지시
4. plan·tasks·analyze와 tasks 검토 게이트
5. skill TDD와 앱 TDD 기반 구현
6. review·verification·converge
