## 공개 범위 결론

- 하이패스 이전에는 전화·팩스·카카오톡으로 주문하고 모든 결제를 계좌이체로 받았다.
- 하이패스는 기존 온라인 주문 시스템을 전환한 작업이 아니라 주문·승인·배송·결제·정산 전체 흐름을 새로 구축한 프로젝트다.
- 백엔드는 사용자가 혼자 담당했다. 프론트엔드는 사용자를 포함한 두 명이 개발했고, 사용자가 초기 디렉터리·상태 관리 기준을 제안하고 직접 기능도 구현했다.
- 사용자 작업 기간 `2024.08 – 2025.08`은 기능 설계부터 유지보수 단계의 마지막 코드 수정까지다.
- 신규 주문·정산 운영은 2026년 6월 종료됐고 현재는 관리자 조회와 데이터 보존 용도로 일부 기능이 유지된다.
- 프로젝트의 전면 메시지는 1인 백엔드 코어 기능 구축, 실제 현금 이동이 있는 결제·정산 안정성, 프론트엔드 협업 구조 기여 순서다.

## 운영 규모와 근거 경계

- 월 주문 약 100건과 월 결제액 약 400~500만 원은 월말 보고서와 관리자·DB 운영 기록을 반복 확인한 값이다.
- 월 약 70건은 전체 정산 실행 수나 지급 건수가 아니라 정산에 포함된 완료 주문 수다.
- 등록된 정산 대상 화원은 약 50곳이고 한 달에 실제 지급된 화원은 약 10~20곳이다.
- 정산은 매월 두 번 실행됐다.
- 운영팀은 월말 보고서 제출 때마다 내부 정산 내역과 지급대행사의 실제 지급 내역을 대조했다.
- 2026년 6월까지 반복한 대사 범위에서는 정산 금액 불일치와 중복 지급을 확인하지 못했다. 시스템 전체에 대한 자동 검증이나 무결성 보장으로 확대하지 않는다.

## 결제와 보상 취소

- 내부 주문 데이터는 DB 트랜잭션으로 처리하지만 외부 Toss 결제 승인까지 하나의 원자적 트랜잭션으로 묶인 구조는 아니다.
- 결제 승인 뒤 주문 저장이 실패하면 내부 DB 작업을 롤백하고 승인된 결제를 취소한다.
- 개발 환경에서 결제 승인 후 DB 오류를 의도적으로 발생시켜 자동 취소 성공을 확인했다.
- 결제 취소 API 자체가 실패하는 이중 실패도 개발 환경에서 재현했지만 별도 복구 절차는 구현하지 않았다.
- 이중 실패가 운영에서 발생한 사례는 확인하지 못했다.
- 현재 회고에서는 취소 API 실패 시 즉시 운영자에게 알리고 결제 내역을 확인한 뒤 수동 취소할 수 있는 절차를 두는 방향을 선택한다.

## 정산 상태와 JSON의 역할

- DB의 정산 상태 `PENDING → PROCESSING → COMPLETED`가 지급 여부의 판단 기준이다.
- 지급 요청 직전에도 UUID로 DB 상태를 다시 조회하고 `PROCESSING`인 건만 지급대행사로 보낸다. 이미 `COMPLETED`인 건은 다시 지급하지 않는다.
- JSON은 정산 상태의 원본이 아니다. 복잡한 쿼리로 계산한 정산 대상·금액·지급 입력을 보존하고 실패 후 같은 결과를 다시 쓰기 위한 보조 저장소다.
- 지급 성공 항목은 DB를 완료 처리한 뒤 JSON에서 제거하고, 실패 항목만 남긴다.
- 남은 실패 항목은 매일 10시·14시 스케줄에서 DB 상태를 다시 확인한 뒤 성공할 때까지 재시도한다.
- 정산 스케줄러는 웹 서버와 분리된 단일 PM2 프로세스로 실행했다. 다중 웹 워커에서 스케줄이 중복 실행되는 것을 막고 정산 작업의 오류·자원 사용을 웹 요청 처리와 분리하려는 목적이었다.
- 2026년 6월까지 JSON 파일 유실·손상·중복 실행 문제는 확인하지 못했다.
- 당시 Outbox, RabbitMQ, Kafka를 알지 못했고 대안으로 비교하지 않았다. 현재 구현을 `간이 Outbox`라고 부르지 않는다.
- 단일 서버·단일 스케줄러·작은 정산 규모에서는 적용 가능한 방식으로 판단한다. 로드밸런싱·스케일 아웃 환경에는 로컬 JSON을 그대로 적용하지 않는다.
- 현재 Redis 보존, DB 단독 관리, 스케줄러 개선 가능성을 고민하지만 비교·검증하지 않아 어느 하나를 정답으로 공개하지 않는다.

## Socket.io 전달 범위와 검증 한계

- 신규 구축 단계에서 Polling과 Socket.io를 비교하고 즉시 상태 전달을 위해 Socket.io를 선택했다. 기존 Polling 구현을 제거한 작업은 아니다.
- 초기에는 공용 Room을 사용했다.
- 개발 중 코드 재검토에서 관계없는 사용자도 주문 이벤트를 받을 수 있는 구조임을 발견했다. 운영 사고나 트래픽 시뮬레이션으로 발견한 것이 아니다.
- 주문 화원과 수주 화원의 `user_<gardenId>` Room에만 이벤트를 보내도록 변경했다.
- 개발 환경에서 서로 다른 화원 계정으로 관련 사용자에게만 이벤트와 화면 갱신이 전달되는 것을 확인했다. 성능 감소량은 측정하지 않았다.
- 공용 Room 시절 서버 송신 기록은 있으나 브라우저가 수신하지 못한 사례를 확인했다.
- User Room 전환 후에는 같은 유실 조건을 재현하는 방법을 찾지 못했다. 따라서 Room 변경으로 유실 문제가 해결됐다고 주장하지 않는다.
- 운영에는 PM2 3개 워커와 Socket.io cluster adapter 구성을 적용했고 브라우저에서 소켓 이벤트가 정상 동작하는 것을 확인했다.
- 다중 워커 사이의 내부 이벤트 전달 구조를 정확히 이해하거나 워커 간 전달만 분리해 검증하지 못했다.
- 당시 네트워크 단절·재연결 중 이벤트 유실 가능성까지만 인식했다. ACK, 재시도 큐·DLQ, Redis Stream cursor 복구, Redis Adapter를 직접 조사하거나 개선 로드맵으로 검토하지 않았다.
- 현재 적용 기준은 특정 사용자·조직 상태 이벤트는 사용자별 Room으로 제한하고, 모두에게 같은 정보가 필요한 공지성 이벤트만 공용 Room을 사용하는 것이다.
- 전달 범위 분리와 전달 보장은 서로 다른 문제로 공개한다.

## 프론트엔드 협업 구조

- 과거 프로젝트에서 작업자마다 구조가 달라졌던 경험을 바탕으로 하이패스 착수 때부터 기준을 세웠다.
- 기능·페이지 단위 디렉터리, 기능 내부 상태 관리, 로그인 사용자 정보 등 공통 값만 전역 상태로 두는 기준을 사용했다.
- 프론트엔드 두 명이 프로젝트 기간 동안 이 기준을 함께 따랐고 코드 리뷰와 유지보수 과정에서도 구조가 유지되는 것을 확인했다.
- 기능 코드 위치와 상태 소유 범위를 파악하기 쉬워졌고 같은 파일·전역 상태를 함께 수정하는 충돌과 재작업이 줄었다.
- 개발 속도나 생산성 향상을 수치로 측정하지 않았다.

## 철회·정정할 기존 주장

- JSON 파일을 Outbox 개념에서 도출하고 RabbitMQ·Kafka와 비교했다는 주장
- 향후 정규 Outbox와 MQ로 전환하겠다는 확정 로드맵
- 주문·결제·외부 결제가 하나의 서버 통제형 원자적 트랜잭션이라는 주장
- 실패 건을 `다음 영업일`에만 재처리한다는 주장
- 정산 재실행에서 DB 조회가 0회라는 주장
- 기존 HTTP Polling을 운영하다 제거했다는 주장
- 공용 Room이 현재 구조라는 주장
- 운영 모니터링·트래픽 시뮬레이션으로 소켓 문제를 발견했다는 주장
- User Room 변경으로 메시지 유실과 트래픽 문제까지 해결했다는 주장
- ACK, DLQ, Redis Stream, cursor 복구, Redis Adapter를 검토했다는 주장
- k6 결과와 테스트 회고. 실제 실행 기억은 있으나 이력·조건·결과가 없어 공개 근거로 사용하지 않는다.
- 월 70건을 정산 실행 수나 지급 화원 수로 표현하는 문장
- 현재 전체 거래 기능이 계속 운영 중이라는 `Production` 표현

## 시각화 결정

- 작업물은 주문 생성·결제 승인·DB 실패·자동 보상 취소와 취소 API 실패를 보여주는 스윔레인 하나를 제공한다.
- 정산 인사이트는 DB 상태, JSON 계산 결과, 지급 요청, 성공 제거, 실패 보존, 다음 10시·14시 재시도를 보여주는 상태·데이터 흐름을 제공한다.
- Socket.io 인사이트는 공용 Room과 화원별 User Room의 전달 대상을 비교하는 Before/After 구조도를 제공한다.
- 작업물은 결제 보상 흐름, 정산 인사이트는 저장 역할과 재처리, Socket.io 인사이트는 수신 대상 분리를 다뤄 시각·장문 중복을 피한다.
