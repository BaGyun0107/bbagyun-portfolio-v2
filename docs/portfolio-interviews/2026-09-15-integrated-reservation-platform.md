## 프로젝트 기본 사실

- 공개 제목은 `행사 호텔 예약·결제 통합 플랫폼`으로 정리한다.
- 기간은 `2025.12 – 2026.03`이다.
  - 2025년 12월은 요구사항 정리, 설계와 프로젝트 준비 기간이다.
  - 프론트엔드 Git 이력은 2026-01-05, 백엔드는 2026-01-07에 시작한다.
  - 백엔드는 2026-03-06에 작업 종료가 기록됐고, 프론트엔드의 2026-04-01 커밋은 Axios 버전 수정 1건이므로 공개 개발 기간을 늘리지 않는다.
- 기존 시스템 교체가 아니라 행사별 호텔 예약·결제 운영을 위한 신규 구축이다.
- 프로젝트는 고객사의 자금 문제로 중단됐다. 공개 문구에서는 고객사의 구체적인 자금 상황을 드러내지 않고 `고객사 측 사업 여건으로 개발 보류`라고 표현한다.
- 공개 상태는 `In Progress`가 아니라 `On Hold`다.
- 정식 운영은 시작하지 않았으며 운영 결제, 운영 건수, 운영 장애율과 성능 지표를 주장하지 않는다.

## 역할과 협업 범위

- 팀 구성은 FE 3명, BE 1명(본인)이며 사용자가 PM·PL을 겸임했다.
- 사용자는 고객사 소통, 요구사항 정리, 일정 조율, 프론트엔드 작업의 우선순위·분담과 API 계약 조율을 담당했다.
- 사용자는 데이터 모델, 관리자 인증, 객실·재고·예약·결제 API와 배포 환경을 포함한 백엔드 전반의 설계와 구현을 담당했다.
- 프론트엔드 개발자 한 명이 관리자 목록 API를 일시적으로 추가한 커밋 1건이 있다. 이는 공동 백엔드 담당자가 있었다는 뜻이 아니므로 `1인 백엔드` 서술은 사실과 일치한다.

## 고객사 검증 범위

고객사는 스테이징 환경에서 다음 핵심 흐름을 직접 확인하거나 UAT로 검증했다.

`행사 생성 → 호텔·객실·재고 등록 → 사용자 객실 조회·예약·결제 → 관리자 예약 확인·취소`

- 결제 승인과 취소는 PG 테스트 환경에서만 진행했다.
- 관광 예약, 결제 링크, 일부 엑셀 다운로드와 문서 템플릿은 보류 시점에 미완성 상태였다.
- 핵심 객실 예약 UAT가 완료됐다는 사실을 전체 프로젝트 완성이나 운영 검증으로 확대하지 않는다.

## Core Product 모델

- `Products`를 공통 상품 부모로 두고 객실과 관광을 각각 `ProductRooms`, `ProductTours`로 분리했다.
- 주문 항목은 상품별 테이블을 분기해 참조하지 않고 공통 `productId`를 참조한다.
- 이 구조를 선택한 직접적인 이유는 객실과 관광 상품을 하나의 주문·결제 구조에서 처리하기 위해서였다.
- 객실의 날짜별 재고는 빈번한 조회 경로를 짧게 유지하기 위해 객실과 객실 옵션을 직접 참조한다.
- 기존 공개 문구의 `JOIN Depth 5단계 이상 → 최대 3단계` 수치는 사용자가 기억하지 못하고 비교 기록도 확인되지 않으므로 삭제한다.
- 컴퓨터·마우스 같은 임의 상품 카테고리 예시는 실제 프로젝트 범위를 벗어나므로 삭제한다.
- 과거 화훼 프로젝트 전체 구조를 반복해 이 설계의 성과처럼 사용하지 않는다.

## 재고 충돌과 결제 경계

- 객실 재고의 `version`을 갱신 조건에 포함하고 다른 요청이 먼저 값을 변경해 갱신 건수가 0이 되면 충돌로 처리했다.
- 사용자는 동시성 상황을 단위 테스트로 확인했다.
- 저장소에는 실제 데이터베이스에 병렬 요청을 보내는 통합 테스트 근거가 없으므로 단위 테스트 수준으로만 공개한다.
- `불일치 0건`, `초과 예약 완전 방지`, `운영 정합성 보장`을 주장하지 않는다.
- 외부 PG 호출은 DB 트랜잭션 밖에서 실행한다.
- 구현 흐름은 주문과 재고를 먼저 `PAYMENT_PENDING` 상태로 기록하고 PG 승인을 요청한 뒤, 성공 결과를 별도의 내부 트랜잭션에서 확정하는 단계형 구조다.
- 최종 내부 반영 실패 시 PG 취소를 시도하는 로직은 구현했다.
- PG 승인 실패 시 주문을 `CANCELLED`, 결제 이력을 `ABORTED`로 바꾸지만 이미 차감한 재고의 즉시 복구는 보류 시점까지 미완성이었다.
- 기존 공개 문구의 `예약·결제·재고를 하나의 트랜잭션으로 묶었다`, `고아 재고 차감 0건`은 사실과 다르므로 삭제한다.
- 회고는 외부 결제가 끼는 흐름에서 각 실패 지점의 상태 전이, 보상, 재시도와 운영자 확인 절차를 함께 설계해야 한다는 현재 판단으로 작성한다.

## BFF와 Cloudflare 대응

- 실제 도메인을 공개하지 않는다.
- 공개 예시는 프론트엔드 `A-domain.com`, API `api.A-domain.com`으로 익명화한다.
- 두 주소는 같은 기본 도메인의 서로 다른 Origin이었다. 완전히 다른 최상위 도메인인 `A.com ↔ B.com`으로 표현하지 않는다.
- BFF 도입 전 브라우저가 API Origin을 직접 호출할 때 인증 쿠키의 저장·전달 실패를 실제로 확인했다.
- Next.js `/bff` rewrite를 통해 브라우저의 호출 Origin을 프론트엔드로 통일했다.
- 이 구현은 응답 조합·프론트 전용 가공·별도 권한 정책까지 갖춘 완성형 BFF가 아니라 reverse proxy로 BFF 경계를 만든 단계다.
- 이후 BFF 서버에서 NestJS API로 보내는 요청이 Cloudflare 봇 차단에 걸렸다.
- 사용자가 원인을 직접 확인하고 BFF 서버의 고정 IP를 Cloudflare 허용 규칙에 등록해 스테이징 통신과 인증 흐름을 복구했다.
- `전 환경 정상화`, `운영 장애 해결`, `스트리밍으로 병목 해결`과 같은 범위 밖 결과를 주장하지 않는다.

## NestJS Middleware와 Guard 회고

- 구현 당시 사용자는 Node.js와 Express에 익숙했고 NestJS 이해가 충분하지 않은 상태에서 익숙한 Middleware 방식을 먼저 선택했다.
- `AdminAuthMiddleware`는 관리자 경로의 Access/Refresh/CSRF 토큰 확인, 토큰 재발급, 쿠키 갱신과 `req.user` 주입을 담당했다.
- `AdminLevelGuard`는 엔드포인트에 필요한 최소 관리자 등급을 확인했다.
- 두 책임을 나눈 구현은 의도적이었지만, Middleware 자체의 선택이 NestJS의 권장 패턴을 충분히 비교한 결과는 아니었다.
- 현재 사용자는 다시 설계한다면 Global Auth Guard로 인증을 기본 적용하고 공개 경로만 제외하며, 관리자 등급은 별도의 권한 Guard로 분리하는 것이 알맞다고 판단한다.
- 기존 인사이트의 `Guard보다 Middleware가 더 견고했다`, `Guard 선언 누락 가능성을 없앴다`는 결론을 삭제한다.

## HTTPS와 비밀번호 전송 회고

- 사용자는 개발자 도구의 Request Payload에 비밀번호가 보이는 것을 네트워크 평문 노출로 오해해 비밀번호의 클라이언트 암호화를 실제로 구현했다가 제거했다.
- 제거 판단에는 다음 세 경험이 모두 포함된다.
  - 개발자 도구가 보여 주는 애플리케이션 Payload와 TLS가 적용되는 네트워크 전송 구간이 다름을 이해했다.
  - 프론트엔드에 포함된 복호화 키는 사용자에게 노출되어 추가 암호화의 실효성이 낮다고 판단했다.
  - 구글과 네이버도 HTTPS 위에서 비밀번호를 별도 클라이언트 암호화 없이 전송하는 것을 직접 확인했다.
- 백엔드가 비밀번호를 bcrypt로 해시해 저장하는 구현은 코드에서 확인했다.
- 현재도 예약 임시 데이터와 이메일을 `sessionStorage`에 보관하는 용도로 AES 유틸리티가 남아 있으므로 `클라이언트 암호화를 전부 폐기했다`고 쓰지 않는다.
- 공개 문구는 `비밀번호 전송을 위한 별도 클라이언트 암호화를 제거했다`로 한정한다.

## 연결 인사이트 결정

기존 연결 인사이트 4건을 다음 3건으로 정리한다.

1. `nestjs-middleware-vs-guard-tradeoff`
   - 새 메시지: `NestJS 인증은 Middleware와 Guard 중 하나를 고르는 문제가 아니었다`
   - Express 경험에서 출발한 선택과 현재의 Global Guard 개선 판단을 중심에 둔다.
2. `nextjs-nestjs-domain-separation-and-bff`
   - 실제 쿠키 실패, Next.js reverse proxy, CSRF 방어와 Cloudflare 서버 요청 차단 대응을 하나의 프로젝트 사례로 다시 쓴다.
3. `https-and-plaintext-password-transmission`
   - 비밀번호 클라이언트 암호화의 구현·제거와 HTTPS 전송 경계 학습을 유지한다.

`enterprise-bff-architecture-and-cors`는 두 번째 인사이트와 내용이 중복되므로 통합한다. 기존 공개 주소는 깨뜨리지 않고 기본 BFF 인사이트로 연결되는 호환 경로를 유지한다. 실제 회사 도메인과 비공개 네트워크 정보는 공개하지 않는다.

## 시각 자료 필요성 판정

- 작업물 예약·결제 UAT 흐름 스윔레인: 필요
  - 운영자 설정, 사용자 예약, BFF, API·DB, PG 테스트 환경의 순차 관계와 재고 충돌·PG 실패 위치를 문장보다 명확하게 보여 준다.
- Core Product 소형 ERD: 필요
  - 공통 Product와 객실·관광·주문·재고 관계를 반복 문장 없이 설명한다.
- Middleware와 Guard 요청 생명주기 다이어그램: 필요
  - 당시 구현 책임과 현재 Global Guard 개선 판단을 비교하기 위해 필요하다.
- BFF 네트워크 경계 다이어그램: 필요
  - 브라우저 직접 호출과 Next.js reverse proxy 이후의 Origin 및 Cloudflare 경계를 비교한다.
- HTTPS 인사이트 다이어그램: 불필요
  - 애플리케이션 Payload와 TLS 전송 구간의 차이는 짧은 문장과 접근 가능한 텍스트만으로 충분히 설명된다.

작업물과 인사이트 시각 자료는 서로 다른 질문을 답해야 하며 같은 흐름을 반복하지 않는다.

## 승인된 공개 강도

- `1인 백엔드 및 PM·PL` 역할은 유지한다.
- 고객사 UAT와 PG 테스트 환경을 구분한다.
- 운영 성과, 운영 결제와 운영 지표는 만들지 않는다.
- 미완성 결제 보상 경로는 프로젝트 보류 시점의 한계와 현재의 개선 판단으로 공개한다.
- 실제 회사 도메인, 고객사 자금 세부 상황, 고객 거래 데이터, 인증값, 시크릿과 비공개 소스는 공개하지 않는다.
