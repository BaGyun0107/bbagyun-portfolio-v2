## 2026-08-25 후속 정정

구조화 상세 구현 후 사용자가 다음 내용을 추가로 바로잡았다. 아래 항목은 이
문서의 2026-08-24 결론 중 충돌하는 부분보다 우선한다.

- 핵심 결과 카드는 `컴플레인 접수 불일치`와 `운영 관찰 기간` 두 개만 남긴다.
  `외부 PMS 평균 응답 약 20초`와 `PMS 장애 지속 약 1시간`은 카드에서 제외한다.
- 운영 관찰 기간 값은 `2024년 오픈 ~ 현재 진행 중`으로 표기한다.
- 약 20초는 PMS의 정상 평균 응답 속도가 아니다. 당시 해당 API에 문제가 있어
  지연된 상태였고, 현재는 API가 수정되어 과거처럼 오래 걸리지 않는다. 이 사건은
  성능 수치보다 timeout을 근거 없이 정하지 않아야 한다는 교훈으로 서술한다.
- 결제의 `resvId`·`tid`·fallback 구현은 사용자가 직접 확인한 사실이 아니다.
  기존 자료 요약에만 있던 표현이므로 공개 상세·스윔레인·회고에서 제거한다.
- WebView 원인의 근거 범위는 유지하되, 문제·제약 본문에 `고객 거래 데이터,
  시크릿, 비공개 소스도 공개하지 않습니다`라는 일반 공개 제한 문장은 넣지 않는다.

## 2026-08-25 연결 인사이트 후속 인터뷰 및 승인

구조화 작업물 다음으로 `spa-api-key-exposure-and-bff-architecture`의 강조점과 현재
적용 기준을 사용자 질의응답으로 확정했다.

- 핵심 메시지는 잘못된 이해를 개발계 테스트에서 발견한 뒤 즉시 서버 경계로
  수정하고 BFF의 필요성을 깨달은 과정이다.
- 개발계에서 발견했으므로 제3자가 API Key를 악용한 일은 없었다. 공개 문안은 운영
  침해 사고처럼 과장하지 않되, 면접관이 판단 변화를 확인할 수 있을 정도로 남긴다.
- 당시 JWT 쿠키 검증은 PHP 미들웨어에서 처리했다. React의 모든 요청을 PHP Proxy로
  보내고, Proxy가 외부 API와 내부 API 중 목적지를 판단했다.
- PHP Proxy는 외부 요청에 API Key를 붙였지만 원본 응답은 그대로 React에 전달했고
  프론트엔드에서 가공했다. 당시 구현을 완성된 BFF로 소급하지 않는다.
- API Key·Secret·인증 헤더가 필요하면 반드시 서버를 거친다. 공개 정보이고 별도
  인증 정보가 없으면 브라우저 직접 호출도 허용할 수 있다.
- 응답 조합·가공, 사용자 권한 통제, 여러 API 취합이 필요하면 단순 Proxy보다 BFF를
  선택한다. public API와 private API의 경계를 백엔드에서 구분하는 기준도 남긴다.
- 로그인/JWT와 응답 가공이 필요한 블랙스톤 같은 프로젝트라면 현재는 BFF를 기본
  후보로 검토하지만, 모든 외부 API에 BFF가 무조건 필요하다고 일반화하지 않는다.
- 작업물의 결제·예약·역할 전체를 반복한다는 내부 편집 설명은 공개 본문에 넣지 않고,
  서버 경계와 Proxy/BFF 판단만 다룬다.
- 답변을 반영한 제목, 요약, 본문 전체 방향을 사용자에게 제시했고 2026-08-25에
  명시적 콘텐츠 승인을 받았다.

   - 결과: 오픈 후 결제-예약 불일치 10건 미만
3. 클라이언트 API Key 노출
   - PHP 프록시 즉시 구축, Key를 서버 환경변수로 이관

### Q2. "10건 미만"의 출처와 분모

**답변 (2026-08-24)**

- 직접 세어본 것은 아니다. **컴플레인으로 들어온 횟수**가 10건 미만이라
  그렇게 적어 두었다.
- 실제 총 결제 건수는 현재 확인할 방법이 없다.
- 서비스는 계속 운영 중이고 유지보수도 진행 중이다. **2026-08 현재까지**
  같은 문제는 없는 상태다.
- 결제량은 정확하지 않지만 평일 대략 10건 이상, 주말 30건 이상으로 알고 있다.

**판정: `reported` — `measured` 불가**

- 시스템 집계가 아니라 **고객 컴플레인 접수 건수**다. 로그나 DB를 세어
  얻은 값이 아니므로 측정값으로 표기할 수 없다.
- 더 중요한 한계: 컴플레인 기준은 **실제 불일치의 하한**이다. 사용자가
  인지하지 못했거나 신고하지 않은 건은 포함되지 않는다. 본문이 이를
  "불일치 10건 미만"으로 쓰면 시스템이 보증하는 값처럼 읽힌다.
  → "컴플레인으로 접수된 불일치"로 측정 대상을 정확히 바꿔야 한다.

**분모 추정 (참고용, 공개 여부는 신중히 판단)**

평일 10건 × 약 22일 + 주말 30건 × 약 8일 ≈ 월 460건.
2024년 오픈 후 2026-08까지 약 2년이면 누적 1만 건 내외.

다만 이 계산은 사용자가 "정확하지 않다"고 밝힌 값에서 출발하고, 오픈
시점과 계절 변동(리조트는 성수기 편차가 큼)을 반영하지 않는다.
따라서 **누적 건수를 수치로 공개하지 않는다.** 대신 "일 단위 수십 건
규모로 2년 이상 운영" 정도의 규모 감각만 밝히는 편이 안전하다.

**기간 갱신**

본문은 "오픈 후 현재까지"로 모호하다. 유지보수가 계속되고 2026-08까지
문제가 없으므로, 관찰 기간을 명시해 "2024년 오픈 이후 2026-08까지"로
적으면 관찰 범위가 분명해진다.

### Q3. 장애 3건의 수치 근거

**답변 (2026-08-24)**

- **평균 약 20초**: PMS 업체가 "응답이 평균 20초 정도 걸리는 이슈가 발생
  중"이라고 **공유해 준 값**이다. 직접 측정한 것이 아니다.
- **timeout 12초**: **임의로 정한 값**이었다.
- **60초로 조정**: PMS 업체 측에서 **요청한 시간이 60초**였다. 사용자 경험
  측면에서는 30초가 낫지 않을까 생각했지만, 결제에서 발생하는 문제는
  불만이 더 크게 번질 수 있어 안전하게 60초를 택했다.
- **장애 약 1시간**: 파트너사 통보도 있었고, **로그로 최초 발생 시각부터
  종료 시각까지 직접 파악**했다.

**본문 수정 필요 — 서술 주체가 잘못되어 있다**

현재 본문: "외부 PMS의 평균 응답이 약 20초인데 예약 생성 timeout을 12초로
두어" → 마치 본인이 20초를 측정해 알고 있었는데 12초로 잘못 설정한 것처럼
읽힌다. 실제 순서는 반대다.

실제 순서:
1. timeout을 임의로 12초로 정함 (근거 없이)
2. 불일치 발생 → 조사
3. PMS 업체가 "평균 20초 걸린다"고 공유
4. 업체가 60초를 요청 → 사용자 경험(30초)과 결제 안전성(60초) 사이에서
   60초 선택

→ "임의로 정한 값이 외부 실제 응답 시간과 맞지 않았다"로 써야 정확하다.
   이것이 오히려 더 정직하고, 근거 없이 정한 값이 장애로 돌아왔다는
   교훈으로 이어진다.

**근거 등급**

| 값 | 등급 | 근거 |
| --- | --- | --- |
| PMS 평균 응답 약 20초 | `reported` | PMS 업체가 공유한 값. 직접 측정 아님 |
| 장애 약 1시간 | `measured` | 로그에서 최초 발생~종료 시각을 직접 확인 |
| timeout 12초 → 60초 | 사실 | 설정값 변경 이력 |

**60초 판단이 이 작업물에서 가장 좋은 대목**

업체 요청(60초)과 사용자 경험(30초)이 충돌했고, "결제 문제는 불만이 더
크게 번진다"는 기준으로 안전한 쪽을 택했다. 단순히 요청을 수용한 것이
아니라 트레이드오프를 인지하고 판단한 기록이므로 본문에 명시한다.

### Q4. 인증 전환 시점과 WebView 세션 유실 원인

**답변 (2026-08-24)**

1. **운영 중 서비스가 아니었다.** 최초 구축된 시스템이 PHP 그누보드
   기반이라 세션 기반 로그인이 되어 있었고, 이를 PHP + React 기반으로
   동작하게 하려고 JWT 검증 미들웨어를 추가한 것이다.
2. WebView 쿠키 유실 원인은 **앱 개발자에게 전달받은 내용이라 확실하지
   않다.** 자동로그인 토큰이 앱 종료 후 재시작 과정에서 유실돼 로그인이
   풀리는 이슈로 인지하고 있었다.

**본문 수정 필요 — "운영 중 서비스" 전제가 사실이 아니다**

현재 본문 곳곳이 "운영 중 서비스"를 전제로 판단 근거를 서술한다.

- 2절: "운영 중인 PHP 서비스를 **중단하지 않고** React를 단계적으로 도입"
- 3절: "**운영 중 서비스의 무중단 전환**과 추가 인프라 부담을 고려해"
- 대안표: PHP 전면 교체 기각 사유 = "**운영 중 서비스라** 전면 교체
  리스크 과대"
- 결과: "PHP 서비스 **무중단** 상태에서 React 도입 완료"

실제는 신규 구축이며, 기존 그누보드 자산 위에 React를 얹은 것이다.
무중단 전환은 달성한 성과가 아니라 애초에 해당하지 않는 조건이다.

→ "레거시 그누보드 구조를 유지한 채 React를 결합했다"로 바꾼다.
   PHP를 전면 교체하지 않은 이유도 "운영 리스크"가 아니라 "기존 자산과
   일정" 쪽으로 정정해야 한다. (기각 사유의 실제 근거는 Q5에서 확인)

**WebView 원인은 등급을 낮춘다**

앱 개발자 전달 사항이고 본인이 확인한 것이 아니므로 단정하지 않는다.
"앱 재시작 과정에서 자동로그인 토큰이 유실되는 것으로 파악했다" 수준으로
적고, 원인을 직접 규명했다고 쓰지 않는다. 대응(브릿지로 토큰 전달)은
본인이 구현한 사실이므로 유지한다.

### Q5. 대안 비교표 3개의 실제 검토 여부

**답변 (2026-08-24)**

1. **서브도메인 분리 — 실제로 고민했다.** 서브도메인을 분리해 예약
   시스템을 만들까 고민했고, CORS 이슈·쿠키 공유 복잡·기존 SEO/링크
   깨짐을 이유로 기각했다.
2. **결제 트랜잭션 — 실제 고민의 내용이 표와 다르다.** Node.js에 익숙해서
   결제 흐름에 따른 상태 변경을 ORM 트랜잭션으로 묶어 처리해 왔는데,
   PHP에서는 그렇게 하기 어려울 듯해서 고민이었다.
3. **API Key — 검토 후 선택이 아니라 실수 발견 후 대응이었다.** 처음
   React를 제대로 이해하지 못했을 때 React의 환경변수는 외부에서 확인
   불가능한 줄 알았다. 프로젝트 중간에 빌드 파일에 포함되는 것을 확인했고,
   방치하면 API 키가 노출되므로 PHP 서버에 프록시를 만들어 대응했다.

**표별 판정**

| 표 | 판정 | 조치 |
| --- | --- | --- |
| 1. 라우팅/인증 | 서브도메인 분리는 **실제 검토·기각 확인** | 유지. 단 PHP 전면 교체의 기각 사유는 "운영 중 서비스"가 아니므로 정정 필요 |
| 2. 결제 | 2PC·이벤트 소싱을 검토했다는 근거 **없음** | **제거.** 실제 고민은 "Node.js에서 하던 ORM 트랜잭션을 PHP에서는 쓰기 어렵다"였다 |
| 3. API Key | "환경변수 난독화를 검토하고 기각" 근거 **없음** | **제거.** 실제는 잘못 알고 있다가 발견해 고친 것이다 |

**표 2 — 실제 고민을 그대로 쓰는 편이 낫다**

현재 본문은 2PC와 이벤트 소싱을 기각한 것으로 적는데 근거가 없다. 실제
고민은 훨씬 구체적이고 경험에 기반한다.

> Node.js에서는 결제 상태 변경을 ORM 트랜잭션 하나로 묶어 처리해 왔다.
> 그런데 이 프로젝트의 결제는 PHP 쪽에 있어 같은 방식을 쓰기 어려웠다.
> 그래서 트랜잭션으로 원자성을 보장하는 대신, 실패 시 역방향으로 되돌리는
> 보상 방식을 택했다.

"익숙한 방법을 쓸 수 없는 환경에서 대안을 찾았다"는 서사가 성립하며,
분산 트랜잭션 이론을 검토했다고 주장하지 않아도 판단의 깊이가 드러난다.

**표 3 — API Key는 실수 서사로 쓰는 편이 강하다**

React 환경변수가 빌드 산출물에 포함된다는 것을 몰랐다가 중간에 발견한
것이다. 이것은 감출 일이 아니라 이 작업물에서 가장 정직한 대목이다.

- 잘못 알고 있었다 → 프로젝트 중간에 빌드 파일에서 확인 → 방치 시 키
  노출 → PHP 프록시로 즉시 차단

"클라이언트에 시크릿을 두는 것 자체가 잘못된 구조"라는 현재 본문의 결론은
유지하되, 그것을 **처음부터 알고 있었던 것처럼 쓰지 않는다.**

### Q6. 스윔레인 개수

**답변 (2026-08-24)**: 1개 (결제·보상취소 흐름).

라우팅·인증 흐름은 Nginx 경로 분기와 JWT 검증으로 단계가 단순해 그림으로
얻는 것이 적다. 결제 흐름은 실패 경로가 여러 갈래라 텍스트보다 그림이
분명하게 전달한다.
