# 포트폴리오 작업물 콘텐츠·데모·스윔레인 개선 핸드오프

- 작성일: 2026-08-20
- 재개 시점: 하네스 업데이트 완료 후 새 세션
- 현재 상태: 검토 완료, 방향 합의, 설계·Spec Kit 계획·구현은 아직 시작하지 않음
- 주요 원문: `docs/portfolio-interviews/2026-08-20-codi-harness-v2.md`
- 주요 대상: `apps/front/src/data/portfolio/features.ts`

## 1. 목표

포트폴리오 작업물 상세 콘텐츠를 다음 원칙으로 전반적으로 정리한다.

1. 모든 작업물은 같은 정보 구조와 읽기 순서를 사용한다.
2. 실제 클라이언트가 존재하고 공개 가능한 작업물은 검증된 데모 URL을 제공한다.
3. 데모가 없거나 소스 공개가 어려운 작업물도 스윔레인·아키텍처 흐름·운영 증거를 통해 설계 판단을 이해할 수 있게 한다.
4. 작업물 본문은 문제·역할·판단·결과를 중심으로 압축하고, 구현 상세와 긴 기술 설명은 관련 인사이트로 분리해 본문 문단에서 직접 연결한다.
5. 수치, 상태, 사용 도구, 운영 범위는 인터뷰 문서와 실제 소스에서 확인된 내용만 사용한다.

## 2. 사용자가 확정한 방향

- 클라이언트가 존재해 실제 데모를 제공할 수 있는 작업물은 데모 버전을 보여준다.
- 스윔레인이 필요한 작업물에는 다이어그램을 제공해 읽는 사람이 시스템 주체, 책임, 정상 흐름, 실패 흐름을 빠르게 이해할 수 있게 한다.
- 상세 기술 설명은 인사이트로 분리하고 작업물 본문에서 직접 연결한다.
- 작업물별 문서 구조와 표현 방식을 하나로 통일한다.
- 위 방향에 따라 데이터와 화면을 포함한 파일 수정을 진행한다.

단, 공개 가능한 작업물과 실제 데모 URL 목록은 아직 확정하지 않았다. 새 세션에서 소스에 이미 기록된 URL을 먼저 검색하고, 발견되지 않는 URL만 사용자에게 한 번에 하나씩 확인한다.

## 3. 현재까지 확인한 좋은 점

`codi-harness-dx-platform` 항목은 다음 인터뷰 사실을 비교적 정확하게 반영한다.

- 기간: `2026.04 – 현재`
- 단독 설계·구현 범위
- Jenkins 교체보다 개발·배포·AI 에이전트 작업 방식 표준화가 핵심이라는 문제 정의
- 하네스 11개 프로젝트 적용, 8개 프로젝트 실제 운영, 팀원 3명 사용
- Jenkins 서버 비용 월 40만 원 제거, GitHub Actions 무료 티어 내 사용
- 5개 호텔 배포 약 15분에서 약 3분으로 단축
- 환경변수 혼입 원인을 Jenkins로 단정하지 않고 책임 경계 개선과 재발 여부만 설명한 점
- Claude Code와 Codex의 실제 규칙 회귀 사례
- 멀티 세션을 완성된 제품이 아닌 특정 마이그레이션 프로젝트의 실험으로 한정한 점
- CI/CD 시간이 모든 상황에서 줄었다고 과장하지 않고 검증 시간 증가를 함께 밝힌 점

## 4. 반드시 바로잡을 내용

### 4.1 현재 도구와 과거 도구의 시점 분리

현재 `features.ts`는 GSD, GStack, Superpowers와 `.planning/`을 현재 하네스 구성처럼 설명한다. 그러나 현재 저장소 기준으로 `.planning/`은 레거시 제거 대상이고, 계획의 정본은 Spec Kit이다. 기존 GStack 브라우저·게이트 기능도 Playwright MCP로 교체되었다.

하네스 업데이트 후 최신 정책을 다시 읽고 다음처럼 구분한다.

- 초기/v1에서 검토·사용한 도구
- 현재/v2에서 실제 사용하는 계획·실행·브라우저 검증 도구
- 제거했거나 대체한 도구와 그 이유

`techStack`에서도 역사적 도구와 현재 핵심 도구를 섞지 않는다. 현재 구성은 업데이트된 하네스 소스를 다시 확인한 후 확정한다.

### 4.2 Jenkins 비용 수치 정합성

인터뷰와 `features.ts`의 최신 수치는 월 40만 원이다. 하지만 `apps/front/src/data/portfolio/insights.ts`의 관련 인사이트에는 월 20만 원, 서버 2대·서버당 10만 원이라는 예전 수치가 남아 있다.

다음 항목을 함께 갱신해야 한다.

- `codi-harness-dx-platform-design`
- `jenkins-retirement-and-github-actions-migration`
- 같은 작업물과 연결된 excerpt, 본문, 결과 문구

수정 전에 40만 원의 서버 구성 세부 내역까지 공개할 수 있는지 원문 또는 사용자 확인으로 검증한다. 구성 근거가 없으면 총비용만 사용하고 서버 수·서버당 비용은 제거한다.

### 4.3 인터뷰 문서만으로 검증되지 않은 세부 주장

다음 내용은 실제로 구현했을 가능성이 높지만 현재 인터뷰 문서만으로는 세부 근거를 확인하기 어렵다.

- Jenkins 관리 담당자 부재, 플러그인 관리 부담, 서버 장애 사례
- `backend_changed`, `frontend_changed`, `dependency_changed` 출력 구조
- dependency security gate와 Slack 알림
- Infisical 상세 경로와 Self-hosted 선택 근거
- CLI의 GitHub 저장소·팀 권한 설정 범위
- shared 파일의 local modification, manifest 복구, stale file 처리 방식

하네스 업데이트 후 실제 `codi-harness-v2` 소스에서 확인하거나 추가 인터뷰를 거쳐 확정한다. 근거가 없으면 표현을 일반화한다.

### 4.4 작업물 본문과 인사이트의 중복

현재 하네스 작업물 본문은 약 216줄, 12,600자로 길고 다음 상세 주제를 모두 포함한다.

- `harness.lock` 패키징
- 프로젝트 초기화 CLI와 `doctor`
- Claude Code/Codex 규칙 패리티와 회귀 테스트
- 멀티 세션 테스트베드
- Infisical 구조
- Jenkins에서 GitHub Actions로의 전환

작업물 본문에는 문제, 역할, 핵심 판단, 대표 구현, 검증 결과, 회고만 남긴다. 위 주제의 상세 구현과 트레이드오프는 인사이트로 옮기고 관련 문단에 직접 링크한다.

## 5. 권장 통합 작업물 구조

모든 작업물은 가능한 범위에서 다음 순서를 공유한다.

1. 프로젝트 개요
2. 나의 역할과 책임 범위
3. 핵심 결과 요약
4. 문제 상황과 제약 조건
5. 대안 검토와 선택
6. 시스템 흐름 또는 스윔레인
7. 핵심 설계와 구현
8. 결과와 검증 근거
9. 회고와 다음 개선
10. 관련 인사이트

각 프로젝트에 정보가 없다는 이유로 근거 없는 항목을 만들지 않는다. 데모·ERD·API 계약·운영 지표는 실제로 존재하는 것만 조건부로 보여준다.

### 핵심 결과 요약 예시

하네스 작업물은 본문 초반에 다음 내용을 짧게 노출하는 것이 좋다.

- 11개 프로젝트 적용, 8개 실제 운영
- 팀원 3명 사용
- Jenkins 서버 비용 월 40만 원 제거
- 5개 호텔 전체 배포 약 15분에서 약 3분으로 단축
- 전환 후 동일 유형의 호텔별 환경변수 혼입 미발생

수치에는 `2026-08-20 기준`, `GitHub Actions 실행 화면 기준`처럼 시점과 측정 근거를 함께 표시한다.

### 발전 타임라인

하네스 작업물은 주제별 설명만으로 끝내지 않고 다음 발전 순서를 짧게 보여준다.

## 6. 데모 표시 원칙

데모 정보는 정규화된 데이터로 관리하고 페이지 컴포넌트에 URL을 하드코딩하지 않는다.

권장 최소 필드는 다음과 같다.

- `url`: 검증된 공개 데모 URL
- `label`: `데모 보기`, `운영 서비스 보기` 등 사용자에게 보이는 문구
- `kind`: 실제 운영 서비스인지, 포트폴리오용 데모인지 구분
- `note`: 로그인 필요, 일부 기능 제한, 샘플 데이터 사용 등 접근 안내
- `status`: 현재 접근 가능 여부

표시 규칙은 다음과 같다.

- 검증된 URL이 있을 때만 데모 CTA를 노출한다.
- 실제 고객 데이터와 운영자 기능은 데모에 노출하지 않는다.
- 접근이 불가능하거나 URL이 확정되지 않은 작업물에는 빈 버튼이나 준비 중 버튼을 표시하지 않는다.
- 프론트엔드가 없는 작업물은 데모를 억지로 만들지 않고 아키텍처·스윔레인·운영 증거를 우선한다.
- 외부 링크는 새 탭으로 열고 `noopener noreferrer`를 적용하며 접근 가능한 라벨을 사용한다.

현재 저장소에서 확인된 공개 URL은 포트폴리오 자체 URL뿐이며 작업물별 데모 URL은 아직 확인되지 않았다.

## 7. 스윔레인 설계 원칙

스윔레인은 장식용 이미지가 아니라 구조화된 데이터와 접근 가능한 렌더러로 제공하는 방향을 우선 검토한다.

권장 데이터 요소는 다음과 같다.

- 제목과 한 문장 목적
- lane ID와 표시 이름
- 단계 ID, 단계 설명, 소속 lane
- 단계 간 연결과 방향
- 정상 흐름과 실패·복구 흐름 구분
- 다이어그램을 보지 못하는 독자를 위한 대체 설명
- 필요할 경우 근거가 되는 인사이트 또는 본문 앵커

표시 원칙은 다음과 같다.

- 데스크톱에서는 lane과 단계의 관계를 한눈에 볼 수 있게 한다.
- 모바일에서는 전체 페이지가 아니라 다이어그램 컨테이너 내부만 가로 스크롤을 허용한다.
- 색상만으로 정상·실패 흐름을 구분하지 않고 선 스타일, 아이콘, 텍스트를 함께 사용한다.
- 키보드와 스크린 리더로도 단계 순서를 읽을 수 있는 대체 목록 또는 설명을 제공한다.
- Mermaid 문자열을 그대로 사용자 콘텐츠에 넣는 방식보다 타입이 있는 데이터와 재사용 컴포넌트를 우선 비교한다.

하네스 작업물의 첫 스윔레인 후보는 다음 흐름이다.

```text
개발자/AI 에이전트
  → Brainstorming·Spec Kit 계획
  → 역할·경로·위험 명령 가드
  → TDD 구현
  → Review·Verification
  → GitHub Actions 배포
  → Infisical 환경 주입
  → PM2·Docker·Vercel 대상 배포
```

세부 lane과 실패 흐름은 최신 하네스 업데이트 후 실제 정책과 배포 흐름을 확인해 확정한다.

## 9. 코드 구조에서 확인된 문제

### `overview`가 상세 페이지에서 보이지 않음

현재 상세 페이지는 `content`가 있으면 `overview`를 렌더링하지 않는다. 하네스의 11개·8개·3명 요약은 `overview`에 있지만 상세 상단에서는 보이지 않고 결과 표까지 내려가야 확인할 수 있다.

구현 시 다음 중 하나를 선택한다.

- 권장: 상세 페이지가 `overview`를 항상 상단 요약으로 렌더링
- 대안: 모든 핵심 결과를 `content` 도입부에 중복 삽입

### 타입 안전성 부족

`SeedFeature.category`와 `SeedFeature.status`가 단순 `string`이고 변환 과정에서 DTO union으로 강제 캐스팅된다. 현재 `FeatureStatus`에 없는 `In Progress` 값도 타입 검사에서 통과한다.

구현 시 `SeedFeature`가 `FeatureCategory`와 `FeatureStatus`를 직접 사용하도록 하고, 실제 필요한 상태를 공식 union에 추가하거나 기존 상태로 정규화한다.

### 파일 전체 포맷 오류

`features.ts`의 다른 작업물 6곳에서 `status`와 `overview`가 같은 줄에 붙어 Prettier ESLint 오류가 발생한다. 콘텐츠 구조를 수정할 때 함께 정리한다.

콘텐츠 계약 테스트는 필수 섹션 존재 여부만 확인한다. 사실 일치, 관련 인사이트 수치 충돌, 데모 URL 유효성, 스윔레인 접근성은 별도 테스트가 필요하다.

## 11. 구현 전 확인해야 할 질문

새 세션에서는 질문을 한 번에 하나씩 확인한다. 첫 번째 질문은 다음이다.

> 현재 8개 작업물 중 외부에 공개 가능한 클라이언트 또는 데모가 있는 작업물은 무엇이며, 각각의 검증 가능한 URL은 무엇인가?

그다음 확인할 항목은 다음과 같다.

- 실제 운영 URL과 별도 데모 URL을 구분해 표시할지
- 로그인이나 샘플 계정 안내가 필요한지
- 모든 작업물에 스윔레인을 만들지, 시스템 주체가 2개 이상인 작업물만 만들지
- 하네스 업데이트 후 현재 도구 구성을 어떤 시점 기준으로 공개할지

## 12. 새 세션 재개 절차

1. 하네스 업데이트를 완료한다.
2. 최신 `AGENTS.md`, `.harness/config/project-profile.yaml`, 프로젝트 로컬 규칙을 다시 읽는다.
3. `specs/*/tasks.md`의 미완료 작업을 다시 확인한다.
4. 이 핸드오프와 원본 인터뷰 문서를 읽는다.
5. 데모 대상과 URL을 확인한다.
6. 스윔레인 표현 방식에 대한 2~3개 접근을 비교하고 사용자 승인을 받는다.
7. 새 Spec Kit 기능 디렉터리를 만들고 `speckit-specify → clarify → plan → tasks(TDD) → analyze`를 진행한다.
8. `tasks.md` 사용자 검토 게이트를 통과한 뒤 구현한다.
9. 콘텐츠 테스트, 타입 검사, ESLint, Production build, 데모 URL 검증, 320·768·1024·1440px 브라우저 QA를 수행한다.
10. `speckit-converge`와 `mise run feature:status:sync`로 마무리한다.

## 13. 세션·작업 트리 주의사항

- 현재 브랜치: `chore/cleanup-downstream-harness`
- 작업 트리에는 사용자가 이미 만든 다수의 미커밋·미추적 변경이 있다.
- 기존 `features.ts`, `insights.ts`, 타입, 테스트, Spec, 인터뷰 문서를 사용자 작업으로 취급하고 보존한다.
- 이 핸드오프를 작성하기 전 세션에서는 구현 파일을 수정하지 않았다.
- 새 세션도 관련 diff를 먼저 확인하고 사용자의 기존 변경을 덮어쓰지 않는다.
- 이 문서는 구현 계획의 정본이 아니다. 하네스 업데이트 후 생성할 새 `specs/<NNN-feature>/` 디렉터리가 구현 계획과 진행 상태의 정본이다.
