## 공개 범위 결론

- 전면 메시지는 호텔별 조건문과 브랜치로 흩어진 예약 프론트엔드를 하나의 기준 코드와 명시적인 확장 경계로 발전시킨 과정이다.
- 2024~2025년에는 단일 코드베이스에 누적된 호텔별 조건 분기를 서버 설정, 코드 설정, 환경변수와 호텔별 배포 브랜치로 분리했다.
- 이 1차 구조는 공통 기능 코드의 수정 범위를 줄였지만, 5개 호텔 브랜치에 공통 수정이 반복되고 브랜치마다 기능 편차가 생기는 문제까지 해결하지는 못했다.
- 2026년에는 공통 기능을 `core`, 호텔별 차이를 `platform`으로 나누고 빌드 시 `PLATFORM` 환경변수로 대상을 선택하는 구조로 5개 플랫폼 코드를 리빌딩했다.
- 코드 저장소와 기준 구현은 통합했지만 실행·배포 단위는 합치지 않았다. 플랫폼별 빌드 산출물을 운영 서버의 호텔별 프로젝트 폴더에 각각 배포한다.
- 2026년 구조의 배치 원칙은 모든 플랫폼이 같으면 `core`, 값만 다르면 `rsConfig`, 화면이나 로직이 실제로 다르면 `platform` 위임이다.
- `ReservationContext`처럼 플랫폼별 차이가 큰 영역은 `core`가 공통 계약을 소비하고 선택된 플랫폼 구현이 그 계약을 제공한다.
- 5개 플랫폼 모두 새 구조로 운영 적용했다. 이후 공통 변경은 `core`에서 한 번 수정하고, 호텔별 변경은 해당 `platform`에 격리하며, 기준 코드를 찾기 위해 호텔별 브랜치를 비교하던 작업을 없앴다.
- 신규 호텔 온보딩 사례는 리빌딩 이후 확인하지 않았으므로 신규 호텔 추가 속도나 코드 수정 0건을 성과로 주장하지 않는다.

- 2026년에는 `core/platform` 경계와 통합 방식을 설계하고 주요 마이그레이션을 직접 수행했다.
- 다른 FE와 BE의 담당 구현을 사용자의 단독 개발로 표현하지 않는다.

## 1차 설정 중심 플랫폼화

- 플랫폼화 전 구조는 프로젝트별 복제가 아니라 하나의 공통 코드베이스 안에 호텔별 조건 분기가 누적된 형태였다.
- 서버 설정은 비회원 예약, 결제수단, 약관 등 세부 기능 정책을 제어했다.
- 앱 최초 진입 시 서버에서 서비스·기능 설정을 조회하고, 응답 전에는 로딩 화면을 유지한 뒤 Context를 통해 하위 화면에 제공했다.
- 코드의 `rsConfig`와 이후 `platform` 영역은 화면 문구·약관·운영 정책, PMS·결제·회원 연동 파라미터, 이미지·스타일 차이를 관리했다.
- 환경변수와 호텔별 배포 브랜치도 함께 사용했다.
- 구조 개선 전에는 호텔 요구사항 때문에 공통 컴포넌트와 조건문을 직접 수정했다.
- 개선 후에는 호텔별 설정 파일, 환경변수와 배포 구성을 추가하되 공통 기능 코드는 거의 수정하지 않는 방식으로 바뀌었다.
- 관리자 설정만으로 프론트엔드 코드 수정과 빌드 없이 호텔을 추가한 구조는 아니다.
- 1차 플랫폼화 당시 모노레포·npm 패키지 같은 별도 대안을 정식으로 비교하지 않았다. 조건 분기를 설정으로 옮기는 방향으로 바로 진행했다.

## 2차 core/platform 리빌딩

- 1차 구조는 5개 플랫폼에 적용됐지만 공통 수정이 호텔별 브랜치에 반복됐고, 시간이 지나면서 브랜치마다 기능과 수정 이력이 달라졌다.
- 2026년에는 5개 플랫폼의 기준 코드를 하나로 합치고 아래 세 조건을 같은 비중으로 만족시키려 했다.
  - 공통 변경을 한 번만 수정할 것
  - 호텔별 차이가 다른 호텔 코드에 섞이지 않을 것
  - 기존 호텔별 빌드·배포 단위를 유지할 것
- 앱과 공통 기능은 `@core`를 사용하고, `core`가 호텔별 차이가 필요한 지점에서만 `@platform`으로 위임한다.
- 값 차이는 `rsConfig`, 화면·로직 차이는 플랫폼 구현 위임으로 나눈다.
- `PLATFORM` 환경변수가 build-time alias 대상을 선택한다. 하나의 운영 빌드가 접속 도메인에 따라 런타임에 플랫폼을 바꾸는 구조가 아니다.
- 런타임 단일 앱, 브랜치 자동 동기화, 별도 패키지 구조를 정식 대안으로 비교했다고 쓰지 않는다.

## 마이그레이션 누락과 검증

- 초기 재구조화가 이전 시점 코드를 기준으로 진행돼, 그 이후 운영 브랜치에 반영된 변경 일부가 통합 트리에 빠졌다.
- 이 문제는 운영 배포 전 개발·통합 검증에서 발견했다. 운영 장애로 표현하지 않는다.
- 기준 커밋과 최신 운영 브랜치의 파일·커밋 차이를 목록화하고, 각 변경 의도를 새 구조의 `core` 또는 해당 `platform`에 수동 이식했다.
- 감사 대상 커밋·파일·누락 후보의 내부 수치는 공개하지 않는다.
- 이후 다음 검증을 함께 사용했다.
  - 5개 플랫폼 빌드와 alias 해석 검증
  - `@platform` 위임 파일과 `ReservationContext` 공통 계약 검증
  - 운영 브랜치와 통합 코드의 패리티 감사
  - 플랫폼별 주요 예약·마이페이지 흐름 검증
- 핵심 교훈은 파일을 새 구조로 옮기고 빌드에 성공한 것과 최신 운영 동작을 모두 보존한 것은 별개의 문제라는 점이다.

## 예약 상태 구조

- 직접적인 문제는 객실 선택부터 정보 입력과 결제로 이어지는 단계가 깊어지면서, 중간 컴포넌트가 사용하지 않는 상태와 setter까지 계속 전달해야 했던 Props Drilling이다.
- App 최상단의 Provider Hell, 실제 불필요 리렌더링, 도메인 밖의 상태 변조 사고가 직접 문제였다고 쓰지 않는다.
- Redux를 검토했지만 예약 라우터 내부에서 사용할 상태에 전역 store 구조가 과했고, 기존 코드와 팀에 Redux 사용 방식을 맞추는 전환 비용도 일정에 비해 크다고 판단했다.
- Zustand는 검토하지 않았다.
- 예약 라우터에 `ReservationProvider`를 배치하고 하위 단계가 `useReservation`으로 상태를 사용하게 했다.
- 이 구조로 중간 컴포넌트의 Props 전달을 줄이고, 예약 흐름을 벗어날 때 관련 상태를 정리할 수 있는 생명주기 경계를 만들었다.
- `useReservation`은 Provider 밖의 잘못된 사용을 오류로 드러내지만, 노출된 모든 상태 변경 권한을 선택적으로 제한하는 접근 제어 수단은 아니다.
- 리렌더링 성능 개선, 예약 순서 보장, 외부 상태 변경 경로 완전 차단을 성과로 주장하지 않는다.

- 외부 NICEPAY 페이지로 이동했다 돌아오거나 페이지가 재로딩될 때 React 메모리 상태가 사라지는 문제를 다뤘다.
- 예약 진행 데이터는 `sessionStorage`에 저장하고 1시간 만료값을 함께 기록했다.
- `localStorage`를 사용했다고 쓰지 않는다.
- 결제 복귀 후에는 예약번호로 최종 예약 정보를 다시 조회해 결과 화면을 구성했다.
- 가격과 재고를 다시 검증하거나 불일치를 감지해 결제를 자동 취소했다고 쓰지 않는다.
- 개발·QA에서 Redirect와 새로고침 뒤 상태 복원 및 결과 조회를 확인했고, 운영 결제에서도 정상 복귀 사례를 확인했다.
- 전체 결제 건수, 성공률, 적용 전후 개선율은 집계하지 않았다.

## 결과와 근거 경계

- 공통 수정은 `core`에서 한 번 수행하고 필요한 플랫폼을 각각 빌드·배포할 수 있었다.
- 호텔별 변경은 해당 `platform` 영역에 두어 공통 코드의 호텔명 조건 분기를 추가하지 않았다.
- 기준 코드가 하나가 되어 어느 호텔 브랜치가 최신인지 비교하는 작업이 없어졌다.
- 새 구조 이후 신규 호텔 온보딩 사례는 없었다.
- 개발시간, 배포시간, 버그 감소율, 생산성 향상률은 측정하지 않았다.
- 현재 파일 수는 코드 구조를 확인하는 참고 근거일 뿐, 변할 수 있는 값을 공개 성과 카드로 사용하지 않는다.

Props Drilling을 줄이기 위해 예약 Context의 생명주기를 라우터에 둔 이유

### Representative replacement paragraph

객실 선택, 투숙객 정보 입력, 결제로 이어지는 화면에서 상위 컴포넌트가 예약 상태와 setter를 들고 있으면 중간 컴포넌트도 사용하지 않는 props를 계속 전달하게 됩니다. Redux도 검토했지만 이 상태는 예약 라우터 안에서만 필요했고, 전역 store 구조와 팀의 전환 비용은 현재 범위에 비해 컸습니다. 그래서 예약 라우터에 `ReservationProvider`를 배치하고 각 단계가 `useReservation`으로 필요한 상태를 읽도록 바꿨습니다. 핵심은 Context 자체가 아니라, 상태가 필요한 화면 범위와 Provider의 생명주기를 일치시킨 데 있습니다.

### 의미 구성

- 질문: 여러 예약 단계가 공유하는 클라이언트 상태를 어디에서 소유할 것인가?
- 직접 문제: 중간 컴포넌트까지 이어진 Props Drilling.
- 실제 대안: Redux. Zustand는 검토하지 않았다.
- 선택 기준: 예약 라우터 내부 범위, 기존 코드 전환 비용, 팀 사용 방식.
- 구현: 예약 라우터 범위의 `ReservationProvider`와 `useReservation`.
- 결과: 중간 props 전달 감소, 예약 흐름을 벗어날 때 상태를 정리할 생명주기 경계 확보.
- 적용 조건: 하나의 라우터에 묶인 다단계 흐름에서 여러 하위 화면이 같은 클라이언트 상태를 공유할 때.
- 회피 조건: 관계없는 여러 라우트가 함께 쓰는 전역 상태이거나 최신 서버 응답이 기준인 데이터를 Context만으로 관리하려는 경우.
- 한계: Hook은 Provider 밖의 잘못된 사용을 드러낼 뿐, 상태 변경 권한을 선택적으로 제한하거나 성능을 자동 보장하지 않는다.
- 프로젝트의 플랫폼화 연혁과 NICEPAY 복귀 흐름은 반복하지 않는다.

## 철회·정정할 기존 주장

- 프로젝트별 복제 구조였다는 주장
- 관리자 설정만으로 코드 수정과 배포 없이 신규 호텔을 온보딩했다는 주장
- 신규 호텔 코드 수정 건수가 `N건 → 0건`이라는 주장
- 공통 변경을 단일 배포로 모든 호텔에 반영했다는 주장. 코드는 한 번 수정하지만 플랫폼별 빌드·배포는 유지한다.
- 모노레포·npm 패키지를 실제 대안으로 검토했다는 주장
- App 최상단 Provider Hell과 관계없는 컴포넌트 리렌더링을 직접 문제로 확인했다는 주장
- Zustand를 검토했다는 주장
- Custom Hook이 상태 접근 권한을 통제하고 도메인 밖 변경을 불가능하게 했다는 주장
- Context 구조가 예약 순차성과 성능 향상을 보장했다는 주장
- `localStorage` TTL을 사용했다는 주장
- 결제 복귀 시 가격·재고를 다시 검증했다는 주장
- 가격·재고 불일치 시 PG 승인을 자동 취소했다는 주장
- 프로젝트가 중단돼 운영 검증이 없었다는 주장
- Next.js SSR 도입을 확정적인 개선 방향으로 검토했다는 주장
- React Query 도입을 확정적인 다음 계획으로 검토했다는 주장
