## 연결 인사이트 후속 인터뷰 — 로그 분리 (2026-08-26)

### 핵심 메시지

사용자는 연결 인사이트의 중심을 다음 두 원칙으로 승인했다.

1. 로그는 많이 남기는 것보다 장애가 났을 때 실제로 조회할 수 있어야 의미가 있다.
2. 외부 API 연동에서는 요청과 응답을 당사 측에도 남겨 책임 범위와 장애 지점을 확인할 수 있어야 한다.

### 실제 문제 범위

- 예약 기능 자체에 발생한 영향은 거의 없었다.
- 예약 문제가 생겨 로그를 확인해야 했지만, 수백만 건이 쌓인 로그 테이블에
  접근하자 DB GUI가 다운됐다.
- 당사 로그로 해당 예약 건을 확인하지 못해 PMS 업체에 확인을 요청해야 했다.
- 기존 공개 본문의 "비정상 대량 요청 클레임을 로그로 방어했다"는 서술은
  사실이 아니므로 제거한다.

### 구현 근거 재검토

사용자가 제공한 비공개 로깅 파일 `tmp/phplog.php`를 코드 근거로 확인했다.
고객 요청·응답 값과 인증 관련 값은 공개 본문이나 검증 기록에 복사하지 않았다.

- `ReadableLogger`에 배열 버퍼, 20건, 2초 조건이 코드로 존재한다.
- `register_shutdown_function()`이 요청 종료 시 `flush()`를 호출한다.
- 사용자는 운영 환경이 PHP-FPM이었다고 확인했다.
- 제공된 호출 구조에서는 한 HTTP 요청마다 `createLogFile()`이 한 번 호출되므로,
  요청 간 배열 버퍼 공유와 20건 단위 배치 효과를 뒷받침하지 못한다.
- 활성 기록 경로는 `syslog()`이며 직접 파일 쓰기 코드는 주석 처리돼 있다.

이에 따라 다음 주장은 철회한다.

- 인메모리 버퍼로 여러 요청의 로그를 모았다는 설명
- 20건 또는 2초 단위 배치 성과
- 파일 I/O 약 95% 감소

사용자는 PHP-FPM 생명주기 오해를 공개 회고로 다루지 않고 버퍼링 내용을
전부 제거하는 선택지 B를 승인했다.

### 역할·구현·결과

- 프로젝트 전체는 이미 정해진 구조 안에서 구현하는 역할이었다.
- 로그 저장 경로를 업무 DB에서 `syslog()`로 분리하는 방향은 사용자가 정했고,
  구현도 직접 담당했다.
- 변경 후 실제 예약 문제를 조사할 때 시스템 로그에서 해당 요청과 응답을
  직접 확인했다.
- 처리 시간 단축이나 장애 감소율은 측정하지 않았으므로 주장하지 않는다.

### 현재 회고와 공개 경계

- 사용자는 `syslog` 구조를 유지하면서 인증값과 개인정보를 마스킹하고,
  장애 추적에 필요한 정보만 기록하며 보존 기간을 관리하는 방향을 승인했다.
- 사용자가 사용하거나 학습하지 않은 ELK, Loki, Datadog은 회고와 선택지에서
  제거한다.
- Redis TTL Lock처럼 이 로깅 인사이트와 직접 관계없는 회고도 제거한다.

### 승인된 공개 구성

- 제목: `로그는 남기는 것보다 조회할 수 있어야 한다: 외부 API 로그 분리기`
- 유형: `project-case`
- 출처: `the-siena-golf-reservation`
- 시각 자료: 변경 전·후 architecture 비교 제공
  - 변경 전: React → PHP Proxy → PMS, 통신 로그 → 업무 DB → 장애 조사 시 DB GUI 접근 불가
  - 변경 후: React → PHP Proxy → PMS, 통신 로그 → `syslog` → 서버 시스템 로그에서 요청·응답 추적
- 사용자는 2026-08-26에 제목, 한 줄 소개, 전체 본문 초안, 시각 자료,
  작업물·소개 페이지를 포함한 연결 주장 정정 범위를 명시적으로 승인했다.
