### Q2. 1500ms → 400ms의 측정 근거

**답변 (2026-08-24)**

1. 브라우저 네트워크 탭에 기록된 실제 시간을 기준으로 비교했다.

2. 날짜를 달리해 여러 번 테스트했다.
3. 같은 검색어로 개선 전후를 비교했다.
4. 비교 시점에 77만 자 데이터가 모두 적재된 상태였다.

**판정: `measured`**

근거 등급을 `measured`로 표기할 수 있다. 다음 조건을 모두 만족한다.

- 관측 도구가 명확하다 (브라우저 네트워크 탭 = 엔드투엔드 응답 시간)
- 동일 검색어 기준 비교
- 단발이 아니라 날짜를 달리한 반복 관측
- 동일 데이터 규모(77만 자 전량 적재) 조건

**본문에 함께 밝힐 범위**

- 측정 대상은 DB 쿼리 단독 시간이 아니라 **네트워크 응답 시간**이다.
  서버 처리와 전송이 포함된 값이므로 쿼리 실행 시간과 동일시하지 않는다.
- 구버전/신버전이 별도 도메인으로 동시 존재해 직접 비교가 가능했다는
  조건 자체가 비교 신뢰도의 근거다.
- 검색어와 반복 횟수의 구체값은 복원하지 않으므로 "여러 차례" 수준으로
  적고 정확한 표본 수를 주장하지 않는다.

### Q3. 하이브리드에 도달한 경로와 대안 시도

**답변 (2026-08-24)**

- 최초에는 FTS만으로 해결하려 했다.
- MySQL 버전이 낮아 N-gram 파서를 쓸 수 없었고, 한글 대응이 제대로 되지
  않았다. `ft_min_word_len`도 2였고 1글자 검색에 제한이 있었다.
- 그래서 하이브리드로 진행했다.
- Elasticsearch는 비용 문제로 시도조차 하지 못했다.

**사용자 질문: `ft_min_word_len`을 1로 설정하는 것이 버전 때문에 불가능했나?**

확인 결과 사실관계 정정이 필요하다.

- `ft_min_word_len` 최솟값은 1이며 버전 제약으로 막히지 않는다.
  (MyISAM 기준. InnoDB는 `innodb_ft_min_token_size`)
- 다만 **1로 낮춰도 한국어 1글자 검색은 해결되지 않는다.**
  기본 FULLTEXT 파서는 공백·구두점 기준으로 토큰을 자르므로
  "수행자의" → ["수행자의"] 하나이고, 1글자 토큰 자체가 생성되지 않는다.
  `ft_min_word_len`은 잘라낸 토큰 중 인덱싱 최소 길이를 정할 뿐
  토큰화 방식은 바꾸지 못한다.
- 토큰화 방식을 바꾸는 것이 N-gram 파서(MySQL 5.7.6+, InnoDB)이며
  "마음가짐" → ["마음","음가","가짐"]으로 잘라 부분 일치가 가능해진다.
- 따라서 당시 결론(코드 레벨 하이브리드)은 결과적으로 타당했다.

**본문 수정 필요**

현재: "`ft_min_word_len`이 2로 강제"
→ 사실이 아니다. "기본값이 2였고, 1로 낮춰도 기본 파서의 토큰화 방식
   때문에 한국어 1글자 검색은 해결되지 않아 의미가 없었다"로 고친다.
   파서와 최소 길이의 차이를 구분해 서술하면 오히려 이해도가 드러난다.

**Elasticsearch 기각 사유 확정**

- 본문의 "프로젝트 일정·인프라 예산 제약"은 유지 가능하나,
  실제 답변은 "비용 문제로 시도조차 못 했다"에 가깝다.
  검토 후 기각이 아니라 애초에 선택지에서 배제된 것으로 서술한다.

### Q3-1. ft_min_word_len 1 설정 실패는 본인 실수였나

**사용자 질문 (2026-08-24)**: 당시 강제로 1로 내리려 했으나 안 됐다.
설정을 제대로 하지 못한 것인가?

**답변**

실수로 단정할 근거가 없다. 흔한 실패 원인이 여럿 있다.

- **엔진 불일치(가능성 최상)**: `ft_min_word_len`은 MyISAM 전용이다.
  테이블이 InnoDB면 이 값을 바꿔도 무효이며 `innodb_ft_min_token_size`를
  봐야 한다. `SHOW VARIABLES`에는 둘 다 보여 적용됐다고 착각하기 쉽다.
- 동적 변수가 아니므로 `my.cnf` 수정 + 재시작이 필요하다.
- 재시작해도 기존 인덱스는 옛 기준이라 `REPAIR TABLE ... QUICK`(MyISAM)
  또는 인덱스 재생성이 필요하다.
- 관리형 DB면 파라미터 그룹 권한 문제일 수 있다.

**결론: 성공했어도 결과는 같았다.**

기본 파서는 공백·구두점 기준으로 자르므로 1글자 토큰 자체가 생성되지
않는다. 최소 길이를 1로 낮춰도 인덱싱할 1글자 토큰이 없다. 따라서 이
설정 실패는 최종 결과에 영향을 주지 않았다.

**본문 서술 방향**

"1로 낮추려 시도했으나 적용되지 않았고, 이후 확인해보니 기본 파서의
토큰화 방식 때문에 성공했더라도 한국어 1글자 검색은 해결되지 않았을
것이다" — 시도 사실과 그것이 무의미했던 이유를 함께 쓴다.

### Q4. 파싱·적재 실제 동작 (코드 확인 포함)

**답변 (2026-08-24)**

1. 레코드 건수는 본문에 있는지 확인 필요 (→ 확인 결과 **없음**. 추가 확정 필요)
2. Sequelize `create`를 바로 호출하고 트랜잭션으로 묶었다.
3. 적재는 5분 내로 완료된 것으로 기억한다.
4. **롤백은 여러 번 발생했다.** Word 텍스트가 규칙과 어긋나는 경우,
   데이터가 제대로 들어가지 않아 빈 값이 생기는 경우 등.

**참고 코드**: `bub_w_upload.js`, `bub_w_yj_upload.js` (사용자 제공)

**코드에서 확인한 사실 — 본문 수정이 필요한 항목**

1. **로컬 스크립트가 아니라 Express API 엔드포인트다.**
   `bub_w_upload = async (req, res, next)` 형태이며 `req.file.path`로
   업로드 파일을 받는다. 관리자가 화면에서 Word를 올리면 서버가 파싱·적재한다.
   → 본문 대안표는 "서버 내 업로드→파싱→적재 자동화"를 **기각**하고
     "로컬 스크립트 채택"으로 적었으나 **기각한 쪽이 실제 구현이다.**
     이 표는 사실과 다르므로 제거한다.

2. **`w` 쿼리 파라미터로 신규/수정을 분기한다.**
   `w === 'u'`면 `update`, 아니면 `create`. 최초 적재와 교재 갱신을
   같은 엔드포인트가 처리한다. 본문의 "파싱 스크립트 재사용"의 실체.

3. **롤백이 두 경로다 — 이것이 가장 중요한 발견.**
   - `catch` 롤백: 예외 대응 (흔함)
   - **검증 롤백**: 예외가 없어도 `titleArray.length > 0`이면 커밋 직전에
     스스로 롤백하고 402를 반환한다. 차례에서 추출한 제목이 본문 단락과
     모두 매칭되면 배열이 비어야 하는데, 남아 있다는 것은 파싱 규칙이
     그 문서를 완전히 읽지 못했다는 뜻이다.

   → "에러가 없다 ≠ 데이터가 올바르다"를 코드로 구현한 것이다.
     사용자가 말한 "규칙과 어긋나는 경우, 빈 값이 생기는 경우"의 롤백이
     정확히 이 장치이며, **안전장치가 실제로 여러 번 작동했다.**
     현재 본문의 "트랜잭션으로 묶어 중간 실패 시 롤백" 서술보다 훨씬 강하다.

### Q5. 검증 로직의 도입 시점과 롤백 대응 방식

**답변 (2026-08-24)**

- 처음부터 넣은 것이 아니다. **실패를 겪고 나서** 어디서 실패했는지
  지점을 알고 싶어 추가했다.
- Word 문서는 **전혀 수정하지 않았고**, 정규식 규칙만 고쳤다.

**해석**

검증 롤백은 설계 시점의 예방책이 아니라 **운영 중 대응으로 만들어진 장치**다.
서사가 다음 순서로 성립한다.

1. 트랜잭션만 걸고 적재 → 실패는 막았지만 원인 지점을 알 수 없었다
2. 실패 위치를 알기 위해 미매칭 제목을 수집·반환하는 검증을 추가
3. 롤백 시 메시지에 남은 제목 목록이 나오므로 어떤 제목에서 규칙이
   깨졌는지 바로 확인 가능
4. 원본 Word는 건드리지 않고 정규식 규칙을 그 케이스에 맞게 보완
5. 재실행 → 반복

**포트폴리오 관점의 가치**

- "원본을 고치지 않고 규칙을 고쳤다"는 것은 파서가 문서에 맞춰야 한다는
  판단이다. 원본을 고치면 다음 갱신 때 같은 문제가 반복되고 원본 훼손
  위험도 생긴다. 재사용 가능한 스크립트가 된 이유가 여기 있다.
- 롤백을 "안전장치를 뒀다"가 아니라 **"실패에서 위치 정보를 얻는 장치로
  발전시켰다"**로 쓸 수 있다. 실제로 여러 번 작동했다.
- 실패 → 진단 가능성 부족 인지 → 도구 보강 → 반복 개선의 사이클은
  하네스의 doctor 서사(존재가 아니라 작동을 검사)와 같은 사고방식이며,
  2023년 시점에 이미 그 접근을 했다는 근거가 된다.

**미확정 (본문에 넣지 않음)**

- 단락 레코드 건수 — 본문에도 없고 기억으로도 복원되지 않음.
  추정치를 만들지 않고 생략한다.

## 확정된 본문 수정 방향

1. **역할 서술 유지** — "1인 백엔드", "서버사이드 전반 주도"는 사실과 일치
2. **1500ms → 400ms를 `measured`로 표기**하되 측정 대상이 브라우저 네트워크
   응답 시간(엔드투엔드)임을 명시. 구/신 도메인 동시 존재로 직접 비교했고
   같은 검색어·전량 적재 상태에서 날짜를 달리해 반복 관측했다는 조건을 남긴다.
3. **`ft_min_word_len` 서술 정정** — "2로 강제"는 사실이 아니다. 1로 내리려
   시도했으나 적용되지 않았고, 성공했더라도 기본 파서의 토큰화 방식 때문에
   한국어 1글자 검색은 해결되지 않았을 것이라는 이해를 함께 쓴다.
4. **Elasticsearch는 "검토 후 기각"이 아니라 "비용 때문에 시도조차 못 함"**
5. **파싱 대안 비교표 제거** — 기각했다고 적은 "서버 내 업로드→파싱→적재"가
   실제 구현이다. 사실과 다르므로 걷어낸다.
6. **파싱을 API 엔드포인트로 정확히 서술** — multer 업로드, `w` 파라미터로
   신규/갱신 분기
7. **검증 롤백을 별도 설계 판단으로 승격** — 예외 롤백과 구분하고, 실패를
   겪은 뒤 진단 가능성을 위해 추가했으며 원본이 아닌 규칙을 고쳤다는
   반복 개선 사이클을 남긴다
