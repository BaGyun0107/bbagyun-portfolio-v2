## 공개 범위 결론

- 공개 제목은 `중앙 회원 관리·인증 서버 설계 및 구축`으로 한다.
- 여러 서비스에서 한 번의 로그인으로 접근하는 SSO가 아니라 ID·비밀번호·UUID의 원본과 인증 책임을 중앙화한 서버다.
- 운영 연결 범위는 HiPass 한 서비스이며 다중 서비스 통합 성과로 확대하지 않는다.
- 사용자는 1인 백엔드 개발자로 초기 Express 서버부터 NestJS·Prisma 전환과 첫 서비스 연동까지 전반을 설계하고 구현했다.
- 구축·확장 기간은 `2024.07 – 2025.06`이고 현재 운영·유지보수 중이다.

## 코드로 확인한 흐름

- 중앙 회원 서버가 비밀번호를 검증하고 Access Token과 Refresh Token을 발급한다.
- HiPass는 로그인 응답의 UUID, 로그인 ID, 토큰과 만료 정보를 로컬 `user_tokens`에 저장한다.
- 현재 Access Token Payload는 로그인 ID와 등급을 포함하고, UUID는 로컬 토큰 레코드에서 조회한다.
- Access Token은 서비스가 Provider 키로 로컬 검증하고 Refresh Token 갱신은 중앙 회원 서버에 요청한다.
- Provider 키는 JSON 파일에 캐시하며 중앙 서버 통신 실패 시 마지막 파일을 사용하는 경로가 있다.
- 관리자 목록은 UUID 배열을 중앙 회원 서버의 Batch API로 조회한다.
- 2025-04-30 NestJS 전환, 2025년 5월 Prisma 전환과 회원 조회·변경 API, 2025년 6월 관리자 기능 확장이 Git 이력에서 확인된다.

## 사용자 보고와 한계

- 2024년 최초 구축은 Express 기반이었다.
- 서비스 DB의 `user_tokens` 레코드를 직접 삭제한 뒤 재로그인을 요구받는 동작을 확인했다.
- 중앙에서 모든 서비스의 세션을 종료하는 기능은 구상했지만 구현하지 않았다.
- 로그인 API가 응답하지 않을 때의 대응은 구현하거나 테스트하지 않았다.
- 2024년 초기 JWT Payload에 UUID가 포함됐는지는 기억과 현재 코드만으로 확정하지 않는다.
- 과거와 현재의 토큰 만료 설정이 달라 구체적인 만료시간은 공개하지 않는다.

## 철회한 기존 주장

- 여러 사내 서비스의 인증 체계를 통합한 SSO 성과
- UUID를 JWT Payload에 담아 서비스가 직접 추출했다는 단정
- Refresh Token을 SSO DB에 중앙 저장하고 전 서비스 강제 로그아웃을 구현했다는 주장
- Access Token 10분, Refresh Token 7일이라는 고정 수치
- Redis 세션을 실제 대안으로 검토했다는 서술
- 중앙 서버 장애에서도 인증이 유지된다는 검증되지 않은 가용성 성과

## 시각화 결정

- 작업물은 사용자·HiPass·중앙 회원 서버·HiPass DB/캐시를 잇는 인증 흐름 스윔레인 하나를 제공한다.
- Provider 키 JSON fallback은 복구 경로로, 미검증 로그인 API 장애는 중단 경로로 표시한다.
- 인사이트는 UUID-only 관계에서 로그인 ID 운영 읽기 모델과 Batch API를 보완한 전후 데이터 흐름을 제공한다.
- 작업물은 전체 인증 경계를, 인사이트는 UUID Soft FK 이후의 운영 조회 문제만 다뤄 중복을 피한다.

## 연결 인사이트 승인 문안

- 제목: `UUID Soft FK만으로는 부족했다: 분리된 회원 데이터의 조회 경계`
- 핵심: 시스템 식별자인 UUID만으로는 관리자·개발자의 조회와 장애 추적이 어려웠고, 로그인 ID 읽기 모델과 Batch API로 운영 조회 경계를 보완했다.
- 한계: 로그인 ID처럼 변경 가능한 복제 값은 명시적인 동기화 경계가 필요하며, 이 프로젝트가 모든 변경 상황의 즉시 일관성을 검증한 것은 아니다.
