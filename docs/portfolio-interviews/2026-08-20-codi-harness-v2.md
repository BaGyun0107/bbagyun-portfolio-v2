## 콘텐츠 구성 결정

이 작업물은 2026년 4월부터 현재까지 하네스가 발전한 과정을 하나의 작업물 안에 담는다.

작업물 상세페이지에서는 다음 흐름을 중심으로 설명한다.

1. Jenkins 비용과 운영 부담에서 출발
2. 프로젝트마다 개발·배포 기준을 반복해서 설정하는 문제 발견
3. AI 에이전트의 작업 방식과 규칙을 통일해야 한다는 문제의식으로 확장
4. `./harness` CLI와 `doctor`를 통한 초기화·검증 제품화
5. shared/project-owned 경계를 통한 하네스 업데이트와 프로젝트별 확장 분리
6. `harness.lock` 기반 패키징 구조로 발전
7. 멀티 세션 오케스트레이션 테스트베드로 확장

`harness.lock` 기반 패키징 전환, 프로젝트 초기화 흐름, AI 에이전트 규칙 표준화, 멀티 세션 운영과 같은 주제는 작업물에서 핵심 흐름을 설명한 뒤 별도의 인사이트로 확장한다. 각 인사이트는 작업물의 해당 문단이나 설계 항목에서 연결한다.

작업물 본문을 작성하기 직전에 세부 사실과 표현의 범위를 다시 인터뷰한다. 현재 기록만으로 임의의 세부 설명이나 수치를 확정하지 않는다.

## 1. 포트폴리오에 포함할 시점

### 질문

현재 포트폴리오에는 기간이 `2026.04 – 2026.05`로 작성되어 있습니다. 실제 저장소는 2026년 8월까지 하네스 패키징, Planning Hub, PHP/Gnuboard 지원, 멀티 세션 오케스트레이션 등의 작업이 이어졌습니다. 어느 범위를 하나의 작업물로 보여줄까요?

### 답변

2026년 4월부터 현재까지의 발전 과정을 하나의 작업물에 녹여내는 것이 좋다.

`harness.lock` 기반 패키지로 변경한 이유, 프로젝트 초기화 흐름 등 상세적으로 작성해야 하는 내용은 인사이트로 작성하고 작업물에서 연결한다.

더 상세한 설명은 실제 작성 직전에 질문을 통해 확인한 뒤 작성한다.

### 반영 메모

- 작업물은 단일 시점의 구축 결과보다 4월부터 현재까지의 발전 과정과 설계 성숙도를 보여준다.
- 세부 주제는 작업물 본문에서 모두 장황하게 설명하지 않고 독립적인 인사이트로 분리한다.
- 현재 멀티 세션 테스트베드는 작업물의 최신 확장 단계로 다루되, 실제 운영 수준과 실험 수준을 구분해 표현한다.

## 2. 프로젝트를 시작한 가장 큰 이유

### 질문

프로젝트를 시작하게 만든 직접적인 계기는 무엇이며, 진행하면서 발견한 본질적인 문제는 무엇이었나요?

### 답변

처음에는 Jenkins 비용과 운영 부담 때문에 시작했다.

하지만 작업하다 보니 진짜 문제는 프로젝트마다 개발·배포 기준을 반복해서 세팅하는 것만이 아니었다. AI 에이전트의 작업을 통일화하고 싶었던 것이 더 큰 이유였다.

하네스의 가장 중요한 역할은 팀원과 실제 프로젝트를 진행할 때 다음 위험을 줄이는 것이다.

- 팀원이나 에이전트에 따라 소스코드가 달라지는 위험
- 어떤 작업을 하고 있고 어떻게 설계했는지에 대한 내용을 spec으로 문서화하지 않는 문제
- TDD 규칙을 지키지 않고 작업하는 문제
- 모노레포에서 백엔드, 프론트엔드 등 맡은 직책과 관계없이 다른 영역의 코드를 수정하는 문제
- 실제 작업에서 어떤 스킬을 사용해야 하는지 사람이나 에이전트마다 달라지는 문제
- 에이전트가 함부로 실행하면 안 되는 명령어를 실행하는 문제
- PR과 브랜치 규칙이 일관되지 않게 적용되는 문제

따라서 하네스에 사내 개발 규칙과 가드레일을 주입해 팀 전체가 통일된 작업 방식으로 진행할 수 있어야 한다고 판단했다.

### 반영 메모

이 프로젝트의 핵심 문제 정의는 다음처럼 정리한다.

> Jenkins를 교체하는 것이 출발점이었지만, 실제로 해결하려 한 문제는 개발·배포 환경과 AI 에이전트의 작업 방식을 사내 표준으로 통일하는 것이었다.

하네스는 CI/CD 도구 모음이 아니라 다음을 함께 통제하는 개발 운영 플랫폼으로 설명한다.

- 설계 문서화
- TDD와 검증 절차
- 직책별 코드 소유권
- 스킬 선택과 실행 방식
- 위험 명령어 가드레일
- 브랜치·PR 규칙
- 프로젝트 초기화와 배포 기준

## 3. 직접 설계·구현한 범위

### 질문

직접 설계·구현한 범위와 기존 공용 도구를 어떻게 활용했는지 설명해 주세요.

### 답변

다음 항목을 모두 혼자 설계하고 구현했다. 누구의 도움도 받지 않았다.

- GitHub Actions workflow 설계
- Infisical 연동 및 시크릿 구조
- `./harness` CLI 설계와 Shell 구현
- `harness.lock`과 패키징 구조
- shared/project-owned 업데이트 정책
- 프로젝트 profile과 경로 가드
- AI 에이전트 작업 규칙
- 테스트·doctor·planning check
- 멀티 세션 테스트베드 설계

GSD, GStack, Superpowers 등 공용 도구는 그대로 사용한 것이 아니다. 각각을 직접 사용해보면서 사내 프로젝트에 적합한 내용을 판단하고, 필요한 구조로 설계했다.

실제 프로젝트를 진행하면서 잘 사용하지 않는 스킬은 제거하고, 필요한 다른 스킬을 가져오는 과정을 반복했다. 하네스는 한 번 완성하고 끝나는 도구가 아니라 실제 사용 결과에 따라 지속적으로 업데이트하는 구조로 운영하고 있다.

### 반영 메모

포트폴리오에서는 다음 두 가지를 구분해 표현한다.

1. 하네스에 포함된 외부·공용 도구의 이름
2. 그 도구들을 실제 사내 개발 방식에 맞게 선별·통합·변형·운영한 설계자의 역할

핵심 표현은 다음 방향으로 정리한다.

> 여러 공용 도구를 나열한 것이 아니라, 직접 사용하면서 팀의 실제 개발 흐름에 필요한 규칙과 도구만 선별하고 하네스 운영 모델로 재구성했다.

## 4. 가장 어려웠던 문제 하나

### 질문

AI 에이전트 간 작업 규칙·코드 영역 불일치 문제를 해결하기 위해 어떤 규칙을 공통화했는가? Claude Code와 Codex의 규칙 설정·해석 방식이 달라 어떤 차이와 회귀를 확인했으며, 이를 줄이기 위해 어떤 검증 방식을 운영하고 있는가?

추가로, 한쪽 런타임의 규칙을 수정했을 때 다른 런타임에서 문제가 발생했던 사례, 새로운 규칙을 추가한 뒤 양쪽에서 검증하는 데 발생한 비용, 아직 해결하지 못한 규칙 불일치가 있다면 함께 기록한다.

### 답변 상태

가장 어려웠던 문제는 AI 에이전트와 팀원 사이의 작업 규칙·코드 영역 불일치 문제다.

현재도 계속 부딪히고 있는 문제다. Claude Code와 Codex가 규칙을 설정하고 해석하는 방식이 서로 다르기 때문에, 한쪽의 규칙을 수정하면 다른 쪽에서 문제가 발생하는 경우가 있다. 새로운 규칙을 추가할 때도 두 런타임에서 모두 검증해야 하므로 시간이 오래 걸린다.

아직까지 모든 규칙 불일치가 해결된 것은 아니며, 하네스 자체에도 잡히지 않은 부분이 남아 있다. 따라서 이 문제는 이미 완전히 해결한 과제가 아니라, 하네스를 지속적으로 운영하고 업데이트하면서 현재도 개선하고 있는 핵심 문제로 기록한다.

Claude Code와 Codex의 규칙을 동일한 파일로 복사하지 않고, 공통 정책과 런타임별 강제 레이어를 분리했다.

- 공통 정책: `.harness/policies/`
- 공통 진입점: 얇은 `AGENTS.md`, `CLAUDE.md`
- Claude Code 집행 레이어: `.claude/rules/`, `UserPromptSubmit` 훅
- Codex 집행 레이어: `AGENTS.md`, `.codex/rules/`, preflight, `PreToolUse` 훅

실제 문제와 대응은 다음과 같다.

- Claude의 `skill-injector`가 키워드가 부족한 Medium+ 작업에서 라우팅 규칙을 놓치는 사례가 있었다. 항상 로드되는 Claude 라우팅 규칙과 Codex preflight·명시적 체크리스트로 보완했다.
- Codex의 `prefix_rule`에서 `e2e`와 `e2e:changed`가 서로 다른 토큰으로 해석되어 규칙 전체가 로드되지 않는 사례가 있었다. 명령을 별도 규칙으로 분리하고, `rule-check`에서 prefix와 매칭 예시의 토큰 일치 여부를 검사하도록 개선했다.

회귀 검증은 다음과 같이 운영한다.

- `context-check`
- `rule-check`
- `doctor`
- 실제 hook payload 테스트
- Codex transcript replay 테스트

특히 잘못된 transcript는 실패하고 올바른 transcript만 통과하도록 해, 규칙 문구의 존재 여부만 보는 것이 아니라 실제 작업 순서까지 검증한다.

결과적으로 정책의 의미는 공통화하되, 각 런타임의 해석·집행 방식 차이는 어댑터와 별도 회귀 테스트로 관리하고 있다.

### 규칙 계층 구조

Claude Code와 Codex의 규칙은 다음과 같은 3단계 구조로 나누어 구현했다.

#### 1단계 — 런타임과 무관한 공통 정책 레이어

팀 규칙의 정본은 `.harness/policies/`에 둔다.

- 작업 규모와 Phase 라우팅: `scenario-phase-routing.md`
- 브랜치·위험 명령·시크릿 보호: `guardrails.md`
- 규칙 추가와 미러링 절차: `rule-lifecycle.md`

공통 정책을 Claude Code와 Codex 설정 파일에 각각 직접 작성하지 않고 한 곳에서 관리해 문서 드리프트를 줄였다.

#### 2단계 — 런타임 진입점

- Codex: `AGENTS.md`
- Claude Code: `CLAUDE.md`

`CLAUDE.md`는 `@AGENTS.md`를 통해 공통 규칙을 불러오고, Claude 전용 hook·skill 경로만 추가한다. 두 진입점에 공통 규칙을 중복해서 작성하지 않는 구조다.

#### 3단계 — 런타임별 강제 레이어

- Claude Code: `.claude/rules/*.md`에서 항상 로드되거나 경로에 따라 로드되는 서술형 규칙 관리
- Codex: `.codex/rules/*.rules`에서 명령 prefix 기반의 `allow`·`prompt`·`forbidden` 정책 관리
- 공용 hook 로직: 브랜치, 현재 경로, 전체 명령어처럼 Codex의 prefix rule만으로 판단하기 어려운 조건을 `.harness/hooks/`의 공용 로직으로 분리
- Claude hook 연결: `.claude/settings.json`
- Codex hook 연결: `.codex/hooks.json`에서 `codex-pretooluse.mjs` 연결

Codex 어댑터는 Codex payload를 공용 `guardrails.mjs`가 이해할 수 있는 형태로 변환해 동일한 차단 로직을 재사용한다.

구조는 다음과 같다.

```text
공통 정책
.harness/policies/
        │
        ├── AGENTS.md ── Codex 진입점
        │       ├── .codex/rules/*.rules
        │       ├── .codex/hooks.json
        │       └── codex-pretooluse.mjs
        │
        └── CLAUDE.md ── Claude Code 진입점
                ├── .claude/rules/*.md
                ├── .claude/settings.json
                └── Claude hooks
```

규칙이 실제로 두 런타임에 모두 연결되었는지는 `./harness context-check`, `./harness rule-check`, `./harness doctor`로 확인한다. 위험 명령과 Codex payload 동작은 `tests/codex-pretooluse.test.mjs`, 작업 순서와 라우팅 회귀는 `codex-replay-check.mjs`로 검증한다.

### 반영 메모

이 문제를 단순한 설정 파일 호환성 문제로 축약하지 않는다. 핵심은 두 AI 에이전트 런타임에 동일한 개발 원칙을 주입하면서도, 각 런타임의 규칙 처리 방식 차이와 검증 비용을 함께 관리해야 한다는 점이다.

포트폴리오에서는 다음 흐름으로 설명한다.

1. 팀원과 AI 에이전트가 서로 다른 방식으로 작업하면 설계와 코드 결과가 달라질 수 있었다.
2. 그래서 공통 규칙과 guardrail을 하네스에 포함했다.
3. 하지만 Claude Code와 Codex의 규칙 설정 방식이 달라 양쪽을 모두 검증해야 했다.
4. 한쪽의 규칙을 개선하면 다른 쪽에서 회귀가 발생할 수 있어, 규칙 자체도 지속적인 테스트 대상이 되었다.
5. 현재도 완전히 끝난 문제가 아니라 하네스 운영 과정에서 계속 개선 중이다.

멀티 세션에서 worktree·컨테이너·DB가 실제로 격리되는지는 이 문제의 대표 사례로 섞지 않는다. 해당 내용은 PHP 그누보드 기반 DB 마이그레이션에서 워커별 E2E 실행과 데이터 격리를 위해 사용하는 별도의 운영 인사이트로 기록한다.

## 5. 가장 중요한 설계 결정

### 질문

다음 설계 결정 중 포트폴리오에서 가장 강조하고 싶은 순서를 확인한다.

- shared/project-owned 경계를 둔 것
- `./harness` CLI와 `doctor`로 초기화·검증을 제품화한 것
- AI 에이전트의 작업 규칙과 guardrail을 하네스에 포함한 것
- `harness.lock` 기반 패키징 구조로 전환한 것
- worktree·컨테이너·DB를 실제 런타임에서 검증하도록 한 것
- Jenkins 대신 GitHub Actions와 Infisical을 조합한 것

### 답변

다음 세 가지를 포트폴리오에서 강조하고 싶다.

1. AI 에이전트의 작업 규칙과 guardrail을 하네스에 포함한 것
2. `harness.lock` 기반 패키징 구조로 전환한 것
3. Jenkins 대신 GitHub Actions와 Infisical을 조합한 것

이 중 가장 중요한 하나는 AI 에이전트의 작업 규칙과 guardrail을 하네스에 포함한 것이다.

### 최종 강조 순위

#### 1순위 — AI 에이전트 작업 규칙과 guardrail

하네스에서 가장 중요한 목적은 AI 에이전트가 팀의 설계·구현·검증 규칙을 동일하게 따르도록 만드는 것이다. spec 문서 작성, TDD, 직책별 코드 영역, 사용 스킬, 실행하면 안 되는 명령어, 브랜치·PR 규칙 등을 하네스에 포함해 팀의 작업 방식을 통일하려 했다.

이 결정은 현재도 계속 발전 중이다. 특히 Claude Code와 Codex 양쪽에서 동일하게 동작하는 규칙을 만들고 검증하는 과정 자체가 하네스의 핵심 운영 과제가 되었다.

#### 2순위 — `harness.lock` 기반 패키징

하네스 고유 파일은 지속적으로 업데이트되어야 하지만, 각 프로젝트의 특수한 규칙과 스킬은 프로젝트가 소유해야 한다. 이 경계를 분리한 뒤 하네스 고유 파일을 패키지로 배포하고, 프로젝트에는 `harness.lock`을 통해 버전을 연결하는 구조로 발전시켰다.

#### 3순위 — GitHub Actions와 Infisical 조합

Jenkins 비용과 운영 부담을 줄이면서, GitHub Actions를 배포 실행 계층으로 사용하고 Infisical에서 브랜치별·프로젝트별 환경변수를 명확히 분리하는 구조를 선택했다.

### 기존 답변의 세부 근거

#### shared/project-owned 경계

하네스 고유로 사용되어야 하는 스킬과 규칙이 존재하지만, 각 프로젝트에서 특수하게 사용해야 하는 규칙과 스킬도 분명히 존재한다고 판단했다. 그래서 두 영역의 경계를 나누었다.

하네스 고유 파일은 항상 하네스 기준으로 업데이트되는 파일임을 명시했다. 이 구분 덕분에 패키징할 때도 어떤 파일을 하네스가 소유하고 어떤 파일을 프로젝트가 소유하는지 판별할 수 있었다.

#### `./harness` CLI와 `doctor`

CLI로 기능을 나누어 에이전트별로 수행하는 행위가 달라지지 않게 했다. 실제로 실행되어야 하는 항목과 확인해야 하는 항목을 정확히 판별할 수 있도록 초기화와 검증을 제품화했다.

#### AI 에이전트 작업 규칙과 guardrail

개인별로 최상위 에이전트 작업 규칙을 직접 변경하지 않으면서도, 특정 프로젝트를 진행할 때 반드시 지켜야 하는 규칙과 가드레일에는 개입할 수 있어야 한다고 판단했다. 그래서 프로젝트에 필요한 규칙과 가드레일을 하네스에 포함했다.

#### worktree·컨테이너·DB 런타임 검증

worktree를 나누어 작업하더라도 실제 런타임 검증을 하지 않으면 에이전트에 따라 기존 설계와 다르게 작업하거나, 존재하지 않는 환경을 있는 것처럼 가정하는 경우가 발생할 수 있다고 판단했다. 따라서 격리를 선언하는 것에서 끝내지 않고 실제 실행 환경에서 검증하도록 만들었다.

### 답변 상태

최종 강조 순위와 가장 중요한 설계 결정까지 1차 확정했다. 실제 상세페이지 작성 직전에 각 결정의 세부 도입 시점과 구현 근거를 추가 확인한다.

### 환경변수 혼입 문제 개선

환경변수 혼입 문제는 Jenkins에서 A, B, C, D, E 호텔 배포를 한 번에 대기열에 걸어둔 상태에서 발생했다. 당시 다른 호텔의 환경변수가 포함된 상태로 배포되는 문제가 있었지만, Jenkins 자체의 오류인지까지는 명확히 판별하지 못했다.

현재는 Infisical에 브랜치별 환경변수를 만들고, workflow에서 해당 브랜치의 환경변수를 호출해 가져오도록 선언했다. 또한 다음 배포 범위를 구분했다.

- `core/` 내부 파일이 수정되면 모든 호텔에 배포
- `platform/` 내부 파일이 수정되면 수정된 호텔에만 배포

그 결과 배포 대상과 브랜치의 환경변수 책임 범위를 분리했고, 현재까지 호텔별 환경변수가 혼입되거나 잘못 전달되는 문제는 발생하지 않았다.

이 부분은 단순히 “시크릿을 안전하게 보관했다”가 아니라, 배포 대상과 브랜치의 환경변수 책임 범위를 분리해 운영 오류 가능성을 줄인 사례로 설명한다.

## 7. 멀티 세션 테스트베드의 위치

### 질문

멀티 세션 오케스트레이션은 실제 운영인지, 특정 프로젝트에서 검증 중인 실험인지, 향후 하네스에 승격할 설계인지 확인한다.

### 답변

Codex는 아직 멀티 세션 통신을 지원하지 않지만, Claude Code에서는 세션 이름을 `rename`으로 명명하면 세션끼리 통신할 수 있는 기능이 추가된 것을 확인했다. 이를 바탕으로 멀티 세션 오케스트레이션을 테스트베드로 삼아 진행하고 있다.

특정 마이그레이션 프로젝트에서 검증 중인 실험이며, 약 2주 정도 사용하고 있다. 현재 결과는 꽤 만족스럽다.

현재 역할은 다음처럼 나누어 운영한다.

- `planner`: 사용자와 대화하며 설계와 계획을 담당
- `shipper`: 작업을 배정하고 진행 상황과 검증을 관리
- `worker`: 실제 구현과 검증을 수행

사용자는 하나의 세션과 대화하지만 내부적으로는 여러 세션이 역할에 따라 작업한다. 이를 통해 작업 속도를 높일 수 있고, 검증도 하나의 세션에서 모아서 확인하고 진행할 수 있다는 점이 만족스럽다.

다만 모든 프로젝트에서 동일한 런타임 격리 구조를 사용하는 것은 아니다. `worker-062`, `worker-063`과 같은 worktree·컨테이너·DB 스키마 분리는 PHP 그누보드 기반 마이그레이션 프로젝트에서 사용한다.

해당 프로젝트는 데이터베이스를 마이그레이션하는 과정에 있기 때문에, 각 워커가 별도의 포트를 사용해야 Playwright 기반 E2E 테스트가 서로의 실행 환경을 침범하지 않는다. 워커별 데이터 저장 공간을 분리하지 않으면 한 워커의 테스트 데이터가 다른 워커의 테스트 결과에 영향을 주거나, 마이그레이션 데이터가 서로 섞일 수 있다. 그래서 이 프로젝트에서는 다음과 같이 워커별 실행 환경을 분리한다.

```text
worker-062
  ├─ worktree: worker-062 전용 브랜치
  ├─ container: worker-062 코드 마운트
  └─ database: worker-062 전용 스키마

worker-063
  ├─ worktree: worker-063 전용 브랜치
  ├─ container: worker-063 코드 마운트
  └─ database: worker-063 전용 스키마
```

이 구조의 목적은 멀티 세션 자체를 사용하기 위해 모든 프로젝트를 복잡하게 격리하는 것이 아니라, DB 마이그레이션처럼 워커별 E2E와 데이터 독립성이 필요한 작업에서 테스트 오염을 막는 것이다.

현재 어려움은 컨텍스트 관리다.

- 적절한 `clear` 시점을 정해 작업하고 있다.
- `clear`가 여의치 않은 경우에는 당장은 `compact` 명령어로 컨텍스트를 관리하고 있다.

### 팀 작업 방식에서 새롭게 발견한 문제

현재 프로젝트 대부분이 모노레포 형태로 진행되다 보니, 에이전트가 프론트엔드와 백엔드를 모두 한 번에 작업하려는 경우를 발견했다. 이는 실제 담당 역할과 코드 소유권을 벗어나 작업 범위를 넓힐 수 있는 문제다.

실제로는 어떤 기능을 만들고 싶지만 해당 기능의 데이터베이스 설계와 백엔드 API 설계가 아직 되어 있지 않은 상태에서, 에이전트가 두 영역을 모두 설계하고 구현하려는 경우가 있었다. 단순히 API만 추가하는 경우라면 영향 범위가 제한적일 수 있지만, 데이터베이스 설계까지 진행하면 기존 설계의 틀을 흔들 수 있다. 이 상태를 방치하면 담당 영역을 넘어선 설계 변경이 기존 프로젝트 구조와 충돌할 수 있다고 판단했다.

이 문제를 해결하기 위해 구상한 `role` 설정은 아직 실제로 사용하지 않은 준비 단계의 기능이다. 따라서 현재 포트폴리오에서는 `role`을 언급하지 않는다.

준비되지 않은 기능을 구현 성과나 개선안으로 작성하면 실제 사용 여부와 효과를 검증하기 어렵기 때문에, 이번 작업물의 범위에서 제외한다.

## 2026-08-27 후속 인터뷰: Cloudflare Tunnel과 Bastion

### 중심축

이번 후속 인터뷰는 2026년 4월의 WAF·connector 실패를 확인한 과정에서 출발해,
현재 Bastion이 외부 진입과 내부 배포 대상 권한을 나누는 경계로 발전한 과정을
기록한다. Tunnel을 연결한 사실만으로 배포 경계가 완성됐다고 설명하지 않는다.

### 코드 확인 근거

공개 가능한 코드·구성 확인 범위에서는 2026년 5월경부터 Cloudflare Tunnel, Access,
Bastion을 공용 진입점으로 재사용하고, `ProxyCommand`로 Cloudflare Access를 거쳐
Bastion에 연결한 뒤 `ProxyJump`로 배포 서버에 연결하는 구조를 확인했다.

- Cloudflare Access의 Service Token 인증과 Bastion SSH 인증이 외부 진입을 제한한다.
- Bastion의 `PermitOpen`은 대상 서버와 포트를 제한하며, 최종 SSH 키는 프로젝트 ×
  배포 서버 조합별로 분리한다.
- Tunnel과 Bastion을 프로젝트마다 새로 만들지 않되, 한 프로젝트의 SSH 키가 다른
  서버의 배포 권한으로 이어지지 않도록 대상 권한을 나눈다.

호스트명, IP, Token, 키, 계정명과 비공개 workflow 소스는 기록하거나 공개하지 않는다.
공개 시각 자료는 작업물에 기존 CI/CD·배포 스윔레인을 유지하는 `provided` 판정,
인사이트에는 초기 실패와 현재 권한 경계를 비교하는 data-flow `provided` 판정으로
분리했다.

### 사용자 보고·운영 관찰 근거

2026년 4월 GitHub Actions에서 사내 서버로 배포하기 위해 direct SSH와 Tunnel을
비교했다. direct SSH는 인바운드 22번 포트를 넓게 열거나 GitHub Actions IP 허용
목록을 계속 관리해야 하는 부담이 있었다. 당시 self-hosted runner는 대안으로 검토하지
않았다.

초기 workflow 실패는 Cloudflare 이벤트 로그에서 WAF 차단으로 확인했다. 배포용
hostname 예외를 적용하고 같은 workflow를 다시 실행해 기존에 막힌 Cloudflare 접근
단계가 통과하는 것을 확인했다.

이후 같은 hostname을 여러 connector에 연결한 구성에서는 요청이 의도하지 않은
connector 또는 서버 방향으로 이어졌고, SSH는 파일 전송이나 배포 명령 전에 실패했다.
잘못된 서버에 실제 배포가 이뤄진 적은 없다. Cloudflare 내부 선택 알고리즘이나
라우팅 계층은 확인하지 않았으므로 주장하지 않는다. 대상별 hostname을 임시로 분리한
뒤 같은 workflow를 재실행해 의도한 서버 배포가 완료된 것은 확인했다.

2026년 5월경에는 공용 Tunnel·Access·Bastion과 대상별 `PermitOpen`, 프로젝트 ×
배포 서버별 SSH 키를 조합하는 구조로 바꿨다. 2026-08-27 기준 사용자는 9개
프로젝트가 하나의 Bastion을 거쳐 5대 서버에 배포되고 있으며, 전환 뒤 같은 유형의
connector·서버 방향 문제를 다시 관찰하지 못했다고 보고했다. 이는 사용자 보고와
운영 관찰 범위일 뿐, 전수적인 사고율이나 보안 보장을 뜻하지 않는다.

### 한계와 회고

Bastion은 새 배포의 가용성 경계가 되는 구조적 SPOF다. Bastion이 중단되면 연결된
프로젝트의 새 배포가 막히지만, 의도적인 중단 테스트도 관찰된 Bastion 장애도 없었다.
실행 중인 서비스가 Bastion과 런타임 통신을 하지 않는다는 구조적 독립성 역시 중단
테스트로 검증한 결과로 제시하지 않는다.

회고의 우선순위는 새 프로젝트·서버 추가 때 반복되는 `PermitOpen`, 공개키 등록,
Infisical 경로 연결을 먼저 자동화하는 것이다. 그다음 Bastion 이중화, 대체 배포 경로,
실제 복구 검증을 진행할 계획이나 아직 완료하지 않았다.
